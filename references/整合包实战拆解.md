## 共性结构（mrpack 解包后）

```
modrinth.index.json      # 清单：formatVersion/files[]/dependencies
overrides/               # 解压后直接铺进 .minecraft 根（与实例目录合并）
  mods/  config/  defaultconfigs/  options.txt  ...（按包而异）
```

## 逐包拆解要点

### 1. bmc4 — Better MC FORGE 1.20.1（Forge 内容包组织范例）
- **overrides/mods/ 直接放 21 个 jar**（不进 files 引用）：biomemusic、chunksending、clientcrafting、
  connectivity、cupboard、easydisenchanting、farsight、fastasyncworldsave、gpumemleakfix、
  lootintegrations+配套、memorysettings、missingmodschecker、recipeessentials、smoothchunk、
  smoothmovement、structureessentials、blueprintfix，以及**作者自制** `bmcpalegardenpatcher`、
  `Quest Kill Task`。→ 手法：CF 没有 / 小工具类 / 自制补丁统一走 overrides/mods 直发，
  不依赖在线引用（在线引用作者删文件=安装失败）。
- **defaultconfigs/ 668 文件**：Forge 1.13+ 机制——defaultconfigs 在每次建新世界时复制成
  世界的 serverconfig（config/ 里放 client+common，defaultconfigs 放"进世界才生效"的服务端项）。
  含 MODPACK_LICENSE.txt（合规声明）。注意：**任务书类（FTB Quests）数据也在 defaultconfigs**，
  本包无任务书故未出现 ftbquests/。
- **configureddefaults/options.txt**（配 README.md）：用 Configured Defaults 类机制预置**客户端
  原始选项**（options.txt 不进 config）。
- **resourcepacks/ 8 个 zip**：GUI 美化（Better Modded GUI / Mandala）、一致性（SE Vanilla
  Consistency / Quark Programmer Art）、去灌木叶 NoBushyLeaves、结构调整类
  （LessStructures-SpacingTweaks / WDA-*）。→ 手法：原版生成调整/外观修正做成 zip 放 resourcepacks，
  玩家可在游戏里开关。
- **shaderpacks/ 8 个 .txt**：`Better MC - High/Low/Ultra/MacBook*.txt` —— 光影**预设档**分发
  （不含光影本体），玩家自备光影后直接选档。
- **modernfix/structureCacheV1/ 3256 文件**：把运行时生成的结构缓存打进了包（预生成加速 or 打包疏漏，
  做包时该清 runtime 产物——对照本技能体检脚本"跳过运行时产物"逻辑）。
- 根文件 options.txt 1 个：预置客户端显示/控制选项。

### 2. fo1 — Fabulously Optimized 1.20.1（Fabric 优化包标杆）
- config/ 极简三层：
  - `yosbr/`（灵魂）：**配置默认值分层机制**——`yosbr/config/*.json` 存放所有 mod 的推荐配置
    （borderlessmining/capes/cem/citresewn/controlify/debugify/dynamic_fps/entity_texture_features/
    iris.properties/lambdynlights/modernfix-mixins/modmenu/moreculling/NoChatReports...），
    启动时作为**只读默认层**注入；玩家改动写真实 config/，不冲突、可随包更新。YOSBR = 该 mod 名。
  - `fabric_loader_dependencies.json`：Fabric 声明的 loader 依赖（给启动器看）。
  - `isxander-main-menu-credits.json`：主菜单致谢实现（"本包由 XX 提供"）。
- 优化包 overrides 体积小（27 文件）——优化靠 mod 选择而非配置堆叠。

### 3. fo26 — 同系列 26.2 版（看版本演进）
- **yosbr → `modpack_defaults/`**（目录改名，机制延续）：`modpack_defaults/config/*` 同样式铺默认配置。
- 新增 `crash_assistant/`：崩溃助手（config.toml + localization + **scripts/** 自动处理脚本）。
- 其余与 fo1 同构（main-menu-credits / fabric_loader_dependencies）。

### 4. pixelmon — Pixelmon Modpack 1.21.1（NeoForge 内容包）
- **NeoForge 时代配置全在 config/**：559 文件平铺（无 defaultconfigs 概念；服务端配置也走
  config/ 下约定，或世界存档内 serverconfig）。子目录仅 fancymenu（主菜单 UI）。
- files 引用仅 14 个 jar——大而全的 Pixelmon 本体 + 少量生态 mod，其余靠 overrides 配置调。

### 5. rso — 红石生电优化 26.2（中文做包者，Fabric）
- config/ 217 文件内容向：**carpet/**（红石规则）、chunky（预生成）、bobby（远距区块）、
  e4mc（内网联机）、emotecraft、chesttracker、appleskin、continuity... 典型"玩法 mod + 调优"。
- 根文件 **options.txt + servers.dat**：servers.dat **预置服务器列表**（多人整合包引流手法）。
- shaderpacks/ 7 个补充包。

## 可复用做包手法清单（直接抄作业）

1. **自制/冷门/小工具 mod → overrides/mods 直发**，别挤在线引用（bmc4 21 个 jar 示范）。
2. **配置默认值分层**（yosbr / modpack_defaults）：只读默认层 + 玩家层，包更新不覆盖玩家改动。
   1.20.1 想用可自己塞 yosbr mod；我们 1.20.1/26.2 包照抄目录结构即可。
3. **预置客户端首启体验**：根 options.txt（bmc4/pixelmon/rso 全用）+ configureddefaults 机制；
   服务器包用 servers.dat 塞自己的服务器。
4. **光影预设档 .txt 放 shaderpacks/**，不绑光影本体。
5. **外观/生成调整做成 resourcepacks zip**（玩家可开关）优于写死 config。
6. **crash_assistant + scripts**：崩溃引导 + 一键修复脚本（FO14 新标配）。
7. **MODPACK_LICENSE.txt / 许可文件**：defaultconfigs 层放一份（bmc4），合规意识。
8. **打包前清 runtime 产物**：bmc4 的 modernfix structureCache 反例（3k+ 文件白占体积）。

## 对我们工具链的启示

- 制作整合包.py 的 mrpack 本地分发（overrides/mods）已兼容"手法 1"。
- 体检/打包时把 `modernfix/*cache*`、`logs/`、`crash-reports/` 等运行时产物列进黑名单
  （bmc4 反例佐证，跳过运行时产物清单可再补 structureCache）。
- 后续做"内容层"可考虑：crash_assistant 目录、servers.dat 生成、shaderpacks 预设档模板。

## 静态验证的两大假阳性（2026-09-18 实测，做「田园纪事」时撞到）

这两类问题会让人误以为包装错了，实际都是**检测工具自己的锅**。

### A. jarJar 内嵌 → 被误报「依赖缺失」

不少 mod 把前置库塞进自己 jar 里，`mods.toml` 仍然声明这个依赖。
若验证工具没登记内嵌 jar，就会报「X 需要 lib，但没人提供」。

**内嵌 jar 的存放目录不固定** —— 这是坑的核心：

| 来源 | 目录 |
|---|---|
| 老 Forge / JarJar 早期 | `META-INF/jarjar/*.jar` |
| 新版本（如 create-new-age 1.2.0） | `META-INF/jars/*.jar` |

实测案例：`clockwork` 内嵌 `kelvin`、`create-new-age` 内嵌 `esl`。

**正确做法**：优先读 `META-INF/jarjar/metadata.json` 里登记的 `jars[].path`
（这是权威清单），退化时**两个目录都扫**。只扫 `jarjar/` 必漏。

### B. 双平台 jar → 把 Forge 包判成 NeoForge

有 mod 在**同一个 jar** 里同时放 `META-INF/mods.toml` 和 `META-INF/neoforge.mods.toml`。
Forge 只读前者、NeoForge 只读后者，两边都能跑。

实测名单（1.20.1）：`create_things_and_misc`、`farmers_delight_christmas_edition`、
`Terralith`、`yet_another_config_lib_v3`。

**踩的坑**：平台推断写成「优先读 neoforge.mods.toml」→ 读到 `neoforge` 依赖 →
`has_neo=True` → 整个 Forge 包的 manifest 写成 `neoforge-xxx`。

**正确做法**：两个 toml **都读**，各自投票，**取多数票**。
田园纪事的真实分布：107 个 jar 声明 `forge`、仅 2 个声明 `neoforge` —— 多数票一目了然。

### C. 顺带：「加载器错配」不要靠文件名判

文件名完全不可靠，三种反例都实际见过：
- Forge 包里绝大多数 jar 名字本来就带 `-forge-`（全标红 = 纯噪音）
- `garnished-...-neoforged.jar` 名字带 neoforged，实为合法 Forge jar
  （查 `mods.toml`：`modLoader="javafml"` + `loaderVersion="[47,)"`）
- 双平台 jar 名字只反映打包时的命名习惯

**能可靠判定的只剩一种**：`fabric`/`quilt` 专属构建混进 Forge 包
（名字含 fabric/quilt，且不含 forge/neoforge/neoforged）。

### D. 版本检查的两个反直觉点（详见 SKILL.md「交付后终极验证」节）

- `mandatory=false` **不豁免**「存在但版本不符」—— 照样崩。所以版本检查要遍历全部依赖。
- 裸版本号（`15.20.0.106`）Forge **不检查**（Maven 语义下无 restriction），
  别当精确匹配 —— 会大量误报。


## 乐事（Delight）生态的结构特征（2026-09-18 实测）

做乐事向整合包时，这套生态有两个结构性事实会反复用到。

### 1. 附属之间用 optional 依赖织兼容网

绝大多数「A 附属 × B 附属」的联动配方，是靠 **`mandatory=false` 的可选依赖**实现的。
实测：`delightlib` 声明 `expandeddelight` / `casualness_delight` 都是 optional。

**直接推论**：想删掉某个乐事附属时，先去依赖它的 jar 里查 `mandatory` ——
是 optional 就能安全删（只会少那部分交叉配方，不会崩）；
`整合包验证.py` 的依赖闭包检查只认 mandatory，所以删完照样「五项全通过」，这是对的不是漏报。

**⚠️ 但注意区分「缺失」和「版本不符」**（2026-09-18 踩过）：`mandatory=false` 只豁免
**完全缺失**；如果那个 mod **在包里但版本不满足 `versionRange`**，照样是崩溃级错误。
`整合包验证.py` 的**版本范围**检查（第 3 项）会遍历全部依赖、含 optional，专门抓这种情况。
乐事生态里最容易中招的就是 `ends_delight`（一堆附属都要 ≥2.5/≥2.6.1）——
选版本时别只看 release 标记，1.20.1 上 2.5/2.6/2.6.1 都标 beta，但它们才是最新的可用版。

### 2. 依赖链有三层，且存在明显枢纽

```
FarmersDelight（核心）
   ├─ 纯直接附属（只挂核心）        ← 大多数
   ├─ 带内部依赖的附属              ← 连锁层
   └─ 不挂核心、只挂附属的（跨 mod 联动，如 Create: Central Kitchen → ends_delight）
```

**最大枢纽是 `Delightful`** —— 它会挂十来个其他附属（实测 13 个），
作用是把各家菜谱串成统一体系。装了它 ≈ 一次性拉进一大票附属的联动。

所以排模组清单时，「装了 Delightful 就等于隐含要求一堆附属」这件事要有意识，
否则容易以为清单很短、实际依赖很密。
