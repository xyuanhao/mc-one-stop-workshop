# 26.x 自定义世界生成器（改地形）

> 面向「写一个改变地形的 mod」这类需求。结论全部在 **MC 26.1 / NeoForge 26.1.0.19-beta** 上实测，
> 并且用专用服务端 + RCON 实地取证过（不是只编译通过）。

## 0. 先认清 26.1 的现状（摸错了会白写一天）

| 事实 | 影响 |
|---|---|
| `data/minecraft/dimension/*.json` **已经从原版 jar 里消失**（26.1 起三大维度定义不再是数据包文件） | 「加一个新维度」不能再靠 `data/<ns>/dimension/xxx.json`，改地形也别往这儿想 |
| `data/minecraft/worldgen/world_preset/*.json` **仍在**，`Registries.WORLD_PRESET` 仍可注册 | **改地形最正的路是「世界预设」**：预设里内联 overworld 的 generator |
| `Registries.CHUNK_GENERATOR` 是 `Registry<MapCodec<? extends ChunkGenerator>>` | 注册的是**编解码器**，不是生成器实例 |
| `WorldPresetTags` 在 `net.minecraft.tags` 包（不是 `world.level.levelgen.presets`） | 想出现在「世界类型」下拉里，要挂 tag |

## 1. 三件事就够

### ① 注册 chunk generator 类型

```java
// 主类
public static final DeferredRegister<MapCodec<? extends ChunkGenerator>> CHUNK_GENERATORS =
        DeferredRegister.create(Registries.CHUNK_GENERATOR, MODID);   // 重载：create(ResourceKey, String)

public static final DeferredHolder<MapCodec<? extends ChunkGenerator>, MapCodec<TerracedChunkGenerator>> TERRACED =
        CHUNK_GENERATORS.register("terraced", () -> TerracedChunkGenerator.CODEC);
// 构造函数里 CHUNK_GENERATORS.register(modEventBus);
```

`MapCodec` 用 `RecordCodecBuilder.mapCodec`，**第一个字段必须是 `biome_source`**（`BiomeSource.CODEC`），
其余参数用 `Codec.INT.optionalFieldOf("name", default)`。

### ② 写生成器

26.1 的 `ChunkGenerator` 抽象方法**就这 10 个**（`JarSig.py` 实读，26.1 与 26.1.2 完全一致）：

```java
protected abstract MapCodec<? extends ChunkGenerator> codec();
public abstract void applyCarvers(WorldGenRegion, long, RandomState, BiomeManager, StructureManager, ChunkAccess);
public abstract void buildSurface(WorldGenRegion, StructureManager, RandomState, ChunkAccess);
public abstract void spawnOriginalMobs(WorldGenRegion);
public abstract CompletableFuture<ChunkAccess> fillFromNoise(Blender, RandomState, StructureManager, ChunkAccess);
public abstract int getBaseHeight(int x, int z, Heightmap.Types, LevelHeightAccessor, RandomState);
public abstract NoiseColumn getBaseColumn(int x, int z, LevelHeightAccessor, RandomState);
public abstract int getGenDepth();       // 主世界 = 384
public abstract int getSeaLevel();
public abstract int getMinY();           // 主世界 = -64
public abstract void addDebugScreenInfo(List<String>, RandomState, BlockPos);
```

要点：

- **构造必须传 generationSettingsGetter**：`super(biomeSource, biome -> biome.value().getGenerationSettings())`。
  只传单参 `super(biomeSource)` 的话，生物群系装饰（树/草/花）一个都不生成，地表光秃秃。
- **`fillFromNoise` 里只在 `state.isAir()` 为 false 时写方块**，既省时间也避免生成一堆空气 section。
- 写完地形**必须 `Heightmap.primeHeightmaps(chunk, EnumSet.of(OCEAN_FLOOR_WG, WORLD_SURFACE_WG))`**，
  否则后续放树/结构时按「全空」判断落点。
- 地形简单就别做表面系统：`blockAt()` 一次铺完表面 → `buildSurface` 留空、`applyCarvers` 留空。
- **`getBaseHeight` / `getBaseColumn` 必须和 `fillFromNoise` 的结果一致**，不然树浮空、结构埋地。
- 世界种子：`RandomState` **不暴露 seed**。派生办法：
  `randomState.getOrCreateRandomFactory(Identifier.fromNamespaceAndPath(ns, "salt")).at(0,0,0).nextInt()`，
  每区块调一次即可（factory 有缓存）。

### ③ 数据包：世界预设 + tag

`data/<ns>/worldgen/world_preset/<name>.json`（**三个维度都要内联**，缺了世界就没有下界/末地）：

```json
    "minecraft:the_nether":{ "type": "minecraft:the_nether","generator": { "type": "minecraft:noise", "biome_source": { "type": "minecraft:multi_noise", "preset": "minecraft:nether" }, "settings": "minecraft:nether" } }
  }

```

**挂进「世界类型」下拉**（不加就只能在文件里看到、UI 里选不到）：

`data/minecraft/tags/worldgen/world_preset/normal.json`
```json

```

## 2. 怎么证明它真的生效（别只编译通过就交）

1. `server.properties` 加 `level-type=<namespace>:<preset_path>` —— 起服务端就直接用这个预设开图；
   顺手 `pause-when-empty-seconds=0`（否则无玩家 60 秒后整个服务端暂停）。
2. 起 `gradlew runServer`，日志里应出现你的注册日志 + `Preparing level "..."` + `Done`。
3. **RCON 实地取证**（`scripts/rcon.py`）：
   ```
   execute if block <x> <y> <z> minecraft:air     → Test passed / failed
   ```
   从 y=130 往下扫，先记「最高非空气 y」，再往下找「第一个非空气非水」= 地面。
   判据：**地面高度差是否都是 `terrace_height` 的整数倍**（原版平滑地形给不出这个规律）。
4. **离线读存档**（不用起服务端，秒出整图统计）：区块 NBT 根下 `Heightmaps.MOTION_BLOCKING`

   - 编码是 `SimpleBitStorage`：**每个 long 固定塞 `64 // bits` 个值、值不跨 long 边界**
     （9 bits → 7 个/long，每 long 浪费 1 位，共 `ceil(256/7)=37` 个 long）。
     ⚠️ 按「连续位流 + 跨边界拼接」解会得到 `-4, -7, -13, -25, -49…` 形状的垃圾值，
     而且**看起来还像离散分布**，能把判定逻辑骗过去 —— 这个坑实打实踩过。
   - raw → y：`y = raw + minY - 1`（主世界 minY = -64）。
   - 判据：**主档位**（占比 ≥1% 的档位）只落在少数几个高度、且两两差是 `terrace_height` 的整数倍 = 量化生效。
     ⚠️ 别拿全量档位判 —— 树叶、水面、结构会把高度顶上去，实测 22 个档位里 18 个是树顶/水面，
     全量判定会误报成「连续平滑」。

   **一条命令搞定**：`python scripts/探地表高度.py --mca <region目录> --step 6`
   （在线模式 `--rcon 127.0.0.1:25575:devtest` 拿真实 y 并区分水面/地面，两者结论应一致——可以互为交叉验证）

   实机输出样例（TerrainForge 的存档）：
   ```
   ★ 127  y=62  11.3%   ★ 133  y=68  52.0%   ★ 139  y=74  32.2%   ★ 145  y=80  3.5%
   按主档位判定：档位 4 个 / 覆盖跨度 19（密度 0.21）→ 离散台阶地形 ✅
   相邻主档位间距：[6]    两两差值对 6 取余：[0]
   ```

## 5. ⭐ 手写噪声做概率性特征时，阈值必须按**实测分布**校准

**这是最容易白写一整天的坑。** 凡是「用噪声 + 阈值决定某个特征出不出现」
（洞穴、竖井、柱子、湖、矿脉……），照理论边界写阈值大概率**永远不触发**。

### 症状长什么样

你会写：

```java
// fbm 返回 [-1, 1]，取最负的 14% 当竖井
double cutoff = -(1.0 - 0.14);      // -0.86
if (noise < cutoff) { /* 竖井 */ }
```

看着天经地义。实测：**289 个区块里一个竖井都没有，巨柱一根没长**，
而参数、代码、日志全部正常，编译也过。

### 为什么

`fbm` 通常是「多八度值噪声 + 双线性 smoothstep 插值」的叠加。
**平滑插值会把值朝中心收**，叠加后更接近钟形分布。实测（6 万点采样）：

| 噪声 | σ | min / max | p99.5 | `noise < -0.86` 命中率 |
|---|---|---|---|---|
| 2 八度 1/220 | 0.319 | -0.94 / +0.94 | 0.73 | **0.08%** |
| 2 八度 1/96 | 0.321 | -0.94 / +0.95 | 0.75 | 0.06% |
| 3 八度 1/320 | 0.281 | -0.90 / +0.83 | 0.63 | 0.02% |

理论边界 ±1 的尾部**根本摸不到**。

### 修法：先把噪声重标定成近似的均匀分布

```java
/** 实测标准差。别拍脑袋，用脚本对**同一套噪声**采样量出来。 */
private static final double FBM_SIGMA = 0.319;

/** fbm 原始值 → 近似 [0,1) 均匀分布（1.702 是正态 CDF 的标准近似系数）。 */
private static double uniform(double noise) {
    return 1.0 / (1.0 + Math.exp(-1.702 * noise / FBM_SIGMA));
}
```

之后阈值就**等于概率本身**，参数名和语义终于对得上：

```java
if (uniform(noise) < shaftChance) return;   // 约 shaftChance 的比例
```

实测重标定后十个十分位各占 8.5%~12%（基本均匀），`u < 0.14` 命中 15.4%。

### 配套：写一个校准脚本，且它要能复现 Java 的位运算

`Abyss/_calibrate_noise.py`（用 `gen_abyss.py` 同级的思路）：
逐位复刻 `hash` / `valueNoise` / `fbm`，**Java 的 long 乘法要按 64 位截断**
（Python 是任意精度，不截断结果完全不同），采样几万点输出 σ、分位、以及
「老阈值命中率 vs 新映射命中率」。改噪声参数后重跑一遍，常量跟着更新。

### 同一个坑的第二种形态：符号哨兵

`if (hi > 0)` 当「有没有地板」——负 y 层的地板本来就是负数，
**整层的柱子全被跳过**，而且只在最底下几层出问题，很容易漏。
用显式 `boolean hasFloor`。

## 6. ⭐ 特征的空间尺度 = 噪声频率，它决定「采样有效样本量」

竖井一开始和墙厚共用 `1/220` 的噪声频率 → 竖井是 **220 格见方的巨块**。
512×512 的采样区里每道墙只有几十个**独立**块，于是「这片区域有没有竖井」
变成掷骰子：实测六道墙里**三道在出生点周围 512 格内压穿率是 0%** ——
玩家在那儿根本下不去。

**规则**：验证脚本的样本量要按「采样面积 ÷ 特征块面积」算，不是按列数。
上面 289 个「列」的有效样本只有约 64 个块，σ 从 2% 涨到 4.3%。

**修法**：拆开不同用途的频率。

| 用途 | 频率 | 理由 |
|---|---|---|
| 竖井（必须走得到） | `1/64` | 保证几百格内必有若干可下的洞口 |
| 墙厚（缓慢过渡） | `1/220` | 「这段厚实、那段薄」该是缓变 |
| 地表起伏 | `1/256` | 大尺度地形 |

## 7. ⭐ 自定义群系的装饰列表会撞 `Feature order cycle found`

用自定义 `BiomeSource` 时，群系各写各的 `features` 数组 → 区块生成直接失败、
服务端崩，报：

```
java.lang.IllegalStateException: Feature order cycle found,
  involved sources: [abyss:abyss_layer_1, abyss:abyss_layer_2]
```

**原因**：原版 `FeatureSorter` 会对**一个生成器里所有群系**做全局拓扑排序。
只要特征 A 在群系 X 里排在 B 前面、在群系 Y 里排在 B 后面，就成环。
两种典型写法都会踩：

1. 同一个 placed_feature 在**同一群系里**写进两个阶段（`glow_lichen` 同时在第 7 和第 9）→ 自环
2. 两个特征在**不同群系里相对次序相反**（`spring_water` 在 layer_1 排在 `glow_lichen` 之后、
   在 layer_3 排在它之前）→ 交叉环

**修法**：给所有特征一条**全局有序序列**，群系只能挑子序列。
这样每个群系的扁平序列都是全局序列的子序列 → 数学上不可能有环。
脚本里加一条判据钉死：

```python
# 每个群系的扁平特征序列必须是全局序列的子序列
for a, b in zip(flat, flat[1:]):
    assert index[a] < index[b]
```

**判据要双向验证**：构造一个「颠倒两个特征」的坏样本，确认它报出来；
正常层表确认 0 误杀。只跑正常样本不算验过。

## 8. 出生点：`getSpawnHeight()` 返回的是**写死的值**，别让它跟地形对不上

`ChunkGenerator#getSpawnHeight(LevelHeightAccessor)` 不接收 x/z，服务端也不会
为每一列重新找地表。所以：

- 如果地表在出生半径内有 ±N 的噪声起伏，玩家就可能**生在半空**或**生在方块里**；
- 实测服务端会自己往上挪一格救回来（`level.dat` 里 spawn 从 2001 变成 2002），
  但那是运气，换个种子就不灵。

**修法**：出生半径内地表**绝对平**（起伏压到 0），出了半径再用几十格渐入
（直接截断会留一道 N 格高的台阶，很丑）：

```java
double dist = Math.sqrt((double) x * x + (double) z * z);
double ramp = Mth.clamp((dist - SPAWN_SAFE_RADIUS) / 64.0, 0.0, 1.0);
int top = SURFACE_TOP_Y + (int) Math.round(24.0 * ramp * fbm(...));
```

顺带：出生半径内也不许出现竖井（否则玩家一出生就掉下去）。

### 8.1 ⭐ 真正能控制「出生在哪一格」的只有事件（26.1 实测）

`getSpawnHeight(LevelHeightAccessor)` **只吃一个高度访问器、没有 x/z** ——
结构上就无法表达"横向位置"。想把人放在"洞口旁边那块台地上"，必须走事件。
26.1 的决定链是：

```
MinecraftServer.createLevels
  └─ if (!levelData.isInitialized())
       └─ setInitialSpawn(...)
            ├─ EventHooks.onCreateWorldSpawn(...)        ← NeoForge 的挂点
            │     └─ NeoForge.EVENT_BUS.post(LevelEvent.CreateSpawnPosition)
            │           isCanceled() == true → 下面整段跳过
            ├─ chunkSource.getGenerator().getSpawnHeight(level)
            ├─ levelData.setSpawn(RespawnData.of(dim, spawnChunk 位置, 0, 0))
            └─ PlayerSpawnFinder 在 ±5 区块内再搜一次，找到就覆盖
```

所以最省事的是**取消事件 + 自己写死**：

```java
@SubscribeEvent
public static void onCreateSpawnPosition(LevelEvent.CreateSpawnPosition event) {
    if (!(event.getLevel() instanceof ServerLevel level)) return;
    // 判据用"生成器是不是我的"而不是"维度类型是不是我的"：地形是生成器造的，
    // 同维度类型换个世界预设就不成立了。
    if (!(level.getChunkSource().getGenerator() instanceof AbyssChunkGenerator)) return;
    event.getSettings().setSpawn(LevelData.RespawnData.of(
            level.dimension(), new BlockPos(SX, SY, SZ), YAW, PITCH));
    event.setCanceled(true);      // 取消后 getSpawnHeight 与 ±5 区块搜索都不再跑
}
```

要点：

- `LevelEvent.CreateSpawnPosition` 实现 `ICancellableEvent`；`getSettings()` 返回
  `ServerLevelData`，它继承 `WritableLevelData`，后者唯一的方法就是
  `void setSpawn(LevelData.RespawnData)`。`RespawnData` 是 record
  `(GlobalPos, float yaw, float pitch)`，工厂 `of(ResourceKey<Level>, BlockPos, yaw, pitch)`。
- **取消 ±5 区块搜索是好事**：大洞口边上一圈到处是虚空，让它自己找会随机挑一个坏点。
- 写进去之后不会被覆盖：`updateEffectiveRespawnData()` 会在初始区块加载完、
  以及几处固定调用点刷新 `effectiveRespawnData`。
- 于是 `getSpawnHeight()` 的返回值**根本没被用到**了 —— 留着表达"地表在哪儿"可以，
  但别再指望它决定出生点。
- 不勾 `LevelEvent.CreateSpawnPosition` 时**别用** `MinecraftServer.setRespawnData()` 打补丁：
  它写的是 `overworldData()`，对非主世界维度是错的。

### 8.2 1.20.1 对照（Forge/NeoForge 47.x · 2026-10-14 实测）

同一套思路在 1.20.1 成立，但有四处写法/行为差异：

| 项 | 26.1 | 1.20.1 |
|---|---|---|
| 事件写法 | `LevelEvent.CreateSpawnPosition` 实现 `ICancellableEvent`，`NeoForge.EVENT_BUS` | 同一个类，但走 Forge 的 `@Cancelable`：<br>`@Mod.EventBusSubscriber(modid, bus = FORGE)` + `@SubscribeEvent` |
| 写 spawn | `event.getSettings().setSpawn(LevelData.RespawnData.of(dim, pos, yaw, pitch))` | `event.getSettings().setSpawn(BlockPos, float yaw)`<br>（`RespawnData` record 是 1.21+ 才有的） |

### 8.3 🔴 1.20.1 出生点的**第二道关**：每次玩家登录都会重挑一次（2026-10-14 实测补齐）

**§8.1/§8.2 的「取消事件」只解决第一道关。** 本工程用户实测反馈「出生点还是在位面晶壁上」，
取证后拿到铁证：`level.dat` 里 `SpawnX/Y/Z` 明明是**球内点**，但玩家登录日志是
`logged in with entity id 11 at (7.5, 704.0, -31.5)` —— y=704 正好是**球壳顶面**。

**真凶**：`ServerPlayer` **构造函数末尾**（字节码偏移 249）无条件调用 `fudgeSpawnLocation`
（SRG `m_9201_`），以 `getSharedSpawnPos()` 为起点**再跑一遍同样的螺旋**。
**没事件、没配置、取消不了。**

**⭐ 走螺旋还是直接 moveTo，由 `DimensionType.hasSkyLight()` 决定（不是 `hasCeiling`！）**：
反汇编 `m_9201_` 首条件读的是 `f_223549_`，用 tsrg 查实 = **`hasSkyLight`**（`f_63856_` 才是 hasCeiling）。
`hasSkyLight && gameType != ADVENTURE` ⇒ 走螺旋；主世界与「有天空光」的自定义维度都走螺旋，
地狱（hasSkyLight=false）才走「直接 `moveTo` + 堵住就向上抬」。
**螺旋半径 = `MinecraftServer.getSpawnRadius(level)`**（游戏规则 `spawnRadius`，默认 10）
⇒ 以 worldspawn 为中心覆盖 21×21=441 列；**起点是随机的**（`RandomSource.nextInt(441)`），
再用与 441 互质的随机步长（`getCoprime`）遍历 → **谁的判据先命中就用谁**。

**判据在 `PlayerRespawnLogic.getOverworldRespawnPos`（SRG `m_183928_`，逐列判定）**：
```java
// ⚠️ 2026-10-14 二次修正：下面这版是对照字节码 + 运行时反射双重确认过的。
//    早前版本把 j>i 当成了「null 出口」，恰好读反 —— j>i 其实是「通过」。
int i = dimensionType.hasCeiling() ? generator.getSpawnHeight(level)
                                   : chunk.getHeight(Heightmap.Types.MOTION_BLOCKING, x, z);
if (i < level.getMinBuildHeight()) return null;
int j = chunk.getHeight(Heightmap.Types.WORLD_SURFACE, x, z);
if (j <= i && j > chunk.getHeight(Heightmap.Types.OCEAN_FLOOR, x, z)) return null;   // ★ 真正的 null
// 然后：k 从 i+1 往下逐格，找「有完整 UP 面的实心块」，命中即返回 pos.above()（= 站立位）
// （反汇编里是 m_7494_ = above —— 这步容易漏，漏了会误以为返回的是实心块自身坐标）
```
（`j <= i` 的语义 ≈「上方没有仅被 WORLD_SURFACE 计入的遮挡物」；把两个条件拼起来才能正确判读。）

**关键技巧：两个高度图对「某种方块」的取舍可以分开调** ——

| 高度图 | 判据（反汇编 `Heightmap$Types`） | 本例的取舍 |
|---|---|---|
| `MOTION_BLOCKING` | `state.blocksMotion() \|\| !state.getFluidState().isEmpty()` | **让壳退出它** → `i` = 内部地面 |
| `WORLD_SURFACE` | `!state.isAir()` | **让壳留在里面** → `j` = 壳顶 |
| `OCEAN_FLOOR` | 同 `!isAir()` 一族 | 同上 |

`blocksMotion()`（SRG `m_280555_`）= `block != COBWEB && block != BAMBOO_SAPLING && isSolid()`；
`isSolid()` = 字段 `legacySolid`，由 `BlockStateBase#calculateSolid()` 算出来：
```java
if (properties.forceSolidOn)  return true;
if (properties.forceSolidOff) return false;   // ★ 唯一能单独关它的入口
if (cache == null) return false;              // 没有 cache 说明形状是空的
VoxelShape shape = cache.cullingShape;
return !shape.isEmpty() && shape.bounds().maxY >= 0.7291666666666666;   // 近似「差不多是整块」
```

→ 给「壳」方块加 **`Properties.forceSolidOff()`**：
- `MOTION_BLOCKING` 忽略它 ⇒ `i` = 内部地面（≈105）
- 仍在 `WORLD_SURFACE` 里 ⇒ `j` = 壳顶（704）
- ⇒ 判定 `j > i` **通过** ⇒ 从 `i+1` 向下找到壳内的实心地表 ⇒ **返回「球内地表站立位」** ✅
- **修复前**（壳算进 `MOTION_BLOCKING`）：`i` = 壳顶高度 ⇒ 同一函数命中的是**壳顶的实心块**，
  返回 `above()` ⇒ 玩家出生在 y≈704 —— 这正是用户报的「出生在晶壁上」。
- **实测闭环**：反射调用该函数对球心列 `(0,0)` → 返回 `(0, 105, 0)`（修复后）vs 修复前会得 `(0, 704, 0)`。

**🔴 落点 = `worldspawn ± spawnRadius` 内随机某列，不是 worldspawn 本身！**
螺旋起点随机（`RandomSource.nextInt(441)`）→ 441 列里**第一个判据命中的列**即采用。
两次实测分别落在 `(0.5, 103.0, -0.5)` 与 `(-0.5, 116.0, 9.5)` —— 都是 `(0,0)` 附近 ±10 内的地表。
**这与 vanilla 主世界的出生行为完全一致**（原版玩家也不是精确落在 worldspawn）。
**所以断言不能写「落点 == worldspawn」，要写「在附近 + 合法站立 + 不在壳上」。**
⚠️ 别把「玩家没落在 worldspawn 正中心」当成 bug —— 那是原版机制；真正的 bug 是落在**壳顶/壳外**。

**⚠️ 别用 `noCollission()` 替代**：它一次关 `hasCollision` + `canOcclude` **两个**字段 ——
玩家会穿墙（对壳/墙类方块等于破坏游戏性）、天光会全断（`canOcclude` 是透光的守门条件，
见 `方块光照与透光.md`）。`forceSolidOff()` **只动 `legacySolid` 一个字段**。

**⚠️ `forceSolidOff()` 标了 `@Deprecated`**（1.20.1 官方映射如此；Mojang 原意是
「固体性应由形状表达，别拿它当日常手段」），但反汇编确认它是**唯一**能单独关 `legacySolid`
的出口、**没有非过时替代** —— 用 `@SuppressWarnings("deprecation")` + 注释固化，
处境与 `getLightBlock` 相同。

**⚠️ 副作用面**（全 jar 常量池扫 `m_280555_` / `m_280296_` 的引用）：`blocksMotion()` 仅 **10** 个
消费者、`isSolid()` **25** 个，除高度图外都是边缘行为（寻路 `GroundPathNavigation`、
流体铺展 `FlowingFluid`、装饰物附着 `HangingEntity`/`ItemFrame`）；
若你的 worldgen 用了 `solid` block_predicate，需重新评估。

**⚠️ 高度图与天光一样烘焙进区块存档**：改方块属性**不回填**已生成区块
⇒ 修复只对**新生成区块 / 新世界**生效，老存档必须开新世界。**别拿老存档验证出生点。**

**守门断言该怎么写（selftest，五条）**：
1. **状态断言**（不依赖世界数据，老存档也稳）：`state.isSolid()==false`
   && `state.blocksMotion()==false` && `!state.getCollisionShape(level, pos).isEmpty()`（碰撞仍在）。
   注意 `isSolid()`/`blocksMotion()` 也是 deprecated —— 包一层带 `@SuppressWarnings` 的 helper。
2. **判据函数直测（★ 最强的一条）**：**反射调用 `PlayerRespawnLogic` 的
   `(ServerLevel, int, int) → BlockPos` 静态方法**（运行时是 SRG 名 `m_183928_`；
   **按签名找、别按名字找**），对球心列断言：返回**非 null**、是**站立位**
   （`pos.below()` 有碰撞 + `pos` 自身无碰撞）、`y < 600`（远低于壳顶）。
   修复前这条会返回 y≈704（壳顶）→ 红。
3. **端到端探针**：`new ServerPlayer(server, level, profile)` —— 构造函数末尾就会跑
   `fudgeSpawnLocation`，**构造完位置即最终落点**，不需要登录、不需要进世界、不需要客户端。
   断言「水平偏移 ≤ spawnRadius+1」「是站立位」「到球心距离 < 半径−8」「y < 600」。
   ⚠️ 别断言「== worldspawn + (0.5, 0, 0.5)」（螺旋起点随机，见上）。
4. **对照断言**：`WORLD_SURFACE` 读到的那一格（j−1）应正好是壳方块
   （证明「原版确实会把人丢在壳顶」）。
5. **老存档信号**：老存档上 2/3/4 会红 —— 那是「**需新建世界**」的信号（高度图已烘焙），
   不是代码问题。

## 9. ⭐ 竖井内壁（collar）：光在岩板上挖个洞，"洞口"是立不起来的

场景：分层世界，每层都是**横贯全世界的空腔**，层间是一块悬在空腔里的**平板**岩板。
想在地表正中挖一口"超级大洞口"（原著那种），每深一层收一圈、收口处露出环形台阶。

**只做两件事是不够的**：

1. 在岩板上按半径挖圆孔 → 从上面看只是"平板上有个洞"，平板边缘之外照旧是通的，
   **根本没有"井壁"这个东西**；
2. 让每层的洞口半径逐层减小 → 也只是几个同心圆孔，玩家从地表往下看能直接
   看到每一层的整个空腔。

所以要**另砌一圈竖直的内壁**，从本层地板顶一直砌到**上一层岩板的顶面**。

### 9.1 参数怎么定（第二版；第一版是错的，见 9.2）

| 量 | 值 | 说明 |
|---|---|---|
| `PIT_RADIUS_TOP` | 428 | **地表岩板开洞**的半径（**不是**洞口半径！） |
| `PIT_MOUTH_RADIUS` | 384 | 真洞口半径 = 第 1 层内壁内沿 = `PIT_RADIUS_TOP − STEP`，直径 768 |
| `PIT_RADIUS_STEP` | 44 | 每深一层收多少 = 环形台地宽度 = **内壁的径向厚度** |
| `pitRadius(i)` | `428 − 44i` | i=0 是地表岩板开洞，i=1..7 是七层内壁内沿 |
| `PIT_WALL_RUFFLE` | 6 | 内沿的竖向起伏幅度（见 9.3，治竖条纹的关键） |
| `PIT_RIM_WOBBLE` | 24 | 洞口边缘的横向抖动，**八层共用同一个偏移** |

⚠️ 第一版是 `pitRadius(i) = 384 − 44i` + 内壁厚 20，收口处露出 24 格台面。
参数看着合理、判据全绿，但用户在游戏里一眼就看出来"**接缝太大**" —— 见 9.2。
第二版把内壁厚度提到整整一档台阶（44）、外沿对齐上一层岩板的开洞位置，
于是"台地可站宽度"就直接等于半径差，不用再减内壁厚。

### 9.2 ⭐ 两条"缝"都是几何性的，调参数治不好

**缝 A：内壁比台阶薄 → 八道贯通竖缝。**
第一版内壁厚 20、台阶 44 → 内壁外沿到上一层岩板洞沿之间剩 **24 格**，
从竖井里看是从顶到底**贯通**的竖缝。
治法：内壁外沿取 `pitRadius(i−1) + wobble`，**一格不剩地填满这一档**。

**缝 B：内壁砌到天花板的"底面" → 环形凹槽。**
岩板有厚度（21~99 格，中心还随噪声起伏 ±56）。砌到底面 = 内壁顶端比上一层地板
**低一整个岩板厚度**，两者之间横着一条环形凹槽 —— 从竖井里看就是"墙脚和地板
之间有一道缝"。
治法：砌到 `slabAt(topY + 1).top()`（**顶面**）。这样内壁顶端就成了上一层地板的
延续，每层地板因此多出一圈 44 格宽、**与地板绝对齐平**的环形台地。
⚠️ 第 1 层的天花板是**地表**（不是 `slabAt` 算的），要单独接 `surfaceTop`。

**顺带：材质也得接上。** 内壁顶那一格用**上一层的地板材质**、往下
`SURFACE_SOIL_DEPTH` 格用上一层亚层，再往下才是本层墙色。不然台地和地板之间
会横着一条**颜色断层** —— 几何齐平了，视觉上还是一条缝。

### 9.3 ⭐⭐ 体素化的圆 + 环境光遮蔽 = 整面墙的贯通竖条纹

这条和 9.2 是**不同的病**，而且更难想到：

半径 400+ 的"完美圆柱"，体素化之后是"**几乎每一格往外错一格**"的台阶形状。
MC 的 AO 会把每个错位格画暗 → 整面墙变成一根根**间距 1 格、贯通上下**的竖条纹，
看起来像一排木板拼的，不像岩壁。

⚠️ **只加二维噪声治不了**：二维噪声在竖直方向是**常量**，每一格的明暗关系
逐 y 复制，条纹照样贯通。必须有一项**随 y 变**：

```java
/** 内沿的竖向细起伏，返回 [-1,1]。y 按 24 格分段 + smoothstep 插值。 */
private static double wallRuffle(int x, int z, int y, int seed) {
    double t = y / (double) PIT_WALL_RUFFLE_BAND;      // 24
    int i0 = Mth.floor(t);
    double f = t - i0;
    double s = f * f * (3.0 - 2.0 * f);                // smoothstep：段间连续，不是台阶
    double a = hash(x, z + i0 * 977, seed + 907);
    double b = hash(x, z + (i0 + 1) * 977, seed + 907);
    return a + (b - a) * s;
}
```

- 用**两次 hash + smoothstep**，不用 fbm：这一段在内沿附近是热路径
  （每条窄带列最多问几百次），fbm 一次要跑 2~3 个八度，太贵。
- 只让 `innerBase ± PIT_WALL_RUFFLE` 那 12 格宽的窄带逐 y 判；更外面的列整层实心、
  直接出一整段（性能兜底）。逐 y 只跑在一圈上，开销可忽略。
- **岩板开洞要比 `innerBase` 再往里让 `PIT_WALL_RUFFLE` 格**，否则墙脚会随起伏
  露出一圈锯齿状的缝。

### 9.4 出生点：必须落在**岩板段**上，不能落在"墙头"上

内壁顶端和台地齐平之后，**洞口到岩板洞沿之间那 44 格也是平的、也能站** ——
但它底下是空的（往下 50 格就是第一层的空腔），站在那儿等于站在一块**悬空盖板**上。

出生半径取 `PIT_RADIUS_TOP + RIM_TERRACE_WIDTH/2`（= 476）：

| 边界 | 值 | 为什么 |
|---|---|---|
| 下界 | `PIT_RADIUS_TOP + PIT_RIM_WOBBLE` = 452 | 岩板洞沿**最远**可能位置 |
| 上界 | `PIT_RADIUS_TOP − PIT_RIM_WOBBLE + RIM_TERRACE_WIDTH` = 500 | 台地边缘**最近**可能位置 |

两端都取抖动的**最坏情况**，所以落进去就与噪声无关。第一版取的
`PIT_MOUTH_RADIUS + RIM/2` = 432 在旧几何下是"洞口外 48 格"（在岩板上），
新几何下岩板洞沿挪到 428，432 就只剩 4 格余量、**有时落在墙头上**。

### 9.5 判据怎么写（这两条是新的，都很锐）

| 判据 | 怎么量 | 为什么这么量 |
|---|---|---|
| **内壁顶端 = 上一层地板面**（9.2 缝 B） | 在墙的**外沿那一列**取墙顶 `y1`，判 `\|y1 − bound\| ≤ 170`（**窗口**）；再判全部样本里 `y1 − bound` 的**中位数** ≥ −12 且第 10 百分位不越界 | 岩板顶随噪声起伏 ±56，**相邻两列差几十格是正常的**（地板不是绝对平的），逐列判"必须相等"会大量误报；但那个起伏是**零均值**的，旧实现的误差是**系统性**的（恒低一整个岩板厚度）。窗口负责挡"墙顶跑到别层去了"，中位数负责量"系统性偏低" |
| **内沿随高度起伏**（9.3） | 8 个方向 × 固定射线上多个 y，量内沿半径 | 这是个**恒等式**：射线上的 x、z 与 y 无关 → 竖直方向零噪声。完美圆柱**恰好恒定**（不同取值个数 = 1），加起伏后 ≥3。**不需要定阈值** |

⚠️ **「量墙顶」必须用墙的*外沿*那一列，不能用内沿、更不能往台地外头扫**。
这一条连踩两版才对，两种错法都记下来：

* **按材质定位（v1）**：向下扫到"第一个上一层地板材质"。层 ≤3 能跑，
  第 4/5 层散架 —— 不是几何变了，是**材质对不上**：层 5 找
  `FLOOR_MATERIAL[4] = tuff`，可它窗口里根本没有第 4 层地板（在 y≈280~490）；
  台地上那 1 格 `tuff` 是**矿脉碎片**；层 5 墙色 `soul_sand` 又**正好是**
  层 6 要找的 `FLOOR_MATERIAL[5]`。**材质只是间接证据，不变量是几何。**
* **"同高度径向连续"扫到台地外头（v2）**：range 一路取到
  `pitRadius(i−2) + 20`。那段根本不是墙，是**上一层台地**（只有它自己的
  岩板 + 柱子，铺在上一层地板上）→ **必然**在上一层地板顶以下出现空档
  （实测层 3 在 `992−96` 就断了），那是上一层自己的地形落差，不是缝。
  **不变量只存在于墙自己占的那一档台地里**（`PIT_RADIUS_STEP` 宽）。

正确做法：从「内沿 + `STEP` + 2」往回扫，找**最后一个"下方见空"的实心列**
= 墙的外沿。**为什么不能用内沿那一列**：`addCollar` 把墙砌到上一层地板顶，
再往上紧跟着就是**上一层的岩板** —— 内沿那一列往上会一路接进岩板里，
读出来的"墙顶"是"上一层岩板的顶"，比真墙顶高 169~231 格（正好是岩板
中心到表面的距离）。**也不能在 `inner..inner+STEP+30` 里挑最外的见空列**：
台地那侧还有**巨柱**，柱子侧壁同样"下方见空"且更靠外，只取
`inner .. inner+STEP+2` 才保证量的是墙。

⚠️ **扫描窗口必须窄、而且锚在"实测内沿"上**（±`2*RUFFLE+6` = 18 格）。
第一版锚在**名义**半径、开 ±42，结果比墙顶高的那些高度上墙是空的，
"第一个实心"跑到**上一层岩板**那里（实测旧存档里 269 突变成 310），
于是完美圆柱也量出 2~3 种取值 —— **判据自己误报**。
锚在实测内沿 + 窄窗之后，窗口永远落在墙体内（内壁径向厚 44），穿不出去。

⚠️ **判据扫到的最远半径变了，`forceload` 的对角线范围必须跟着改**。
斜向 45° 的采样点是 `(round(0.707r), round(0.707r))` —— r 越大要的区块号越大。
洞口半径从 384 挪到 428、判据要扫到 r≈476 之后，斜向落到区块 21，
而 forceload 只盖到区块 17 → 斜向在**最远那几格静默返回 `None`**，
判据读成"这个方向量不到内壁"，看起来像地形少了 4 面墙。
→ 见 `专用服务端自动化验证.md` §4.8：**前置判据必须"按采样半径点名查区块"**，
「整体加载率 95%」这种统计式判据挡不住它。

### 半径必须**线性**递减、抖动必须**各层共用**

| 做法 | 结果 |
|---|---|
| 等比递减（384→96，台阶 69…21） | 最底几层**可站宽度为负**，玩家没落脚点 |
| **线性**递减 44 | 台阶恒 44，台地宽度恒 44 ✅ |
| 每层独立抖动 ±24 | 最底层半径差 44 而抖动 ±24 → 可能抖到**反序**，露出倒台阶 |
| **八层共用同一个偏移** | 相邻层半径差与抖动无关，恒等于设计值 ✅ |

## 10. ⭐ 装饰的高度锚点是**绝对的**，自定义深世界会长错地方

26.x 的 `placed_feature` JSON 里**已经没有 `biomes` 字段**了，落点完全由
`placement` 里的高度锚点决定。而原版锚点是**绝对 y**：

| 特征 | 原版锚点 | 在 4064 格高世界里的实际落点 |
|---|---|---|
| `cave_vines` / `sculk_vein` / `large_dripstone` | `[above_bottom, absolute 256]` | `[-2032, 256]` → 只有中下层 |
| `ore_coal_upper` | `[absolute 136, below_top]` | `[136, 2031]` |
| `patch_tall_grass_2` / `trees_plains` | `heightmap` | 贴地表（所以台地上有草 ✅） |

实测全世界（15 个 region）：`glow_lichen` 只出现在 y ∈ [-32, 32]，`tall_grass`
只在 1984~2000，而 **`cave_vines` / 钟乳石 / 幽匿脉络 / 蘑菇 / 树 一个都没有** ——
"繁茂洞穴层"没有藤蔓、"钟乳石层"没有钟乳石，看着像漏装模组。

**修法**：给每层写**自己的** placed_feature 副本（内容照抄，只把 `height_range`
换成该层的 y 区间）：

```json
{ "type": "minecraft:height_range",
  "height": { "type": "minecraft:uniform",
              "min_inclusive": { "absolute": -16 },
              "max_inclusive": { "absolute": 487 } } }
```

群系改引用 `abyss:cave_vines_layer4` 这类 id。
⚠️ 副本仍然是 placed_feature，**依然要遵守全局装饰序**（见 §7），否则又是 `Feature order cycle found`。

## 11. 26.1 撞到的 API 变动（写生成器时都会碰到）

| 老写法 | 26.1 |
|---|---|
| `ResourceLocation` | **`Identifier`** —— `ResourceLocation` 这个类**已经不存在**了 |
| `data get block` 读普通方块 | 只对**方块实体**有效；普通方块报 `The target block is not a block entity`，要用 `execute if block` |
| 主世界 region 在 `world/region` | `world/dimensions/minecraft/overworld/region`（跟下界/末地平级） |
| `level.dat` 的 `SpawnX/Y/Z` | `Data.spawn = {pos:[x,y,z], dimension, yaw, pitch}` |

| `FogData` 两个距离 | 五段：`environmentalStart/End`、`renderDistanceStart/End`、`skyEnd`、`cloudEnd` |

`.mca` 的压缩标记是 **1=gzip / 2=zlib**（写反了报 `Not a gzipped file`，
会以为存档坏了）。读取时**必须按 `Status == minecraft:full` 过滤** ——

（实测 144 个区块里只有 9 个是 full，竖井率被虚报到 93.8%）。

那是 `ServerChunkCache` 才有的方法，客户端的 `ClientChunkCache` 没有，两边就得写两套。
用 `level.dimensionTypeRegistration().is(MY_DIM_TYPE_KEY)` 一套通吃（服务端/客户端都有）。

## 12. ⭐ 把入口做成「四面环海的岛」时，高度是**倒着算**的（2026-09-25 深渊第四轮）

### 需求形态

「主入口 = 一个岛，洞口在岛中心的盆地底，岛四面环海，保证不漏水」。
听起来是纯几何题，真正的约束是**世界顶**：

- `BlockPos` 的 y 只有 12 位 ⇒ 硬顶 `y=2031`（`[-2032, 2031]`，共 4064 格）；
- 生成器还会把地表钳到 `WORLD_MAX_Y - 8`。

而「盆地底 < 山脊顶 < 世界顶」三段**全要塞进海平面以上的那几十格里**。
第一版把 `ISLAND_RIM_Y = 2074` 写超了 43 格 —— **服务端不报错、判据不报错**，
只有在剖面图上才看得见（山脊被齐着世界顶削平）。
⭐ 这类错误必须有一条**断言**钉死：`盆壁顶 + 余量 ≤ WORLD_MAX_Y - 8`，写进生成脚本。

### 「不漏水」要做成三条**互不相干**的保险，不要靠"希望几何对"

深渊是贯穿世界的空腔，海水漏一处，四千米竖井变水柱。三条保险：

1. **盆壁全程高于海平面**（几何）：盆地底 1990 → 盆壁顶 2012，海平面 1950；
2. **洞口半径内显式禁水**（逻辑）：`NO_WATER_R = 盆地半径 + 120`，不生成任何水方块；
3. **低地/海床岩板强制加厚**（兜底）：地表顶低于 `SEA_LEVEL + 40` 就强制 ≥56 格厚。

判据各验各的（[J] 逐半径量地表顶 / [K] 洞口内零水 / [L] 海床 56 格实心占比 ≥70%）。
⚠️ [K] 这类"零水"判据**不需要故障注入**也能证明有牙齿：给一个**正对照** ——
[M] 用同一套水检测在海上测到了水（且"海平面下 30 格仍是水"），说明检测器和
采样几何都对，此时洞口内的零水才是真的零水。

### 海床判据的口径：判「挡不挡水」要按**实心占比**，不按连续

海床 56 格里夹着 2 格 `cave_air` + 1 格 `lava`（岩浆湖装饰）—— 岩浆挡水且是封闭泡，
按"连续实心"判就误报。用 `solid_frac ≥ 70%`，实测最差 95%。

### ⭐⭐ 岩檐没画出来：`if (ledgeBand && !insidePit)` 这种"顺手加个条件"会整条判掉自己

想让井壁上长石头（治"空腔太空"），在**墙内侧那一圈**（`ledgeBand`）画岩台，
结果条件里叠了一个 `!insidePit`（井腔），而岩檐带与井腔**重叠的正是"伸进井腔的那段"——
也就是檐本身**。只剩 `2×RUFFLE=12` 格宽的一圈能通过，那一圈本来就被内壁砌实了。
症状：判据恒 0%，极易误读成"画得太淡"去调概率参数（越调越错，因为根本没进分支）。
⭐ 往一个几何判断里叠第二个条件前，先问一句：**这两个区间是相交还是相离？**

### ⭐⭐ 「顶到某个面」的结构，那个面必须是**实测值**

巨柱/悬石的天花板原来用 `layer.topY()`（层表名义值，第 1 层恒 1949）。
岛改完后海床降到 1900，柱子按 1949 当顶一路长到 1948 —— **直接捅出海面**，
海只剩 2 格深。名义值和实测地形是两份独立维护的真相，改地形它就静默失效。
一律用 `ceilingTopOf(layer, surfaceTop, x, z, seed)` 这种实测函数。

### ⭐⭐ 判据会被被测对象自己带偏（本轮三个案例）

| 案例 | 机制 | 修法 |
|---|---|---|
| [N] 岩檐恒 0% → 修好后恒 11% | 旧判据先测内沿 `INNERS` 再取 `INNERS-20/-36` 扫实心；檐一画出来，从井里往外扫到的第一个实心就是**檐**（比墙靠里 62 格），INNERS 跟着漂 → **檐画得越狠测得越少** | 不再先测内沿：每个高度从井腔往外扫 `e(y)`，判「多少比例的高度 `e ≤ max(e)−20`」，用同一列自己的最大值 |
| [N] 修好后仍两层假绿 | 采样窗口没避开贴地的门：门里的列"第一个实心"是门外的**巨柱**，`max(es)` 被顶上去 | 只扫上半段 0.58~0.95 |
| [F] 开口率虚报 86% | 判据挑「顶端最高的段」当墙；岛改完后墙顶上方是上一层井腔（有巨柱/悬石），选中一根 20 格厚的悬石，把"墙顶与悬石之间的空腔"当成"门" | 窗口钉在**本层自己的 y 区间**（挡掉上下层井腔的东西）+ 墙取**最厚的段**（墙 225~425，岩板 ≤99）+ 门下沿须落在地板 ±170 内 |

### 天然竖井（≈14%）会破坏「中位数」型判据

地表岩板有 ~14% 概率被噪声压成 0（天然竖井，设计的一部分），那一列**没有地表**。
竖井**成片出现**（噪声空间相关），一条 16 格采样带能被吃掉 10 格 ⇒ 中位数被拖低 ⇒ 假红
（实测"盆地最高点 1834 ≠ 1990"）。修法：「**最高点 ≤ 设计+tol** 且 **≥1/4 列落在设计±tol**」，
并把"整带竖井"与"区块没加载"**分开记账**。
⚠️ 记完账要 `continue`，否则它还会掉进下一条判据里变成假红（实测踩过）。

### 「地表」的量法：水、植被都不算地

- 海底每个取样点用 `top_solid` 都会量到**海平面那一格**（水是实心）→ 判"岛剖面"全错；
- 盆地里长一丛 `tall_grass`（2 格）→ "盆地绝对平 1990" 报成 1992。

修法：`top_ground(x, z, y_lo, y_hi, min_run=4)` —— skip 水 + skip 植被
（名字黑名单：`_grass/fern/flower/sapling/leaves/_log/bamboo/cactus/...`）+ 连续厚度兜底。
判"海床还在"同理。

### 判据量出 10.7% ≠ 地形错了：先查样本量

门率设计 30%，8 方向测得 10.7%（n=56，期望 16.8±3.4，差 3σ）——
差点当成 bug 去调生成器。**32 方向复测 24.3%（n=107）**，就是样本太少。
⭐ 百分比型判据报出来的数和设计值差得远时，先算"这个样本量下差几个 σ"，
再决定是修地形还是加样本。

## 13. ⭐⭐ 把「每层形状都不一样」做出来之后，判据会集体失效（2026-09-25 深渊第五轮）

元的原话：**「深渊生成的地形实在是太烂了，只有大断层才直挺挺的，其他的地方都是有粗有细，研究原著的地形」**。

### 13.1 先量，别猜：「有粗有细」的四个来源

对每一层、每个方向，沿 y 逐格扫"从井腔往外遇到的第一个实心"，把 `e(y) − 名义半径` 列成表，
一眼就分得出是哪种病：

| 症状 | 数据长什么样 | 根因 |
|---|---|---|
| **环向不圆**（最主要） | 同一层不同方向的墙内沿差 ±24 格 | 环向抖动 `PIT_RIM_WOBBLE` 是个**全层共用**的常数 —— 在半径 384 的第一层是 6%，在最底层半径 72 的那层是 **33%** |
| **檐参差不齐** | 0° 的檐在 y+100、45° 的檐在 y+220 | 出檐高度按 **(x,z) 逐列**用噪声决定，绕井一圈是一堆碎凸台 |
| **井壁开大洞** | 某些方向 `e` 跳到墙**外**（≈ 外沿半径） | 贴地开口 30%，按 (x,z) 噪声成片出现 |
| **上下层交界不干净** | 层间岩板中心 ±53、厚 21~99 | 大尺度噪声（这个是设计，不动） |

**竖直方向墙其实是直的**（同一方向沿 y 波动 ±3）—— 所以"粗粗细细"不在竖直方向，
别去调竖向参数。

### 13.2 原著怎么查（这些是硬约束，不是审美）

- 每一层的**深度与厚度是极不均的**（作者设定 20000m 总深）：
  1 层 0~1350、2 层 1350~2600、**3 层大断层 2600~7000（4400m）**、
  **4 层巨人之杯 7000~12000（5000m，最厚）**、**5 层亡骸之海 12000~13000（只有 1000m，垂直最短但横向最辽阔）**、
  6 层 13000~15500、7 层 15500~20000+。
  ⇒ 按比例映射到可用竖深（`1949 − (−2032) = 3981` 格）：**268 / 249 / 876 / 995 / 199 / 498 / 897**。
  **"七层等高"这件事本身就是错的**。
- 大断层的定义句是「**长度 4000 米以上的平整的巨大圆形峭壁**」——
  「平整」+「圆形」两个词直接对应 `wobble = 0`、`不下檐`、`不开门`。
- 洞口直径约 1000m（1 格 ≈ 1 米时就是半径 ~500，我们的 428/384 是同量级）。

### 13.3 ⭐⭐ `PIT_RADII` 从"线性递减"改成表，四个连环后果

改动的核心是：**井壁内沿半径、环向抖动、贴地开口率、岩檐风格，全部从标量变成逐层表**。
（"每层收窄幅度一样"本身就不符合原著。）

⚠️ 连带必须改的：

1. **井壁径向厚度不再恒定** = `pitRadius(i-1) − pitRadius(i)`，逐层不同（30~78）。
   凡是写着"从内沿往外 44 格"的地方**全部失效** —— 判据里 `wall_face` 的扫描起点、
   `[E]` 的 `x_wall` 上界都写死了 `PIT_STEP`，会把扫描窗口开到墙**外面**去，
   读回的"墙顶"是台地/巨柱的顶（实测把 `[E]` 的中位数从 −8 漂到 −15）。
2. **抖动逐层之后，"相邻层半径差恒定"这个不变量没了** ——
   必须改用"最坏情况可站宽度 = 相邻半径差 − 两层抖动之和 ≥ 20"来兜底。
3. **`PIT_RADII` 必须单调不增**：井壁砌在 `[R(i), R(i−1)]` 那一档里，
   R 反增会让"外沿"跑到"内沿"里面，**墙翻进井腔** —— 编译、启动、日志全干净。
   加一条断言钉死。
4. **檐深要跟半径联动**：`檐深 × 2 + 24 < 该层半径`，否则两侧檐在井心接上，玩家掉不下去。
   逐层判（不能只看最窄那层，因为檐深也是逐层的）。

### 13.4 ⭐⭐ 判据是「第三份手写副本」—— 这是本轮最大的假红来源

生成器改了层表和井壁参数之后，判据一次性报了 **21 处失败**，其中大半是它自己造的：

| 判据里的东西 | 问题 | 后果 |
|---|---|---|
| `LAYERS = {1: ('深界一层', 1496, 1949), ...}` | **手抄的层表**没跟着改 | `[G]` 拿着旧 y 去量新地形（报"y≈992 竖井率 42.5%"，而 992 已经是别人的地盘）；`[E]/[D]/[P]` 对第 5 层整层量不到东西 |
| `PIT_STEP = 44`、`RIM_WOBBLE = 24`、`pit_radius()` 自己算 | **手抄的几何** | 判据验的是"另一口井" |
| `ys = [1999, 1950, ...]` | 硬编码的 y | 地表从 2000 挪到 1990 之后，全错位 |

⭐ 修法：**能 import 就别抄**。层表 `{l.index: (l.zh, l.bottom, l.top) for l in _gen.LAYERS}`、
半径 `_gen.pit_radius`、抖动/檐/开口率 `_gen.PIT_*_BY_LAYER`。
⚠️ 而且"只用来包住最坏情况的余量"（如 `RIM_WOBBLE = max(...)`）要**和"逐层判据用的值"分开**，
别让一个全局最大值去替某一层背书（那等于给大断层发免罪符）。

### 13.5 ⭐⭐ 判据的**采样几何**必须和被测地形的**格网对齐**

`[R]`（"标志地形真的长出来了"）第一版沿 8 个方向、按半径扫 —— **三层全报 0 盏**，而地形完全正确：

- 遗迹格心在 `z = 26 + 52k`、荷叶盘心在 `z = 28 + 56k`；
- 采样线只有 `z=0 / x=0 / 对角线`，`z=0` 到最近格心的垂直距离恒为 **26 / 28**；
- 而遗迹半边长 ≤20、盘半径 16~30 ⇒ **采样线永远从格心旁边擦过去，一次都进不去**。

修法：改沿驱动脚本真正铺满的那条带（`x∈[400,1400]`、`z∈[0,15]`）密集扫。
⭐ 一般化：**先想清楚"被测特征在空间里的周期/格网"，再设计采样线**；
采样密度还要和"特征体积占比"匹配 —— 一棵倒挂树在 1664 个采样点里只占 0.26%（期望命中 4.3 个，
门槛却是 20），也就是**地形全对也会报红**。

### 13.6 ⭐⭐ 判据的"参照量"要抗噪；能不用窗口就别用窗口

量"墙内沿"需要一个参照，三种取法各踩一次：

| 取法 | 怎么坏 | 实测 |
|---|---|---|
| `max(e)`（旧口径） | 内壁的**门**里第一个实心跑到墙**外**的台地/巨柱上，最高点被抬上去 ⇒ 所有正常高度都成了"深" | 两层假绿（11.2% / 23.4%） |
| `statistics.mode(e)` | 墙内沿因竖向起伏**一直在变**（每个整数值只出现三五次），而檐的内沿是一整条**平的**岩环边（同一个值出现几十次）⇒ 众数选中了**檐** | 巨人之杯 ref 被判成 146（正是檐），真墙在 246 |
| **按 12 格分箱再取众数** ✅ | 墙的那一簇重新变成多数，檐（深 20~90）也仍分得开 | 层 4 同心度 0.92、层 6 是 1.00 |

⭐ 由此推论：**"只扫层高的 0.58~0.95 躲开门"这种窗口是负担** ——
檐的分布一变，那个窗口反过来把檐躲掉了（实测层 1/2 报"0/8 个方向有檐"）。
只要参照量抗噪，就可以放开扫**整层**。

⭐ 另一条：**判"是不是檐"的阈值必须相对化**。檐深是逐层的（20~90），
用固定的 `|e − (ref − depth)| ≤ 18` 在浅檐层（第 7 层檐深 20）会把**墙**也算成檐 ——
檐高占比虚报 **51.4%**（设计只有 3%）。改成 `e ≤ ref − 檐深/2` 就自洽了。

### 13.7 ⭐⭐ 「顶到某个面」的结构，那个面必须是**那个面的底面**

`ceilingTopOf()` 返回的是天花板岩板的**顶面**（= 上面那一层的地面）。
巨柱/悬挂类地形拿它当起点，就会**穿过整块岩板（厚 21~99）**，在上一层的地面上冒出一格：

- 实测出生点台地"草方块下面那格土"被**安山岩**顶掉（判据 `[B]` 报
  `(0,476) y=1989 是土 → 实际 andesite`）；
- 柱高是"净空的比例"（40%~95%），本来够不到天花板，所以只在**净空被岩板吃掉一截**的列上出现 ——
  **静默、随机、极难复现**。

修法：加一个 `ceilingBottomOf()`（岩板底面）专门给"悬挂类"用，
`ceilingTopOf()` 只留给井壁（井壁本来就该砌到上一层地板顶面）。
⭐ 规律：**同一个"天花板"对不同结构有两个语义 ——"砌到哪个面"和"从哪个面往下挂"是两回事。**

### 13.8 ⭐ 参数要跟着**尺度**走：檐间距 vs 层高

檐间距 112 格放在 268 格高的层里，整层只落得下 **2 个档**，再乘 55% 的出现率 ⇒
**这一层经常一个檐都没有**（判据报 1/8、0/8 个方向）。而同样的 112 放在 995 格高的层里毫无问题。
⭐ 凡是"每隔 N 格来一次"的参数，都要问一句：**这一层放得下几次？**（目标 4~8 次）

### 13.9 ⭐ 索引语义要显式：`LAYERS` 是按 y 排序的**列表**

`gen_abyss.py` 里 `LAYERS.sort(key=lambda x: x.bottom)` ——
所以 `LAYERS[0]` 是**最深那层**，不是 index 0。
判据里写 `_gen.LAYERS[i].floor` 拿材质，结果每一层都拿错材质，
`[G]` 的竖井率**全部报 100%**（"一层岩板都找不到"）。
⇒ 用 `{l.index: l for l in _gen.LAYERS}` 显式建索引。

### 13.10 水层与下潜通道的冲突：**裂口必须开在水面之上**（玻璃是错的）

「亡骸之海」整层是水，但中央竖井要留给下潜。这里有一个**硬物理约束**：

> 只要水面与下潜通道之间存在任何通路，水就会顺着它灌进竖井，
> 再从竖井底部的口子一路漏到下一层。MC 没有水压，水一定找得到路。

第一版的做法是**在井壁上镶一圈玻璃**当"水族馆"（挡水 + 看得见海，逻辑上成立）。
**元看过之后否掉了：「玻璃太不自然了」** —— 在一堵 4000 米的天然岩壁上
镶一圈玻璃，出戏得没法看。

✅ 正确的做法：**把裂口整条开在水面之上**。
水不会往上流，所以"下沿 > 海面"这一条就足以让密闭天然成立 ——
不需要任何人工材料去堵。玩家沿井壁的**海蚀阶地**（岩檐）爬上去，
从裂口翻出去，外面就是一望无际的海。
（相应的，这一层要配岩檐当落脚点；判据量的是"裂口带高度上那几个角的井壁是空的"，
外加一条硬断言 `裂口下沿 > 海面`。）

⚠️ 配套两条：
1. **水层的边界岩板不许有天然竖井** —— 14% 的竖井在别的层是下潜通道，
   在这一层就是泄水口，要强制存在。
2. **水面之上的空间要留够**：裂口 + 让玩家爬上去的岩台都要塞在这一段里。
   层高只有 ~200 格时（这一层原著就是"垂直最短"），水面别定太高。

### 13.11 判据的扫描窗口**别越界到邻层**（口径太宽 ⇒ 假绿）

`[R]` 量"盘里的水"用了 `[bottom−120, bottom+120]` —— 而 `bottom−120` 已经落进
**下一层的海**（海面只低 82 格）。量出 **34221 格水**，数字大得离谱，
判据却"通过"了（门槛只有 20）。
⭐ 数字明显大于设计量级时，先怀疑**窗口/口径**，别庆幸它过了。

### 13.12 ⭐⭐ 「同一件事两份口径」——本次是"天花板到底存不存在"

生成岩板时用的是 `surfaceThickOf()`（原始噪声 + **低地下限兜底**：低地一律 ≥56 格），
而判断"这一列有没有天花板"时我用的是 `surfaceThickNoise()`（原始噪声）。

于是低地上那些"原始噪声 = 0（天然竖井）"的列：
**岩板其实照样建了**（被下限兜到 56 格），但天花板判定说"没有" ⇒
柱子退回按 `layer.topY()` 当顶 ⇒ 柱长算成 237 格 ⇒
**从海床（1900）里捅出海面 34 格，把海水挤掉**。

判据看到的是：`[J] 海床最高 1934（设计 1900）`、`[M] 水下 30 格只有 5/16 列是水`。

⭐ 规律：**凡是"某个东西在不在"的判定，必须和"当初决定要不要生成它"的判定用同一个函数。**
两份口径的典型症状是"改动只在某个分支上出现"——这里就是"只在低地出现"。

### 13.13 ⭐⭐ 纯随机的「每隔 N 个来一次」在薄层会**永久**失效

檐的档判定原来是 `uniform(...) < chance`。看起来没问题，实际上：

- 薄层（层高 268 / 249）折算下来整层只有 **3~4 个档**；
- 连着几档都没抽中的概率是 4%~35%；
- ⚠️ **而同一个世界种子的结果是确定的** —— 一旦某层抽空了，
  它就在**每一次**生成里都是空的（实测层 2 连续两轮生成都报"0/8 个方向有檐"）。

⭐ 修法：给一个**结构性的兜底**，比如"偶数档必出、奇数档随机" ——
薄层因此至少有 2~3 圈规整的岩环，整体又不会退化成等距梯田。
⭐ 一般化：**"每隔 N 个来一次"这类参数，要么保证 N 相对总量足够小（≥8 次），
要么就别让它完全靠随机。**

## 14. ⭐⭐ 井壁形态一改，判据集体失效；概率类判定的四个隐形坑（2026-09-25 深渊第六轮）

元进游戏走了一圈，回来三条：**「1 是洞和空腔不相连被洞壁隔开了，2 突出的平台是干嘛的，
还有就是地形太不自然了」**（同时贴了原著的阿比斯剖面图）。

### 14.1 三条抱怨是同一个根因

第五轮我把井壁做成了「**一根完整的圆管墙** + 30% 概率的**贴地小门**」，
外加「按高度等距伸出的**薄板岩檐**」。当时的想法是"规整 = 好看"，
但原著里那一圈是**天然岩层** —— 洞与各层靠岩层自己的**断口**连通。

| 元的话 | 真实问题 |
|---|---|
| 洞和空腔不相连 | 完整圆管墙把两个空间彻底隔开，门只有 30% 且贴着地，玩家绕一圈也未必找得到 |
| 突出的平台是干嘛的 | 薄板悬在半空、踩不到、没有落脚价值，还把岩壁切成一排排书架 |
| 太不自然 | 等距薄板 + 完美圆柱 + 规整同心环 —— 那是"工程感"，不是"岩石感" |

✅ 改法：**缺口按高度分段 + 逐段独立**（缺口率 55~62%）⇒ 留下一圈**错落的岩柱**；
薄板 → **岩层**（内沿随高度 sin 低频鼓包，近水平、周期固定）。

### 14.2 ⭐⭐ 概率类判定的四个隐形坑（都只在跑起来之后才看得见）

1. **不等号方向要拿边界值各验一次。**
   `chance` 是"缺口率"，缺口应判 `值 < chance`。写成 `>= chance` 之后，
   **`chance = 0` 的层（亡骸之海）变成"段段全缺"** —— 那一层整圈井壁被删光，
   海水直接灌进井腔（正是这一层最不能出的事）。
   ⭐ 规则：**凡"概率/占比"参数，用 0 和 1 各跑一遍**，看行为是否符合作者意图。

2. **把 `fbm` 换成 `hash` 修校准时，别把 fbm 自带的空间尺度一起丢掉。**
   逐格的 hash 判定给出的是**逐格雪花点**（墙上每隔一格一个洞）——
   既不像岩柱也通不了人，判据"从井腔一路扫到墙外"**永远能碰到实心**（通孔率量出 0%）。
   ⭐ 修法：判定前先把 `(x,z)` **量化到格子**（`PIT_MOUTH_CELL = 56`）。
   因为井壁径向只有 44~90 格厚，一片 56×56 的缺口就 = **贯穿整个墙厚**的大洞。

3. **`uniform(fbm(...))` 的阈值必须按实测分布校准**（第一轮就记过，这次又踩）。
   设计缺口率 58% 的层实测只有 **18%**（恰好一半）——
   `FBM_SIGMA` 是对另一个频率标定的。hash 出来的是严格均匀分布，阈值直接等于概率。

4. **"地层/岩层"在水平方向必须是连续的。** 第一版把岩层的周期和相位都做成 (x,z)
   的**中频**噪声，绕井 45° 相位就漂 0.29、放大之后层位相差 **20 格** ⇒
   同一高度上绕井一圈的半径又参差不齐了（正是上一轮元抱怨的「有粗有细」）。
   ⭐ 真实的沉积岩层在水平方向连续：**层理只该随高度变，水平方向只允许很缓的倾斜。**

### 14.3 ⭐⭐ 判据里每个"参照量"都写死了它假设的形态

井壁形态一变，这些判据集体失效：

| 判据里的东西 | 它假设的形态 | 形态变了之后 |
|---|---|---|
| `wall_inner` 的 `split_off`（"比墙靠里 N 格就不算墙"） | 有**独立的薄板**伸出来 | 岩层是墙**自己的一部分**，鼓包整段被判成"这里没墙"，深层量不到东西 |
| `collar_inner` 取**最小值** | 墙是竖直的、各高度半径相同 | 岩层让内沿随高度鼓包，取最小值 = 专门量鼓包峰 |
| `[N]` 的 `ref − min`（ref = 分箱众数） | 内沿分布集中 | 鼓包把分布摊开，众数不稳（设计 46 量到 13） |
| `[C]/[D]/[E]/[P]` 的容差 | 内沿只受抖动影响 | 要把**岩层深度**和**缺口**算进去 |

⭐ 结论：**判据不是"地形对不对"的客观尺子，它自己也编码了"地形应该长什么样"。
形态一变，先回头把每个参照量重新问一遍"它还成立吗"。**

### 14.4 ⭐ 判据的"取样窗口"要和"被测特征的空间尺度"匹配

`[Q]` 第一版用"从井腔**径向扫 80 格**、全空才算缺口"去测 **56 格见方**的缺口 ——
窗口跨到隔壁"有墙"的格子上去了，**设计 62% 只能量出 32%**（差不多一半）。
改成在井壁厚度**正中那一格单点取样**就对了。

### 14.5 ⭐ 对称分布的 p10~p90 跨度**恒等于 0**

想用分位数跨度去度量岩层鼓包，可岩层是 **sin** 波形：
`sin(0.1π) = sin(0.9π)` ⇒ p10 和 p90 是同一个值 ⇒ **跨度恒等于 0**，
只剩"幅度变化"那一丁点（设计 40 只量到 15）。
⭐ 改用「**第 3 大 − 第 3 小**」：拿到真正的波峰波谷，又剔掉个别离群点。

### 14.6 ⭐⭐ 先用**离线复现**验证生成逻辑，再花 20+ 分钟生成

这一轮的两个致命 bug（不等号写反、缺口雪花点）都是"生成 27 分钟 → 跑判据 → 才发现"。
最后一次改成：**把 Java 的 hash 在 Python 里照抄一遍，喂真实的种子和坐标**，
几秒钟就能看到图案：

```

层3 半径320 缺口率 20%  实测 10/72 =  14%  .......XXX..XX.........................................
层5 半径220 缺口率  0%  实测  0/72 =   0%  ....................................................
```

一眼就能判断"成片的岩柱"✓ 还是"逐格雪花点"✗、以及 0 概率的层是否真的没缺口 ✓。
**世界种子是固定的**（`server.properties` 里 `level-seed=20260923`），所以离线结果与实地一致。

## 15. ⭐⭐ 一体腔：腔是连续曲线之后，判据必须跟着模型走（2026-09-26 深渊第八轮）

元的原话：**「不是葫芦只是形容，意思是洞和空腔是一个整体而不是隔开」**。
病症是「洞壁挡住了空腔」：洞穴噪声在井腔里照样生效，实测井轴 4033 格里 1255 格实心
（还有 +1169..+1469 共 301 格的整段实心）—— 井被岩块填死，下不去。

### 15.1 一体腔模型：`bore(y)` 是唯一真相

解法是把"井"从**几何体**降级成**曲线**：

- 腔的净空半径是**逐 y 连续的 `bore(y)`**（控制点 = 每层中点，smoothstep 插值），
  允许半径反复收放（原著第 3 层收 150 → 第 4 层扩 260 → 第 5 层最宽 420 ——
  旧模型"墙砌在 `[R(i), R(i-1)]`"隐含要求半径单调不增，根本表达不了这个形状）；
- 墙只是**贴着曲线外侧的一层壳**（`rimAt` 从 `bore` 推导）；
- 洞穴噪声在腔内被**绝对净空带**压制（`clean = smooth01(((bore−CLEAN)−dist)/SOFT)`）；
- 层界岩板的开板闸门也用 `bore`（`dist < bore(y)−CLEAN` 处不砌板 ⇒ 上下直通）。

⭐ **三处全部从同一个 `bore` 推导**，Python 侧 `gen_abyss.bore()` 是唯一真相，
Java 照抄、判据 import —— 对账脚本逐点断言（581 点 max|diff|=0）。
各写一份的下场不是"数字差一点"，而是**判据按 A 段验收、地形按 B 段生成，全绿但验的不是生成的东西**。

⚠️⚠️ 净空带压制**方向极易写反**：写成 `smooth01((dist−(bore−CLEAN−SOFT))/SOFT)` 时
`dist=0`（腔心）参数 ≈ −6.9 → 截到 0 → **腔心反而不压制、腔壁反而压制**，正好反了。
症状：改动前后探针数字**逐位相同**。正确方向：`clean` 在腔心为 1、在 `bore−CLEAN` 外为 0。

### 15.2 ⭐ 模型一换，判据口径集体失效（本轮 5 条假红全是这个）

改完地形跑旧判据：**48 基线 → 50/5**。五条红逐条查，**五条全是判据的口径还停在旧模型**：

| 判据 | 旧口径（隐含假设） | 为什么失效 | 新口径 |
|---|---|---|---|
| [S] 墙内沿 | 极差 ≤180（假设每层半径是常数） | 曲线让内沿天然从 157 漂到 388（第 4 层），**231 里 200 格是 bore 自己的形状** | 内沿 − `bore(y)` 的偏差 ∈ [−90, +70]（曲线减掉后墙真的没漂：实测 −58..+6） |
| [D] 层间板 | 采样半径 = 上一层半径 + 80/220/380 | **下一层更宽时采样点落进下一层的腔里**（第 4 层界取 150+80=230，而腔半径 260）→ 那里本来就该空 | max(本层, 下一层) + 井壁外沿（115/145 两档） |
| [E] 台地 | 台地在墙**外** r+170 | 一体腔里台地在**腔内边缘**（墙在 bore 外侧）；而且"窄层→宽层"的界闸门比腔还宽 ⇒ **直通口，本来就没有台地** | 环带 [闸门, min bore(窗口)]；闸门 ≥ 腔的界改验"井心 ±30 格全空" |
| [E] 闸门 | `下一层中点半径 − CLEAN` | `shaftInner` 是 **`bore(y)` 驱动的**，不是查表 ⇒ 闸门算窄 150 格 → 台地环整个落在被挖空的地方 → 0/8 | `bore(lo) − CLEAN` |

常数卡曲线 = 把模型自己的形状读成缺陷。

### 15.3 ⭐ 连通性要直接验，不能靠代理指标（新增 [W] 泛洪判据）

⭐ **判据内置坏样本**：每层顺手在 0.6R 处注入一堵贯穿全层高的竖墙再泛洪一次，

## 16. ⭐⭐⭐ 判据验错了方向：只验竖向连通，横向包死两轮没人发现（2026-09-27 深渊第十轮）

### 16.1 事故形态：**全绿，但用户一眼就看出不对**

第八轮把「井壁」做成了贴着腔壁 `bore(y)` 的一层 **70~90 格厚的空心壳**
（径向双侧 `smooth01`）。第九轮结束时 `_judge7.py` **55 通过 / 0 失败**，
[W] 泛洪判据七层全绿，剖面图看着也"对"。

元看完图一句话：「**洞和每层不相通**」。

### 16.2 病根：`[W]` 只在**竖向**切片上验连通

看 `[W]` 的实现就知道问题在哪：它在 **z=8 的纵剖面**上从井轴泛洪。
竖剖面上，这层壳是腔壁**左右两侧各一道竖条** —— 泛洪往左右走？左边撞墙、
右边撞墙，但**上下**是通的（`bore` 曲线连续、岩板只在 `bore` 之外生）。
判据只要 `|x| ≥ 0.75·bore`，而泛洪能沿 y 一路走到很浅/很深的宽层再去够那个
半径 —— **轻松过线**。

横剖面上是另一回事：那层壳是一圈**完整的圆环**，井腔在环内、噪声挖出的
空间在环外，**两者被圆管硬隔开**。

⇒ **横向连通从未被任何判据验过**，所以这个形态存在了整整两轮。

### 16.3 ⭐ 教训一：判据要按**方向**拆，"连通"不是一维属性

「连通」在 3D 里至少有三种独立含义，验一种**不能**推出另一种：

| 方向 | 含义 | 典型病灶 |
|---|---|---|
| 竖向 | 从地表能一路掉到世界底 | 层间岩板把井口封死 |
| **横向** | **从井里能走进每层的大空间** | **空心壳 / 环墙** |
| 斜向 | 层与层之间的台地/闸门是否可通行 | 闸门比腔还宽 ⇒ 直通 |

⭐ **横向判据（`_judge_conn.py`，[X] 组）怎么写** —— 简单且锐：
1. 取每层**中点**的 y，做一张**水平切片**（网格 step 8）；
2. 从井轴 `(0,0)` 做 4 邻域泛洪；
3. 验三条：泛洪面积 ≥ 腔内空气的 80%、泛洪最远半径 ≥ `bore(y)×0.9`、
   泛洪起点必须是空气。
   - 环墙存在时：泛洪走不出井腔 ⇒ 面积骤降、半径卡在 `bore−壳宽` ⇒ 立刻红。
   - 实测（岩体模型）：七层达半径 **104%~116%**，干净通过。

⚠️ 防静默判绿：**腔内空气格数 == 0 时必须 `SystemExit`**。
扫描范围写死、而腔半径长大了的时候，切片可能整张落在腔外 ——
泛洪起点是石头、`ratio = 0`，如果只判"ratio ≥ 阈值"就会一路绿着出门。

### 16.4 ⭐⭐ 教训二：墙的形态只有两种，选错了判据全白做

| | **壳（hollow shell）** | **岩体（solid rock）** |
|---|---|---|
| 定义 | 贴 `bore` 的一层定厚空心环 | `dist − R(y) > 0` 全是实心，**没有外沿** |
| 横剖面 | 一圈完整圆环 | 一个洞 + 连片岩石 |
| 洞与层空间 | **被隔开** | 天然是同一个空间 |
| 顶界 | 有限厚度，自己收边 | 必须跟**逐列地表**走，否则远海竖石墙 |
| 墙外 | 洞穴噪声挖出的空间（"另一个世界"） | 岩体里的**隐藏洞穴**（要离壁设 `GUARD_BAND`，否则壁面被掏碎） |

⭐⭐⭐ **《来自深渊》原作 mod（`Made-In-Abyss`）用的是岩体** ——
`HopperAbyssHole` / `GeneralAbyssHole` 的公式短得惊人：

```java
// getHeightValue:  f = dist*8 − (abyssRadius*2*mul + radius) / 2 * clamp(1 + y/64, 1, 2)
// f < 0 → 空气；f > 0 → 实心岩体。  没有"井壁环"这个概念。
```

它的"层"只是**按深度换生物群系与材质**，几何上**从头到尾是一个洞**。
照这个改完，横向连通立刻全绿。

### 16.5 配套：单侧渐入 + 护壁带（岩体模型的三个必填参数）

```java
double inner = shaftInner(...) + BIG_WALL_WOBBLE * fbm2(x, z, seed + 4601, 2, 1.0/700.0);
double rock  = ROCK_STRENGTH * smooth01((dist - inner) / WALL_SOFT);   // ⭐ 单侧，无外沿
rock *= smooth01(((surfaceTop - surfaceThick + 6.0) - y) / 30.0);      // ⭐ 顶界跟逐列地表
double guard = smooth01((dist - inner - GUARD_BAND) / GUARD_SOFT);
rock -= 4.0 * guard * smooth01((cave - DIG_TH) / 0.6);                 // 隐藏洞穴
```

- `BIG_WALL_WOBBLE = 110`（波长 700）：没有它，2100 格的洞在俯视图上是个**正圆**，
  太规整。⚠️ 幅度必须 < 墙判据的扫描窗（`bore−150` 起），否则判据找不到壁、假红。
- `GUARD_BAND = 60`：离洞壁 60 格以内**不挖**隐藏洞穴 —— 壁面才完整、不出碎块。
- `DIG_TH = 0.35`：挖掘掩码对**已加 bias 的 cave**，等效 `P(原始噪声 > 1.10) ≈ 13.6%`。

### 16.6 ⚠️ 模型一换，**所有引用旧几何的调用点都要复查**（本轮撞到三处）

改完 `rimAt → rockAt` 编译通过，但语义上还有三处"隐藏引用"：

| 位置 | 旧语义 | 岩体模型下 | 修法 |
|---|---|---|---|
| 亡骸之海铺水 | `dist >= rimOuter(5)`（墙外沿之外） | **没有"墙外沿"了**，那儿全是实心 ⇒ 挖不出放水的腔 | `dist >= bore(floorTop) + SEA_GUARD_R(150)` |
| 标志地形守卫 | `dist < rimInner(i+1)` 就跳过（井腔里不放） | **反向失效**：层空间**就是**井腔，跳过等于全不放 | 删掉守卫，改用"这一列有没有地板"判 |
| `shape()` 调用序 | 先 slab/cave 再 rim | 挖掘掩码要用**压制后的 cave** | `cave = caveAt(...)` 提前算，传进 `rockAt` |

共性：**改了"墙是什么"，凡是提到墙的地方都要重新问一遍它的语义**。
编译器只查得签名，查不出语义。

### 16.7 ⭐⭐ forceload 1152 个区块会 OOM —— 改**分批加载 + 批后卸载**

第十轮第一次生成世界，跑一半炸了：

```
java.lang.OutOfMemoryError: Java heap space
  at ...BlockLightSectionStorage$BlockDataLayerStorageMap.copy
  at ...LevelLightEngine.runLightUpdates
```

⚠️ **不报任何 mod 相关错误** —— 日志里只有一段光照线程的堆栈，
很容易误判成"地形生成器写崩了"。真实原因：

- 这个世界 y ∈ [−2032, 2031] ⇒ 每个区块 **254 个 section**（原版主世界的十几倍）；
- forceload 会把采样区区块**全部常驻内存**（方块数据 + 预算光照，一个区块好几 MB）；
- 1152 个 × 254 section ⇒ `-Xmx8G` 也撑不住（机器只有 16 GB，加堆没意义）。

**修法：别让它们同时在内存里。**

```python
for label, rects in groups:           # 一批 = 若干 forceload 矩形
    for (a, b, c, d) in rects:
        cmd(f'forceload add {a} {b} {c} {d}')
    wait_stable(label)                # 等这一批 Status=full 的区块数连续 3 轮不动
    cmd('save-all flush')             # ⭐ 落盘
    cmd('forceload remove all')       # ⭐ 卸载，内存还回去
```

⭐ 关键认知：**判据是离线读 `.mca` 的**，区块一旦写进 region 文件，
卸不卸载都不影响判据 ⇒ 分批完全无损。

#### ⚠️⚠️⚠️ 更隐蔽的一种 OOM：**外部脚本抢内存，把服务端 JVM 挤死**（第十五轮）

第十五轮生成跑到 39/84 个 region 时**整服务端崩掉**。日志里**没有任何 mod/地形报错**：

```
# There is insufficient memory for the Java Runtime Environment to continue.
# Native memory allocation (mmap) failed to map 4194304 bytes. Error detail: G1 virtual space
```

⚠️ 注意这不是 `java.lang.OutOfMemoryError: Java heap space`（堆满），
而是 **`mmap` 失败 / G1 virtual space** —— **进程连虚拟地址都申请不到**，
说明是**整机物理内存**被吃光，不是堆参数问题。

根因：我一边跑生成，一边还挂着**三个扫 `.mca` 的 Python 判据脚本**
（每个 1~3 GB，合计 **5.9 GB**），加上 `_slice_goblet.py` 的 OpenBLAS 也报
`Memory allocation still failed after 10 retries`。整机 15.7 GB，可用只剩 **0.1 GB**。

**教训（必须写进流程）**：
> **生成世界期间，不要同时跑任何内存密集脚本。**
> 扫 `.mca` 的判据脚本（一次要读几百 MB~GB 的区块数据 + numpy 数组）
> **必须排在生成完全结束之后**再跑。

诊断口径：`Get-Process python,java | 看 WorkingSet64` + `Win32_OperatingSystem.FreePhysicalMemory`。
本次实测可用内存 0.1 GB ⇒ 先 `Stop-Process` 清掉 Python，回到 10 GB，再重跑就好了。

⭐ 判断崩溃性质的关键词对照：
| 日志关键词 | 性质 | 修法 |
|---|---|---|
| `java.lang.OutOfMemoryError: Java heap space` | **堆**满 | 加大 `-Xmx` / 少 forceload |
| `Native memory allocation (mmap) failed` / `G1 virtual space` | **整机物理内存**被吃光 | 关掉抢内存的旁路进程 |

### 16.9 ⚠️⚠️ 判据口径跟着模型漂：**同一批 5 条假红，全是口径陈旧**（第十轮实测）

岩体模型跑完世界生成，`_judge7.py` 报 **50 通过 / 5 失败**。逐条查，
**五条没有一条是地形错** —— 全是判据还停在旧模型上：

| 判据 | 旧口径（旧模型的隐含假设） | 岩体模型下为什么失效 | 新口径 |
|---|---|---|---|
| [S] 墙内沿偏差 | 上界 `+70`（墙贴 bore，只会往下漂） | 洞壁叠了 `BIG_WALL_WOBBLE=110` 的大尺度起伏，内沿**本来就该往正方向偏**（实测 +84/+83） | 上界放宽到 `+150` |
| [L] 亡骸之海 | 采样在 `r5+120/+300/+500`（墙**外**的空腔） | 岩体模型里墙外**全是实心岩**，那儿不该有水 ⇒ 0/24 | 采样改成 `bore+150+extra`（岩体里的隐藏洞穴带） |
| [P] 颠倒森林 | `abs(x) < r+60` 跳过"井腔" | 岩体模型里**层空间就是井腔**，跳掉 2600 列后分母全是岩石 ⇒ 必然 0 命中 | 删掉跳过 |
| [P] 不归之都 | 同上 | 同上 | 删掉跳过 |

⭐ **共性判据**（值得背下来）：

> **判据里的每一个几何量，都要问一句"它在旧模型里是常数/在腔内、在新模型里是曲线/在腔外吗"。**
> 常数卡曲线 = 把模型自己的形状读成缺陷；
> "跳过腔内"类守卫 = 模型一换就变成"跳过了全部有效样本"。

⚠️ 更阴的是这四条**方向不一**：

- [L]/[P] 是**采样位置错**（量到了另一个地方）⇒ 假红；
- 而如果反过来把阈值放宽去"让它绿"，就掩盖了真问题。

⇒ 所以"改阈值"之前必须先确认**这个数在物理上应该是什么**，
   而不是"调到能过"。上面每一条的修法都附了"为什么这个新口径是对的"。

### 16.10 ⭐⭐⭐ 几何类改动：先**离线纯函数自检**，再花 52 分钟生成世界（第十二轮）

> 📌 **方法论总纲见 [`验证判据设计.md`](./验证判据设计.md)** —— 那一份讲的是"判据该怎么设计"，
> 本节只是它在**世界生成**这一场景下的落地实例。改了生成器之后**先读那一份**。

**第十二轮又踩了同一个模式的第三次**：改完池子几何 → 生成 52 分钟 → 看结果
→ 发现还在漏 → 再改。三轮共浪费约 2.5 小时。

而池子/盘子这类**标志地形**的几何是**纯函数**：只依赖
`(半径, 沿宽, 盘心地面, 层界, 天花板)`，跟噪声分布无关、跟区块无关。
⇒ 完全可以离线用一个 `dict[(x,y,z)] = 块名` 的模拟跑一遍，
**在 3 秒内**验出"水会不会漏"，不必等世界生成。

第十一轮 `_proto_cup.py` 实测：一次就抓出**两个**真 bug ——
`[C3]` 水悬空（垫底起点写错）、`[C1]` 沿脚横向漏（沿从 base 起而非 base−1），
**在生成世界之前**就修掉了。

**离线自检该验什么**（照 Java 逐行抄，成对覆盖）：
```
[C0] 池水只有 1 层厚          ← 阶梯水的特征就是"水有十几层"
[C1] 每个水格四个水平邻居都是水或实体（没有"水挨着空气"= 漏点）
[C2] 正上方是盖板   [C3] 正下方是实体
[C4] ⭐ 用**逐列起伏的地面**跑，仍全绿   ← 专抓"池面逐列漂"的阶梯水
[C5] 天花板过低时整列填实、不建池（不能留半截）
[C6] ⭐⭐ 盘子**整个坐在洞腔之外**：cdist − rr − 沿宽 − 裙宽 ≥ bore + 噪声余量
[C7] ⭐⭐ 盘心那列必须有地板；哨兵 ⇒ 不建
[C8] ⭐⭐ **分区块模拟**：造"盘心跨在洞腔边界上"的坏样本
     ⇒ 必须复现出"水有 N 格、敞口 M 处"；再造"整盘在外"的好样本 ⇒ 必须全封死
[C9] ⭐⭐⭐ **洞腔噪声吃掉池内列**（第十五轮）：真实洞腔外沿 > bore（外扩几十格）。
     造"盘心在基准圆外、但池内一角伸进真实洞腔"的坏样本 ⇒ 必须复现漏
     （实测 512 格水 / 57 处漏）；好样本 ⇒ 必须 0 漏
[C10] ⭐⭐⭐ **判据的噪声余量**：同一位形，旧口径（无余量）必须**放行**、
     新口径（有余量）必须**拦住** —— 这才证明余量真在起作用
```

⚠️ **[C8]/[C9] 测漏必须做泛洪，不能只看水格的直接邻居**：盘沿有 6 格宽，
水离缺口还有 6 格 —— 只查 1 格邻居永远报"0 处"（= 等于没验）。
必须**逐格推进**（水横进一格空气 → 再从那里继续推进），穿出盘子覆盖范围才算漏。
第十五轮第一次写 [C9] 就踩了这个坑，坏样本报"横向可流 0 处"。

⚠️ **为什么必须加 [C4]**：前三个场景用**平地**跑全绿，但只要换成
±3 格的起伏地面就立刻爆红 —— 而真实岩檐差 200 格。
**"平地全绿"是假绿**：平地恰好让逐列地面 = 盘心地面，
把"池面逐列漂"这个 bug 完美掩盖。**成对样本必须包含"会让 bug 现形"的那一档。**

⚠️⚠️ **为什么必须加 [C8]（第十四轮的教训）**：[C6] 是判"整盘在洞腔之外"的
**判据本身**，拿理想样本（整盘在外）去验它，只能证明"好情况好"——
证明不了"坏情况会被拦"。必须**另造一个坏样本**：让 `floor_of` 在洞腔列
返回 `None`（= Java 里 `floorTop == NO_BOUND` 会被 continue 跳过），
把盘心放在洞腔边界上，**看它是不是真的复现出敞口**。
实测 [C8a] 一次复现出"1193 格水 / 67 处敞口"，与存档里那只漏水杯同形态；
[C8b] 换成整盘在外 ⇒ 全封死。**判据和"会让它报错的样本"必须成对存在。**

⚠️⚠️⚠️ **为什么必须加 [C9]（第十五轮的教训，比 [C8] 更隐蔽）**：
[C6] 的判据是 `cdist − rr − 沿宽 ≥ bore` —— 它假设**洞腔边界就是 `bore` 那条圆**。
但这个假设是错的：洞腔真实外沿还要往外走 `CAVITY_SOFT` 软化带
+ 洞穴/岩板**噪声外凸**（团块尺度 30~50 格）。实测某杯 `cdist − rr − 沿宽
= 1362.6 > bore(1322)` **判据放行**，可那一侧洞腔实际外扩到 **1373**，
把池内列（本该铺水）整片吃成 `NO_BOUND` ⇒ 水面缺一块 ⇒ 水从池内横流入洞腔 ⇒ **真漏**。

⇒ 修法两条：① 判据加 `CAVITY_MARGIN`（按"洞腔**最外**能到哪"判，实测取 56 > 51）；
② 盘沿外加 `SKIRT` 找平裙（填掉岩檐斜面造成的悬空带）。

⭐ 方法论（值得背）：
> **凡判据里出现"解析边界"（半径/圆/直线）而后面的地形是"噪声边界"，
> 就必须问：噪声把边界推出去多远？判据要按"最坏情况"留余量。**
> 而且要**统计代价**（本次砍掉 1.6% 的杯子），确认不是"为了安全把东西全砍光"。

⭐ 推广（值得背）：
> **凡是"改一个纯几何参数 → 生成半小时 → 看结果"的循环，都要先问：
> 这个几何能不能离线算？能就先离线，把循环从"半小时一轮"压到"3 秒一轮"。**
> 离线判断全绿，才上世界生成；生成完再用**存档判据 + 出图**做最终验收。
> 这和 §16.9 是一对：**改几何前用离线自检，改口径后用存档判据。**
