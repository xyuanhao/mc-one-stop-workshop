# 26.x：改雾效 + 把另一个维度的结构搬进深层 + 给「另一个维度的地盘」换刷怪表

> 来源：2026-09-23「上下四千米 / 深层地狱」实战（MC 26.1 + NeoForge 26.1.0.19-beta）。
> 三条线都实测过：雾效改完构建通过，结构搬完在存档里扫到了方块，
> 刷怪线完成了服务端冒烟（自然刷那条路径要真人进游戏才跑得起来）。

## 一、改雾效：26.1 的雾系统被重写过，别按老版本写

### 关键结论

| 你以为的 | 实际情况（26.1） |
|---|---|
| `ViewportEvent.RenderFog` 没了 | **还在**。触发点搬到了 `ClientHooks.onSetupFog`，事件照旧能收到 |
| 按 `FogRenderer` 里有没有 import 判断事件是否作废 | **不可靠** —— 26.1 的 `FogRenderer.java` 里确实没有 `ViewportEvent` 的 import，但事件照样被 fire |
| 改 fog 的「近端/远端」两个距离 | `FogData` 拆成了**五段**，改错字段等于没改 |

`FogRenderer.setupFog` 的收尾（源码实读）：

```java
net.neoforged.neoforge.client.ClientHooks.onSetupFog(chosenEnvironment, fogType, camera, partialTickTime, renderDistanceInChunks, fog);
```

### `FogData` 的五段，各自该不该动

```java
public class FogData {
    public float environmentalStart;    // 环境雾起点  ← 要改这个
    public float environmentalEnd;      // 环境雾终点  ← 要改这个
    public float renderDistanceStart;   // 视距边缘淡出 ← 别动，动了区块边缘生硬
    public float renderDistanceEnd;     // 视距边缘淡出 ← 别动
    public float skyEnd;                // 天空背景雾   ← 顺手一起收紧
    public float cloudEnd;              // 云的雾       ← 顺手一起收紧
    public Vector4f color = new Vector4f();
}
```

**只改近端远端不改 `skyEnd`，天边会透出一条没被雾盖住的亮边。**

### 模板

```java
@EventBusSubscriber(modid = MODID, value = Dist.CLIENT)   // 26.x 没有 bus 属性了，默认就是 GAME bus
public final class MyFogClient {
    @SubscribeEvent
    public static void onRenderFog(ViewportEvent.RenderFog event) {
        if (event.getType() != FogType.ATMOSPHERIC) return;   // 水/岩浆/细雪各有各的雾，别搅
        float strength = ...;                                  // 0~1，按玩家位置算
        if (strength <= 0.0F) return;

        FogData fog = event.getFogData();
        fog.environmentalStart = Mth.lerp(strength, fog.environmentalStart, targetNear);
        fog.environmentalEnd   = Mth.lerp(strength, fog.environmentalEnd,   targetFar);
        fog.skyEnd   = Math.min(fog.skyEnd,   fog.environmentalEnd);
        fog.cloudEnd = Math.min(fog.cloudEnd, fog.environmentalEnd);
        fog.color.set(r, g, b, fog.color.w);                   // Vector4f
    }
}
```

### ⭐ 雾不发光 —— 「会发光的雾」必须拆两半做

雾只是**把远处糊掉的颜色**，它不会照亮任何方块。用户说「近了照明、远了遮挡视线」时，
这两件事在 MC 里完全独立：

| 效果 | 归谁管 | 做法 |
|---|---|---|
| 远了遮挡 | 客户端 | 上面的雾效 |
| 近了照明 | **服务端** | 给玩家一段隐藏夜视：`new MobEffectInstance(MobEffects.NIGHT_VISION, dur, 0, true, false, false)` |

`ambient=true, visible=false, showIcon=false` → 不刷粒子、不占 HUD，玩家只会觉得「忽然看清了」。

**用「续期」而不是「常驻」**：给一段远长于检查间隔的短效（如 25 秒，每 1 秒续一次）。
离开区域后自然过期，**不需要写移除逻辑** —— 写移除反而危险，会把玩家自己喝的夜视药水一起干掉。
`addEffect` 对已存在的同效果走合并（取时长更长的），所以玩家的 3 分钟药水不会被 25 秒的顶掉。

### 过渡带

阈值处做硬开关，玩家穿过边界那一帧画面会硬跳。给一条 `fadeRange` 宽的过渡带，
雾的距离和颜色都按强度插值：

```java
if (y <= topY) return 1.0F;
if (fade <= 0) return 0.0F;
double t = (y - topY) / (double) fade;
return t >= 1.0 ? 0.0F : (float) (1.0 - t);
```

### 配置分家

雾效一半服务端一半客户端，配置也跟着分成 `COMMON`（照明，跟随服务器）和
`CLIENT`（雾的观感，每人各调各的）。

⚠️ `ModConfigEvent.getConfig().getSpec()` 返回的是 **`IConfigSpec` 不是 `ModConfigSpec`**
—— 想强转再比较会直接编译报错，用**引用比较**判断是哪一份配置。

## 二、把另一个维度的结构搬进改过高度的世界

### 前提认知

结构认的是**自己 json 里的 `biomes` 字段**，不是「这个维度有哪些群系」。
所以**不用先做群系切换** —— 把 `biomes` 改成目标世界的群系 tag 就行。

```json
// data/<modid>/tags/worldgen/biome/has_structure/<名字>.json
{ "values": ["#minecraft:is_overworld"] }
```

复制结构定义到**自己的命名空间**，别覆写原版 —— 覆写会连原维度一起改掉。

### ⭐⭐ 最重要的判据：用「这个世界有多深」，别用「是不是主世界」

改结构高度的 Mixin 动的全是**原版类**，原维度也在走同一份代码。
下界要塞写死的是 `y=64` —— 无脑改会把真下界的要塞一起拽到深层（下界只有 256 高，直接出界，
**一个要塞都不会剩**）。

```java
public static boolean isDeepWorld(LevelHeightAccessor h) {
    return h.getMinY() <= -1000;   // 主世界被拉深 → -2032；下界/末地 → 0，原版行为不动
}
```

这个判据比「维度是不是主世界」更准：它认的是**前置真的生效了**，
前置没加载时结构会安静退回原版行为而不是崩。

### 四个下界结构各自的 y 定法（26.1 源码实读）

| 结构 | 类型 | y 怎么定 | 能否只改数据包 |
|---|---|---|---|
| 要塞 `fortress` | `minecraft:fortress` | **两处硬编码**：`new BlockPos(x, 64, z)` 和 `builder.moveInsideHeights(random, 48, 70)` | ❌ 要 Mixin |
| 堡垒 `bastion_remnant` | `minecraft:jigsaw` | 数据包 `start_height.absolute` | ✅ |
| 下界化石 `nether_fossil` | `minecraft:nether_fossil` | 数据包 `height`，**但还有一道海平面判据** | ❌ 要 Mixin |
| 传送门废墟 `ruined_portal` | `minecraft:ruined_portal` | `findSuitableY` 里 `IN_NETHER` 分支写死 `32~100` | ❌ 要 Mixin |

**要塞只改一处等于白改**：pieces 是在 y≈64 附近拼出来的，最后靠 `moveInsideHeights` 整体平移落位。
只动起点不动落位窗口，结构会被平移回 48~70。
（`moveInsideHeights` 是**平移**不是缩放：`y0Pos = lowestAllowed + random.nextInt(heightSpan)`，
`heightSpan <= 1` 时 `y0Pos = lowestAllowed`。）

建议直接在 `findGenerationPoint` 的 HEAD 上 `@Inject(cancellable = true)` 整体重写 ——
比跟 `@ModifyArg` / `@Redirect` 的参数捕获规则较劲更直白。

**下界化石会被海平面静默挡死**：

```java
int seaLevel = context.chunkGenerator().getSeaLevel();   // 主世界 = 63
int y = this.height.sample(...);                          // 我们给的 -1100
while (y > seaLevel) { ...往下找地面... }                  // -1100 > 63 不成立，一次都不跑
if (y <= seaLevel) return Optional.empty();               // 直接放弃，且日志什么都不报
```

→ Mixin 里把判据从「海平面」换成「世界底 + 16」。

### 结构 y 是三份静态真相

1. Java 里的常量（Mixin 用）
2. `structure/*.json` 的 `start_height`
3. `structure/*.json` 的 `height`

**数据包是静态 JSON，读不到配置** —— 结构高度没法做成运行时可配。改一处就要改三处。

### 实测会看到的「异常」：结构纵向拖得极长

搬到 1582 格高的空腔后，堡垒从 `start_height` 一路挂到 700 格以下。

**这不是 bug**：jigsaw 是**从起点向下挂**的，原版下界只有 128 格高、岩浆海在 y=31，
结构被空间卡住了看不出来。空间放大后就一路挂到底。

**判断形状的姿势**：别只看汇总的 y 段分布（会把多个结构混在一起）。
要看**每个 chunk 各自的 y 范围**：
- 上界一致、下界各异 → 从起点向下**悬挂**
- 下界一致、上界各异 → 从地面向上**堆叠**

要调手感就给 jigsaw 加垂直限制，或把 `start_height` 往上提。

## 三、验证链（四层，缺一层就可能漏）

| 层 | 怎么做 | 说明 |
|---|---|---|
| ① 服务端能起来 | `gradlew runServer`，grep `Done (` | 数据包解析失败会直接刷 ERROR |

## 四、给一片地形换刷怪表 —— **不用切生物群系**

> 场景：把下界搬进了主世界深处，方块已经是地狱岩了，但刷出来的还是骷髅和苦力怕。

### ⚠️ 先别写 `spawn_overrides`：对「复制出来的结构」它是死代码

`NaturalSpawner#mobsAt` 那条分支是这样的（javap 实读）：

```java
if (isInNetherFortressBounds(pos, level, mobCategory, structureManager)) {
    Structure s = structureManager.registryAccess().lookupOrThrow(Registries.STRUCTURE)
        .getValueOrThrow(BuiltinStructures.FORTRESS);          // ← 硬编码原版 fortress
    var monsterSpawns = s.spawnOverrides().get(MobCategory.MONSTER);
    ...
}
```

而 `isInNetherFortressBounds` 三连：

```java
if (category != MobCategory.MONSTER) return false;
if (!level.getBlockState(pos.below()).is(Blocks.NETHER_BRICKS)) return false;
Structure s = registry.getValue(BuiltinStructures.FORTRESS);   // ← 硬编码
return s != null && structureManager.getStructureAt(pos, s).isValid();
```

**第 ③ 条查的是注册表 key**。你把自己的结构定义复制成 `xx:deep_fortress`（哪怕 `type` 还是
`minecraft:fortress`），也永远敌不过这行 —— 因为 key 不同。写在自己那份 json 里的
`spawn_overrides` **一个字都不会生效**，且**不报错、不告警**。

### 正确路径：NeoForge 的 `LevelEvent.PotentialSpawns`

`mobsAt` 的**两条 return 分支都包了** `EventHooks.getPotentialSpawns`，它会 fire
`LevelEvent.PotentialSpawns`，而事件内部持有的就是候选刷怪表本身 —— **就地换掉 = 换掉这个位置的群系**。

```java
public static void onPotentialSpawns(LevelEvent.PotentialSpawns event) {
    if (!(event.getLevel() instanceof ServerLevel level)) return;
    if (level.dimension() != Level.OVERWORLD) return;
    if (!isOurZone(event.getPos().getY())) return;              // 自己的深度 / 区域判据

    List<Weighted<SpawnerData>> replacement = pick(level, event.getPos(), event.getMobCategory());
    if (replacement == null) return;                            // 这个分类不管

    // ⚠️ 见下，不能直接 mutate
    new ArrayList<>(event.getSpawnerDataList()).forEach(event::removeSpawnerData);
    replacement.forEach(event::addSpawnerData);
}
```

#### 🔴 坑：列表不可变，`getSpawnerDataList().clear()` 会崩

`WeightedList` 在构造时就 `this.items = List.copyOf(...)`，`unwrap()` 交出来的是**不可变** list。
事件类有个**私有** `makeList()`，只有 `addSpawnerData` / `removeSpawnerData` 会触发它，
之后 `view` 才换成 Builder 的可变 list。所以：

| 写法 | 结果 |
|---|---|
| `event.getSpawnerDataList().clear()` | ❌ `UnsupportedOperationException` |
| 先 `new ArrayList<>(getSpawnerDataList())` 快照 → 逐个 `removeSpawnerData` → 逐个 `addSpawnerData` | ✅ |

#### 🔴 坑：26.1 的 `SpawnerData` 是三字段 record，**weight 不在它身上**

```java
public record SpawnerData(EntityType<?> type, int minCount, int maxCount)
public record Weighted<T>(T value, int weight)
```

按老版本的 `new SpawnerData(type, weight, min, max)` 写会编译不过。正确写法：

```java
private static Weighted<SpawnerData> of(EntityType<?> type, int weight, int min, int max) {
    return new Weighted<>(new SpawnerData(type, min, max), weight);
}
```

### 刷新表换了还不够：还要给「原版判据说不」的生物放行

`SpawnPlacements` 的谓词是按「这种生物原本该待在什么样的地方」写的。深层地下天然不满足其中几条
（下界生物常被要求对环境有要求），**表里有、某地也选中了，仍然刷不出来**。

监听 `MobSpawnEvent.SpawnPlacementCheck`，对白名单里的类型补票：

```java
if (event.getDefaultResult()) return;                                  // ① 原版判过了就别管
if (event.getSpawnType() != EntitySpawnReason.NATURAL) return;         // ② 刷怪蛋 / summon 不受影响
if (!OURS.contains(event.getEntityType())) return;                     // ③ 只放我们自己表里的
if (event.getEntityType() == EntityType.GHAST) return;                 // ④ 恶魂例外（见下）
event.setResult(MobSpawnEvent.SpawnPlacementCheck.Result.SUCCEED);
```

④ 的原因：恶魂的谓词里除了亮度还有「放得下 4x4x4」的**空间检查**，那是物理合法性，
放行了会把它塞进石头缝。它在大空腔里本来就能过。

放行后 `Mob#checkSpawnObstruction` 仍然生效 —— 实体不会落到方块里。

### 几条踩出来的经验

- **判据要用「深度 / 方块」，不要用「群系」** —— 这类需求多半就是因为群系没法切才来的。
- **分界线要和方块替换用同一条**，否则会出现「方块已经是地狱、却还在刷僵尸」的错层。
- **平衡要不要动玩家可以抄原版**：`fortress.json` 的 `spawn_overrides`（blaze 10 / wither_skeleton 8 /
  zombified_piglin 5 / magma_cube 3 / skeleton 2）照抄不失手；开阔处的表要自己按空间重排
  （岩浆怪原版只给 2，在开阔的下界岩层够用，在稀疏的深层体表就几乎见不到了）。
- **僵尸猪灵在主世界不会因为所处维度受损** —— 26.1 的 `ZombifiedPiglin` 源码里没有任何
  非 piglinSafe 维度掉血的逻辑（那是基岩版的机制），`DimensionType` 里也没有 `piglinSafe`。
  但 **Hoglin 有**（会变 zoglin）、**Blaze 淋雨会受伤**（地下 `canSeeSky=false`，没事）——
  选生物的时候这两个要单独考虑。

### 验证到哪一层

自然刷只在**有玩家**在附近时才跑这条路径：服务端开着但没人时，
这段代码**一次都不会被调用**（包括 `spawnMobsForChunkGeneration`，它走的是
`biome.getMobSettings().getMobs(CREATURE)`，不过 `mobsAt`）。所以：

| 能验 | 怎么验 |
|---|---|
| 编译、模组加载、配置落地 | `gradlew runServer` + grep 模组日志/错误 |
| **真的换成了目标刷怪表** | ⏳ **只能进游戏**。在 handler 里加一行「第一次接管时打印日志」（`AtomicBoolean` 只打一次），作为游戏里的确认标志 |

## 五、⚠️ 放开世界高度的隐藏副作用：自然刷怪被摊薄

`NaturalSpawner#getRandomPosWithin`（javap 实读）：

```java
int x    = chunkPos.getMinBlockX() + random.nextInt(16);
int z    = chunkPos.getMinBlockZ() + random.nextInt(16);
int maxY = chunk.getHeight(Heightmap.Types.WORLD_SURFACE, x, z) + 1;
int y    = Mth.randomBetweenInclusive(random, level.getMinY(), maxY);   // ← 整个纵向区间均匀随机
return new BlockPos(x, y, z);
```

**y 是在 `[世界底, 该柱地表]` 整个区间上均匀取的。** 把世界从 [-64, 320] 拉到 [-2032, 2031] 之后，
浅层 / 地表能分到的刷怪点占比从百分之几十掉到约 7% —— **这是整个世界的连锁副作用，
跟「地狱段」无关，整张地图的上层都会变稀。**

要处理的话从这几个方向挑一个（**都会改变原版行为，务必先跟用户确认**）：
- Mixin 改 `getRandomPosWithin`，把 y 的取值改成「偏向地表」的分布（保留一定概率探到深层）；
- 或者保持原样，在深层用一个独立的刷新器补。
