## 1. 格式规范（硬事实）

### 1.1 尺寸与格式

| 项 | 值 |
|---|---|
| Java 接受 | **64×64**（1.8+ 现代）、**64×32**（1.8 前旧版） |
| Bedrock 接受 | **128×128**（仅此一种） |
| 格式 | **必须真 PNG**（RGB 或 RGBA）。JPEG/GIF 一律拒收 |
| 透明 | 只在**外层**有效；**基础层一律按不透明绘制** |

> ⚠️ **改名不算转格式**。把 `a.jpg` 改成 `a.png`，文件头仍是 JPEG，上传必被拒，
> 或者透明区被压成黑块。这是皮肤上传失败**最常见**的原因 —— `皮肤校验.py`
> 第一项就是按文件头（`\x89PNG\r\n\x1a\n`）查这个。

> ⚠️ **Java 与 Bedrock 是两个格式，不是分辨率差异**。Java 皮不会"放大"成 Bedrock 皮，
> Bedrock 皮丢给 Java 也不会缩一半 —— 是**不同尺寸的不同 UV 布局**，互相不认。
> 一份皮要两边用，得**分别做**。

### 1.2 部件尺寸

| 部件 | 宽×高×深 | 备注 |
|---|---|---|
| 头 | 8×8×8 | |
| 躯干 | 8×12×4 | |
| 手臂（classic） | 4×12×4 | 正面/背面 4 格宽 |
| 手臂（slim / Alex） | 3×12×4 | 只读前 3 列，**第 4 列不采样** |
| 腿 | 4×12×4 | |

### 1.3 完整 UV 表（64×64）

**基础层**（锚点 = 该部件 `front` 面的左上角）：

| 部件 | front 锚点 | 展开图规律 |
|---|---|---|
| 头 | (8, 8) | 行1：top(8,8×8) bottom；行2：right/front/left/back |
| 躯干 | (20, 20) | 同上 |
| 右臂 | (44, 20) | 同上（臂的面 4×4） |
| 右腿 | (4, 20) | 同上 |
| 左臂 | (36, 52) | 同上 |
| 左腿 | (20, 52) | 同上 |

每个部件的六面由锚点**推算**（不要手抄第二份表）：

```
front  = (ax, ay, w, h)
right  = (ax - d, ay, d, h)         ← front 左边紧邻 right
left   = (ax + w, ay, d, h)
back   = (ax + w + d, ay, w, h)
top    = (ax, ay - d, w, d)         ← top 在 front 正上方
bottom = (ax + w, ay - d, w, d)
```

**外层（第二层）** —— ⚠️ **不是"一律向下 16"**：

| 部件 | 外层位置 | 偏移 |
|---|---|---|
| 头（帽子层） | (40, 8) | **右移 32** |
| 躯干（夹克层） | (20, 36) | 下移 16 |
| 右臂（袖子） | (44, 36) | 下移 16 |
| 右腿（裤子） | (4, 36) | 下移 16 |
| 左臂（袖子） | (52, 52) | **右移 16** |
| 左腿（裤子） | (4, 52) | **左移 16** |

> 🔴 六个外层里只有 3 个在"正下方 16"。左臂往**右**、左腿往**左**、帽子往**右 32**。
> 当成"都向下 16"会**静默画到别的部件上**，而且不报任何错 —— 你在左臂袖子上画的
> 东西会出现在别人（左腿/躯干）身上。`皮肤规范.py` 里 `OVERLAY_OFFSET` 显式存了
> 这四条方向，`build_overlay_faces()` 由规则推算第二张表，就是为了掐死这种漂移。

### 1.4 classic / slim 判定（唯一规则）

```
sample  x 46–47, y 20–31     ← 2 宽 × 12 高 = 24 像素
count   窗口内 alpha > 0 的像素
slim    if count < 6          （即 ≥6 判 classic）
```

三条容易搞错的：

1. **窗口跨在"前/后/左/右"四张面的列边界上**。右臂 `front` 从 x=44 起、每面 4 列，
   所以 44–47 是 front、48–51 是 left…… 窗口 x=46–47 **不是"某面的第 4 列"**，
   就是右臂矩形里那一条竖直窄带。自己按"每面第 4 列"重算会算成 **96 个像素**（我踩过）。
2. **阈值是 6 不是 1**。只描了几笔边的 slim 皮不该被误判成 classic；反过来，
   一张 classic 皮如果第 4 列只轻轻用了几笔（<6 格），会被**悄悄判成 slim**、白掉一个臂宽。
3. **PNG 里不存模型**。上传时由玩家自己选 Classic/Slim；服务端那边则是从
   profile 的 `textures` 属性 base64 里的 metadata 读（那是账号侧记录的，不是文件里的）。

### 1.5 各版本差异

| 版本 | 头像 | 半透明外层 | 备注 |
|---|---|---|---|
| ≤1.7 | 64×32 | 无 | 左右镜像、无 slim |
| 1.8+ | 64×64 | 全透明或全不透明 | 引入双层 + slim |
| 1.9+ | 同上 | **允许半透明** | Java 才支持；Bedrock 会丢掉 alpha≤25 的像素 |

## 2. 生成皮肤（`皮肤生成.py`）

### 2.1 为什么是"程序化"而不是"AI 生图"

皮肤只有 64×64 = 4096 个像素，且 **UV 是硬约束**：脸必须落在 `head/front` 那 64 格里，
衣服必须落在 `body` 区域。AI 生图给不出"像素精确落在指定矩形内"的结果，
只能当灵感参考。程序化逐像素画的三个好处：**可控（参数化）、可复现（固定 seed）、可自检**。

### 2.2 用法

```bash
# 全默认
python 皮肤生成.py -o skin.png

# 指定一切
python 皮肤生成.py --model slim --skin-tone "#F2D5B8" --hair-color "#2B2B38" \
    --hair long --eyes purple --shirt "#3A6EA5" --pants "#2C2C40" \
    --accessories glasses,scarf -o out/me.png

# 用内置预设
python 皮肤生成.py --preset 少女 -o out/girl.png

# 看所有可选值
python 皮肤生成.py --list

# 顺手出预览图
python 皮肤生成.py -o skin.png --preview preview.png
```

| 参数 | 说明 |
|---|---|
| `--model` | `classic`（默认）/ `slim` |
| `--preset` | 经典 / 少女 / 工装 / 法师 / 机械师 / 黑长直 |
| `--hair` | none / short / bob / long / ponytail / spiky / bald |
| `--eyes` | 8 个具名色（black/brown/blue/green/purple/red/amber/gray）或 `#RRGGBB` |
| `--accessories` | glasses / hat / earrings / scarf / jacket / cape / belt（逗号分隔） |
| `--seed` | 噪点种子，同种子结果完全可复现 |

### 2.3 生成器的硬保证（这几条是"能穿"的底线）

1. **尺寸严格 64×64**
2. **基础层六个部件的每个面都填满不透明** —— 收尾有一步 `_enforce_base_opaque()`
   兜底：任何还透明的基础层像素用邻域色补上。游戏把基础层按不透明画，
   留透明会渲染成**黑块**（新手最常翻的车）
3. **判定窗口按所选模型强制对齐** —— 选 slim 就清空窗口、选 classic 就填满，
   生成后立刻用 `detect_model()` 复验并在退出码里体现（不一致返回 1）
4. **外层默认全透明**，只有显式开启的配件才画
5. **脚底 / 头顶 / 手端这些"跳起来才看见"的面也画了**（不画的话跳跃时露馅）

### 2.4 绘制顺序（改代码时要注意）

```
head → body → arms → legs → hair(外层) → 配件(外层)
```

头发在配件**之前**画 → 围巾/外套会压住头发（现实里也是这样）。
**长发垂肩画在 `body` 的 overlay 上**，不是画在"头 overlay 下方"：

> 🔴 头 overlay 只有 8×8。往它下方补"长发的延续"，画到的是
> **body base 的 top/bottom 区**（那是躯干自己的贴图）—— 实测盖掉躯干贴图且不报错。
> 游戏里"长发垂肩"本来就是靠 body overlay 上部实现的，照做即可。

## 3. 换色（`皮肤换色.py`）

跟 `纹理变色.py` 的分工：那个按**整张图**亮度梯度换色，适合物品贴图；
皮肤换色必须**按部位**（头发不能跟着衣服一起变），所以单独一个工具。

**部位判定靠 UV 区域，不靠"颜色相近"** —— 所以不会把脸红和红衣服混在一起。

```bash
python 皮肤换色.py --list
python 皮肤换色.py base.png --part shirt --color "#B03030" -o out.png
python 皮肤换色.py base.png --part hair --colors "#E8C84A,#7A4A9E" --names 金,紫 -o out/
python 皮肤换色.py base.png --preset 烈焰 -o out.png
```

| 部位 | 覆盖 |
|---|---|
| `skin` | 六部件基础层（脸/手/腿露出的皮肤） |
| `hair` / `hat` | 头的外层（⚠️ 两者**同一块区域** —— 分不出哪像素是头发哪像素是帽子） |
| `shirt` | 躯干基础层 |
| `sleeve` | 双臂基础层 |
| `pants` / `shoes` | 双腿基础层（⚠️ 两者同一区域） |
| `jacket` | 躯干 + 双臂的外层 |
| `overlay` | 全部外层 |

模式：`ramp`（亮度梯度，对比最强）/ `hue`（只转色相，保留原打光）/ `tint`（乘法叠加，最轻）。

> ⚠️ **已知局限**：头发和帽子、裤子和鞋在 UV 上是**同一块矩形**，无法只换其中之一。
> 这是格式决定的（游戏也不分，都是"head overlay"/"leg base"）。
> 要分开只能靠生成器重新画，不能靠换色。

## 4. 预览（`皮肤预览.py`）

```bash
python 皮肤预览.py skin.png -o preview.png --scale 6
python 皮肤预览.py skin.png -o atlas.png --atlas-only
python 皮肤预览.py --selftest
```

出两张图：左边**六面展开**（框选标注每个 UV 区域），右边**人物三视图**（正/侧/背）。

> 🔴 **别做等距/透视渲染**。第一版用等距投影 + 仿射贴图，公式把"高度"和"深度"
> 混进同一项，立方体退化成一条线 —— 人形只画出 **9 个像素**（画布 75144 像素）。
> 正交三视图用矩形拼接就能保证正确，且对"配色对不对、配件贴在哪、比例顺不顺眼"
> 这些**验收目的**表达力更强。
> **判据**：预览器现在有 `--selftest`，会断言"人形覆盖率 > 10%"——第一版那种空转
> 会被直接拦下。

## 5. 体检（`皮肤校验.py`）

### 5.1 判据分层

```
能打开 ⊂ 尺寸对 ⊂ 基础层铺满 ⊂ 判定窗口与所选模型一致 ⊂ 游戏里真能穿上
```

脚本查到第 4 层；第 5 层（上传后客户端是否显示）没法离线验，只能把
"该选哪个模型、去哪传"讲清楚。

### 5.2 检查项

| # | 检查 | 为什么 |
|---|---|---|
| ① | 文件头是真 PNG | 改名 JPEG 是最常见的上传失败原因 |
| ② | 尺寸 64×64 或 64×32 | 其他尺寸一律不收 |
| ③ | **基础层每个面铺满不透明** | 留透明 → 游戏渲染成黑块 |
| ④ | **判定窗口与声明模型一致** | 不一致 → 上传后掉一个臂宽 |
| ⑤ | 外层半透明像素计数 | Java 允许、Bedrock 丢 alpha≤25 → 跨版本差异 |
| ⑥ | UV 空档区残留（默认关，`--strict-info` 开） | 官方只要求"应当透明或保持原样"，**不是错误** |

> ⚠️ ③ 对 **slim 皮要豁免判定窗口那 24 格** —— slim 的第 4 列本来就不采样、本来就该空。
> 第一版没豁免，把正常的 slim 皮报成"基础层有透明缺口"。

### 5.3 旧版转换

```bash
python 皮肤校验.py legacy.png --convert -o new.png
```

64×32 → 64×64：**左臂/左腿只能由右侧镜像补全**（旧版格式里根本没存左边）。
所以**旧皮转出来必然左右对称** —— 这是格式限制，不是代码偷懒。

## 6. UV 表是唯一真相源（`皮肤规范.py`）

生成器、预览器、校验器三方共用同一张表，**不各写一份**。

> 🔴 这个 skill 反复踩的坑就是"两个真相源必然漂移"。皮肤这块的 UV 有 72 个区域
> （6 部件 × 6 面 × 2 层），手抄三份必然出错，所以从设计上就只允许一份。

`皮肤规范.py` 还内置 `selfcheck()`：断言每个面都在 64×64 内、且六面面积之和
等于 `2(wd + dh + wh)`。改表后跑 `python 皮肤规范.py` 就能立刻发现越界。

### 验证历史（别删，这是判据可信度的来源）

- **UV 表**：逐条比对官方数据 —— body base/overlay 的 12 个矩形、head overlay 的
  6 个矩形**全部精确一致**；左臂 overlay front 推算得 (52,52)、左腿得 (4,52)，
  与官方给的 `(52,52)` / `(4,52)` **完全吻合**（这是推导链对的证明，不是巧合）。
- **判定规则**：`皮肤规范_自检.py` 做**双向验证** —— 4 个样本 + 1 个旧版样本，
  含**阈值两侧各一像素**（窗口填 5 个判 slim、填 6 个判 classic）。
  没做过坏样本注入的检查不算数。

### 踩过的坑（第一版写错的地方）

| 症状 | 根因 | 修法 |
|---|---|---|
| `right_arm/back` 算到 (68,36) 越界 | 把"层宽/层高"当成"面区域宽高"用 | 表面矩形直接存 `(x,y,w,h)`，不再靠 `+4` 步长推 |
| 判定窗口算出 96 个像素（实际 24） | 以为窗口是"每面的第 4 列" | 窗口是**跨面边界的固定窄带** x46–47 |
| 长发画到了躯干贴图上 | 往"头 overlay 下方"补长发 | 长发画 `body` overlay 上部 |
| `hx('black')` 报"颜色格式不对" | 只判 `len==6`，5 字符落进该分支 | 显式判 3/4/6/8 与具名色 |
| 预设的瞳色没被转换 | 颜色转换写在预设合并**之前**，被预设字符串盖回 | 先合并预设，**最后**统一转色 |
| 预览人形只画出 9 像素 | 等距投影公式把高度与深度混项 | 改正交三视图，并加覆盖率断言 |
| 64×32 旧皮被报 544 个"空档像素" | 把"不在我表里的格子"全判空档 | 空档**不是错误**，降级为提示且默认关 |

## 7. 上传（做完之后怎么穿上）

| 版本 | 步骤 |
|---|---|
| **Java** | ① minecraft.net 登录 → Profile → Skins → 上传 PNG ② **选对模型 Classic/Slim** ③ 保存 ④ **完全退出并重开客户端** |
| Java（备选） | 官方启动器 → Skins 标签 → New Skin → 浏览选 PNG → 选模型 → Save & Use |
| **Bedrock**（Win/iOS/Android） | 主菜单 → 更衣室（衣架图标）→ Classic Skins → Owned → Import → 选 PNG → 选模型 |
| Bedrock 主机版 | ❌ 不支持导入自定义 PNG，只能用 Character Creator 或市场皮肤包 |

**穿上后看不到新的**：两层缓存（自己客户端的、别人客户端的）+
服务器可能还有第三层。先**完全重启客户端**，再等几分钟。
反复重传**不会**加速缓存。

**离线模式服务器**：不上传签名的话别人看不到你的皮（Java 只显示带官方签名
的皮肤）。这是服务端设置问题，不是皮肤文件问题。
