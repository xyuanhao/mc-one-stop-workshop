# 26.x 自定义升级 / 觉醒系统：等级、属性与材料

自己搭一套「升级 → 属性/效果」系统（等级 + 觉醒 + 技能 + 材料）时要处理的几类问题。
以 AttrLevel（人间之神）为实例，26.1 实测。

---

## 1. 结构：等级是唯一真相

```
等级（存数据附件 / attachment，会进存档）
  └── 推 ──→ 属性修正器（AttributeModifier，运行时挂、不进存档）
  └── 推 ──→ 效果（状态效果 / 事件回调）
```

**核心规矩：属性修正器一律由等级"推"出来，绝不各自记一份。**

好处是「改平衡数值、读档、重生、加等级」都只需要重新跑一次 `applyModifiers(player)`。

```java
public static void applyModifiers(ServerPlayer player) {
    for (UpgradeStat stat : UpgradeStat.VALUES) {
        Holder<Attribute> attribute = stat.attribute();
        if (attribute == null) continue;
        applyModifier(player, attribute, MODIFIER_IDS[stat.ordinal()],
                stat.amountFor(data.get(stat)), stat.operation());
    }
    // 觉醒 / 特殊技能里那些"有原版属性可挂"的，也在这里接上
    SpecialSkills.applyReach(player);
}
```

**`applyModifier` 要幂等**（值和方法都没变就什么都不做）—— 它会挂在登录、重生、
升级、每 N tick 的兜底上，不幂等的话属性同步会被刷爆：

```java
static void applyModifier(ServerPlayer player, Holder<Attribute> attribute, Identifier id,
                          double amount, AttributeModifier.Operation operation) {
    AttributeInstance instance = player.getAttribute(attribute);
    if (instance == null) return;
    if (amount <= 0.0D) {                      // 0 就摘掉，别留一个 0 值修正器
        if (instance.getModifier(id) != null) instance.removeModifier(id);
        return;
    }
    AttributeModifier existing = instance.getModifier(id);
    if (existing != null && existing.amount() == amount && existing.operation() == operation) return;
    instance.addOrUpdateTransientModifier(new AttributeModifier(id, amount, operation));
}
```

做成 **package-private 而不是 private**：别的类（技能实现）也要挂属性，
共用一个入口才能共享「幂等 + 0 就摘掉」两条约定。各写一份迟早有一边忘了判 0。

## 2. 🔴 枚举 ordinal 就是存档格式：新条目**只能追加在末尾**

技能/属性用 `enum`，等级存成 `int[]`（按 `ordinal()` 排列）时，
**插在中间会让老存档的所有条目串位** —— 玩家的 10 级夜视变成 10 级别的东西，
而且不报任何错。

```java
public enum SpecialSkill {
    NIGHT_VISION(1, 1, ...),
    // ...
    INVISIBILITY(1, 1, ...),   // ← 后来的新条目一律加在这里（末尾）
    REACH(5, 1, ...);          // ← 再后来的加在更后面
}
```

## 3. 🔴 「第 N 级换一种材料」：边界只能有**一个**入口

需求形如「前 4 级吃 A，第 5 级吃 B」。最容易犯的错是**差一格**：

> 「第 10 级要下界之星」= **目标等级**为 10 时要星星，
> 而玩家**当前**等级是 9（正准备升第 10 级）。

所以判断要包成一个方法，服务端扣料与客户端按钮判断**都走它**：

```java
public UpgradeMaterial materialFor(int currentLevel) {
    if (this.finalLevelMaterial != null && currentLevel + 1 >= this.maxLevel) {
        return this.finalLevelMaterial;
    }
    return this.material;
}
```

**为什么不能让调用方自己判**：客户端要算「这个按钮能不能点」，
服务端要算「扣哪种材料」。两边各写一遍 `currentLevel + 1 >= maxLevel`，
早晚有一边写成 `currentLevel >= maxLevel`（差一格），
表现是「界面说材料够、点了却没反应」或者「该要星星的那一级白送了」。

> 判据写法：**不要复刻一份逻辑**去比对（那是检查它自己），
> 而是从方法体里**把 if 条件抽出来**，用 Python 实算每个 (技能 × 当前等级) 组合：
> ```python
> cond = re.search(r"if\s*\((.*?)\)\s*\{", body, re.S).group(1)
> cond = cond.replace("this.", "").replace("&&", " and ").replace("!= null", "is not None")
> env = {"currentLevel": cur, "maxLevel": mx,
>        "finalLevelMaterial": fin, "material": mat}
> got = eval("finalLevelMaterial if (%s) else material" % cond, {"__builtins__": {}}, env)
> ```
> 把 `+ 1` 去掉，判据立刻红给你看。

## 4. 材料表是纯数据 —— 必须用脚本断言，编译不会帮你

「哪些技能吃哪种材料、几级、每级几个」是**没有类型保护**的数据。
改错了编译一样过、运行也不报错，只表现为「玩家攒够了却升不了级」。

自检脚本要做四件事：

1. **解析枚举参数**（不是抄一份表）：
   ```python
   m = re.search(r"public\s+enum\s+SpecialSkill\s*\{(.*?)\n\}", code, re.S)
   for mm in re.finditer(r"^\s{4}([A-Z][A-Z_0-9]*)\s*\(([^)]*)\)\s*[,;]?\s*$", m.group(1), re.M):
       name, args = mm.group(1), mm.group(2)
   ```
2. **断言归属表**，并且**反向检查多余项** —— 新加的技能若没进契约表，
   报「出现了契约表里没有的技能 X」，否则它的材料没人管：
   ```python
   if set(parsed) - set(EXPECTED):
       fail("出现了契约表里没有的技能 —— 新技能要同时补进 EXPECTED")
   ```
3. **实算边界**（见 §3）。
4. **扣料入口不许写死物品**：查实现类里不得出现 `stack.is(Items.XXX)`，
   必须走 `material.matches(stack)`；查客户端技能行不得出现 `Items.`，
   必须走 `skill.materialFor(level).item()`。

顺带：**描述文案也要一起校验**。「材料表改了但说明没改」是必踩的——
断言「吃 A 的技能，说明里必须提到 A」。改数据忘了改文案，玩家看到的是错的。

## 5. 「每级翻倍」的属性：用 `ADD_MULTIPLIED_BASE` 给 `2ⁿ-1`

`AttributeModifier.Operation` 三种：

| Operation | 语义 | 拿来表达 ×2ⁿ |
|---|---|---|
| `ADD_VALUE` | 直接加固定值 | ✗ 只能做线性 |
| `ADD_MULTIPLIED_BASE` | 加上 `amount × 基础值` | ✅ 给 `2ⁿ - 1` |
| `ADD_MULTIPLIED_TOTAL` | 乘**当前总值** | ⚠️ 会连别的来源一起乘 |

```java
double bonus = level <= 0 ? 0.0D : Math.pow(2.0D, level) - 1.0D;
applyModifier(player, Attributes.BLOCK_INTERACTION_RANGE, REACH_BLOCK_ID, bonus,
        AttributeModifier.Operation.ADD_MULTIPLIED_BASE);
```

**别用 `ADD_MULTIPLIED_TOTAL`**：它乘的是"当前总值"，
跟别的 mod / 附魔的属性叠在一起会**滚雪球**（每次重算基数都变大）。
`ADD_MULTIPLIED_BASE` 乘的是原版基础值，可预测。

> 判据：从算式里实算 —— 底数必须是 2、指数必须是 level、减数必须是 1。
> 只查"有没有 `Math.pow`"会被"改成线性"漏过。

## 6. 🔴 一个功能往往对应**两个**属性：别只挂一个

「交互距离」在原版是**两个独立属性**：

| 属性 | 默认 | 管什么 |
|---|---|---|
| `BLOCK_INTERACTION_RANGE` | 4.5 | 挖方块、放方块、开容器 |
| `ENTITY_INTERACTION_RANGE` | 3.0 | 攻击、喂食、与生物交互 |

只挂一个的表现非常具体：
- 只挂实体 → 「能隔空摸到怪，却挖不到方块」
- 只挂方块 → 「能隔空挖矿，却摸不到旁边的怪」

**同类要多问一句**：这个功能在原版是否被拆成了多个属性？

> 判据：两个属性名都要在实现里出现，**且逐个 `applyModifier` 调用检查**。
> ⚠️ 只查「方法体里有没有 `ADD_MULTIPLIED_BASE`」会被"两处改坏一处"漏过
> （同名多处，这个坑已踩到第三次）：
> ```python
> calls = re.findall(r"applyModifier\s*\((.*?)\)\s*;", body, re.S)
> if len(calls) != 2: fail("应有 2 次 applyModifier（方块 + 实体）")
> for call in calls:
>     if "ADD_MULTIPLIED_BASE" not in call: fail("有调用用错了 Operation")
> ```

## 7. 客户端界面：材料数量要**两种都显示**

技能页顶部原本写着「下界之星：N」。改成双材料后如果只显示星星，
玩家会对着「星星够但按钮是灰的」发懵（其实缺的是另一种）。

```java
gfx.centeredText(font, Component.translatable("attrlevel.gui.materials",
        countOf(player, Items.SCULK_CATALYST),
        countOf(player, Items.NETHER_STAR)), ...);
```

**成本文本按材料着色**（每种材料一个主题色），一眼能看出"这一行现在要哪种"，
不用去读名字。

> 删掉旧键（`gui.stars` / `gui.star_cost`）时，判据要**反向检查它不再存在** ——
> 否则新旧键并存，未来改文案时不知道该改哪个。

## 8. 🔴 材料名 / 扣料 / 界面计数：三个都是静默 bug

这一节来自一次线上反馈三连（「材料名是英文」「背包数量不实时更新」「消耗之后能力不给」）。
三条**编译全过、游戏不报错**，只在界面上表现成"看着不对"。

### 8.1 翻译键问物品自己，别硬编码

```java
// ❌ 硬编码
SCULK_CATALYST(Items.SCULK_CATALYST, "item.minecraft.sculk_catalyst", 0xFF7FD8D0);

// ✅ 问物品自己
public Component label() {
    return Component.translatable(this.item.getDescriptionId());
}
```

**为什么硬编码必错**：Minecraft 里**方块**的物品形式（`BlockItem`）
翻译键是 `block.minecraft.*`，不是 `item.minecraft.*`。
幽匿催发体、**龙蛋**都是方块 —— 实测原版语言文件里：

| 键 | 是否存在 |
|---|---|
| `item.minecraft.sculk_catalyst` | **不存在** ❌ |
| `block.minecraft.sculk_catalyst` | `Sculk Catalyst` ✅ |
| `item.minecraft.dragon_egg` | **不存在** ❌ |
| `item.minecraft.nether_star` | `Nether Star` ✅（这个是真物品，对的） |

键不存在时，`Component.translatable` 会**把这串键名原样显示**出来 ——
玩家会描述成"名字是英文"，但其实是一串 key。
**同一个枚举里两种前缀混着，手写必错一个** —— 所以让物品自己报。

### 8.2 🔴 绝不在服务端 `getString()` 拍平 Component

```java
// ❌ 在服务端求值：服务端的语言固定是 en_us，翻出来永远是英文
player.sendOverlayMessage(Component.translatable("attrlevel.msg.need_material",
        cost + " " + material.label().getString()));

// ✅ 把 Component 原样当参数传出去，让客户端用自己的语言翻
player.sendOverlayMessage(Component.translatable("attrlevel.msg.need_material",
        cost, material.label()));
```

**两层伤害**：
1. `getString()` 在**服务端**执行 —— 专用服务端/服务器只加载 `en_us`，
   玩家是中文也照样拿到英文；
2. 一旦拼成 `String`，外层的 `Component.translatable` 里那部分就**再也不会被翻译**了。

配套：语言文件的占位符个数要跟着改（`"需要一个 %s"` → `"需要 %s 个 %s"`），
**所有**调用点都要补参数 —— 同一个键常常在好几个地方用，
少改一处就是"消息里冒出个 %s"。

### 8.3 🔴 「有多少扣多少」的 API 不能当"够不够"的判据

```java
// clearOrCountMatchingItems 的语义是：把能匹配的扣掉，**返回实际扣掉的件数**。
// 它不会因为"不够"就整个放弃 —— 它会把手里的那点扣光。
private static boolean takeMaterial(ServerPlayer player, UpgradeMaterial material, int amount) {
    return player.getInventory().clearOrCountMatchingItems(
            material::matches, amount, player.inventoryMenu.getCraftSlots()) >= amount;
}
```

**病**：调用方写成
```java
if (!takeMaterial(player, material, cost)) { 提示材料不足; return false; }
```
材料不足时 → **扣光玩家手里那点材料** → 返回 false → 拒绝升级。
**材料凭空消失、能力没给** —— 正是"消耗之后能力不给"。

**修**：先查、后扣，两步分开。
```java
if (!player.isCreative() && !material.hasEnough(player, cost)) { 提示; return false; }
if (!player.isCreative()) { takeMaterial(player, material, cost); }
```

> ⚠️ 只需求 1 个时（`takeOne`）这个 API 是安全的：最多删 1 个，
> 有就删 1 返回 1、没有就返回 0 且**什么都没删**。
> **危险只在 `amount > 1` 时** —— 而"熔炉 2 个、矿物嗅探 5 个、虚化 10 个"正好都是 > 1。

### 8.4 🔴 客户端计数和服务端扣料必须同一个口径

```java
// ❌ 自己循环：漏掉合成格和鼠标手上拿着的
for (ItemStack stack : player.getInventory()) { ... }

// ✅ 和服务端扣料用同一个 API、同一套范围
//    amountToRemove = 0 就是「只数不删」，双端都安全
return player.getInventory().clearOrCountMatchingItems(
        stack -> stack.is(item), 0, player.inventoryMenu.getCraftSlots());
```

`clearOrCountMatchingItems` 的统计范围是**背包 + 合成格 + 鼠标手持**。
自己循环 `getInventory()` 只有背包 —— 玩家把材料拖在鼠标上或摆进合成格时，
**界面数字偏小、按钮变灰，而服务端其实扣得到**。玩家只会觉得"这数字怎么不对"。

> `Player.inventoryMenu` 就是 `InventoryMenu` 类型（没有字段隐藏），
> 所以这个方法可以直接收 `Player` 参数，两端共用一份。

### 8.5 这类问题怎么验：加一条探针命令

四个坑里有三个是"看不到运行时真相"造成的。加一条命令就能把它们摆到眼前：

```
/attrlevel probe_material
→ SCULK_CATALYST -> key=block.minecraft.sculk_catalyst name=Sculk Catalyst
→ NETHER_STAR    -> key=item.minecraft.nether_star        name=Nether Star
```

判据极其简单：**译名等于键名 = 没翻出来**（就在行尾标 `<未翻译!>`）。
实测一次把"键到底是什么、能不能翻出来"全验完，不用进游戏盯界面猜。

> 注意专用服务端只有 `en_us`，所以 `name=` 是英文属于**正常**——
> 它验的是"键存在且翻得出"，不是"中文对不对"。中文在客户端由客户端语言翻。

### 8.6 🔴 扣完料必须**显式**把背包推给客户端

**症状**：升级扣了材料、服务端等级也涨了，但**界面上那个数量纹丝不动**。
玩家以为材料没扣，或者觉得"界面坏了"。

**根因**：扣料走 `clearOrCountMatchingItems`，它是直接 `itemStack.shrink(n)` ——
改的是**手里那个 ItemStack 对象**，**不经过 `Container.setItem`**。
原版理论上会由 `inventoryMenu.broadcastChanges()` 每 tick 比对补发，
但**实测（同一时刻客户端 / 服务端日志对照）客户端那边就是不刷新**。
所有同步 API 读起来都是对的，纯读代码找不出来。

**修法**：扣完全量重推一份。

```java
    /** 把玩家背包全量重推给客户端。 */
    public static void resyncInventory(ServerPlayer player) {
        player.inventoryMenu.sendAllDataToRemote();
    }
```

`sendAllDataToRemote()` 会把每个槽位 `force` 一遍再整包发出去，一定生效。

**关键是收口**：把所有扣料都收进**一个入口**（`UpgradeMaterial.consume`），
在里面统一"扣完 → 重推"。散在各处（技能升级 / 觉醒 / 抬上限 / 龙蛋）的话，
迟早有一处忘了推，玩家就得再报一次 bug。

> 判据：任何**会删东西**的 `clearOrCountMatchingItems` 调用后面都必须跟一次 `resyncInventory`。
> 只数不删的那种（参数里 `, 0,`）除外。

### 8.7 怎么测「客户端界面」这类问题（自动化，不用真人操作）

界面问题全在客户端，服务端日志看不到，但也没必要请人手动点着测。

1. 加一个**临时**的 `@EventBusSubscriber(modid, value = Dist.CLIENT)` 诊断类，
   在 `ClientTickEvent.Post` 里：
   - 等进世界。**不要在 `TitleScreen` 干等** —— 直接
     `mc.createWorldOpenFlows().openWorld("<存档名>", () -> {})` 自己进去；
   - 到某个 tick 数就 `mc.setScreen(new XxxScreen())` 打开要测的界面；
   - 每 20 tick 打一行日志：界面类名 + 关键数值 + 客户端缓存值；
   - 中途发一次**真实请求**（例如升级包），再看数值有没有变 —— 这一步才是关键；
   - 收尾 `mc.schedule(mc::stop)` 自动退出，不然游戏窗口会一直挂着。
2. 服务端侧再加个临时类给玩家发材料，并同步打印**服务端**的数值。
3. `./gradlew runClient`，两端日志一对照，一眼看出是"服务端没扣"还是"扣了没同步"。
4. **测完全删**：临时类、`build.gradle` 的改动、试出来的测试存档。

**两个坑**：

- ⚠️ **别用 `--quickPlaySingleplayer`**：那条路要先过一遍 mod 加载警告页
  （`WarningScreen`），自动流程会被卡在主菜单。从 `TitleScreen` 调 `openWorld` 更可靠。
- ⚠️ `--quickPlaySingleplayer <名字>` 找的是 **`run/saves/<名字>`**，
  不是 `run/<名字>`（那是专用服务端的世界目录）。要测的话得先复制过去。

> 顺带：那个警告页本身也该修 —— 主类上挂 `@OnlyIn(Dist.CLIENT)` 是多余的
> （类已经在 client 包里了），26.1 会因为"runtime member-stripping 行为不再存在"
> 弹一条警告挡在启动路径上，**每次进游戏都要手动点一下**。

## 8.8 「一颗解锁」而不是「每颗 +N」——门槛机制要和 UI 文案对齐

**玩家反馈**：「从 40 升到 41 怎么还需要龙蛋？」

**当时的实现**：龙蛋管的是**等级上限**，每颗 +10 级（`CAP_STEP = 10`）。
所以 30 → 40 之后，40 又顶到了，界面按钮变回「突破」→ **看着就像「升 41 要龙蛋」**。

**玩家视角 vs 实现视角**：
- 实现：「用龙蛋抬 10 级上限」
- 玩家看到：「点突破 → 能升几级 → 又被拦 → 又要蛋」= **「升级要龙蛋」**

**修法**：一颗直接解锁到技术封顶，`CAP_STEP` 整个删掉。

```java
    public boolean raiseCap(UpgradeStat stat) {
        int index = stat.ordinal();
        if (this.caps[index] >= UpgradeStat.HARD_CAP) {
            return false;                        // 已经解锁了，不再吃蛋
        }
        this.caps[index] = UpgradeStat.HARD_CAP;  // ← 一次到位
        return true;
    }
```

配套要改的（漏一处就是自相矛盾）：
- **文案**：`"等级上限提升到 %s"` → `"永久解锁等级上限"`（不再承诺数字，调用点也要去掉那个参数）
- **界面显示**：`cap` 到顶时别再印 `100000`，显示 `∞`
- **提示**：`raise_hint` 里那个 `+N` 也要去掉

> **教训**：**有「门槛 / 上限 / 分档」的机制，UI 文案必须说清楚它拦的是什么。**
> 这里按钮写「突破」，玩家自然理解成「突破当前的等级限制」，于是下一次被拦时
> 就以为"升级又要材料了"。凡是分档消耗，文案里最好写明**在哪一级会拦**
> （比如"上限 40/40，突破后 +10"），否则档位越多越像 bug。

## 8.87 分页容器的容量：让「一页」有单一真源

需求形态：「亚空间背包改成前九级一级一页」。

原实现是 `PER_LEVEL = 10`（每级 +10 格，9 级 = 90 格），而界面一页是 `9 列 × 6 行 = 54 格`
—— 两者对不上，翻页时最后一页永远是个**半页的尾巴**。

**改法：让容量直接引用界面的一页尺寸，不要另写数字。**

```java
    // SubspaceBag 里
    public static final int PER_LEVEL = SubspaceBagMenu.PAGE_SIZE;   // ← 引用，不是 54
```

这样 1~9 级容量 = 54 / 108 / … / 486，**页数恰好等于等级**，
「第 N 页 / 共 M 页」不会再有半页。

**为什么必须引用而不是写死 54**：哪天界面从 6 行改成 5 行，写死的那个数不会跟着变，
容量就又变成"一页半"了 —— 而且是**静默**错位，只有翻到最后一页才看得出来。
自检里加了一条专门卡这个（`PER_LEVEL` 必须是 `SubspaceBagMenu.PAGE_SIZE`）。

**实测（打印各级容量与页数）**：

```
一页 = 54 格（9 列 × 6 行）
1 级：容量=54  页数=1 ✓      6 级：容量=324 页数=6 ✓
3 级：容量=162 页数=3 ✓      9 级：容量=486 页数=9 ✓
10 级：无限（动态增长）
```

> **兼容性**：容量是**变大**的，已有存档里的物品都在前 90 格里，不会丢。

## 8.85 「挖掘速度加成不明显」——先查算法，再谈数值

**反馈**：「挖掘速度的提升并不明显，速度倍率应该是手持工具后的速度相乘」。

**先别改代码，去读原版怎么算**（`Player.getDestroySpeed`）：

```java
float speed = this.inventory.getSelectedItem().getDestroySpeed(state);  // 工具速度
if (speed > 1.0F) speed += MINING_EFFICIENCY;                           // 加法（类似效率附魔）
if (hasDigSpeed) speed *= 1 + (amp + 1) * 0.2F;
if (hasMiningFatigue) speed *= scale;
speed *= BLOCK_BREAK_SPEED;                                             // ← 乘法
if (isEyeInFluid(WATER)) speed *= SUBMERGED_MINING_SPEED;
```

所以 `BLOCK_BREAK_SPEED` **本来就是乘数**，挂 `ADD_MULTIPLIED_BASE(0.1×等级)`
得到的就是「工具速度 × (1 + 0.1×等级)」—— **已经是玩家要的语义了**。

**实测确认**（读 `player.getDestroySpeed(state, pos)`，这才是真正参与计算的最终值）：

```
钻镐 0 级  → 8.00    （属性 1.00）
钻镐 10 级 → 16.00   （属性 2.00）  = 8 × 2 ✓
钻镐 20 级 → 24.00   （属性 3.00）
空手 10 级 → 2.00
```

### 那为什么"体感不明显"？—— 因为看的是**绝对时间**

破坏进度是 `speed / 硬度 / 30` 每 tick 累积，所以**时间 ∝ 1/speed**。翻倍确实省一半时间，
但省下来的**绝对秒数**取决于方块多硬：

| 方块 | 0 级 | 10 级 | 感受 |
|---|---|---|---|
| 石头（硬度 1.5） | 6 tick ≈ 0.3s | 3 tick ≈ 0.15s | 差 0.15 秒，几乎无感 |
| 黑曜石（硬度 50） | 187 tick ≈ 9.4s | 94 tick ≈ 4.7s | 省 4.7 秒，非常明显 |

> **判据**：判断"加成够不够明显"**不能只看倍率**，要看你实际在挖的东西有多硬。
> 挖软方块时的倍率感知天然被压缩 —— 这不是数值 bug。

### 顺带踩的坑

诊断里用 `inventory.setSelectedSlot(inventory.getContainerSize() - 1)` 想切到"空手" ——
**`getContainerSize()` 是 36，而 `setSelectedSlot` 只接受 0~8（快捷栏）**，
直接抛 `IllegalArgumentException: Invalid selected slot` 把**服务端线程**崩掉。
想空手就 `setSelectedSlot(8)` 再把那格 `setItem(8, ItemStack.EMPTY)`。

## 8.9 技能联动：两项能力凑一起再给额外效果

需求形态：「所有技能都应该能相互关联，比方说飞行虚化时的挖矿速度」。
落地成一个通用入口 `applySynergies(player, data)`，挂在 `applyModifiers` 里，
以后的联动都往里加。

### 三条必须遵守的规矩

**① 联动的修正器 ID 必须带独立前缀**（`synergy_xxx`）。

```java
    private static final Identifier FLIGHT_MINING_ID =
            Identifier.fromNamespaceAndPath(AttrLevel.MODID, "synergy_flight_mining");
```

因为 `applyModifier` 是**按 ID 查**的 —— 同 ID 会被当成同一个修正器直接覆盖，
**联动加成会把主加成吃没**（不是叠加，是替换）。

**② 条件是「两项都满足」，不是「有其一」。**

```java
    private static boolean isFlyingPhasing(ServerPlayer player, PlayerUpgrades data) {
        return data.getSpecial(SpecialSkill.PHASING) > 0 && player.getAbilities().flying;
    }
```

判据里要**同时**看技能等级和当前状态。做完记得**反向验证**一次
（把技能拿掉、保持状态，加成应该消失）。

**③ 状态是「即时动作」时，别等周期兜底。**

飞行开关是玩家按一下空格就变的，而属性重挂的兜底周期是 20 tick ——
等它意味着「起飞之后要愣一秒挖矿才变快」。做法是每 tick 做一次**廉价比对**
（一次 `getModifier` 查询），只在失同步时才触发重挂：

```java
    public static boolean synergiesOutOfSync(ServerPlayer player, PlayerUpgrades data) {
        AttributeInstance instance = player.getAttribute(Attributes.BLOCK_BREAK_SPEED);
        if (instance == null) return false;
        return (instance.getModifier(FLIGHT_MINING_ID) != null) != isFlyingPhasing(player, data);
    }
```

### 🔴 怎么测「飞行中」这类状态联动（踩过的坑）

**服务端的 `abilities.flying` 是「客户端权威」的。**
服务端直接写 `player.getAbilities().flying = true` 会在下一 tick 被客户端移动包覆盖
（`ServerGamePacketListenerImpl`: `flying = packet.isFlying() && player.mayFly()`）。

所以「设成 true → 等几 tick → 读值」**必然读到 false**，看起来像功能没实现。

两个可行做法：
- **同一 tick 内**连着做：设 `flying` → 调 `applyModifiers` → 立刻读值（验逻辑本身）
- 或者从**客户端**设 `flying`（并确保服务端 `mayfly` 已为 true），走真实的包同步

> 另外 `mayfly` 也要留意：它由 `applyPhasingFlight` 设置，而后者原本只挂在
> 200 tick 的 `refreshEffects` 周期里 —— 所以**升级虚化后可能最多 10 秒飞不起来**。
> 已经让 `tryUpgrade` 升级成功后立刻刷一次（和本节 ③ 是同一个道理：动作后立即应用）。

## 9. 给技能加「分级效果」（夜视 1 级 → 2 级：生物标亮）

需求形态：「某技能增加一级二级，二级能 XXX」。
做法就是三处：改等级上限、加 `>= N` 的分支、补文案和自检表。

### 9.1 改等级上限

```java
// 改前：1 级
NIGHT_VISION(1, 1, UpgradeMaterial.SCULK_CATALYST),
// 改后：2 级，每级仍 1 颗
NIGHT_VISION(2, 1, UpgradeMaterial.SCULK_CATALYST),
```

⚠️ 随之要改的（漏一处就是静默不一致）：
- 技能说明文案（`*.skill.<name>.desc`，中英各一份）
- 自检脚本里那张契约表（等级上限写死在里面）

### 9.2 「标亮生物」怎么做：用原版发光效果

```java
creature.addEffect(new MobEffectInstance(MobEffects.GLOWING,
        HIGHLIGHT_DURATION_TICKS, 0, false, false, false));
```

选它的理由：轮廓**能透墙看见**——正好就是"隔墙知道怪在哪儿"想要的效果；
而且是原版机制，**不用碰渲染层**，不会和光影 / 优化 mod 打架。
自己写描边渲染要处理的东西（深度、遮罩、性能）多得多。

**三个参数都要 `false`**（`ambient, visible, showIcon`）：
只留轮廓。开着的话一群怪各冒一圈药水粒子，**比不标还乱**。

### 9.3 🔴 刷新周期要按「信息的新鲜度」定，不是照抄现成的

这个技能已有的 `EFFECT_REFRESH_INTERVAL` 是 **200 tick（10 秒）**——
因为夜视效果本身是**恒久**的，10 秒补一次完全够。

但"怪在哪儿"这种信息**晚 10 秒知道就没用了**。
所以标亮得走**自己的一条 20 tick 刷新**：

```java
if (player.tickCount % HIGHLIGHT_INTERVAL == 0) {   // 20 tick
    tickHighlight(player, data);
}
```

> 教训：**同一个技能里的两个效果，刷新频率可以差一个数量级**。
> 别因为"它在同一个方法里"就跟着别人的节奏走。

### 9.4 两个必须加的护栏

| 护栏 | 不加会怎样 |
|---|---|
| **单次上限**（`HIGHLIGHT_LIMIT`） | 刷怪塔旁边一次几百只，白跑一圈循环 |
| **已亮且剩余时间够就 `continue`** | 每 20 tick 给几十只怪反复 `addEffect`，白费功夫还不停重置时长 |

给的效果时长要**略长于刷新间隔**（40 > 20），否则生物会在边界上闪一下。

### 9.5 怎么验（真服务端，不用人看画面）

复用 §8.7 那套临时诊断：
- 服务端侧：在玩家旁边 `EntityType.ZOMBIE.spawn(level, pos, EntitySpawnReason.COMMAND)`
  刷 5 只 → 每 20 tick 数一遍「附近几只生物 / 其中几只有 `GLOWING`」
- 客户端侧：负责自动进世界 + 跑完自动退出

实测输出（等级设成 2 之前 / 之后对比）：

```
t=100 附近生物=7 其中标亮=0     ← 等级 0，不亮
t=140 附近生物=6 其中标亮=0
>>> 夜视设为 2 级
t=160 附近生物=6 其中标亮=0     ← 刚设置，还没到 20 tick 刷新点
t=180 附近生物=6 其中标亮=6     ← 全亮
```

**这个实验同时验证了三件事**：等级门槛生效（0 级不亮）、
效果真的挂上了（2 级全亮）、刷新周期确实是 20 tick 而不是 200。

### 9.6 半径怎么定：跟「原版的某个距离」对齐

第一版给了 **24 格**，玩家反馈"太近了"。改成 **64 格**后合适。

**24 格为什么不够**：它大约只有"眼前这一屏"的范围，
玩家想找怪的时候视线本来就在更远处扫 —— 标不到反而更别扭。

**64 格是怎么来的**：**原版实体渲染距离就是 64** ——
取这个数意味着「**视野里看得见的怪，基本都标得到**」，语义正好自洽。
（别拍脑袋取 50、80 这种数，取那个"和现有机制对齐"的数，
以后要解释也有话说。）

**边界要实测确认**。摆两档距离的样本，日志按距离逐只打：

```
9格亮 | 9格亮 | 47格亮 | 52格亮 | 59格亮 | 64格亮 |
75格暗 | 80格暗 | 87格暗 | 94格暗 | 106格暗
```

一眼看出分界线落在 64 —— **比"看着差不多"靠谱得多**。
（顺便：这一跑也暴露了世界里本来就有 55 只生物，
说明半径放大后**上限护栏是真的会被撞到**，`HIGHLIGHT_LIMIT` 别省。）

## 10. 🔴 把「等级」映射成属性数值之前，先查那个属性的硬上限

2026-10-05 实测（人间之神 · 交互距离技能）。

`Attributes.BLOCK_INTERACTION_RANGE` / `ENTITY_INTERACTION_RANGE`
（1.20.1 Forge 那边是 `ForgeMod.BLOCK_REACH` / `ENTITY_REACH`）都是
**`RangedAttribute`，min 0 / max 64**。而技能用的是"每级翻倍"
（`ADD_MULTIPLIED_BASE` 给 `2ⁿ - 1`），算出来 4 级 72、5 级 144 —— **全被夹在 64**：

```
等级   方块交互   实体交互
 0       4.5        3         原版默认
 1         9        6
 2        18       12
 3        36       24
 4        64       48         ← 方块侧算出来 72，被夹
 5        64       64         ← 144 / 96，都被夹
```

**后果**：方块侧第 4、5 级是同一个数 ⇒ 玩家花了下界之星、升了级、**什么都没变**
（标准的"空壳级别"）。**曲线越陡，越容易在最后几级撞天花板。**

**规矩**：任何「等级 → 属性数值」的设计，写完先把每级**最终值**列成表，和属性的 max 对一遍。
超了只有两条路：改曲线（饱和式递增）、或把满级压到没被夹的档数。
⚠️ **基数小的属性最容易撞**（4.5、3.0 这种）：翻倍 4 次就过 64 了。

### 10.1 没有玩家时，怎么量出属性上限

专用服务端没有玩家，`/attribute` 又必须指定实体。三个办法：

| 办法 | 怎么做 | 适用 |
|---|---|---|
| **找个"像玩家"的实体** | 26.1 有 `minecraft:mannequin`（`extends Avatar`，玩家骨架）。它带 `entity_interaction_range`：<br>`summon minecraft:mannequin` → `attribute @e[type=mannequin,limit=1] minecraft:entity_interaction_range base set 1000` → `get` → **回读 64.0** 就是上限 | 有实体带该属性时最直接（注意 mannequin **不带** `block_interaction_range`） |
| **复现自己的加成算法** | `base set 3` → `modifier add <id> 31.0 add_multiplied_base`（= 满级那套）→ `get` → 直接看到**最终值** 64.0 | 比只量上限更有用：验的是"我这套公式实际落在哪" |
| **读字节码常量池** | 扫 `Attributes.class` / `ForgeMod.class` 里 `ldc2_w`（`0x14` + 2 字节索引）加载的 double：**`64.0` 出现 2 次 = 方块/实体各一次**；默认值 `4.5` / `3.0` 各 1 次 | 连实体都找不到时（`block_interaction_range` 只挂玩家身上） |

⚠️ `attribute … get` 打印的是**夹取后**的值 —— `base set 1000` 回读 64，
所以"回读值 ≠ 我设的值"本身就是上限证据，不用再去翻 max。
（同时它也是 `AttributeInstance.getValue()` 会夹取的第一手证据：算出来的 96 也一样被夹。）
