# 26.x 改维度高度 / 放开垂直边界（含「无限高」的真相）

> 结论全部在 **MC 26.1 / NeoForge 26.1.0.19-beta** 上实测取证，用专用服务端 + RCON + 直接解析存档
> 三方交叉验证过，不是只编译通过。
>
> 触发场景：元说「方块放到无限高」「地底无限深」「扩高世界」「改世界高度」「垂直边界」。

## 0. 先泼冷水：垂直方向**做不到无限**

`net.minecraft.core.BlockPos` 把坐标压进一个 64 位 long：

```java
PACKED_HORIZONTAL_LENGTH = 1 + log2(30000000) = 26   // x 占 26 位，z 占 26 位
PACKED_Y_LENGTH          = 64 - 2 * 26       = 12   // y 只剩 12 位，一个 bit 都不多
// 于是：
Y_SIZE = (1 << PACKED_Y_LENGTH) - 32 = 4096 - 32 = 4064
MAX_Y  = 2032 - 1 = 2031
MIN_Y  = -2032
```

**维度高度的合法区间 `height ∈ [16, 4064]`、`min_y ∈ [-2032, 2031]` 不是可配策略，
而是 `BlockPos` 位置编码的直接结果。**

超过范围时原版**直接拒绝加载数据包**，报得很快很清楚：

```
java.lang.IllegalStateException: Failed to parse minecraft:overworld from pack mod/xxx
Caused by: Value 40000000 outside of range [16:4064];
            Value -20000000 outside of range [-2032:2031]
```

**任何声称「无限高度」的模组只有三种情况**：说大话、只做了十几倍、或者改了 `BlockPos`
（会同时牵动存档格式、网络协议、以及所有依赖坐标打包的原版与各模组代码 —— 属于重写游戏底层）。
**接需求时第一时间把这条讲清楚，别闷头做到一半才发现。**

能拿到的真实上限对比（主世界）：

| | 原版 | 本方案 | 倍数 |
|---|---|---|---|
| 最高 y | 320 | **2031** | 6.3× |
| 最低 y | -64 | **-2032** | 31.8× |
| 总高度 | 384 | **4064** | 10.6× |

## 1. 方案选择：三条路，选哪条

| 路线 | 做法 | 什么时候用 |
|---|---|---|
| **A. 数据包改维度类型**（推荐） | 覆盖 `data/minecraft/dimension_type/overworld.json` | 只想改现有维度的垂直范围 |
| B. 世界预设 + 自定义 ChunkGenerator | `world_preset` 内联 generator | 要完全自写地形算法 → 见 `26.x-自定义世界生成器.md` |
| C. Mixin 改段访问 | 注入 `LevelChunkSection[]` 数组 | **不要在合法高度范围内用**，见下 |

**方案 A 为什么够用**：合法范围内（4064 格 = 254 段）原版段数组本身就覆盖全高，
不存在「数组下标越界」，所以**根本不需要 Mixin**。

> 踩过的坑：第一版设计了「按需扩容稀疏段数组」的 Mixin（`LevelChunkSectionHeightMixin`）
> 来支持 ±2000 万格。改到 4064 之后整套 Mixin 变成纯负债——
> 少一个 Mixin = 少一个版本升级失效的风险点。**改高度前先确认目标值，别提前写注入。**

## 2. 方案 A 完整做法

### 2.1 维度类型（放开高度）

`src/main/resources/data/minecraft/dimension_type/overworld.json`

```json
{
  "min_y": -2032,
  "height": 4064,
  "logical_height": 4064
}
```

- 其余字段照抄原版（`ambient_light`、`has_skylight`、`monster_spawn_block_light_limit` …）
- **`logical_height` 必须同步拉满**，否则传送门与重生点搜索范围仍被旧值限制
- 254 段 vs 原版 24 段，内存开销可控

> 26.1 注意：`data/minecraft/dimension/*.json` 已从原版 jar 消失，但
> **`dimension_type` 仍在**，可以正常覆盖。

### 2.2 关键一步：处理 `noise_settings` 的 y 梯度（**先分清语义，再决定动不动**）

**只改维度高度是不够的。** 原版 `noise_router` 里有若干处 `y_clamped_gradient`，
它们把**绝对 y 坐标**映射成地形密度。这几处梯度是本章最容易改错的地方。

> ## ⛔ 先说结论：「线性拉伸」是**根本性错误**，实测毁档
>
> **曾经的做法**：以为这些梯度是「需要缩放到新高度的坐标」，于是用
> 「锚定 y=64 的分段线性映射」把 `-64 → 320` 拉伸成 `-2032 → 2031`，并写了校验脚本。
> **这是错的。它把整个世界变成一片 111 格深的巨海，一块石头都没有。**
>
> **为什么错**：`y_clamped_gradient` **自带 clamp 饱和** —— y 超出 `[from_y, to_y]`
> 就取端点值。原版用 `-64` / `320` 表达的正是**「世界底 / 世界顶」语义**，
> 这个饱和行为**天然适配任意高度**：
> - 新世界 y ≤ -64 → 自动拿 `from_value`（世界底部该有的值）✓
> - 新世界 y ≥ 320 → 自动拿 `to_value`（世界顶部该有的值）✓
>
> 线性拉伸等于把「世界底部」搬到 -2032、「地表」搬到 y≈1300，
> **中间所有高度的值全部错位**。实测（`sloped_cheese` 的地形密度基线）：

| y | 原版 | 拉伸后 | 差值 |
|---|---|---|---|
| **64（地表）** | 0.500 | **-0.048** | **-0.548** |
| 0 | 1.000 | -0.000 | -1.000 |
| -64 | 1.500 | 0.047 | **-1.453** |
| -500 | 1.500 | 0.369 | -1.131 |

> **毁档机制**：密度基线整体下移 → `final_density` 变负 → 地下从石头变空气
> → 含水层把空腔填成水 → **水面停在 y=63，一路填到 y≈-48，111 格全是水**。
> 顺带 `preliminary_surface_level` 用的是同一个基线，地表高度一并算错。
>
> 存档实测（225 个完成地形生成的区块，已扣掉未生成空壳区块的干扰）：
> `y ∈ [64,79]` 100% 空气、`y ∈ [-48,62]` **100% 水、0% 石头**、
> 直到 `y ≤ -49` 才出现约 2% 的固体。
>
> 副作用还会扩散到繁茂洞穴：地形崩成巨大空腔后，洞穴植被在空腔里到处生成，
> 看起来「到处都是繁茂洞穴，正常洞穴反而没有」。

#### 正确做法：按语义分三类

| 语义 | 例子 | 做法 |
|---|---|---|
| **① 世界底→顶的密度基线** | `-64 → 1.5, 320 → -1.5` | **保持原版**。饱和行为会把新世界的底部/顶部自动映射到正确端点值 |
| **② 绝对高度的局部特征** | 洞穴入口 `-10 → 0.3, 30 → 0.0` | **保持原版**。它锚定「地表附近」，而地表仍在 y=64 |
| **③ 相对世界底/顶的过渡带** | 底部实心化 `-64 → 0.0, -40 → 1.0` | 语义是「世界底往上 24 格」，**可整体平移**到新边界（非必需） |

**默认操作：一个都不改。** 先把世界跑正常，再单独调深层手感 ——
别在同一轮里既搭地基又做装修。

#### 改之前必须查清引用关系

`noise_router` 的字段值有两种形态，**比对脚本必须都能展开**：

```json
"depth": { "type": "minecraft:add", "..." : "..." }   // ① 内联表达式
"depth": "minecraft:overworld/depth"                  // ② 纯字符串引用
```

② 是 `Either<DensityFunction, ResourceKey>` 的引用形式。
**只按 JSON 内容比对的脚本，会把「引用串相同」判成「没变」——
而被引用的文件内容早被改了**（本项目就栽在这，`noise_router.depth` 因此漏检）。

污染传播链（改任何一个文件前先画一遍）：

```
depth.json ──> sloped_cheese.json ──┬──> final_density                  （固体/空气）
                                    └──> preliminary_surface_level      （地表高度）
                                                     ↓
                                               Aquifer（空气/水）
```

`Aquifer.computeFluid` 有个捷径分支：单元格若完全在地表以下，
**直接返回 `globalFluid`、不查 floodedness 噪声**。地表高度一错，整片区域的水判定全错。

**写生成脚本时加这条校验**：把生成结果与原版逐字段比对（引用递归展开），
断言**只有预期字段发生变化**，其它一字不差。手改 4000 行的 JSON 一定会漏。

#### 2.2.1 已经改错了，怎么修回来

1. **删掉那 3 个独立的 density_function 覆盖文件**（`overworld/depth`、
   `caves/entrances`、`caves/spaghetti_2d`）。
   它们被 `noise_router` 以**字符串引用**的形式引用着，留在数据包里就是覆盖原版。
2. `noise_settings/overworld.json` **只保留 `noise.min_y` / `noise.height` 两处改动**，
   内联的 5 处 `y_clamped_gradient` 全部还原。
3. **生成脚本的判据要反转成黑名单式**：白名单（「允许 y 相关字段变化」）会让
   拉伸操作合法通过 —— 改成「除 `noise.min_y` / `noise.height` 外，
   **任何差异都是错误**」。
4. 顺手加两条独立判据：
   - `noise_router` 与原文 `json.dumps(sort_keys=True)` **逐字节相等**
   - 那 3 个覆盖文件**在数据包里不存在**（这条能兜住「引用串没变但文件被改」）

**实测效果**（同机、同模组、324 个区块 vs 修前 225 个，按区块数归一）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 水 | 856 万块 | **19.6 万块（-97.7%）** |
| 岩浆 | 48 万块 | 1 万块（-97.9%，底部岩浆海保留） |
| 石头 | 5,401 块（几乎没有） | **272 万块** |
| 苔藓块（繁茂洞穴） | 47 万块 | **3.6 万块（-92%）** |
| 基岩 / 远古残骸 / 钻石矿 | — | 与修前按比例一致 |

y 分层看：`[64,79]` 从「100% 空气」变成「29.7% 固体 + 樱花树」，
`[-48,-1]` 从「100% 水」变成「91~94% 深板岩」，
`[-2032,-2017]` 是「100% 固体 + 基岩层」。

> **注意「繁茂洞穴太多」也被一并修好了。** 它的根因不是 `max_steps`，
> 而是地形崩溃后地下变成巨大空腔、植被在空腔里到处生成。
> **排查这类「某个特征突然暴多」的抱怨时，先确认地形本身是不是正常**，
> 别一头扎进那个特征的参数里调。

### 2.3 降低生成压力：把「结果本来就是常数」的区间短路掉

**症状**：世界拉高 10.6 倍后，区块生成慢到服务端 `Can't keep up! Running 34s behind`，
100 区块要 2~3 分钟。

**成本从哪来**：`NoiseChunk` 的 `cellCountY = height / (4 × size_vertical)`。
384 高 → 48 层；4064 高 → **508 层**。每个 cell 都要把密度函数算一遍（含 3D 噪声）。

#### 核心观察：两端是常数，就不用算

原版 `final_density` 的 argument1 分支：

```
min( squeeze( 0.64 * interpolated( blend_density( add(
      C = 0.1171875,
      mul( A(y), add( D = -0.1171875, add( E = -0.078125,
                      mul( B(y), add( F = 0.078125, R ) ) ) ) )
) ) ) ), caves/noodle )

A(y) = y_clamped_gradient(-64 → 0.0, -40 → 1.0)
B(y) = y_clamped_gradient(240 → 1.0, 256 → 0.0)
R    = range_choice(sloped_cheese, ...)      ← 含 3D 噪声，最贵的部分
```

`y_clamped_gradient` 在区间外**饱和**，于是：

```
y ≤ -64  →  A = 0  →  X = C
y ≥ 256  →  B = 0  →  X = C + D + E = -0.078125
```

**两端都是常数 —— 那个最贵的 R 压根不参与结果。**
用 `range_choice(input=y)` 短路掉，是**代数恒等，不是近似**。

```json
"blend_density": {
  "argument": {
    "type": "minecraft:range_choice",
    "input": "minecraft:y",
    "min_inclusive": -64.0,
    "max_exclusive": 256.0,
    "when_in_range": "<原来的 add(...)>",
    "when_out_of_range": {
      "type": "minecraft:range_choice",
      "input": "minecraft:y",
      "min_inclusive": -1000000.0,
      "max_exclusive": -64.0,
      "when_in_range": 0.1171875,
      "when_out_of_range": -0.078125
    }
  }
}
```

> ⚠️ **必须包在 `interpolated` 的\*\*内部\*\*。**
> 包在外面没用 —— `NoiseChunk` 初始化时会遍历整棵树收集 `Marker.INTERPOLATED`
> 节点，照样给它建插值器、照样逐 cell 求值。
> **只有让每个 cell 的采样短路才省得下来。**

效果：需完整计算的 cell 层 **508 → 40（-92%）**。

#### ⚠️ `range_choice` 的边界有 Codec 范围限制

`min_inclusive` / `max_exclusive` 受 `Codec.doubleRange(-1000000.0, 1000000.0)` 约束。
**越界会让整个数据包加载失败**：服务端 14 秒就崩，Gradle 只报 `runServer FAILED`，
真因藏在日志深处一句：

```
Value -1.0E7 outside of range [-1000000.0:1000000.0]
```

下界直接写 `-1000000.0`，别贪心地写个"更负"的数。
**这类错误静态 JSON 检查抓不到** —— 要专门写一条判据，扫所有 `range_choice`
的边界值是否落在 `[-1e6, 1e6]` 内。

#### 先确认没有重复劳动：`vein_toggle` 原版已自带短路

一开始以为矿脉噪声是瓶颈（`OreVeinifier` 对每个方块先算 `veinToggle` 再做范围检查），
准备照 `VeinType` 的 y 范围（`COPPER[0,50]` ∪ `IRON[-60,-8]`）也包一层。

**实读发现原版早就做了** —— `noise_router.vein_toggle` 本身就是：

```json
{"type": "minecraft:interpolated",
 "argument": {"type": "minecraft:range_choice",
              "input": "minecraft:y",
              "min_inclusive": -60.0, "max_exclusive": 51.0,
              "when_in_range": {"type": "minecraft:noise", "noise": "minecraft:ore_veininess", ...},
              "when_out_of_range": 0.0}}
```

边界跟 `VeinType` 严丝合缝。**动手前先读一遍原版是怎么写的。**

#### 实测效果

100 区块、同种子、机器空载：

| | 生成耗时 |
|---|---|
| 未优化 | **242 秒** |
| 优化后 | **151 秒** |

**提速 37.6%（-91 秒）。**

> ⚠️ **测这类指标必须保证机器空载。** 同一版本跑两次分别是 303 秒和 151 秒 ——
> 差了一倍，因为第一次跑的时候我在后台改代码 / 跑脚本抢了 CPU。
> **单次测量不可信**，要么多跑几次取平均，要么跑的时候什么都不干。

#### 怎么证明「无损」

**第一步：剥离式判据（代码层）**

把包装剥掉后必须与原版**逐字节相等**。见 §2.2 的 `unoptimize()` ——
它比「白名单允许某些字段变化」硬得多，白名单会放过意料之外的改动。

**第二步：A/B 同种子逐方块对比（存档层）**

⚠️ **但这里有个陷阱：MC 的世界生成本身就不是确定性的。**

实测（同一种子，都是 324 个完成地形的区块）：

| 对比 | 差异格数 | 占比 |
|---|---|---|
| 未优化 vs 优化 | 132,902 | 0.039% |
| **同一版本跑两次** | **147,957** | 0.044% |

**「优化前 vs 优化后」的差异比「同版本两次运行」还小。**

差异全部是植被 / 苔藓的落点微调，且成对抵消
（`air→oak_leaves` 28,419 vs `oak_leaves→air` 27,459；
`air→vine` 8,288 vs `vine→air` 8,904；`deepslate↔moss_block` 1,944/1,816）——
是方块被"挪了几格"，不是"消失/新增"。

根源：**服务端异步生成区块，跨区块特征（树冠、藤蔓）的"邻区块可用性"随调度顺序变化**。

> ⭐ **教训**：验证「无损」之前，先测出**固有噪声基线**。
> 否则你会把噪声当成回归，或者反过来把真回归当成噪声。
> 判据应该是「**实验组差异 ≤ 对照组差异**」，而不是「差异必须为 0」。

#### 下一步该优化什么？（用实测数据反推成本构成）

不用 profiler 也能推断瓶颈在哪 —— 用「优化前后的耗时差」反推：

设「密度函数求值」占总时间比例为 x。本次优化把 cell 层从 508 降到 40（保留 7.9%），
实测总耗时 242 → 151 秒：

```
242 × (1 − 0.921x) = 151   →   x ≈ 0.41
```

| 阶段 | 未优化 | 优化后 |
|---|---|---|
| 密度函数求值 | ~99 秒（41%） | **~8 秒（5%）** |
| features / 光照 / 序列化 / IO | ~143 秒（59%） | **~143 秒（95%）** |

**结论：瓶颈已经不在噪声上了，在 features（矿脉 + 繁茂洞穴的放置）、
光照、区块序列化。继续抠密度函数没有意义。**

> **顺带回答一个常见想法：「能不能把世界生成交给显卡？」**
>
> 理论上噪声采样确实适合 GPU（纯数据并行），但实际不可行：
> 1. Java 的 GPU 计算生态（Aparapi / TornadoVM / JCuda）不成熟，
>    而 MC 的生成路径充斥着对象分配、`Holder<T>`、虚函数调用；
> 2. 世界生成里大量分支（`range_choice` / `if`）、**跨区块依赖**（树冠延伸）
>    和**顺序依赖的随机序列**（`RandomSource`），这些是 GPU 最不擅长的；
> 3. **更关键的是**：按上面的反推，噪声现在只占 5%，
>    就算全搬上显卡，最多再省 ~8 秒。
>
> **GPU 在 MC 里真正有用的是渲染（Sodium / Nvidium 那一路），不是世界生成。**
> 世界生成该走的路是：减少无效计算（本节的短路）→ 优化 features 放置 → CPU 并行
> （C2ME 那一路）。

## 3. 矿脉：两个静默失效的大坑

### 坑 1：文件存在 ≠ 会生成（必须写 biome modifier）

`configured_feature` 和 `placed_feature` 只是「定义」。**不在任何 biome 的 `features` 列表里
就永远不会被放置，而且服务端零报错。**

用 NeoForge 修饰器（**别覆盖原版 biome json**，会和其它数据包互相覆盖）：

`data/<ns>/neoforge/biome_modifier/<name>.json`

```json
{
  "type": "neoforge:add_features",
  "biomes": "#minecraft:is_overworld",
  "features": "<ns>:<name>",
  "step": "underground_ores"
}
```

字段名从 `neoforge-26.1.0.19-beta-universal.jar` 的
`BiomeModifiers$AddFeaturesBiomeModifier` 常量池实读：**`biomes` / `features` / `step`**。
注册名 `neoforge:add_features` 从 `NeoForgeMod.class` 实读（同类的还有
`remove_features` / `add_spawns` / `add_carvers` / `add_spawn_costs` 等）。

`step` 合法值 = `GenerationStep.Decoration` 枚举名：

### 4.1 诊断「世界生成坏了」的正确姿势：先离线统计，别急着起服务端

**直接解析已有存档的 `.mca` 统计方块分布，几秒钟就能定位问题。**

本轮就是靠这个一眼看出病灶 —— 把统计里「未生成空壳区块」的干扰扣掉后：

| y 区间 | 构成 |
|---|---|
| [64, 79] | **air 100%**（连陆地都没有） |
| [48, 62] | **water 100%** |
| [0, 47] | **water 100%** |
| [-48, -33] | **water 100%** |
| [-49, -64] | water 95.6% + 固体 2.2% ← 才开始有石头 |

**读这个表的两个关键技巧**：

1. **先看 `Status` 分布，把「未生成完的区块」剔除**。本存档 1089 个区块里
   只有 225 个走到地形阶段（`full` / `initialize_light` / `carvers`），
   其余 864 个是空壳。**空壳贡献的 pure-air 会稀释所有比例**，
   不扣除的话会把「100% 水」算成「20% 水」，结论直接错。
   扣法：`(空气数 - 空壳数×4096) / (已生成区块数×4096)`。
2. **按 sectionY 分段看，别看总量**。总量只能证明「有」，证明不了「在哪」。
   水面高度这类信息只有按段看才读得出来（本轮的 `[48,63]` 段是
   93.8% 水 + 6.2% 空气 —— 那 6.2% 正好是 y=63 一层，即水面）。

## 4.5 扩高之后必然撞上的两个「硬编码绝对 y」（**必读**）

把世界拉深 10 倍，原版那些**写死的绝对 y 常量**会从「小装饰」变成「世界级灾难」。
这两个坑的共同特征：**数据包层面完全无解，且服务端零报错**，只能代码层拦截。

### 坑 A：岩浆洪水 —— `createFluidPicker` 里的 `-54`

`NoiseBasedChunkGenerator.createFluidPicker()`（源码实读）：

```java
Aquifer.FluidStatus lavaStatus = new FluidStatus(-54, Blocks.LAVA.defaultBlockState());
int seaLevel = settings.seaLevel();                  // 63
Aquifer.FluidStatus seaStatus = new FluidStatus(seaLevel, settings.defaultFluid());
return (x, y, z) -> y < Math.min(-54, seaLevel) ? lavaStatus : seaStatus;
```

而 `Aquifer.FluidStatus.at(blockY)` = `blockY < fluidLevel ? fluidType : AIR`。
于是 **`y < -54` 的空洞全被填成岩浆**。

| | 覆盖范围 | 占世界高度 | 实测岩浆占比 |
|---|---|---|---|
| 原版（min_y=-64） | y -64 ~ -54，10 格 | 2.6% | 正常（底部一层） |
| 扩高后（min_y=-2032） | y -2032 ~ -54，**1978 格** | **49%** | **12.4%**（6.4 亿方块里 6371 万是岩浆） |

**两个被实测推翻的错误解法，别再试**：

1. ❌ **`noise_settings.aquifers_enabled = false`** —— 反编译确认 `aquifersEnabled`
   在全项目里**只出现在 `NoiseGeneratorSettings` 内部，没有任何地方消费它**（26.1 已废弃该语义）。
   关掉后 NoiseChunk 走 `Aquifer.createDisabled(globalFluidPicker)`，
   而那个 picker 正是上面带 `-54` 的 lambda，**岩浆照填**。
   实测：设成 false 后岩浆仍有 63,719,495 块。
   *（更早还试过放大 `lava.y_scale` 想"压薄"岩浆，结果占比 0.56% → 9.74%，反向恶化 17 倍。
   `y_scale` 是采样坐标乘数，只决定花纹快慢，不改变命中率 —— 详见本文件「y_scale 不要动」。）*
2. ❌ **`default_fluid`** —— lambda 里用的是 `Blocks.LAVA` 字面量，压根不读这个字段。

**唯一解法：Mixin `@Redirect` 掉那个 `Math.min`**。新阈值取 `世界底部 + 10`，
与原版「底部 10 格岩浆海」语义一致，只是随世界一起下沉。

```java
@Mixin(NoiseBasedChunkGenerator.class)
public class LavaLevelMixin {
    private static final int LAVA_SEA_THICKNESS = 10;

    @Redirect(
        method = "lambda$createFluidPicker$0",        // ← 关键！不是 createFluidPicker
        at = @At(value = "INVOKE", target = "Ljava/lang/Math;min(II)I")
    )
    private static int endlessdepth$redirectLavaLevel(int originalLavaLevel, int seaLevel) {
        return Math.min(EndlessDepth.WORLD_MIN_Y + LAVA_SEA_THICKNESS, seaLevel);
    }
}
```

> **⭐ `method` 必须指向 lambda 合成方法，不是原方法名。**
> 第一版写 `method = "createFluidPicker"`，报：
> ```
> Redirector ... failed injection check, (0/1) succeeded. Scanned 0 target(s).
> ```
> 用 `javap -p -c` 反汇编才看清：`javac` 把 lambda 体编译成了**独立的私有合成方法**，
> 那段 `Math.min` 在那里，不在 `createFluidPicker` 体内：
> ```
> private static Aquifer$FluidStatus lambda$createFluidPicker$0(..., int, int, int);
>     ...
>     10: bipush        -54
>     12: iload_1
>     13: invokestatic  java/lang/Math.min:(II)I
> ```
> **凡是要注入的代码在 lambda 里，`method` 就得写 `lambda$<外层方法名>$<序号>`。**
> 定位方法是 `javap -p -c <class>` 搜目标指令，别猜。

实测效果（同一套 224 区块）：

```
修前：lava 63,719,495 (12.45%)  ← 半个世界泡岩浆
修后：lava    409,981 ( 0.08%)  ← 减少 99.4%
```
且段 -127（y -2032~-2017）保留 1,708 块岩浆 = 底部岩浆海还在，符合预期。

### 坑 B：植被长不出来 —— `EnvironmentScanPlacement.max_steps = 12`

`environment_scan` 的 `max_steps` 在源码里被 `Codec.intRange(1, 32)` 限制
（`EnvironmentScanPlacement.java:24`），原版值是 **12**，那是给**窄洞穴**调的：
落点离地板通常几格，12 步够用。

**本模组的洞穴形态完全不同** —— 扩深后负段空气占比恒定 65~79%，
是**大片连通空洞**而非窄缝，落点离地板经常在十几格开外，
12 步够不到 → 这一次尝试直接作废，**且服务端不会有任何报错**。

实测症状很有诊断价值：`count` 从 325 加到 769（**+137%**），
但深层繁茂方块只从 2,285 涨到 3,998（**+75%**）——
**不成比例**就说明瓶颈在「每次尝试的成功率」而不是「尝试次数」。

修法：把 `max_steps` 抬到上限 `32`。

```
修后：深层繁茂方块 3,998 → 2,344,604（约 586 倍），131 个深度段都有分布
```

> ⚠️ **但这个数字是在「地形已崩坏」的前提下测出来的**（见 §2.2 的毁档事故）——
> 当时地下大半是空腔，繁茂方块的空间基数本身就虚高。
>
> **地形修好后复测（324 区块，与崩坏期按区块数归一）**：
> 苔藓块 47 万 → 3.6 万（-92%），洞穴藤蔓 13.8 万 → 0.3 万。
> **即「繁茂洞穴太多」的抱怨主要来自地形崩溃，不是 `max_steps`。**
> `max_steps = 32` 本身可以保留 —— 深层确实是大空洞，
> 原版 12 步够不到地板这一点依然成立。**但下次要先确认地形正常再谈密度。**

> 写生成脚本时的**前置判据**很重要：只靠"落盘后读回来校验"会漏 ——
> `scan['max_steps'] = SCAN_STEPS` 是合法赋值、不触发任何 assert，
> 坏值会被写进盘再被读回来才发现，**磁盘已被污染**。
> 所以要在**赋值之前**断言常量本身：`assert SCAN_STEPS == 32`。

### 坑 C（同类预警）：凡是「相对世界底部/顶部」的语义，扩高时都要查一遍

上面两个坑本质相同：**原版把绝对 y 当常量写死，而这个常量隐含假设了世界高度**。
扩高/扩深时应当主动搜一遍这类常量。已知需检查的：

| 常量 | 位置 | 是否随世界自适应 |
|---|---|---|
| `-54`（岩浆液面） | `NoiseBasedChunkGenerator.createFluidPicker` | ❌ 硬编码，需 Mixin |
| `MAX_Y = 2031` / `MIN_Y = -2032` | `BlockPos` 编码 | 硬上限本身，不可改 |
| 各 `y_clamped_gradient` | `noise_router` | ⚠️ **分语义**：多数应保持原版，见 §2.2 |
| `max_steps` | `environment_scan` 等 placement | ❌ 原版按窄地形调的值 |

> **查这一类常量时不要只看「它在哪」，要看「它的端点代表什么」**：
> 端点写 `-64` / `320` 的，多半是「世界底/顶」语义（clamp 饱和已正确，别动）；
> 端点写 `-10` / `30` 这类小数，才是「某个具体绝对高度」（地表附近），
> 而地表在扩高后位置不变，所以同样别动。

## 5. 起测试服务端的坑（26.1）

- **`gradlew runServer` 与 RCON 必须串行**：上一条 `stop` 没生效会让端口 25575 不释放，
  下一次启动直接 `Failed to initialize server`（异常还被吞了，crash report 里只有
  `IllegalStateException: Failed to initialize server` 无 cause）。
  判据：日志开头出现 `Unable to delete file ... latest.log` = 上一个进程还活着。
  排查：`netstat -ano | grep 25575` 拿 PID → 确认是测试服务端 → RCON `stop`。
- **强载区块会压垮服务端**：`forceload add -64 -64 64 64`（81 区块）会让服务器
  `Can't keep up! Running 20949ms behind`，RCON 连接被 reset（`WinError 10054`），
  甚至让 Gradle daemon 直接消失。
  实测可用档位：**`forceload add -112 -128 111 127`（224 区块）能跑完**，
  但会 `Running 34493ms behind` + RCON 请求超时（生成期间主线程被占满）。
  **要拿 RCON 结果就等生成完再发下一条**，别在 forceload 后立刻发命令。
  `forceload` 的硬上限是 **256 区块**（超出报 `Too many chunks in the specified area`）。
- **RCON 超时不等于服务端死了**：世界生成期间 `rcon.py` 会抛
  `TimeoutError: timed out`（socket 读超时）。直接看 region 文件时间戳/大小判断进度，
  或隔几分钟重发。日志里的 `Marked N chunks` 说明 forceload 命令**已受理**。
- **`--offline` 下 gradle 找不到 JDK toolchain**：报
  `Cannot find a Java installation ... languageVersion=25`。
  解决：`export JAVA_HOME=<jdk-25 路径>` 再跑，或显式传
  `-Porg.gradle.java.installations.auto-detect=true`。
  注意官方启动器 runtime 目录下的是 **JRE，没有 javac**，不能用于 toolchain。
- 服务端内嵌 RCON：`server.properties` 要 `enable-rcon=true`、`rcon.port=25575`、
  `rcon.password=...`、`pause-when-empty-seconds=0`、`max-tick-time=-1`。
- **RCON 的 `say` 输出不回传**，会写进 `run/logs/latest.log`；要验证条件命中就读日志。

### 5.1 自动化验收流程（本轮实测跑通，3m56s 全流程）

把「起服务端 → forceload → 等生成 → 停」串成**一个脚本后台跑**，别手工分步 ——
手工很容易漏掉 `stop`，导致下一轮端口占用。

```bash
./gradlew runServer --offline > run/server.log 2>&1 &
# 1. 等启动：轮询日志里的 "Done ("
# 2. forceload：见下面第 1 点（会超时，但生效）
# 3. 等生成：轮询 region 目录大小，连续 3 次不变即完成
# 4. RCON stop，再轮询端口 25575 是否释放
```

**三个反直觉的点：**

1. **`forceload` 命令本身会 RCON 超时**（`TimeoutError: timed out`）。
   命令触发的世界生成会占满主线程，响应根本发不出来 ——
   **但命令已经送达并生效了**。判据是服务端日志出现
   `Can't keep up! Running 22238ms behind` + 存档区块数确实变多。
   **别把超时当失败去重试**（重试等于再压一次主线程）。

2. **判「生成完成」别用固定 sleep**，用 **region 目录大小连续 3 次不变**。
   注意 `du -sb` 在文件还在写时读数会跳，所以要「连续 3 次」而不是一次。
   实测：100 区块约 3 分钟，224 区块更久。

3. **`run/mods/` 是空的也正常** —— NeoGradle 的 `runServer`
   **直接从 `build/libs` 加载工程 jar**，不需要手动往 `mods/` 里拷。
   验证时只要确认 `build/libs/*.jar` 是刚构建的那份。

4. **验收顺序建议**：先 `世界生成体检.py`（秒级、离线）看整体是否正常，
   要查深层再加 `--all`。**确诊「世界是不是坏了」不要用 RCON 逐点探测** ——
   慢、还会超时、也看不出全局。

### 5.2 把传送门改到「同维度的另一个高度」（比如把下界搬到地底）

**需求形态**：「传送门不要通到另一个维度，通到主世界地下」。

**唯一入口**是 `NetherPortalBlock.getPortalDestination()`，
目的地维度是**硬编码**的：

```java
ResourceKey<Level> newDimension =
    currentLevel.dimension() == Level.NETHER ? Level.OVERWORLD : Level.NETHER;
```

数据包改不动 → 只能 Mixin（`@Inject` 到 HEAD + `cancellable`）。

**⭐ 但原版 `PortalForcer.createPortal` 在世界拉深之后完全不能用：**

```java
int maxPlaceableY = min(level.getMaxY(), level.getMinY() + level.getLogicalHeight() - 1);
int height = min(maxPlaceableY, level.getHeight(MOTION_BLOCKING, x, z));  // ← 整列最高阻挡方块
for (int y = height; y >= level.getMinY(); y--) { ... }
```

`height` 拿到的仍是**地表高度**（≈70），而 `getMinY()` 是 -2032
→ 它会**从地表往下扫两千多格，最后在地表附近建门**，跟「传送到地下」正好相反。
而且逐格 `canPortalReplaceBlock`，开销是灾难级的。

**解法：自己实现「找 / 造出口」**（本项目里的 `DeepPortalBuilder`）：

1. 目标 y **由配置直接给定**，不做螺旋搜索；
2. 就地挖一个小空腔 + 放传送门方块（不依赖 `createPortal`）；
3. 找已有门时**自己按 y 距离加权** —— 原版 `findClosestPortalPosition` 是同维度搜索，
   会认领到地表那些门（那是「另一个世界层」的门，认领过来就把人传回地表了）。

**`TeleportTransition` 是 record，有 6 参数便利构造**，不用手填
`missingRespawnBlock` / `asPassenger` / `relatives`。

**失败要退回原版**：造不出出口时**不设** `CallbackInfoReturnable`，
让它走原逻辑去真下界 —— 比把玩家卡在门里强。

### 5.3 已知的良性警告：Mixin 的 class 版本

用 Java 25（MC 26.1 的编译目标）编出来的 class 是 **version 69**，
而 Mixin 的 `compatibilityLevel` 最高只到 `JAVA_24`（class 68）：

```
Class version 69 required is higher than the class version supported by
the current version of Mixin (JAVA_24 supports class version 68)
```

**这是良性的** —— 后面紧跟的 `does use it's CallbackInfoReturnable`
说明注入正常完成，功能不受影响。`compatibilityLevel` 填 `JAVA_24`
（能填的最高值）即可；**不要为了消掉这句话去降编译目标**（MC 26.1 要求 Java 25）。

### 5.4 把一个维度的地形搬进另一个维度（例：把净界放到主世界地底）

**需求形态**：「主世界往下挖会进入净界」/「地狱在地底下而不是另一个维度」。

#### 密度函数可以直接搬，但 y 端点必须重映射

净界的 `final_density` 内联在 `noise_settings/nether.json` 里（没有独立文件），
而且**骨架和主世界是同一套**：

```
squeeze(0.64 * interpolated(blend_density(add(
    2.5,
    mul( A(y), add(-2.5, add(0.9375,
         mul( B(y), add(-0.9375, "minecraft:nether/base_3d_noise") ) ) ) )
))))
A(y) = y_clamped_gradient(from_y=-8,  from_value=0.0, to_y=24,  to_value=1.0)   ← 底部过渡
B(y) = y_clamped_gradient(from_y=104, from_value=1.0, to_y=128, to_value=0.0)   ← 顶部收口
```

差别只在端点值（净界只有 128 格高）和噪声源。所以**把三个 y 端点按高度比例映射**即可：

```
scale_y(y_nether) = NEW_MIN_Y + (y_nether / 128) * (段高度)
```

搬进主世界深层后，包一层 `range_choice` 把区间隔开：

```json
"final_density": {
  "type": "minecraft:range_choice",
  "input": "minecraft:y",
  "min_inclusive": -1000000.0,
  "max_exclusive": <地狱段顶>,
  "when_in_range": <重映射后的净界密度>,
  "when_out_of_range": <原来的主世界逻辑>
}
```

#### ⚠️ 坑 1：海平面/岩浆面也要一起按比例重映射

**只搬密度函数会得到一个"整个洞窟区都泡在岩浆里"的世界。**

净界是 `sea_level = 32`（占高度 128 的 25%）—— 岩浆海只在下部。
如果还沿用主世界配置的岩浆液面（比如 -560），而洞窟区在 -1600~-640，
那**所有洞窟都在液面之下** → 全填岩浆，实测岩浆占到 27%。

**正确做法**：把 `sea_level` 也按同一比例映射：

```
lavaSeaLevel = NEW_MIN_Y + (32 / 128) * 段高度
```

#### ⚠️ 坑 2：固体方块是 `null`，注入点别选错

搬了密度函数，`default_block` 仍是**主世界那个**（`stone`），
因为它是每个维度一个的字段。要按 y 换方块，只能从代码层拦。

**别选 `MaterialRuleList.calculate`** —— 看它的语义：

```java
// Aquifer.NoiseBasedAquifer.computeSubstance
if (density > 0.0) return null;        // ← 固体：直接返回 null
```

`MaterialRuleList` 是「返回第一个非 null」，所以**固体位置压根走不到"有返回值"的分支**，
链跑完是 `null`，最后由调用方兜底：

```java
// NoiseBasedChunkGenerator.doFill
BlockState state = noiseChunk.getInterpolatedState();
chunk.setBlockState(pos, state == null ? settings.defaultBlock() : state, false);
```

所以要拦的是 **`null`（= 该填固体）** 这一步 ——
**注入 `NoiseChunk.getInterpolatedState` 的 `RETURN`**，
而且那里的 `this` 就是 `NoiseChunk`，它本身就是 `FunctionContext`，`blockY()` 直接可用：

```java
@Inject(method = "getInterpolatedState", at = @At("RETURN"), cancellable = true)
private void swap(CallbackInfoReturnable<BlockState> cir) {
    int y = ((NoiseChunk) (Object) this).blockY();
    BlockState s = cir.getReturnValue();
    if (s != null && !isStoneLike(s)) return;   // 空气/水/岩浆/矿石都放行
    cir.setReturnValue(Blocks.NETHERRACK.defaultBlockState());
}
```

**用白名单判断「石头类」**，不要写「非空气就换」—— 那会吃掉水、岩浆、矿石，
以及以后别的模组放进来的装饰方块。

#### 副作用：深层不再能走常数短路

前置模组为了省算力把深层短路成常数（§2.3），但**常数密度 = 实心 = 没有地貌**。
搬进净界密度之后那一段要重新参与计算，生成会变慢 —— 这是「有地貌」的必付代价。
实测：100 区块从短路时的 ~150s 变成 ~127s（区块数不同，只说明量级没爆炸）。

#### ⚠️ 坑 3：噪声的垂直尺度必须跟着拉伸比一起调

**这是「搬过去之后看着不像」的头号原因。**

对比两个维度的 `base_3d_noise`：

| | y_scale | 该维度的世界高度 |
|---|---|---|
| 净界 | **0.375** | 128 |
| 主世界 | 0.125 | 384 |

净界的 `y_scale` 是主世界的 **3 倍** —— 它靠这个高采样率，
在只有 128 格的矮世界里挤出层次感。

**把它原样搬进 1582 格高的地狱段（拉伸 12.36 倍）会出问题**：
噪声的**绝对空间尺度没变**，于是同一套花纹在垂直方向重复了 12 倍 ——
本该是「厚实心 / 大空腔 / 厚实心」的**三大层**，
被摊成上百层细碎均匀的小洞。观感完全不同（元原话：「真正的地狱更像一个三明治」）。

**修法**：把 `y_scale` 除以拉伸比。

```
y_scale_new = y_scale_nether / (段高度 / 净界高度)
            = 0.375 / (1582 / 128)
            = 0.375 / 12.36
            = 0.0303
```

`xz_scale` **不动** —— 水平方向世界尺寸没变。

> ⚠️ **不能直接改原版那个文件** —— 真净界维度还在用它。
> 要复制一份到自己的命名空间（如 `deepnether:deep_base_3d_noise`），
> 再把净界密度里的引用换过去。

#### ⚠️ 坑 4：海平面也要按比例调，但别照搬

**严格按比例算出来的岩浆海面，放大之后会「太厚」。**

净界海平面 y=32 / 高 128 = 25% 高度处。按比例映射到地狱段
（[-2032, -450] 高 1582）就是 **-1636**。

**但实测那样从 -1824 一直淹到 -1636，共 188 格，其中 176 格连一个空气腔都没有**
（`air = 0.0%`）—— 往下望是一整片看不到底的岩浆。
净界本身只有 32 格厚，玩家「游过去」就完事；放大 12.4 倍后观感完全变了。

本项目把默认值调薄到 **-1750**（约 74 格），保留「游过去」的感觉，
并在配置注释里写明「想严格还原净界比例就改回 -1636」。
**这类「按比例算出来的值」要按观感再调一轮**，不能只信数学。

#### ⚠️ 坑 5：传送门落点必须落在**天然空腔**里

第一版的做法是「就地挖一块放门」，**结果玩家一到就泡在岩浆里**：
`setBlock(AIR)` 确实清掉了流体，但**旁边的岩浆会立刻顺着流体更新灌回来** ——
而地狱段的洞窟底部大片是岩浆。

**正确做法**：从目标高度**上下交替扫描**（先往上，岩浆在下面、空气在上面），
找第一处「门框 + 四周留白」**全是空气**的位置，找到就用，一格都不挖；
整段扫完都没有，才退回「挖 + 用地狱岩糊住四周封边」。

> 判「干净空腔」时**不要把岩浆算作可用空间** ——
> 那正是要避开的东西。

## 7. 血泪教训（把世界拉深/拉高**必然**会撞的通用规律）

这一节是本文件最该记住的部分，比具体配置更通用。

### 7.1 「原版把绝对 y 当常量写死，而这个常量隐含假设了世界高度」

扩高/扩深之后，这类常量会从「小装饰」变成「世界级灾难」。**两次踩坑都符合这条规律**：

| 常量 | 位置 | 扩深后的后果 | 能否用数据包修 |
|---|---|---|---|
| `-54`（岩浆液面） | `NoiseBasedChunkGenerator.createFluidPicker` | 49% 的世界被填成岩浆 | ❌ 只能 Mixin |
| `max_steps = 12` | `environment_scan` 等 placement | 大空洞里扫不到地板，植被静默不生成 | ❌ 只能改值（已在数据包内） |

**做法**：改高度前先搜一遍这类常量。但**「搜到就改」是错的** ——
一定要先问「这个端点在表达什么语义」，见 §7.5。

### 7.2 「先怀疑自己上一轮的结论，再动手改」

本任务连着三轮踩在同一个陷阱上：

| 轮次 | 当时的结论 | 实测结果 |
|---|---|---|
| 上轮 | 「放大 `lava.y_scale` 能压薄岩浆」 | ❌ 反向恶化 17 倍（0.56% → 9.74%） |
| 上轮 | 「关掉 `aquifers_enabled` 就能避免岩浆洪水」 | ❌ 无效，该字段在 26.1 全项目无人消费 |
| 本轮 | 「`y_clamped_gradient` 要锚定地表做分段线性拉伸」 | ❌ 把世界变成 111 格深的巨海 |

三次都犯同一个错：**从源码"读到一个看起来相关的机制"，就认定它是解法**，
没有做「改它之前 vs 改它之后」的对照实测就写进结论。
**改任何配置前，先想清楚"如果我理解错了，症状会是什么样"** ——
本轮的答案就是「整个世界没有陆地」，而它 slipped through 了所有自动化判据。

### 7.3 判据必须钉在**外部权威**上，不能用被测物校验被测物

双向验证时抓到的真缺陷：判据写成 `assert ms == SCAN_STEPS`。
当有人把常量 `SCAN_STEPS` 自己也改成 12 时，两边仍然相等 → **静默通过**。
正确写法是钉死来源自源码的字面量：

```python
assert ms == 32, f'max_steps 必须为 32'
assert SCAN_STEPS == 32, f'常量被改成了 {SCAN_STEPS}'
```

同理，**原子性判据要在同一个用例内部比**（跑前/跑后），
取在循环外会让「跑过任何一趟」之后的用例全部误报。

### 7.4 lambda 里的代码要注入，`method` 得指名合成方法

`javac` 把 lambda 体编译成独立的私有合成方法 `lambda$<外层方法名>$<序号>`。
`@Redirect` 的 `method` 写外层方法名会报 `Scanned 0 target(s)`。
**用 `javap -p -c <class>` 反汇编搜目标指令来定位，别猜。**

### 7.5 「`clamp` / 渐变类函数的端点是**语义边界**，不是待缩放的坐标」

`y_clamped_gradient` 自带饱和：y 超出 `[from_y, to_y]` 就取端点值。
原版用 `-64` / `320` 表达「世界底 / 世界顶」——
**这个语义在扩高后依然成立，而且饱和行为会自动把新边界映射到正确的端点值。**

把它当成「需要缩放到新高度的坐标」去线性拉伸，等于**把整个世界的密度基线搬到错误位置**：
地表密度基线从 0.5 掉到 -0.05 → 地下全变空气 → 被含水层填成水（实测 111 格巨海）。

**最阴的地方在于：构建不报错、数据包加载不报错、Mixin 不报错、高度自检全绿、
区块 Status 也能走到 `full`** —— 所有自动化判据都通过，只有打开存档看方块才发现。

判断该不该动，问三个问题：

| 端点在表达什么 | 例子 | 结论 |
|---|---|---|
| 「世界边界」 | `1.5 → -1.5`（`-64`→`320`） | **保持原版**，clamp 已自动适配新边界 |
| 「某个具体绝对高度」 | 地表洞穴入口 `-10 → 30` | **保持原版**，地表位置没变 |
| 「离世界底/顶 N 格的过渡带」 | 底部实心化 `-64 → -40` | 可平移，但**先测再动** |

**通用规律：凡是自带 clamp / saturate 的函数，它的端点承载的是「边界语义」。
改变世界尺寸时，这些端点通常应当保持 —— 让饱和去处理新边界，
而不是把它们拖到新位置。**

### 7.6 改数据包前先画**引用图**，字符串引用是隐藏的边

`noise_router` 的字段可以写成两种形式：

```json
"depth": { "type": "minecraft:add", "..." : "..." }   // 内联
"depth": "minecraft:overworld/depth"                  // 纯字符串引用
```

第二种是 `Either<DensityFunction, ResourceKey>`。**只比对 JSON 内容的审计脚本
会把「引用串没变」判成「这个字段没动」，而被引用的文件内容早被改了。**

本项目就栽在这：改了 `depth.json`（它被 `noise_router.depth` 以字符串形式引用），
但审计脚本报 `noise_router.depth: 相同`，于是漏掉整条污染链，
直到从存档里挖出 111 格水才反查出来。

**正确做法**：写一个**递归展开引用**的审计脚本，把「被覆盖的文件」与
「引用它的路径」连成图再判断影响面。别只做扁平的内容 diff。
