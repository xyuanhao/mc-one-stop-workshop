# 26.x 自定义容器界面：用原版贴图**切片拼装**

用户反馈过一句很典型的话：**「这界面的颜色和箱子背包的颜色格格不入」**。

根因几乎总是同一个：界面是拿 `gfx.fill(...)` 平面色 + `gfx.outline(...)` 描边画出来的，
而原版容器是**暖灰纹理面板**、**格子凹陷是烘在贴图里的**。
平面色无论怎么调色号都对不上。**唯一出路是切原版图集。**

本文记录整套实测数据与踩过的坑（26.1 实测，26.2 同构）。

---

## 0. 先做减法：能搬出去就搬，搬不出去就**并排**

**切图集只能给你 176 宽**（见 §3、§4 坑②）。所以只要面板"塞不下"，
第一反应不该是"怎么拼得更宽"，而是先问：

> 这几块内容**都必须同屏**吗？如果必须同屏，**能不能横着并排**？

### 0.1 三种去处，按代价排序

| 方案 | 什么时候用 | 代价 |
|---|---|---|
| **A. 搬去独立界面** | 两块内容**不需要互相拖东西** | 最小：直接 `new` 原版菜单类 |
| **B. 左右并排同屏** | 需要**互相拖**（如"从背包拿材料合成"） | 中：整块面板变宽，槽位坐标要整体偏移 |
| **C. 硬塞进一列** | 都不行才考虑 | 最大：横向要相互让位、纵向白吃高度 |

⚠️ **别一上来就选 C。** 更常见的错是先做了 A、被用户打回来
（"我要直接拿背包里的材料"），然后**退回 C**——
其实这时候正确选项是 **B**。

### 0.2 方案 A：搬去独立界面（最省事）

**原版菜单的构造函数是 public**，可以直接用：
```java
// 客户端配的就是原版 CraftingScreen，贴图/槽位/配方书全原生，一像素都不用画
player.openMenu(new SimpleMenuProvider(
        (id, inv, p) -> new CraftingMenu(id, inv),
        Component.translatable("container.crafting")));
```
（`CraftingMenu(id, inv)` 走 `ContainerLevelAccess.NULL`，
`stillValid` 那个"附近要有工作台方块"的检查会放行，所以能脱离方块存在。）

### 0.3 方案 B：左右并排同屏（要互相拖东西时）

**核心思路：整块面板 = 176 + 缝 + 176。** 两块各占图集的整幅可用宽，
谁都不用让位，底图基本是"原样搬"。

```java
public static final int PANEL_W    = 176;              // 单块 = 图集整幅宽
public static final int PANEL_GAP  = 4;                // 缝（<2 会让两块描边糊成一条）
public static final int WORKBENCH_X = PANEL_W + PANEL_GAP;   // 180
public static final int WIDTH      = WORKBENCH_X + PANEL_W;  // 356
```

四条硬规则（每条都有对应的坑，见 §4 坑⑧~⑪）：

1. **右半块的槽位坐标 = 原版坐标 + `WORKBENCH_X`**（`3×3` 原版 `(30,17)` → `(210,17)`；
   成品格 `(124,35)` → `(304,35)`）。
2. **玩家背包**只挂一份，留在其中一块，另一块共用。
   （原版 CraftingMenu 自带一份玩家背包，**不能直接 new 它** —— 见 §4 坑⑨。）
3. **右半块的底图整幅贴**，u/v 从 0 起，不要自己算切片。
4. **两块高度不一致是必然的**，矮的那块下方必须用**整幅平带**补齐（带描边），
   否则"有底没有框"。

**判断顺序**：① 能不能搬走？ ② 要同屏就并排。 ③ 都不行才考虑自绘/硬塞。

## 1. 先搞清楚 26.x 的渲染分段（不改对钩子，贴了也白贴）

| 26.x 之前 | 26.x |
|---|---|
| `Screen#renderBackground` | `Screen#extractBackground` |
| `AbstractContainerScreen#renderBg` | **没有 `renderBg` 了** |

`AbstractContainerScreen` 的顺序：

```
extractRenderState
 └─ extractContents
      ├─ 内部先调 super.extractRenderState → extractBackground   ← 画面板底图的钩子
      ├─ extractSlots → extractSlot                              ← 只画物品与高亮
      ├─ extractSlotHighlightBack / Front
      ├─ extractCarriedItem
      ├─ extractSnapbackItem
      └─ extractTooltip
```

**两个关键结论：**

1. **`extractBackground(GuiGraphicsExtractor, int mouseX, int mouseY, float partialTick)`
   是画面板底图的正规钩子**（原版 `ContainerScreen` 就覆写它）。底图必须在这里贴，
   晚了会被槽位内容盖住。
2. **26.x 不再单独画槽位花纹**：`extractSlot` 只画物品和高亮，
   格子凹陷**烘在贴图里**。所以"花纹在不在槽位上"完全取决于切片 u/v 对不对。

顺带：高亮用 `blitSprite` + `SLOT_HIGHLIGHT_BACK_SPRITE` / `SLOT_HIGHLIGHT_FRONT_SPRITE`。

## 2. `blit` 的签名（26.x）

```java
gfx.blit(RenderPipelines.GUI_TEXTURED, Identifier texture,
         int x, int y, float u, float v,
         int width, int height, int textureWidth, int textureHeight);
```
- `x/y/width/height` 是 `int`，**`u/v` 是 `float`**（容易忘 `(float)` 转换）
- `RenderPipelines.GUI_TEXTURED`
- 贴图 id：`Identifier.withDefaultNamespace("textures/gui/container/xxx.png")`

## 4. 七条命脉级的坑

### 🔴 坑①：图集里「格线比槽位靠外 1px」

- 箱子：**格线在 x=7 → 槽位 x=8**；纵向 **格线 v=17 → 槽位 y=18**
- 玩家背包：**格线 v=83 → 槽位 y = 83 + 1**

**推论：如果面板宽刚好是 176（= 图集可用宽），整幅贴过去格线自然落在 7/25/43…，
槽位在 8/26/44…，差 1px 正好 —— 什么都不用挪。**

早期版本的面板比图集宽，才需要"左内缩 / 9 格 / 右描边"三段错位拼：

```java
// ⚠️ 只有在面板宽 ≠ 176 时才需要这么写；面板=176 直接整幅贴
blit(gfx, tex, x,         dstY, 0,   v, 7,      height);
blit(gfx, tex, x + 7,     dstY, 7,   v, 9 * 18, height);
blit(gfx, tex, x + 169,   dstY, 169, v, 7,      height);
```

**教训：先把面板收回到 176，能省掉一整类错位 bug。**

### 🔴 坑②：不能拿图集右侧区域去"补宽"

想让面板比 176 宽、于是切 `generic_54` 右侧（x>176）去填 → 裁到的是
**图集未使用区域 / 半截格线**，拉出一片横条纹。

**结论：图集能提供的宽度上限就是 176。** 面板要做宽，右侧只能纯色填，
缝不出原版观感 —— 这就是"别把面板做宽"的技术理由。

### 🔴 坑③：右描边是 **7px**，不是 6

`generic_54` / `inventory.png` 的右描边是 `x=169..175`（浅内壁 169..172 + 深灰 173..174 + **黑 175**）。
取 6 会漏掉那根黑线 → 面板最右缘空出一条 1px 白缝。

**判据：`EDGE_X + EDGE_W == 176`。**

### 🔴 坑④：`inventory.png` 的 v=165 是「外边界」，切片**绝不能含**

v=165 是 178 宽**全黑**（x=0..177）。整幅贴 → 面板右下角连同右描边一起烧掉，
预览图上就是**「右下角缺了一块」**。

**修法：玩家段切片取到 v=164 为止**（`PLAYER_TILE_H` = `164 - 83 + 1` = **82**）。

**判据写法**（用"下一行必须是全黑外边界"来锚定终点，比硬写数字稳）：
```python
last = PLAYER_TILE_V + PLAYER_TILE_H - 1        # 164
assert img[last]    == 深灰 85                  # 底边框
assert img[last + 1] == (0,0,0,255)             # 下一行是全黑外边界 → 到此为止
```

### 🔴 坑⑤：成品格外轮廓「三缺一」，**不能整块贴**

把 `crafting_table` 的 `(119,30,26,26)` 整块贴过来，会带进：
① 一个**上边框只到 x=143** 的不闭合框；② 框内一大片深色内壁 139。
在满格纹的面板上，看着就是一个**突兀的大灰方块**。

**正解：贴内缩 1px 的 24×24 内部块**（四边闭合、内部是标准槽位格纹）。

定位要**以槽位倒推**，不能按图集硬搬：
```
框左上（面板） = BENCH_RESULT_X − 边框1px − 内部让位4px
```
（原版槽位在框内 +5 处；内部块 24 宽而标准槽位视觉 16 宽，所以还要再让 4px 才居中。）

> 这里没有"箭头遮缝"的运气 —— 箭头右缘 111 < 框左缘 119，中间是实打实的留白，
> 所以不闭合的框会**直接暴露**。别赌。

### 🔴 坑⑥：自检脚本「扫源码找残留标识符」时，**必须先剥注释**

判据里常有一类：「源码里不该再出现 X」（废弃常量、已搬走的类）。
但 Javadoc / 行注释里**恰恰常常写着「为什么不再用 X」**——
不剥注释，就会把自己刚写的那段说明当成残留，报一堆假错。

```python
def strip_comments(text):
    text = re.sub(r"/\*.*?\*/", "", text, flags=re.S)
    text = re.sub(r"//[^\n]*", "", text)
    return text

# 「不该出现 X」的判据一律用剥注释后的版本
code = strip_comments(src)
if re.search(r"\bBENCH_X\b", code): fail("工作台已搬走，不该再有 BENCH_X")
```

**反面教材**：这个坑真踩过 —— 在 `SubspaceBagMenu` 的类注释里写了
「为什么不再继承 `AbstractCraftingMenu`」，判据就报了「还在继承 AbstractCraftingMenu」。

> 推论：凡是**语义上"代码里有没有"**的判据，作用对象应该是 `strip_comments(src)`；
> 只有「常量解析」「方法体解析」这类**结构性**判据才需要处理注释（它们的正则本来就跳过注释也行）。

### 🔴 坑⑥-b：判据要查**方法定义 / 调用点**，不能只查"名字出现过"

坑⑥ 的另一面：就算剥了注释，查 `"recalcResult" in src` 依然会**假绿** ——
因为方法名在**调用点**里也出现。把方法名一改，字符串仍在，判据照样通过。

同一类错误的三种变体（全都踩过）：

| 写法（错） | 为什么假绿 | 正解 |
|---|---|---|
| `"recalcResult" in src` | 调用点里也有这词 | `re.search(r"private\s+void\s+recalcResult\s*\(", src)` |
| `"ClientboundContainerSetSlotPacket" in src` | **import 行**里就有 | `re.search(r"connection\.send\s*\(\s*new\s+ClientboundContainerSetSlotPacket\s*\(", src)` |
| `"OpenWorkbenchRequest" in src` | 同上，import 里就有 | `re.search(r"sendToServer\s*\(\s*new\s+OpenWorkbenchRequest\s*\(", src)` |

**通用规则**：要断言「做了某件事」，就匹配**那件事的完整语法形态**
（定义 / 调用 / 构造 + 参数），而不是匹配一个类名或方法名。

**第三层：分支判据要限定作用域。** 想断言「某方法里按 X 分了支」，
不能全文搜 `if (X)` —— 同一个变量在别处（标题、底边收口）也会用。
先**把那个方法体切出来**再搜：

```python
m = re.search(r"extractBackground\s*\([^)]*\)\s*\{(.*?)\n    \}", screen_code, re.S)
if not m: fail("方法体没解析出来 —— 判据要跟着改")
elif not re.search(r"if\s*\(\s*benchOpen\s*\)\s*\{", m.group(1)):
    fail("底图没有按 benchOpen 分支")
```
（还要匹配**分支形态** `if (X) {`，不是 `"X" in body` —— 三元表达式里
`x + (X ? ... : ...)` 也含 `X`，只查名字一样假绿。）

> 验证方法：注入坏样本时必须**同时确认报错文本里有你要的关键词** ——
> 双向验证脚本的 `needle` 若写成类名/变量名，而报错是中文描述，
> 就会被误判成"漏过"（**这一轮因此误判了 4 次**）。
> needle 一律写**报错文本里真正出现的那个词**（往往是中文短语）。

> 顺带：**改了产品代码就要回头核坏样本的锚点**。这一轮有 2 个坏样本因为锚点
> 不匹配被静默"跳过"（输出里只有一行 ⚠️），差点漏掉。
> 双向验证的收尾必须确认**没有"跳过"**，而不只是看拦下数量。

**第四层：判据要绑「分支 + 被包住的代码」，坏样本锚点要唯一指向目标。**

源码里同一句 `if (X) {` 往往出现**好几处**（这一轮有 3 处 `if (benchOpen) {`：
铺底 / 贴工作台 / 画标题）。两个方向都要处理：

| 方向 | 错误写法 | 正解 |
|---|---|---|
| 判据 | `re.search(r"if \(X\) \{", body)` —— 别处还有，改坏一处照样绿 | 绑住**被包住的代码**：`r"if \(X\) \{[^}]*?CRAFTING_BG"` |
| 坏样本 | 锚点只写 `"        if (X) {"` → `replace(..., 1)` 改到了**第一处**（不是要测的那处），于是判据"正确地放行"被误判成漏过 | 锚点**带上下一行上下文**，唯一指向目标 |

### 🔴 坑⑦：容器「按容量铺格」时，`writeBack` 的**写入范围**有两个相反的坑

只要容器支持**按需增长**（满级无限、格子随内容长），就有这一对孪生 bug。
设 `visible = 本页铺出来的格数`、`lastUsed = 本页最后一个有东西的相对下标`、
`backupLast = 后备列表本页范围内最后一个有东西的相对下标`：

| 写法 | 后果 |
|---|---|
| `for i in 0..visible-1`（整页无条件写回） | 满级会铺出**整页空格**（如已用 3 → 铺 54），存档列表被从 3 白撑到 54，NBT 白占 |
| `for i in 0..lastUsed`（只写本页内容） | 玩家把本页**最后一个物品拿走**后，那一格不会被写回 → 关界面又冒出**旧物品**（数据回滚） |

**正解：写到 `max(lastUsed, backupLast)` 为止。**

```java
int upto = Math.max(lastUsed, backupLast);
for (int i = 0; i <= upto; i++) {
    int index = offset + i;
    while (backing.size() <= index) backing.add(ItemStack.EMPTY);
    backing.set(index, mirror.stored(i));
}
```

两个坑的严重度差一个量级：撑长只是浪费存档空间，**回滚是玩家能看到的数据错误**。
所以宁可写多一点，把 `backupLast` 一起算上。

> 判据写法（自检脚本里）：断言 `writeBack` 的方法体里出现 `Math.max(lastUsed, backupLast)`。
> 两个方向各注入一个坏样本，必须都能拦下。

## 4-bis. 并排面板专用：合成格怎么接进自己的菜单

并排时"另一块是工作台"是最常见的需求。这块**坑密度极高**，
因为"能显示"和"能合成"是两件事 —— 前者只要贴对图，后者要接四条线才成。

### 🔴 坑⑧：`slotChangedCraftingGrid` 在 `CraftingMenu`，**不在** `AbstractCraftingMenu`

想"白拿"父类的重算逻辑会直接编译失败。**必须自己写一遍**：

```java
private void recalcResult(ServerLevel level, @Nullable RecipeHolder<CraftingRecipe> hint) {
    if (!(this.owner instanceof ServerPlayer sp)) return;
    CraftingInput input = this.craftSlots.asCraftInput();
    ItemStack result = ItemStack.EMPTY;
    Optional<RecipeHolder<CraftingRecipe>> maybe =
            level.getServer().getRecipeManager().getRecipeFor(RecipeType.CRAFTING, input, level, hint);
    if (maybe.isPresent()) {
        RecipeHolder<CraftingRecipe> holder = maybe.get();
        if (this.resultSlots.setRecipeUsed(sp, holder)) {        // ← 不能省：绕过配方解锁
            ItemStack assembled = holder.value().assemble(input);
            if (assembled.isItemEnabled(level.enabledFeatures())) result = assembled;
        }
    }
    this.resultSlots.setItem(0, result);
    this.setRemoteSlot(0, result);
    // ↓ 少了这一句：服务端算出了成品，客户端看不见（成品格一片空白）
    sp.connection.send(new ClientboundContainerSetSlotPacket(
            this.containerId, this.incrementStateId(), 0, result));
}
```

**三处最容易漏**：`setRecipeUsed`（绕过解锁）、`setRemoteSlot`（服务端自己的镜像）、
`connection.send`（推给客户端）。漏任一个的表现都不同，但都是"不出成品"。

### 🔴 坑⑨：玩家背包**只挂一份** —— 不能 `new CraftingMenu`，也不能 `addStandardInventorySlots`

原版 `CraftingMenu` 构造函数里就带 `this.addStandardInventorySlots(inventory, 8, 84)`。
并排时用它 = **同一格物品同时出现在两块面板上**（而且点击会互相打架）。

正解：继承 `AbstractCraftingMenu`（它有网格容器 + 配方书接线，**但不自己 addSlot**），
槽位自己排：

```java
// 顺序：亚空间 → 3×3 → 成品格 → 主背包 27 → 快捷栏 9
for (row) for (col) addSlot(new Slot(this.craftSlots, col + row*3, BENCH_GRID_X + col*18, ...));
addSlot(new ResultSlot(player, this.craftSlots, this.resultSlots, 0, BENCH_RESULT_X, BENCH_RESULT_Y));
// 玩家背包只在这里挂一次
```

**`AbstractCraftingMenu` 要实现的抽象方法**：`getResultSlot()` / `getInputGridSlots()` /
`getRecipeBookType()` / `owner()`，外加 `slotsChanged()`（重算产地）、
`beginPlacingRecipe()` / `finishPlacingRecipe()`（配方书摆料开关，默认空实现）。

### 🔴 坑⑩：合成格下标**必须从 `visible` 推**，不能写死

如果容器按容量铺格（满级无限、页数可变），那 3×3 与成品格的下标**一直在漂**：

```java
public int benchGridStart()   { return this.visible; }                  // 亚空间之后
public int benchResultIndex() { return this.visible + 3 * 3; }
```

写死 `54` 的话：低级玩家的下标是对的、满级玩家全错 —— 而且这种错
**不报任何异常**，表现为"材料放得进去、Shift 点不出来"。

### 🔴 坑⑪：关界面时要回收合成格，否则**丢件**

`save()` 只管容器自己的数据。合成格里剩下的材料要显式回收：

```java
@Override
public void removed(Player player) {
    super.removed(player);
    this.clearContainer(player, this.craftSlots);   // 背包满了会掉在脚下
}
```

### 🔴 坑⑫：`crafting_table.png` **绝不能整幅贴** —— 它自带一整套玩家背包

这是本轮最狠的一个坑，玩家直接来问了：**「工作台下面为什么还有格子啊」**。

实测这张图的完整纵向结构：

```
v=0..2      顶部描边（黑 / 白）
v=3..40     内壁 198（原版放 "Crafting" 标题的带子）
v=17..70    3×3 合成格（槽位 30,17 起；18 步进）
v=35..49    箭头        v=30..59  成品格粗框（x=119..144）
v=44..82    内壁 198（箭头/成品格下方的空白）
──────────  ⚠️ 从这里往下全是**原版的玩家背包** ──────────
v=83        玩家背包第 1 行格线        v=84..135  玩家背包 3 行
v=141..157  快捷栏
v=163..164  深灰底边框   v=165 全黑外边界   v=166 透明
```

**两个后果，都真实发生过：**

| 切片高度 | 后果 |
|---|---|
| 165 或 166 | 右半块底下多出 **3 行 + 1 行没有槽位的假格子** —— 玩家看到「工作台下面还有格子」，点上去毫无反应 |
| 166 以上 | 还会额外带进 v=165 那根 **176 宽全黑外边界**，底缘横一道粗黑线 |

**正解：`BENCH_TILE_H = 83`**（贴 v=0..82，正好在玩家背包格线之前），
下面交给整幅平带补齐。这里没有任何"取巧"的空间。

> **通用规矩（横向纵向都适用）**：
> **凡是要贴过来的区域，先确认它的每一块花纹下面都有对应的槽位。**
> 没有槽位的地方就别把台纹贴过去 —— 玩家一定会去点那些假格子。
> 横向的版本是「只铺 3 列，右边 6 列不铺」（§5），
> 纵向的版本就是本坑。两次踩的是**同一个坑**，只是方向不同。

> **判据写法**：别写死 `83`。从图集里实测「玩家背包第 1 行的格线在哪」——
> 用结构特征扫：一条深灰 55 后面**紧跟**槽位内壁 139 的行，就是一行格子的开始。
> （⚠️ 不要用「某行某个固定 x 是不是 55」去判 —— 行格线在**格子之间**的位置
> 会取到 139，采样点选错就扫不到，这个错也踩过。）

### 🔴 坑⑫-b：让一排槽位"可收起"——`isActive()` 和 `mayPlace()` **两个都要接**

想把某一块面板做成「可展开/收起」（精妙背包那种侧栏），**千万别靠"不建那些槽位"** ——
客户端/服务端槽位数必须相等，少了就是内容包越界断线。
正确做法是让槽位**失效**，但原版的"失效"是**两个独立口径**：

| 方法 | 管什么 | 不接会怎样 |
|---|---|---|
| `isActive()` | **渲染**（`extractSlots` 里 `if (slot.isActive())`）+ **鼠标命中**（`getHoveredSlot`） | 收起后槽位还被画出来、还能点 |
| `mayPlace(ItemStack)` | **程序化放入**（`AbstractContainerMenu#moveItemStackTo`） | 🔴 收起后 **Shift 点击背包，物品被搬进看不见的合成格 —— 玩家以为丢件** |

`moveItemStackTo` 只查 `mayPlace`，**完全不查 `isActive`** —— 所以只做一半会留下一个
"吞东西"的暗坑，而且测试时不容易发现（要点 Shift 才会撞上）。

```java
private boolean benchVisible = true;          // 菜单上的开关

private static class BenchSlot extends Slot {
    private final MyMenu menu;
    @Override public boolean isActive()  { return menu.isBenchVisible(); }
    @Override public boolean mayPlace(ItemStack s) { return menu.isBenchVisible() && super.mayPlace(s); }
}
```

**这是纯客户端状态**：服务端那份菜单的开关保持 true，槽位数不变，两边照样一致。

#### 另外三条配套（都会让"收起"看着像没做）

1. **`imageWidth` 是 `protected final`，改不了。** 传展开态的宽度，
   收起时**自己重算 `leftPos`**：`leftPos = (width - 实际显示宽) / 2`。
   不重算的话面板会按展开态居中而偏左，右边空出一大片。
2. **切换后要 `rebuildWidgets()`** —— 面板宽变了，按钮的 x 与 leftPos 都得重算。
3. **底图要按状态分支**，而且**底边收口的右端也要跟着变** ——
   否则收起时底边会画到面板外面去。

> **判据写法**：`if (benchOpen)` 这类分支判据必须**限定在方法体内**匹配。
> 源码里往往不止一处用同一个变量（标题、底边收口都用），
> 只搜全文的话，把底图那处改坏、别处还在，判据照样绿（这个错真踩过）。
> 更别用 `"benchOpen" in src` —— 那连"变量名出现过"都算通过。

### 🔴 坑⑬：并排的两块**高度不一样时，别把矮的那块"补"到一样高**

两块并排、高度不同（如左 243 / 右 85），最自然的反应是"把矮块下方补齐，
让两块一样高"。**这个方向是错的** —— 补出来的是一片没有任何槽位、
也没有任何内容的**空面板**。玩家原话：

> 「展开右边工作台下面有大片无用界面」

**正解：矮的那块就照它自己的高度画，下面什么都不画。**

```java
if (benchOpen) {
    blit(gfx, CRAFTING_BG, x + WORKBENCH_X, y, 0, 0, PANEL_W, BENCH_TILE_H);
    // 自己补一条 2px 收口让面板闭合（切片把原图底边框一起切掉了）
    gfx.fill(x + WORKBENCH_X, y + BENCH_TILE_H,
             x + WORKBENCH_X + PANEL_W, y + BENCH_TILE_H + 2, PANEL_EDGE);
}
```

**三条配套，缺一条就前功尽弃：**

1. **底不能铺满整块。** 别写 `fill(x, y, x + imageWidth, y + imageHeight, PANEL_FILL)` ——
   右半块只有 85 高，这一句就把下面 160px 全铺成面板，等于白做。
   要**按两块各自的区域分开铺**。
2. **底边收口只收左半块**（右半块是独立小面板，自带底框）。
3. **`hasClickedOutside` 要覆写** —— `imageWidth×imageHeight` 是包围盒（356×243），
   默认判定会把右半块下面那片**空地**算成"界面内"，
   玩家在那点一下 → 手上有物品时触发丢弃。**看着是空地却把东西扔了。**

```java
@Override
protected boolean hasClickedOutside(double mx, double my, int guiLeft, int guiTop) {
    if (mx < guiLeft || my < guiTop
            || mx >= guiLeft + displayWidth() || my >= guiTop + this.imageHeight) return true;
    // 展开时右半块只有工作台那么高，再往下就是空地
    return benchOpen && mx >= guiLeft + WORKBENCH_X && my >= guiTop + BENCH_TILE_H + 2;
}
```

> 同理，滚轮之类的"区域判断"也要带上纵向范围 —— 面板下方是空地，
> 在空地滚轮就该照常翻页。

> **量化验证**：预览脚本要单独统计「右半块面板下方」那一区，
> **它的纯色占比必须是 0.0%**（完全透明 = 那里没画面板）。
> 修好后整块纯色从 55.1% 掉到 **23.5%** —— 这个数字直接反映"少铺了一片无用面板"。

## 5. 面板段表（推荐写法）

面板拆成一串**首尾相接**的段，每段 = `(面板起始 y, 高, 图集, 图集 v)`：

```
① 顶栏              generic_54   v=0     h=17
② 容器格子 N 行      generic_54   v=17    h=N*18     （图集正好 6 行可循环）
③ 收口+标签带        generic_54   v=124   h=15       （124 是第 6 行下沿，125..138 平带）
④ 自定义区          见下
⑤ 收口+标签带        generic_54   v=124   h=15
⑥ 玩家背包段         inventory.png v=83   h=82       （到 v=164 为止！）
⑦ 按钮行            generic_54   平带循环铺
⑧ 底边 2px 深色收口
```

**任何"不画格子"的区域都拿 `v=125..138` 那条平带循环铺**（逐像素比对确认整段同款，
左右描边也一致，所以接缝看不出来）。**不要用 `fill` 纯色** —— 用户会一眼看出补丁。

**自定义区（以"3×3 + 箭头 + 成品格"为例，全部复用行带，不切 `crafting_table` 整片）**：

```java
int bandW = 7 + 3 * 18 + 1;                    // 62：3 列格子 + 第 4 列格线收口
blit(container, x, top, 0, ROW_V, bandW, height);          // 前 3 列行带
gfx.fill(x + bandW, top, x + EDGE_X, top + height, PANEL_FILL);   // 右侧留白
blit(container, x + EDGE_X, top, EDGE_X, ROW_V, EDGE_W, height);  // 右描边
blit(crafting,  x + ARROW_X, top + (ARROW_V - CT_GRID_V),
     ARROW_U, ARROW_V, ARROW_W, ARROW_H);                   // 箭头
blit(crafting,  x + RESULT_X - 1 - 4, top + (RESULT_V - CT_GRID_V),
     RESULT_SLOT_U, RESULT_SLOT_V, 24, 24);                 // 成品格内部块
```

为什么**只铺 3 列**而不是铺满 9 列：右边那 6 列没有槽位，铺上台纹会变成
「能看不能点」的假格子，玩家一定会去点。

**留白要"打散"**：把箭头/成品框摆在中间，让右侧留白分成 2~3 段（各 ≤26px），
而不是堆成一整块 —— 一整块平白在满格纹面板上非常显眼。

## 6. 把"界面烂"变成数字：分区纯色占比

**「好看」要能测量，否则改完还是靠感觉。** 预览脚本里按区统计"内壁色占比"：

```python
def pure_ratio(y0, y1):
    return 纯内壁色像素数 / 总像素数 * 100
```

实测基线（26.1 原版）：

| 区域 | 纯色占比 |
|---|---|
| `generic_54` 格子区 | **4%**（满格纹的参考值） |
| `crafting_table` 工作台区 | **58%**（原版工作台背景本就是大片纯色） |

**判据：任何紧邻"满格纹区"的新区域，纯色占比别超过 ~60%，且留白要分段。**
工作台区从 55~69% 改到 58%（但留白被切成 23/22/14 三段）后，观感完全不同 ——
**同样占比，分布不同，观感差很多**。所以占比只是入场券，还要看分布。

## 8. 自检脚本要断言什么

除了槽位下标契约（见 `改造原版复用.md` 第 8 节），贴图坐标要单独一条：

```
A 行带：格线 x=7；ROW_BAND_U==7；BAG_X-ROW_BAND_U==1；BENCH_X-ROW_BAND_U==1
        格线 v=17 ⇒ BAG_Y==18；ROWS_IN_ATLAS == VISIBLE_ROWS
B 描边：EDGE_X==169 且 EDGE_X+EDGE_W==176（别漏最外侧黑线）
C 平带：SEAM_V==124 且 FLAT_V==125 / FLAT_H==14；
        且 v=125..138 **逐像素**与 v=125 相同（证明它真"全平"，可循环铺）
D 切块：箭头包围盒 == 常量推出来的框；
        成品格外轮廓上边框实测 == 25（证明它三缺一）⇒ 断言"只能定位不能整块贴"；
        RESULT_SLOT == 外轮廓 + 边框偏移；内部块四角不是内壁色 198
E 几何：箭头/成品框不压行带、不越右描边；右侧留白分段每段 ≤26px
F 玩家段：格线 [83,101,119,141]；LIFT==1；间距==141-83；
        **切片末行是深灰底边框、下一行是全黑外边界**（防止含进 v=165）
G 纵向栈：每段的顶 == 上一段的底（首尾相接，无缝无重叠）；
        底缘 + 21 == HEIGHT；按钮右缘 ≤ WIDTH-8
```

**全部要双向验证**：逐个注入坏样本（把 `PLAYER_TILE_LIFT` 改成 14、
`EDGE_W` 改成 6、`BAG_Y` 改成 20、`SEAM_V` 改成 125 …）确认脚本**报出来且报得准**，
再还原确认全绿。

⚠️ 双向验证时**每个用例前先还原**：否则第一个坏样本会一直挂在那儿，
后续用例看到的都是同一条报错 —— 会误判成"全都拦住了"。

## 9. 一句话

> 自定义容器界面要"像原版"，就得**切原版的图**，而不是调原版的色。
> 切图的四条命脉：**格线比槽位靠外 1px**、**别想补宽**、**段间别留纯色**、
> **切到"外边界"就停手**。
> 「好看」要能量化（分区纯色占比 + 留白分段），交付前用 PIL 离线拼一遍、叠上槽位框自己先看。
