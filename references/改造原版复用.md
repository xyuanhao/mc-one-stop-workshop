# 改造原版复用 —— "拿原版改一改就能用"

> 大量物品/生物/机制不需要从零做：**原版已经有形状、有明暗、有 AI、有数据**，改颜色或改参数即可。
> 这份文档说明素材在哪、怎么取、怎么改。所有类名/方法名/数量都是 2026-09-10 在 26.2 原版 jar 上**实测**的。

---

## ⚠️ 抄原版的边界：抄形状与工艺，别抄"身份"（2026-09-10 实战教训）

**"拿原版改一改就能用"有个前提：你做的东西在原版里没有。** 一旦产物与原版同款并存，
它就不是"复用"，而是**冗余** —— 玩家分不清、不能与原版堆叠、还白占创造栏。

一次真实翻车（用本 skill 生成 26.1 模组「Matter Forge」，十种物质的工具/盔甲/方块）：

- 木/石/铜/铁/金/钻石 六种**直接复制了原版贴图** → 产物与原版一模一样，
  玩家看到的是"又一个铁剑"，且与原版铁剑**不能堆叠**（id 不同）。
- 方块同理：`wood_block` 直接用 `oak_planks.png`、`iron_block` 直接用铁块贴图 →
  外观与原版方块零差异，等于把原版方块重注册了一遍。
- **只有青金石 / 红石 / 绿宝石 / 紫水晶这四种（原版没有对应装备）才是真正的新内容。**

### 什么能抄、什么抄了白做

| 抄什么 | 能不能抄 | 说明 |
|---|---|---|
| 形状（工具轮廓、模型骨架、UV 布局） | ✅ 抄 | 这才是"改一改"的本体 |
| 工艺（明暗层次、噪声风格、数值档位） | ✅ 抄 | 让产物达到原版水准 |
| 结构（配方/战利品表/语言键名/AI 逻辑） | ✅ 抄 | 省事且不易错 |
| **身份（做出一模一样的东西）** | ❌ **别抄** | 这就是冗余 |

**一句话判据**：把产物与原版同类物品并排放在同一个创造栏里 ——
**如果玩家会问"这不就是原版铁剑吗"，那就是做错了。**

### 落地检查（选题阶段就要做，不是做完再补）

1. **先列原版已有清单**。打算做"十种材质的装备"时，先查原版有哪几种。
   已有的（木/石/铜/铁/金/钻石/下界合金）**要么不做，要么必须做出差异化**
   —— 新数值档位、新特效、新用途、新获取方式。**光换个 id 不叫差异化。**
2. **贴图不要直接复制**。即使形状必须一样，配色也要有可见区分度：
   全部走 `纹理变色.py`（同材质也要调色相/加细节），**直接 copy 原版贴图 = 视觉零差异 = 白做**。
3. **方块尤其危险**。`X_block` 与原版 X_block 同贴图同外观，就是重复注册；
   做方块前先问"原版有这块吗、外观像不像"。
4. **数量不重要，"是新的"才重要**。与其硬凑十种（其中六种原版已有），
   不如老实做四种原版没有的 —— 那才叫内容。

> 这不是"不要复用原版"，而是**复用原版的形，不要复用原版的位**：
> 原版是素材库与基准，不是你要重复一遍的对象。

## 1. 物品贴图：提取 → 变色 → 用

```bash
# ① 取原版贴图
python 原版资源提取.py --ver 26.2 --extract-pattern "textures/item/*_door.png" -o out/
# ② 改色（形状不动，只换颜色；一次出整套）
python 纹理变色.py out/assets/minecraft/textures/item/oak_door.png --preset woods --prefix door -o tex/
# ③ 产物按注册 id 命名放进 assets/<modid>/textures/item/
```

**实测**：26.2 有 17 张门贴图（12 种木材 + 4 阶段铜门 + 铁门），拿 `oak_door.png` 过一遍
`--preset woods` 直接得到 12 种木材的门，原版的窗格、边框立体感全部保留。

- 想要**原版同款色**而不是近似色：先采样再改
  `python 纹理变色.py <贴图> --sample` → 打印暗/中/亮三档真实色值，拿去当 `--colors`。
  woods/copper 两组内置色板就是这么来的（oak 实测 `#9A804D`，不是拍脑袋的 `#B8945F`）。
- 做**新木材**：采样原版橡木得到中调色 → 微调色相 → `--colors` 喂进去即可。
- 门/活板门/栅栏门/木板是四套不同贴图，**别指望一张改出四套**，各取各的底图。

## 2. 生物：模型 / 贴图 / 寻路 三件事

### 2.1 模型 —— 抄 `LayerDefinition`，改尺寸或加部件

26.2 原版有 **171 个模型类**，且已按生物分目录（1.20.1 是平铺的，路径完全不同）：

```
net.minecraft.client.model.animal.cow.CowModel        ← 成年牛
net.minecraft.client.model.animal.cow.BabyCowModel    ← 幼年
net.minecraft.client.model.animal.cow.ColdCowModel    ← 寒冷变种
net.minecraft.client.model.animal.cow.WarmCowModel    ← 温暖变种
net.minecraft.client.model.animal.chicken.ChickenModel
net.minecraft.client.model.animal.equine.HorseModel ／ DonkeyModel
net.minecraft.client.model.animal.feline.AdultCatModel
```

查有哪些、以及某类的真实签名：

```bash
python 原版资源提取.py --ver 26.2 --list-classes net.minecraft.client.model.animal
python JarSig.py <原版jar> net.minecraft.client.model.animal.cow.CowModel --brief
```

**实测拿到的关键 API（26.2）**：

| 类 / 方法 | 签名 | 用途 |
|---|---|---|
| `CowModel.createBodyLayer()` | `static () → LayerDefinition` | 抄原版整套体型 |
| `CowModel.createBaseCowModel()` | `static () → MeshDefinition` | 只要骨架、自己改造 |
| `LayerDefinition.apply(...)` | `(MeshTransformer) → LayerDefinition` | **对整套模型做变换** |
| `LayerDefinition.create(...)` | `static (MeshDefinition, int xTexSize, int yTexSize) → LayerDefinition` | 用新贴图尺寸重新烘焙 |
| `LayerDefinition.bakeRoot()` | `() → ModelPart` | |
| `MeshTransformer.scaling(f)` | `static (float) → MeshTransformer` | **整体等比缩放** |
| `PartDefinition.addOrReplaceChild(...)` | `(String, CubeListBuilder, PartPose) → PartDefinition`；也有 `(String, PartDefinition)` 重载 | 加/换部件 |
| `PartDefinition.getChild(name)` | `(String) → PartDefinition` | 拿到原版某个部件（如 `"head"`） |
| `PartPose.offset/rotation/offsetAndRotation` | `static (f,f,f) / (f,f,f) / (6×f)` | 摆位 |
| `PartPose.translated / scaled / withScale` | `(f,f,f) / (float) / (float)` | 在已有姿态上微调 |

**三条改法，按改动量从小到大**：
1. **只换贴图**（最省）：模型完全用原版，只提供自己的 `textures/entity/<你的生物>.png`。
   生物渲染器指向你的贴图即可 —— 换皮不换形。
2. **整体缩放**：`CowModel.createBodyLayer().apply(MeshTransformer.scaling(1.4f))` —— 巨牛/迷你牛。
3. **加部件**：`createBaseCowModel()` → `getChild("head").addOrReplaceChild("horn", CubeListBuilder..., PartPose.offset(...))`
   —— 在原版体型上长角/加装饰。改完记得同步贴图 UV 分区（见 `代码片段.md` §16）。

> 动手前先跑 `scripts/实体模型预览.py` 建基线：**脚底必须落在模型坐标 y=24**，UV 与贴图分区硬绑定。

## 5. 一个必须知道的版本差异：混淆

| 版本 | 原版类 | 资源（贴图/模型/数据包/语言） |
|---|---|---|
| **1.20.1 及以前** | **带混淆**（类躺在 `a/b/c` 之类包里，`net/minecraft/` 下只剩 25 个）→ **类名不可照搬**，要经 mappings 反查 | **照抄没问题** |
| **26.1+** | **无混淆**，`net/minecraft/` 下 10000+ 个真实类名 → `JarSig.py` 直接查签名 | 照抄没问题 |

**结论：无论哪个版本，资源随便抄；类名只在 26.1+ 能直接抄。**
要在 1.20.1 上抄类，得先看 26.1+ 的同名类确认名字，再用双工作区对照法落到 1.20.1 的写法。

`原版资源提取.py --scan` 会直接标出每个 jar 是"类名混淆"还是"无混淆"。

## 7. 把原版容器"接"到自己的数据上：别继承 `SimpleContainer`（2026-09-28 实战）

做自定义背包 / 仓库 / 任何"界面背后是自有数据结构"的容器时，需要一个
`Container` 桥把 `Slot` 的读写转发到自己的列表上。**直觉是继承 `SimpleContainer`
只覆写 `getItem` / `setItem` —— 这是错的，会得到一个"只能看、不能动"的容器。**

### 为什么错

`SimpleContainer` 自带一份**私有的 `items` 影子列表**，而 `Slot` 的关键路径
**不走** `getItem` / `setItem`：

| 玩家动作 | 走的方法 |
|---|---|
| 拿起物品 | `Slot.remove()` → `container.removeItem(slot, n)` |
| 放入 | `container.addItem()` / `removeItemNoUpdate()` |
| 清空 / 判空 | `container.clearContent()` / `isEmpty()` |
| 最大堆叠 | `container.getMaxStackSize()` |

只覆写 `getItem`/`setItem` 的后果：**界面显示正常**（读走覆写版），
但一拿起物品 `removeItem` 命中的是那个**永远空的影子列表** → 返回空栈、原格子不动。
症状就是"物品放不进去 / 拿不出来"，而且**不报任何错**。

### 正确做法：直接 `implements Container`

`Container` 是接口，抽象方法只有 8 个，全部转发到自己的列表即可，只有一份真相。
必须覆盖的（含两个易漏项）：

```java
public class MyContainer implements Container {   // ← 不是 extends SimpleContainer
    private final List<ItemStack> backing;
    private final int offset;        // 本视图在 backing 里的起点
    private final int visibleSize;   // 本视图铺几格

    private int real(int i) { return (i < 0 || i >= visibleSize) ? -1 : offset + i; }

    @Override public int getContainerSize() { return visibleSize; }
    @Override public boolean isEmpty() { for (int i=0;i<visibleSize;i++) if(!getItem(i).isEmpty()) return false; return true; }
    @Override public ItemStack getItem(int i)   { int r=real(i); return (r<0||r>=backing.size()) ? ItemStack.EMPTY : backing.get(r); }
    @Override public ItemStack removeItem(int i, int n) { /* 手写 split(n)，空则置 EMPTY */ }
    @Override public ItemStack removeItemNoUpdate(int i) { /* 取出并置 EMPTY */ }
    @Override public void setItem(int i, ItemStack s) { /* 必要时先把 backing 补长 */ }
    @Override public void setChanged() { }            // 真相在 backing，无独立脏标记
    @Override public boolean stillValid(Player p) { return true; }
    @Override public void clearContent() { /* 逐格置 EMPTY */ }
    @Override public int getMaxStackSize() { return 64; }   // ⚠️ 见下
}
```

### 两个容易漏的点

1. **`getMaxStackSize()` 的接口默认值是 `99`，不是 64。**
   `SimpleContainer` 返回 64，所以"从上一版继承改成 implements"时这个会**静默从 64 变 99** ——
   表现为"堆叠上限被改了"，普通物品能叠到 99。**必须显式 `return 64;`**（或按物品取 `stack.getMaxStackSize()`）。
2. **`clearContent()` 来自 `Clearable` 父接口**，不在 `Container` 的前 8 个方法里，容易漏。
   `Container` 声明：`extends Clearable, Iterable<ItemStack>, SlotProvider, ContainerExtension`。

### 配套：写回时**不要**裁掉尾部空槽

多页容器里，`save()` 若按"去掉尾部 EMPTY"收缩列表，会踩这个坑：
玩家在第 2 页放了东西、第 1 页大半是空的 → 关掉第 1 页触发收缩 →
**第 2 页整段内容消失**。格子位置由下标表达，写回只需保证"覆盖到的最大下标以内都写入"，
长度不足就补长，**绝不主动变短**。

### 自检脚本要做"真解析"

写版面/槽位下标自检时，**不要把自己那几个常量抄一份进脚本** ——
抄一份的话，改了源码脚本照样绿（"检查它自己以为的布局"）。
要从源码里解析常量（`+ - * /` 与常量互相引用用 AST 求值），解析不了就**报错而不是跳过**。
并且**注入坏样本验证它真会报**：把第二个方块区的 X 挪到贴着第一个区，确认脚本报出重叠。

## 8. 自定义 `MenuType` 的**槽位数必须两边算得一样**（2026-09-29 实战，最高危）

做自定义容器界面时最容易踩、后果最严重的一类 bug：**客户端和服务端各自
`new` 一份菜单，两边算出的槽位数不一致 → 服务端的内容包在客户端一解析就越界 → 当场断线。**

### 崩溃长什么样

```
[Render thread/ERROR] Failed to handle packet
  ClientboundContainerSetContentPacket[containerId=4, stateId=1, items=[…126 项…]]
java.lang.IndexOutOfBoundsException: Index 73 out of bounds for length 73
  at AbstractContainerMenu.getSlot
  at AbstractContainerMenu.initializeContents
  at ClientPacketListener.handleContainerContent
Client disconnected with reason: 网络协议错误
```

特点：**不生成 crash-report**（走的是"网络协议错误"断线路径），只在 `logs/latest.log`
里留一段堆栈。用户只会说"崩了"。**排查第一步永远是 `tail logs/latest.log` 找
`ClientboundContainerSetContentPacket` 那行，数一下 items 有几项。**

### 为什么会两边不一致

`ClientboundContainerSetContentPacket` 的 items 数组长度 = **服务端菜单的槽位数**，
客户端拿它去 `menu.getSlot(i)` 逐项填。所以铁律是：

> **服务端菜单的 `slots.size()` 必须 == 客户端菜单的 `slots.size()`。**

而客户端菜单是**客户端自己 new 的**（`MenuType` 的工厂在两边都会跑），
它拿不到服务端的数据。任何让槽位数**依赖"内容量"**的写法都会分叉：

```java
// ❌ 错：槽位数依赖 usedSize
private static int visibleSlots(int usedSize, int capacity, int offset) {
    if (unlimited(capacity)) return Math.max(usedSize - offset, PAGE_SIZE);
    ...
}
```
- 服务端：`usedSize` = 真实内容长度（比如 106）→ 菜单 127 槽
- 客户端：自己的数据副本是**空的**（`slots(player)` 返回 `new ArrayList<>()`）
  → `usedSize=0` → 菜单 73 槽
- 差 54（正好一页）→ 越界

**修法：槽位数只依赖「容量 / 页号」这类两边都能算出来的量。**

```java
// ✅ 对：只依赖 capacity / offset
private static int visibleSlots(int capacity, int offset) {
    if (unlimited(capacity)) return PAGE_SIZE;          // 满级 = 每页恒定 N 格
    return Math.max(0, Math.min(PAGE_SIZE, capacity - offset));
}
```
"无限容量"要表达成**页数无限**（`pageCount` 返回 `Integer.MAX_VALUE`），
**不是**"单页越来越长"。

### 配套：页号必须随「打开」送到客户端

`MenuType.MenuSupplier` 只给得到 `(containerId, playerInventory)`，**传不了页码**，
所以客户端永远按第 0 页建菜单（症状：翻到第 3 页，标题/标签还是第 1 页的）。

用 NeoForge 的 `IMenuTypeExtension.create(IContainerFactory)` —— 它能拿到
`RegistryFriendlyByteBuf`：

```java
// 注册端
MENUS.register("my_menu", () -> IMenuTypeExtension.create(
        (containerId, playerInventory, extraData) -> {
            int page = extraData != null && extraData.isReadable() ? extraData.readVarInt() : 0;
            return new MyMenu(containerId, playerInventory, page);
        }));

// 服务端开界面
player.openMenu(provider, buf -> buf.writeVarInt(page));
```

### 别忘了玩家背包本身

自定义容器界面若只放 `hotbar`（9 格）而漏了**主背包 27 格**，
玩家就拿不到自己背包里的东西 —— 用户会描述成"玩家背包显示不对"。
正确次序（照原版箱子）：**容器格 → 中间段 → 主背包 27 → 快捷栏 9**，
玩家槽位永远排在 `slots` 末尾，`quickMoveStack` 里用
`playerStart = slots.size() - 36` 定位，别写死"末尾 9 个"。

```java
// 主背包：Inventory 下标 9..35
for (int row = 0; row < 3; row++)
    for (int col = 0; col < 9; col++)
        addSlot(new Slot(playerInventory, 9 + row * 9 + col, x + col * 18, y + row * 18));
// 快捷栏：Inventory 下标 0..8
for (int i = 0; i < 9; i++) addSlot(new Slot(playerInventory, i, x + i * 18, hbY));
```

### 把这条写进自检脚本（强烈建议）

在槽位自检里加一条**回归守卫**，断言 `visibleSlots` 的参数里不许出现
`used / size / content / count / len` 这类语义：

```python
m = re.search(r"private\s+static\s+int\s+visibleSlots\s*\(([^)]*)\)", text)
params = [p.strip() for p in m.group(1).split(",")]
bad = [p for p in params if re.search(r"used|size|content|count|len", p, re.I)]
if bad:
    fail("visibleSlots 参数里出现内容量 %s —— 客户端/服务端会算出不同槽位数，必断线" % bad)
```
再补一条：`this.visible = ...` 的算式里不许出现 `backing` / `slots()` / `.size()`。
**注入坏样本验证它真会报**（把 `usedSize` 参数加回去，确认报 2 处后还原）。

### 一句话

> 自定义菜单的槽位数是**客户端与服务端之间的一份隐式契约**。
> 只要它依赖任何"只有一边知道"的量（尤其内容长度），就一定会崩。
> **判据：让槽位数成为 `(capacity, page)` 的纯函数。**
