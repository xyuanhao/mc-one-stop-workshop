# 26.x 客户端按键系统改造（组合键 / 按键扩容 / 屏蔽按键）

> 适用 26.1 / 26.2（两个版本已用 javap 逐字段比对，结构完全一致）。
> 典型需求：「模组太多键位不够用」「想给按键加个修饰键条件」「屏蔽某个键」。

## 一、结构速查（26.1 实测）

```java
public class net.minecraft.client.KeyMapping implements Comparable<KeyMapping> {
  private static final Map<String, KeyMapping> ALL;                                   // name → 映射
  private static final Map<InputConstants.Key, List<KeyMapping>> MAP;                 // 物理键 → 该键上的映射
  private final String name;
  private final InputConstants.Key defaultKey;
  private final KeyMapping$Category category;
  protected InputConstants.Key key;      // ← 当前绑定。注意是 protected，不是 private
  private boolean isDown;
  private int clickCount;
  private final int order;

  public static void set(InputConstants.Key key, boolean state);   // 按住 / 松开
  public static void click(InputConstants.Key key);                // 点按计数 ++
  private static void forAllKeyMappings(InputConstants.Key key, Consumer<KeyMapping> operation);  // ★ 唯一分发点
  public static void setAll(); public static void releaseAll();
  public boolean isDown(); public boolean consumeClick(); public void setDown(boolean);
  public boolean isUnbound(); public String saveString();
  public static KeyMapping get(String name);
  // ⚠ 26.1 起没有 getKey()，只有 getDefaultKey()
}
```

`KeyMapping$Category` 是 record，`register(Identifier)` 创建。

## 二、唯一注入点：forAllKeyMappings

`set()`（按住/松开）和 `click()`（点按计数）**都**把各自的 lambda 交给 `forAllKeyMappings`
去遍历 `MAP.get(key)`。所以：

> 注入这一个点，按住/松开 + `consumeClick()` 计数语义**同时**正确，
> 完全不用碰 `isDown` / `clickCount` 这些内部状态。

```java
@Mixin(KeyMapping.class)
public class KeyMappingMixin {
    @Shadow private static Map<InputConstants.Key, List<KeyMapping>> MAP;

    @Inject(method = "forAllKeyMappings", at = @At("HEAD"), cancellable = true)
    private static void xxx$forAll(InputConstants.Key key, Consumer<KeyMapping> op, CallbackInfo ci) {
        if (!shouldIntercept(key)) return;              // 不干预时零开销，走原版
        List<KeyMapping> list = MAP.get(key);
        if (list != null) {
            for (KeyMapping km : list) {
                if (allows(km, key)) op.accept(km);     // 逐条决定放行
            }
        }
        ci.cancel();
    }
}
```

### 「同一个键分给多个功能」的判定模板

同一个物理键上可以挂多个 KeyMapping（原版允许，控制界面会标红冲突但能用）。
按下时它们本来会全部触发，用修饰键在时间上区分：

```java
public boolean allows(KeyMapping km, InputConstants.Key key) {
    List<Resolved> list = byMainKey.get(key);        // 该键上的组合键定义
    if (list == null) return true;                   // 不是组合键主键 → 原样放行
    for (Resolved r : list) {
        if (isPhysicallyDown(r.modifier())) {
            return km == r.target();                 // 修饰键按着 → 只归这一个功能
        }
    }
    return !targets.contains(km);                    // 没按修饰键 → 被接管的功能让路，其余照常
}
```

主键**不要从配置读**，读映射的实际绑定（`@Accessor`），否则配置与游戏设置会不同步。

## 三、四个必踩的坑

1. **`InputEvent.Key` 不可取消** —— 它没实现 `ICancellableEvent`（`InteractionKeyMappingTriggered` 才有）。
   想拦截按键只能是 Mixin，别指望事件。
2. **没有 `getKey()`** —— 26.1 只剩 `getDefaultKey()`。读「当前绑定」要开访问器：

   ```java
   @Mixin(KeyMapping.class)
   public interface KeyMappingAccessor {
       @Accessor("key") InputConstants.Key xxx$getKey();
   }
   ```
   因为 `key` 是 `protected`，`@Accessor` 能直接读；不推荐用 `saveString()` 反解字符串。
3. **修饰键判定别依赖事件顺序** —— 直接用 `InputConstants.isKeyDown(Window, int)` 问 GLFW 物理状态。
   `Key.getValue()` 对 `Type.KEYSYM` 就是 GLFW keycode，可直接传。无竞态。
4. **`@Shadow` 静态字段要在同一个 mixin 类里**，且 mixin 类里的 handler 也得是 `static`
   （目标是静态方法）。

## 四、两个必须补的兜底

- **tick 兜底**：原版在切窗口 / 开背包时会 `releaseAll()`，组合键驱动出来的按下状态会**卡住**。
  每 tick 检查：修饰键或主键任一离开按下状态 → `setDown(false)`。
- **重建索引**：如果缓存了「映射 → 主键」的索引，玩家在控制界面改键后索引就过期了。
  每 10 tick 用映射的**当前绑定**重建一次（几十条记录，开销可忽略），改动 0.5 秒内生效。

## 五、纯客户端 mod 三件套

- `@Mod(value = MODID, dist = Dist.CLIENT)`
- `xxx.mixins.json`：类只登记在 `"client"` 段，`"mixins"` / `"server"` 留**空数组**
- `neoforge.mods.toml`：`[[mixins]] config="xxx.mixins.json"`
- 遍历全部按键用 `Minecraft.getInstance().options.keyMappings`（public 数组），不必开访问器读 `ALL`

## 六、中文乱码（必踩）

`gradle.properties` 按 Java Properties 规范以 **ISO-8859-1** 读取，所以
`mod_name=组合键` 经 `expand` 插进 mods.toml 会变成 `ç»åé`（双重编码的 mojibake）。

两条都要做：

1. mods.toml 里 `displayName` 写**中文字面值**，不要用 `${mod_name}`；`mod_name` 保持 ASCII。
2. `build.gradle` 的 `generateModMetadata` 任务加 `filteringCharset = 'UTF-8'`
   （模板里的中文描述也靠它保住）。

验收：`python -c "import zipfile;print(zipfile.ZipFile(jar).read('META-INF/neoforge.mods.toml').decode())"`
看 `displayName` 是不是正常中文。

## 七、交付前：注入契约静态检查

Mixin 依赖原版**内部**实现（private 方法、private 字段），**编译期验证不到**——
我们不直接调用它，所以编译一定过；运行期才崩，且崩在玩家机器上。

做法：用 javap 对目标 MC jar 做契约断言，并**双向验证**（注入坏样本确认脚本会报错，
否则脚本就是个永远返回通过的摆设）。

必断言项：
- `forAllKeyMappings` 存在、private static、签名 `(InputConstants$Key, Consumer)`
- `MAP` 仍是 `Map<InputConstants$Key, List<KeyMapping>>`（正则注意嵌套尖括号，别用 `[^>]*`）
- `key` 字段仍在且可见性没变成 private
- `InputConstants.isKeyDown(Window,int)` / `UNKNOWN` / `Options.keyMappings` 仍在

换 MC 版本时先跑它；也可以加 `--mc-jar` 参数对别的版本预检，判断产物能否平移。

## 八、版本下限该怎么填

玩家实例常停留在同小版本里更老的构建（如 `26.1.0.19-beta`），而编译默认取最新正式版
（`26.1.2.109`）。同小版本内 API 一致，所以：

- 编译目标：用 gradle 缓存里已有的最新构建（构建快）
- `versionRange`：**写死小版本下限** `[26.1.0,)`，一个产物覆盖全部 26.1.x
- 版本上限交给 `minecraft` 的 `[26.1,26.2)` 卡住，别自己放宽
