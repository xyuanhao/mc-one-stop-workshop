# 专用服务端自动化验证（RCON + 离线扫存档）

> 面向「写完了 mod，要证明它真的能跑」这一步。所有结论都在 **MC 26.1 / NeoForge 26.1.0.19-beta** 上实测过。
> 配套脚本：`scripts/rcon.py`（驱动命令）、`scripts/扫区域文件.py`（非破坏性统计）。

---

## 0. 为什么需要这套东西

`gradlew build` 成功只说明**编译通过**。数据包 JSON 能不能解析、维度会不会生成、
地物/结构会不会真的落进世界、传送门会不会真的传送——这些只有跑起来才知道。
而专用服务端没有玩家、没有画面，所以要用 **RCON 发命令 + 事后读存档** 来取证。

> 🔴 **前置：服务端 mods 目录必须先剔除「纯客户端 mod」**（2026-09-17 实测踩到）
>
> 拿一个做好的客户端实例去跑专用服务端时，**不要整个 `mods/` 拷过去**。
> 纯客户端 mod 在服务端会加载客户端 GUI 类直接崩，报：
> `Attempted to load class net/minecraft/client/gui/screens/Screen for invalid dist DEDICATED_SERVER`
> （实测：Oculus 光影 mod 就是这么把服务端炸掉的，`LoadingFailedException: Oculus (oculus) has failed to load correctly`）。
>
> **先排除这些**：光影/渲染（oculus、embeddium、iris）、小地图（xaero*）、
> 背包整理（inventory-profiles-next、libIPN、kotlinforforge）、鼠标/键位（mouse-tweaks、controlling）、
> 纯 HUD（appleskin、lighty、betterf3、item-highlighter、justzoom）、性能渲染（immediatelyfast、entityculling）。
>
> 判断依据：客户端 mod 的 `mods.toml` 里 `side="CLIENT"`；但**有些 mod 声明不规范**，
> 所以要靠上面这份经验清单兜底。注意 justzoom / betterf3 / mousetweaks 会自己优雅降级并打日志
> （`Disabling ... since it's a client-side mod`），**不崩不代表没被加载**——真崩的是不声明 `side` 的那些。
>
> 顺带：**只有真崩了才说明问题**。如果你之前用筛选过的子集跑成功、这次用全量崩了，
> 先怀疑是自己拷多了，别怀疑 mod 包坏了。

## 1. 起服务端前：三个会静默坑死你的前置

### 1.1 空转暂停（最坑，必改）

`server.properties` 默认 `pause-when-empty-seconds=60`。**没有玩家 60 秒后整个服务端暂停**，
世界 tick 全停：猪不会走、传送门不会传、地物不会长、随机 tick 不跑。
此时你用 RCON 做的一切**实体/时间相关**验证都会得到"没反应"的假结果，而且日志只有一行：

```
[Server thread/INFO]: Server empty for 60 seconds, pausing
```

```properties
pause-when-empty-seconds=0     # 做自动化验证时必须关
```

> 方块/区块的即时操作（setblock / fill / place / 区块生成）不受影响，所以很容易误判成"逻辑有问题"。
>
> ✅ **2026-09-12 起不用手动改了**：`scripts/新建工程.py` 生成的 `run/server.properties` 已经默认带上
> `pause-when-empty-seconds=0` + `enable-rcon` + `max-tick-time=-1`，新建的工程可以直接跑 RCON 验证。

### 1.2 残留 java 进程会锁死世界

反复 `gradlew runServer` 而不正常退出，会留下一串 java 进程，
下一次启动直接崩在：

```
java.io.IOException: 另一个程序已锁定文件的一部分，进程无法访问。
    at net.minecraft.world.level.storage.LevelStorageSource$LevelStorageAccess.createLock
```

每次起服务端前先确认没有残留（只杀 runServer/runClient 那几条，别杀 Gradle daemon）：

```powershell
Get-CimInstance Win32_Process -Filter "Name='java.exe'" |
  Where-Object { $_.CommandLine -like "*runServer*" -or $_.CommandLine -like "*runClient*" -or $_.CommandLine -like "*fml.modFolders*" } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

### 1.3 世界锁 / 想干净复跑

`run/world` 是开发用世界，想每次从零生成就 `mv run/world run/world_bak_$(date +%H%M%S)`（**别在服务端还开着时删**）。
世界目录结构在 1.21.9+ 是 `run/world/dimensions/<ns>/<dim>/region/*.mca`，
主世界是 `run/world/dimensions/minecraft/overworld/region/`。

### 1.4 🔴 独立服务端（Forge 安装器产出的那种）怎么启动（2026-09-18 实测）

前面几节讲的是开发环境（`gradlew runServer`）。**验证整合包**用的是另一种：
从 Forge 安装器装出来的独立服务端目录（含 `libraries/` / `mods/` / `config/` /
`user_jvm_args.txt` / `run.bat` / `run.sh`）。这个场景下**两个官方脚本都不好用**：

| 脚本 | 问题 |
|---|---|
| `run.sh` | 引的是 `unix_args.txt`，里面 classpath 用 **`:`** 分隔。在 **Windows + Git Bash** 下 java 直接报<br>`Error occurred during initialization of boot layer`<br>`java.nio.file.InvalidPathException: Illegal char <:> at index 70: libraries/cpw/mods/bootstraplauncher/...jar:libraries/...` |
| `run.bat` | ① 用**裸 `java`**（依赖 PATH）；② 末尾有 **`pause`** → 等 stdin，自动化里会挂住；③ 用 `cmd //c "run.bat nogui"` 起时**可能 284ms 就"完成"且没有任何输出**（静默失败，最坑） |

**✅ 正确姿势：直接调 java + `win_args.txt`（Windows 路径分隔符已是对的）**

```bash
cd <服务端目录>
java @user_jvm_args.txt @libraries/net/minecraftforge/forge/<MC>-<FORGE版本>/win_args.txt nogui
```

**配「起 → 等 → 优雅停」的一次性自动化**（注意 `stop` 要等它启动完再喂）：

```bash
# 120 秒后喂 stop；服务端读到 stop 会走正常关闭流程，日志里能看到 "Stopping server"
(sleep 120; echo "stop") | java @user_jvm_args.txt \
    @libraries/net/minecraftforge/forge/1.20.1-47.4.23/win_args.txt nogui \
    > logs/_verify.txt 2>&1
```

**🔴 三个必须注意的坑**：

1. **别 grep `logs/latest.log` 当"本次结果"** —— 它可能是**上一轮**的（本次就差点被
   `Done (4.059s)` 骗过去，那行是几十分钟前那次跑出来的）。要**自己重定向到本次专用文件**
   （上面 `> logs/_verify.txt`），或先记录 `latest.log` 的行数/时间戳再对比。
2. **后台启动"瞬间完成"不等于成功**。`run.bat` 那次返回 284ms、输出为空，
   真实情况是根本没跑起来。**判据只能是日志内容**，不是退出码、不是"命令返回了"。
3. **🔴 改过 `config/` 就必须重跑 `同步验证服务端.py`，而且要核对任务数**（见 §0 前置）。
   漏同步的后果**不是"不执行"，而是"用旧副本执行、照样 `Done`"** —— 这是**静默假通过**：

   - 实测（2026-10-01）：本地任务书已写到 **92** 个任务（新增 1 条 + 改 21 处文案），
     但服务端报的是 `Loaded 5 chapter groups, 13 chapters, 91 quests`，`Done (1.083s)`
     一切正常。**只 grep `Done` 就会收工，这次改动等于没验。**
   - **判据：验证输出里的 `N quests` / `N chapters` 必须等于你刚写进去的数量。**
     数字对不上 → **先怀疑没同步，而不是先怀疑文件写错了**。
   - 自检顺序：`grep -c "<新任务id>" server/config/ftbquests/quests/chapters/*.json5`
     —— 服务端那份里查不到新 id，就是没同步，别急着改任务书。

   > 为什么容易漏：手动 `cp` 了 jar 到 `server/mods/` 之后，会**误以为"服务端已经是最新的"**。
   > jar 和 config 是两条独立的同步线，`同步验证服务端.py` 一次管两条。

**验收要看的两行**（`Done` 只代表服务端起来了，任务书是之后单独加载的）：

```bash
grep -n "Done ("                        logs/_verify.txt   # Done (3.771s)! For help, type "help"
grep -n "Loaded .* chapter groups"      logs/_verify.txt   # Loaded 6 chapter groups, 12 chapters, 84 quests
grep -n "Stopping server"               logs/_verify.txt   # 优雅关闭，说明 stop 被正常处理
```

> ⚠️ **`Done` 之后还可能炸**：FTB Quests 在 `ServerStartedEvent` 里加载任务书，
> 非法 id 会在这里抛异常 → `Exception in server tick loop`。
> **看到 `Done` 不能收工，必须继续往后看有没有异常**（详见 SKILL.md「任务书 item id 非法」专章）。

## 2. RCON 驱动

`server.properties`：

```properties
enable-rcon=true
rcon.port=25575
rcon.password=devtest
```

```bash
python scripts/rcon.py "datapack list" \
                      "execute in otherworld:otherworld run locate biome otherworld:ashen_waste"
```

**语法别去翻反编译源码，先问游戏自己**：`/help <命令>` 会直接列出参数形态，
RCON 也一样管用（`python scripts/rcon.py "/help loot" "/help place"`）：

```
/loot spawn <targetPos> (fish|loot|kill|mine)      ← 位置在前，"loot <表>" 在后
/place template <template> [<pos>]                 ← 直接放结构模板（走 pos 所在区块）
/place structure <structure> [<pos>]
/place jigsaw <pool> <target> <max_depth> [<position>]   ← target 必须是起始部件上真实存在的 jigsaw 名
```

取一件战利品表的东西（无玩家时最好用的验证手段）：

```
/loot spawn ~ ~ ~ loot <命名空间>:chests/<表名>     # 掉落物直接进世界
/loot give @s loot <命名空间>:chests/<表名>         # 直接进背包
```

要点：

- **`execute in <维度>` 只对位置类操作生效**（setblock / fill / place / forceload / locate 都会正确切维度）。
- **实体选择器别指望它切维度**：`execute in otherworld run kill @e[type=pig]` 会杀到主世界的猪。
  跨维度判实体要用 **`positioned` + `distance`**：
  ```
  execute in otherworld:otherworld positioned 0 86 0 run data get entity @e[type=minecraft:pig,distance=..64,limit=1] Pos
  ```
  这条能证明"猪在彼岸的 (0,86,0) 附近"；换成主世界坐标查不到就说明它真的过去了。

### 2.1 ⭐ 长响应会被**分包**，`rcon.py` 必须循环收包（2026-10-03 实测）

一条命令的输出超过 **4096 字节**就会被拆成多个包依次发。`rcon.py` 早期只收一个包，
于是 `attrlevel rules` 这种"dump 一整套 JSON"的命令**被静默腰斩** ——
截断点落在 JSON 中间（实测第 182 行），看起来像"服务端只答了一半"，
极容易误判成 mod 的 bug 而去查一个根本不存在的问题。

```
包1: type=0 payload_chars=4036 payload_bytes=4096   ← 满包
包2: type=0 payload_chars=1652 payload_bytes=1652   ← 余数，结束
```

两个必须记住的点：

- **终止条件是「这一包不足 4096」**，**不能**写成"一直读到空包为止"。
  原版对不足一满包的响应**不会**再补终止包，那样写会一直等到 socket 超时；
  而短输出/空输出恰好都是单包，所以"不足一满包"这个判据同时也兜住了它们。
- 🔴 **按字节判、不按字符判。** 实测服务端就是**按字节**切的：含中文的那一包正好
  4096 字节，但解码出来只有 4036 个字符。第一版按 `len(解码后的字符串)` 判，
  于是把满包误判成末包，照样腰斩 —— 而且"看起来已经修好了"（短命令正常、长命令还是断）。
  正解：让收包函数**直接返回 bytes**，长度比较与拼接都在字节层做完，最后再整体解码。

**定位这类问题的通用手法**：连上后逐包打印 `类型 / payload 字节数 / payload 字符数`。
一眼就能看出服务端到底发了几个包、每包多大、边界是按字节还是按字符 ——
比盯着被截断的输出猜要快得多。

**另一种绕过办法**（不依赖上面这些）：**让服务端把长内容写进文件，再离线读文件**。
例：要核对规则表就把当前规则 `rules_preset_save <名>` 落成
`config/<modid>/presets.json`，本地 `json.load` 读全量 —— 完全不受 RCON 行长与分包影响。
验证"服务端算出来的东西对不对"时，这条路通常比调 RCON 更省事、更可靠。

## 3. `/place` 系列命令的致命局限（验证结构时的头号误判源）

`/place structure` 和 `/place jigsaw` 内部都是
`StructureStart.placeInChunk(..., new ChunkPos(pos))` —— **只写 `pos` 所在那一个区块里的部件**。
一个村庄 6×6 区块，你看到的就是 1~2 栋房子；神庙如果落在别的区块，**根本不会被写进世界**，
于是你"扫遍全场也没有神庙"，得出完全错误的结论。

**结论：结构/模板池注入不要用 `/place` 验证，要用自然生成。**

顺便记几个别踩的坑：

| 现象 | 真因 |
|---|---|
| `place jigsaw <池> minecraft:empty 7 <pos>` → `Failed to generate jigsaw` | `target` 必须是**起始部件上真实存在的 jigsaw 名**，村庄里用 `minecraft:building_entrance`（原版池用 `minecraft:bottom` 也行）；填 `minecraft:empty` 必失败 |
| `place structure` 报 `That position is not loaded` | 该区块没加载。`/forceload add` 是**按方块坐标**给的（`forceload add 32 32 160 160` → 区块 [2,2]~[10,10]），单次上限 **256 区块** |
| 模板池元素权重写 2000 → 启动崩 | `weight` 合法范围 **`[1:150]`**（`Value 2000 outside of range [1:150]`） |

## 4. 非破坏性统计：怎么数方块才不会把方块数没

**别用 `/fill ... air replace <方块>` 当计数器**——它是把方块换成空气，数一遍删一遍。
同一片区域第二次统计必然是 0，会让"到底有没有生成"彻底失真（这个坑真的会骗到自己）。

可行的三种：

1. **读存档（首选）**：`python scripts/扫区域文件.py run/world otherworld:ashen_brick minecraft:bell`
   直接解压 `.mca` 里的区块 NBT 找方块名，只读文件、绝对安全，还能给出区块坐标。
   （`.mca` 表项是 **3 字节大端偏移 + 1 字节扇区数**，别按 4+1 读，会错位读到 0 个区块。）
2. **挖掉再数**：`fill ... air replace <方块>` 只在"数完就清理"的场合用，别当计数工具复用。
3. **反查 `if block`**：`execute if block <x> <y> <z> <方块>`，点位少时最直观。

统计前先 `/save-all flush`，否则新生成的区块还在内存里，磁盘上扫不到。

## 4.5 没有玩家时，怎么证明注册真的成功（实测）

**别用 `/give @a <物品>`** —— 服务端一个玩家都没有时，选择器 `@a` 先失败并返回
"没有找到玩家"，你根本不知道那是"物品不存在"还是"没人可给"。这个验证是无效的。

改用 **`/summon` 一个带 NBT 的物品实体**，让游戏自己去查这个 id：

```
summon minecraft:item 0 100 0 {Item:{id:"<命名空间>:<物品id>",Count:1b}}
```

| 返回 | 含义 |
|---|---|
| `Summoned new 未来眼镜`（显示名） | ✅ 物品 id 已注册，**且 `lang` 里的显示名也生效了** |
| 报 `Unknown item` / 召唤出空气 | ❌ 注册没成功，或 id 拼错 |

这一个命令同时验掉了**注册**和**本地化**两件事，比翻日志靠谱（日志不报错 ≠ 注册对了）。

同理推广：

| 要验什么 | 命令 |
|---|---|
| 实体类型注册 | `summon <ns>:<实体id> 0 100 0` |
| 方块注册 | `setblock 0 100 0 <ns>:<方块id>` |
| 配方加载 | 对比启动日志的 `Loaded N recipes`（原版基线 + 自己加的条数） |
| datapack 函数 | `function <ns>:<函数名>` |
| 标签内容 | `execute if entity @e[type=#<ns>:<标签>]` |

> 记完就清理：`kill @e[type=minecraft:item]`（上面那个实体还留在世界里）。

## 4.6 验证「玩家行为触发」类模组：用调试命令代替假人（26.1 实测）

连锁挖矿、自动种植、右键交互这类模组，触发点是**玩家的手部动作**，
而专用服务端没有玩家输入通道。踩过一圈坑之后的结论：

**别去折腾假人实体，直接给模组加一条调试命令。**

### 走过的弯路（都别试）

| 尝试 | 结果 |
|---|---|
| `summon minecraft:display` 造假人 | ❌ 26.1 已**移除** Display 实体，报 `Can't find element 'minecraft:display'` |
| `/ride` 自骑乘推动实体撞进方块 | ❌ 无效，`vehicle` 查询为空 |
| `tp` 实体进方块触发破坏 | ❌ 26.1 `Player.isStayingOnGroundSurface()` **就是 `isShiftKeyDown()`**，非潜行时 `maybeBackOffFromEdge` 会把它挡住 |
| `data merge entity {pose:"sneaking"}` | ❌ 服务端每 tick 由 `updatePlayerPose()` 重算，立刻被改回 `standing` |
| 服务端塞一个真玩家 | ❌ 专用服务端没有可编程的客户端输入 |

### 正确做法：加一条会构造事件的调试命令

> ⚠️ **类名随版本变**：26.1.0.x 是内部类 `BlockEvent.BreakEvent`，
> **26.1.2 起改成独立类 `net.neoforged.neoforge.event.level.block.BreakBlockEvent`**。
> 本文示例统一按 26.1.0.x 写，26.1.2+ 请自行替换类名与 import。
> 详见 `版本差异矩阵.md` §9.3 ⑨。

命令的作用是**手动构造一次破坏事件（`BlockEvent.BreakEvent` / `BreakBlockEvent`）并交给模组的处理入口**，
走的是和玩家真实操作**完全同一条代码路径**，覆盖处理函数的全部判断分支。

```java
public static LiteralArgumentBuilder<CommandSourceStack> build() {
    return Commands.literal("modid")
            .requires(source -> source.permissions().hasPermission(Permissions.COMMANDS_GAMEMASTER))
            .then(Commands.literal("break")
                    .then(Commands.argument("x", IntegerArgumentType.integer())
                            .then(Commands.argument("y", IntegerArgumentType.integer())
                                    .then(Commands.argument("z", IntegerArgumentType.integer())
                                            .executes(ctx -> { /* 构造 BreakEvent 并处理 */ })))));
}
```

注册：

```java
@SubscribeEvent
public void onRegisterCommands(RegisterCommandsEvent event) {
    event.getDispatcher().register(MyCommand.build());
}
```

**控制台执行时没有 `ServerPlayer`** —— 用 NeoForge 的假玩家顶上：

```java
FakePlayer fake = FakePlayerFactory.getMinecraft(level);   // 传 ServerLevel 取一个
fake.setShiftKeyDown(true);                                 // 满足「需潜行」的判定
fake.setItemSlot(EquipmentSlot.MAINHAND, new ItemStack(Items.IRON_PICKAXE));  // 满足「需手持工具」
fake.setPos(x + 0.5, y, z + 0.5);
```

`FakePlayer extends ServerPlayer`，所以 `instanceof ServerPlayer` 检查、`player.gameMode`
全部照常可用，`isFakePlayer()` 也能识别。

### ⚠️ 26.1 权限 API 已重构（编译期就会撞上）

`CommandSourceStack.hasPermission(int)` **被删除**。26.1 换成了 `PermissionSet` 体系：

```java
// 旧写法（26.1 编译不过：找不到符号 hasPermission(int)）
.requires(source -> source.hasPermission(2))

// 26.1 正确写法
.requires(source -> source.permissions().hasPermission(Permissions.COMMANDS_GAMEMASTER))
```

对应关系：原等级 2 ≈ `Permissions.COMMANDS_GAMEMASTER`。
另有 `COMMANDS_MODERATOR` / `COMMANDS_GAMEMASTER` / `COMMANDS_ADMIN` / `COMMANDS_OWNER`
（包 `net.minecraft.server.permissions`）。
`CommandSourceStack` 的方法变成 `permissions()` / `withPermission(PermissionSet)`。

### 🔴 递归陷阱：`destroyBlock` **确实会**发 `BreakEvent`（本次最贵的坑）

这是**真实 bug，不只是测试问题** —— 玩家实机挖方块同样会栈溢出。

```
handle() → gameMode.destroyBlock(pos) → CommonHooks.fireBlockBreak()
         → BlockEvent.BreakEvent → 自己的监听器 → handle() → ... 无限递归
         → java.lang.StackOverflowError
```

堆栈关键字（一眼认出）：

```
at .../CommonHooks.fireBlockBreak(CommonHooks.java:594)
at .../ServerPlayerGameMode.destroyBlock(ServerPlayerGameMode.java:270)
at .../myMod.MyHandler.handle(MyHandler.java:NN)
at .../myMod.MyMod.onBlockBreak(MyMod.java:NN)
```

**修法**：在调用 `destroyBlock` 的整段外面打重入标记，自己发起的那层事件直接放行。

```java
private static final ThreadLocal<Boolean> IN_PROGRESS = ThreadLocal.withInitial(() -> Boolean.FALSE);

public static void handle(BlockEvent.BreakEvent event) {
    if (Boolean.TRUE.equals(IN_PROGRESS.get())) {
        return;   // 这次破坏是我们自己链式发起的，交给原版流程
    }
    // ... 收集目标 ...
    IN_PROGRESS.set(Boolean.TRUE);
    try {
        for (BlockPos pos : targets) {
            gameMode.destroyBlock(pos);   // 它内部会再发事件，被上面这行挡住
        }
    } finally {
        IN_PROGRESS.set(Boolean.FALSE);   // 必须 finally，否则异常后永久卡死
    }
}
```

标记要**只包住 `destroyBlock` 循环**，不要把前置检查也包进去 ——
否则其他模组在事件里的正常工作会被误跳过。
其他模组的监听器**照常收到**这些事件，我们只是自己不再处理。

> 反汇编（javap）推断「不发事件」是**不可靠**的：`destroyBlock` 内部经 `CommonHooks`
> 转发，静态看字节码很容易漏。**必须实机跑一次才算数。**

### 验证脚本的两个必备细节

1. **穿 tick 边界再统计**。破坏在主线程异步完成，`RCON` 发完命令立刻查方块状态
   会拿到**旧值**，表现为「明明破坏了却查到还在」。

   ```python
   rc.cmd("chainmine break 0 -60 0")
   rc.cmd("time query gametime")   # 同步点：确保跨过一个 tick
   time.sleep(0.5)
   # 现在再统计才准
   ```

2. **正负样本都要做**。只测「能连锁」证明不了判定在工作，也要测「不该连锁的确实没连锁」：
   - 混入不同方块（石头堆里嵌泥土）→ 泥土必须留着
   - 混入黑名单方块（石头堆里嵌箱子）→ 箱子必须留着
   - 对空气触发 → 必须被拒绝且不报错

   本次两个脚本：`tools/verify_chain.py`（正）、`tools/verify_negative.py`（负），
   最终 4/4 + 1/1 全过才算收工。

### 4.6.1 更进一步：只读探针（2026-09-30 分类判据实测）

上面那套是「调试命令**构造事件**」——会真的改世界，跑一次就得复位。
如果被测的只是**一段判定逻辑**（什么算矿物、什么算木头、算不算同一类），
可以做得更轻：命令**只收集、不执行**，把中间结论打成一行。

```
/attrlevel probe <pos>          # 某坐标方块的分类结论 + 族键
/attrlevel probe_name <名字>     # 直接喂一个**名字**（不必真实存在这个方块）
/attrlevel chain <pos>          # 从这点出发会连锁到哪几块（只收集，不破坏）
```

好处是**能在同一个世界里反复试不同摆法**（3×3×3 矿脉 / 5×5×5 测上限 /
混不同矿种测同族过滤），不用复位、不用造假玩家。
连锁真正容易失控的地方（连太多、连错矿种、上限没生效）**全在收集这一步**，
后面的破坏只是一遍原版 API 调用。

实测一次跑完 **30 个方块 + 18 个名字 + 6 组连锁**，全程无人值守。

**三个设计要点**：

1. 🔴 **探针要分「查实体」和「查名字」两种**。有些判据的边界情况
   **在原版根本没有真实样本** —— 比如「名字里含 ore 却不是矿石」的方块一个都没有
   （`minecraft:forest_rock` 听着像，其实是**地形特征 feature**，`setblock` 会报
   `Unknown block type 'minecraft:forest_rock'`）。这种只能喂**臆想出来的字符串**，
   所以必须有 `probe_name` 这种直接吃字符串的入口。
2. **探针输出要能被正则稳定解析**（形如 `id -> ore=true log=false chainable=true family=...`），
   脚本直接断言；别让日志里混进颜色码或多余前缀。
3. **探针必须只读**。一旦它会改世界，就又回到"跑一次复位一次"的老路上了。

## 4.7 世界生成类：离线扫存档前的六道前置（2026-09-24 深渊实测）

自定义 chunk generator 的验证几乎只能靠**离线读 `.mca`**（`execute if block` 数上千个点位太慢）。
但下面每条都能让你读到"看着像数据、其实是假象"的结果，逐条对照。

### ① 判据必须先按 `Status` 过滤 —— 本次最贵的坑

区块 NBT 里 `Status` 不是 `minecraft:full` 的，**整列都是空气**（`structure_starts` / `features` 阶段）。
实测：289 个待检区块里 **135 个还停在 `structure_starts`**，被当成"竖井（空气柱）"计入，
竖井率虚报到 **93.8%**。

```python
if chunk.get("Status") != "minecraft:full":
    skipped += 1
    continue
```

> **推广（最重要的一条）**：「空竖井」和「没生成的区块」在方块层面**完全一样**。
> 一个分不清"没生成"和"特征不存在"的判据，**比没有判据更坏**——它会给你一个精确的错数字。
> 凡是"统计某物为空/存在"的判据，先问一句：**我凭什么确定这块数据是生成完的？**

### ② 采样点取区块正中的固定局部队列，别用 `gx & 15`

用 `lx = gx & 15` 会把采样点落到区块边缘，跨区块的特征（大范围竖井/洞穴）在边缘处
状态跳变，统计出来的比例毫无意义。统一取 `lx = lz = 8`（区块正中）。

```python
lx = lz = 8          # 固定列；不要 gx & 15
index = ((ly & 15) << 8) | (lz << 4) | lx
```

### ③ 横切的 y 要落在"特征真正存在的高度"，不是一个固定值

竖井、柱体这类特征只占局部高度。取"洞穴中段"会全是空气，取"地板往上 150 格"才切得到。
本次柱体抽查就是在地板往上 150 格处横切，七个层各自取自己地板的高度：

```
✔ 深界一层   y=  1646 实心  35/289 = 12.11%
✔ 最终之涡   y= -1882 实心  59/289 = 20.42%
```

### ④ 判据要断言**精确值**，不要用阈值

- 地表顶必须**恰好** `y == 2000`（生成器里有 ±24 的噪声起伏，用"2000 附近"这种阈值就检不出）
- 出生点必须**恰好** `(0, 2001, 432)`（主洞口那套地形；台地上、面朝洞）

```python
assert top_y == 2000, f"地表顶 = {top_y}，应为 2000"
assert (sx, sy, sz) == (0, 2001, 432)
```

阈值型判据（"跨度 < N""在 X 附近"）是假阴性的头号来源，能用**精确相等**就别用范围。

### ⑤ 存档路径与压缩标志（26.1 全变了）

| 项 | 26.1 实际情况 |
|---|---|
| 原版世界区域文件 | `world/dimensions/minecraft/overworld/region/r.X.Z.mca`（**不是** `world/region`） |
| 自定义维度 | `world/dimensions/<命名空间>/<维度名>/region/r.X.Z.mca` |
| `.mca` 表项压缩标志 | **`1 = gzip`，`2 = zlib`**（和直觉相反，别"先试 gzip 失败再 zlib"，会读半天才发现方向反了） |
| `level.dat` 出生点 | `Data.spawn = {pos:[x,y,z], dimension, yaw, pitch}`，**没有** `SpawnX/Y/Z` |

### ⑥ 数方块前的三件同步事

1. `/save-all flush` —— 新生成的区块还在内存里，不 flush 磁盘上扫不到（§4 已提）。
2. `/forceload add` 吃的是**方块坐标**，单条上限 **256 区块**。`forceload add -320 -320 320 320`
   = 641×641 方块 = **1681 区块** → 直接报 `Too many chunks`。要按方块坐标切成四块（如 `±160`）。
3. 报 `No chunks were marked for force loading` **不等于失败** —— 服务端内部已记着这些区块，
   重复调用是 no-op。另外 `server.properties` 里 `pause-when-empty-seconds=0`（§1.1）没改的话，
   空转暂停会让所有 tick 相关的验证全部失真。

## 4.8 「量某段结构有没有 / 在哪」的判据怎么写（2026-09-24 深渊主洞口实测）

§4.7 讲的是**前置**。这一节讲判据本身的四个反模式，以及采样区怎么准备。
每个都是"判据报错，但地形是对的" —— 这类假失败会让人去改对的东西。

### ① 未加载的区块 = `None`，绝不能当成"空气"

```python
def block_at(x, y, z):
    if chunk 读不到: return None      # ← 不是 'minecraft:air'！
def is_solid(x, y, z):
    b = block_at(...)
    return b is not None and b not in AIR
```

`is_solid` 对 `None` 返回 `False`，于是"没数据"和"是空腔"**读起来一模一样**。
实测：斜向 45° 的采样点在 (x,x) 那些区块里，而驱动脚本只 forceload 了十字条 ——
**8 个方向里 4 个齐刷刷报"没量到内壁"**，看起来像地形缺了四面墙，实际是没数据。

修法两条，必须都做：

1. **加一条 [0] 前置判据**，专测"每个采样点读不读得到"：

```python
missing = [f'第{i}层{k*45}°' for i, k in all_sample_points()
           if probe(axis, r, y) is None]
check(not missing, "8 层 × 8 方向的取样点都读到了数据", f"读不到的: {missing[:6]}")
```

2. **驱动脚本要 forceload 全套采样区**（十字条 + 两条对角线，见下 ⑤）。

> 推广：判据里**凡"扫出来是空的"结论，都必须先排除"没扫到"**。
> 函数不知道怎么区分时，就返回"扫到的条目数"，调用方见 0 直接报错退出。

### ② 「某一处采样」≠「这一层的性质」：采样高度要自适应

内壁顶端接在天花板底面，而天花板底面**随噪声起伏 ±100 格**。
在"空腔 85% 高处"量内壁，有相当比例落在内壁**上方**的空处（实测第 3 层
0°/90° 两个方向都这样），读成"没内壁"。

修法：**多高度取样，取最小值**。内壁是竖直的墙，各高度半径相同；
高于墙顶的高度返回 `None`、开口处第一个实心跑到墙外 —— 两者都只会让值
**偏大或缺失**，不会偏小，所以**最小值恒等于真实内沿**。

```python
best = None
for f in (0.25, 0.35, ..., 0.85):
    y = bottom + int((top - bottom) * f)
    for r in range(expect - 60, expect + 61):
        if solid_at(axis, r, y):
            best = min(best or r, r); break
```

### ③ 窗口别用固定偏移 —— 要锚在「结构自己决定的量」上

竖井判据第一版取 `[b+10, b+120]`（b = 岩板边界）。但岩板中心随噪声起伏 **±53**、
厚度 **21~99** —— **薄板的上表面能低到 b-60 以下**，半窗直接落空 → 判成"竖井"。
实测竖井率虚报到 **44.7% / 47.9%**（设计 14%），看着像"这一道墙没了"。

改成 `[b-320, b+150]` 立刻回到 **7.5%~16.7%**。
宽窗口本来担心把"岩板自己的悬石"算进来，但**悬石和柱子都要求本列有岩板才生成**，
真正的竖井列里什么都没有 —— 放宽是安全的。

> ⭐ 教训：**窗口要锚在"结构自己决定的量"上。** 这里的锚是"边界 y"，
> 但结构的中心是 `边界 + 噪声×53`、厚度是 `21~99` —— 结构自己能偏出窗口，
> 判据就一定不准。实在要锚，就把窗口按**结构可能出现的范围**定，别按"我觉得它在这"。

### ④ "实心区段的顶端" ≠ "地板顶"

地板上面立着柱子，同一列里地板和柱子是**连着的**，区间会并成一段 ——
量"这段的顶端"量到的是**柱顶**（实测第 2 层读出 1292，比名义边界高 300 格，
看着像"地板飘了"，其实只是柱子顶）。

修法：用**材质**定位。地板顶那一格铺的是该层专属的 floor 材质
（`MOSS_BLOCK` / `PODZOL` / `SCULK`…），柱子用的是另一种材质，
所以"找该材质出现的最高那一格"就是地板顶：

```python
FLOOR_MATERIAL = {1: 'minecraft:moss_block', 2: 'minecraft:podzol', ...}
top = next(y for y in range(bottom + 150, bottom - 180, -1)
           if probe(axis, r, y) == FLOOR_MATERIAL[i])
```

> 推广：**找"某个结构的面"时，优先找它独有的材质，而不是找"第一块实心"**。
> 材质是结构自己打的标记，位置怎么飘都跟着它走。

### ⑤ forceload 采样区：十字条 + 两条对角线（8 方向采样必备）

按 8 方向（每 45°）采样就要覆盖 (x,x) 和 (x,-x) 两类区块，
只 forceload 十字条会漏掉全部斜向（见 ①）。

```python
for k in range(-17, 18):                 # 半径覆盖到 272
    for (cx, cz) in ((k, k), (k, -k)):
        cmd(f'forceload add {cx*16} {cz*16} {cx*16+15} {cz*16+15}')
```

⚠️ **f-string 里多写逗号会静默阉掉整批命令**：

```python
f'forceload add {x,} {z} ...'   # ✗ 元组！服务端只回 "Expected integer"
f'forceload add {x} {z} ...'    # ✓
```

失败回显是 `Expected integer`，**不影响后续命令**，所以整批对角区块静默漏掉。
驱动脚本要**见到 `Expected` 就抛异常退出**，别让它继续往下跑。

### ⑥ 剖面自检：自己画图可以，但**先把 y 轴方向钉死**

判据只能证明"这一格是什么方块"，证明不了"洞口像不像漏斗、台阶露没露出来"。
所以交付前用 `numpy + PIL` 把存档渲成剖面图看一眼是对的，但：

- 图像第 0 行是 **y1**（高处）还是 y0？写成 `img[y - y0]` 图是**上下颠倒**的，
  而右侧 y 刻度是按"上=高"画的 → 图和数据对不上，**我会把台地看成洞底、
  把 70 格厚的地壳读成 293 格**。
- 渲染前**过滤 `Status != full`**，否则"没生成"会被画成"空腔"。
- 没登记颜色的方块画成品红并打印名字 —— 逼着自己补色表，否则"别的方块"
  在图上和"石头"一个样。
- 位打包解码（`block_states.data`）在 NumPy 2 下有个坑：
  `uint64 >> int64` 按 NEP 50 会**提升成 float64** → 报 `right_shift not supported`。
  移位量也要转 `uint64`：

```python
vals = np.array([int(v) & 0xFFFFFFFFFFFFFFFF for v in packed], dtype=np.uint64)
li = (np.arange(4096) // per_long).astype(np.uint64)
sh = ((np.arange(4096) % per_long) * bits).astype(np.uint64)
idx = (vals[li] >> sh) & np.uint64(mask)
```

### 6.1 血泪教训：别把被测条件自己消掉（实测踩过）

上面这套探针跑通**并不代表传送没问题**。真实踩坑记录：

> 为了能用 `positioned` + `distance` 查实体，我先在目标维度 `forceload add 0 0` 把出口区块加载了。
> 区块一加载，`level.getHeight(...)` 就返回真实地表（y≈86），猪漂亮地落在 y=87 —— 探针全绿。
> 但玩家实际操作时，**去彼岸的落脚区块从来没被加载过**，`Level.getHeight()` 在
> `hasChunk(...) == false` 时直接返回哨兵值 **`getMinY()`（-64）**：
> 于是"找地表"的逻辑从 y=-64 起往上试 12 格 → 得到 y=-52 → 门建在世界底部 →
> **玩家穿过门落在基岩层**，还得自己挖出来。

要点：

1. **`getHeight` 返回 `getMinY()`（或紧贴它的值）= "这个区块没加载"的明确信号**，不是真的地表。
   想要"未加载位置的地表"要用 `chunkGenerator.getBaseHeight(x, z, Heightmap.Types.WORLD_SURFACE_WG, level, randomState)`（走生成器，不需要区块）；
   或者先 `poiManager.ensureLoadedAndValid(level, pos, radius)` / `level.getChunk(x, z, ChunkStatus.FULL, true)` 再查。
   原版 `PortalForcer.findClosestPortalPosition()` 第一步就是 `ensureLoadedAndValid`，所以原版地狱门从不掉到地底。
2. **凡是"跨维度/远距离"的功能，验一遍"目标区块从未加载、从未去过"的情况**：
   新世界、不 `forceload`、不 `/tp` 预先踩点，直接走门进去，然后看落地 y。
3. **反模式自查**：当为了让某条验证命令能跑而必须先做一件事（forceload / tp / 预加载）时，
   想一想"这件事是不是正好把被测前提消掉了"——这是最容易骗过自己的那类错误：**探针通过，是因为探针改变了被测系统**。

## 7. 客户端侧单独验什么

服务端跑通 ≠ 客户端画得出来。客户端至少要看一遍日志里的资源告警：

```
gradlew runClient
grep -in "Unable to load model\|Missing model\|missing texture" run/logs/latest.log
grep -in "otherworld" run/logs/latest.log | grep -i "missing\|unable\|fail"
```

- 方块模型 / 贴图 / `items/*.json` 模型定义的问题**只会在客户端日志里出现**。
- 26.1 起渲染类型按贴图 alpha 自动判定（详见 SKILL.md 反模式 #16/#17），
  "传送门看着像实心板" 这类问题查 alpha，不要查 `render_type`。

### 7.1 老版本（1.20.1/1.21.x）用 quickPlay 自动进世界截图（2026-10-14 实测）

没有进程内代理 ≠ 只能验到主菜单。**quickPlay 能让客户端启动后直接进指定存档**，
配合离线摆位，可以验收一切「要看画面」的需求（天空遮罩 / 渲染层级 / 贴图分层 / HUD）。

```groovy
// build.gradle —— runs.client 里加（⚠️ 不要走 init script，会被 ForgeGradle 重建时覆盖）
client {
    if (project.hasProperty('qpWorld')) {
        args '--quickPlaySingleplayer', project.property('qpWorld').toString()
    }
}
```

```bash
# ① 摆位（写 level.dat 的 Data.Player，不是 playerdata！）
python _tmp/摆位2.py run/saves/<世界> <x> <y> <z> <yaw> <pitch>
# ② 前置：level.dat 的 confirmedExperimentalSettings=1；options.txt pauseOnLostFocus:false
# ③ 跑 + 抓图（工程级脚本：_tmp/视觉验证.py <世界> <前缀>，单轮约 70s）
gradlew runClient -PqpWorld=<世界>
```

- **进世界判据** = 窗口标题 ` - Singleplayer`（内置服务器**不打印** `For help, type`）；
  找主窗口要排除 FML 的 `Minecraft: Forge Loading...` splash（320×196 小窗先出现）。
- **对照实验是判据的核心**：同一机位带/不带渲染开关各拍一组（均值应接近）；
  远机位（超出渲染距离）看到的「什么都没有」**不是 bug** —— 本轮「星界全黑」
  排查的最终结论就是机位/渲染距离问题，靠 5 组对照机位才收敛。
- 客户端日志里中文可能是乱码，**grep 判据用英文子串**（`AFTER_SKY`、`ERROR`）。

#### 🔴 两个会让「看画面」判据撒谎的坑（2026-10-14 实测，都会伪装成 mod 的 bug）

**① DPI 缩放会让抓图被裁掉左上 ~2/3 —— HUD/热键栏/准星位置全部对不上。**

显示缩放 150% 的机器上，**DPI-unaware** 进程的 `GetWindowRect` 返回的是**逻辑像素**，
`CreateCompatibleBitmap(w,h)` 也只建那么大 ⇒ PrintWindow 拿到的位图只有真实窗口的左上部分。
症状：准星不在图中心、热键栏整条看不见、HUD 元素缺失 ⇒ 很容易误判成「HUD 没画出来」
（实测就是这么错的：以为手持雷达的 HUD 没渲染，其实是它被裁在画外）。

```python
import ctypes
ctypes.windll.shcore.SetProcessDpiAwareness(2)   # ★ 抓图前先声明 per-monitor DPI 感知
# 之后 枚举窗口/GetWindowRect/抓图 才是真实像素
```

**② `options.txt` 的键名写错会被游戏静默丢弃 ⇒ 「关了却没关」的无效对照。**

- 关原版云：键是 **`renderClouds`**（值 `"true"` / `"fast"` / `"false"`），
  **不是** `clouds`。写错键 → 下一轮保存时整行消失（MC 只写自己认识的键）→
  你以为关掉了，其实一直是开的 → 对照实验白做。
- 判据：**改完跑一轮，再看这行还在不在**。活下来才算数。
- 同类：`renderDistance` / `guiScale` / `fov` / `pauseOnLostFocus` 都在这个文件里；
  摆位脚本要动的是 `level.dat`（`Data.Player`、`Data.DayTime`），别搞混。

> 通用教训（与 smoke 的双重假阳性同源）：**先证明取证工具没撒谎，再怀疑被测对象**。
> 排查顺序 = 固定机位 + 只切一个变量 → 换一个独立手段复核（本轮的最终结论是靠
> **离线扫存档**定的，不是靠截图）。

### 7.2 自绘天空/遮罩的三个 GL 铁律（2026-10-14 实测）

1. **`disableDepthTest()` 必须配 `depthMask(false)`**：只关测试不关写入，遮罩盒
   （半径 32、离相机近）会往深度缓冲写「近深度」→ 之后的地形渲染深度测试全失败
   → **地形整片丢弃**（画面除准星/HUD 外全黑）。画完两者都还原。
2. **必须自己 `setShader(getPositionColorShader)`（与 `BufferBuilder` 的顶点格式匹配）**：
   `AFTER_SKY` 阶段当前 shader 是原版天空盒最后用的那个（**带 UV/贴图**），
   你往 `POSITION_COLOR` 的缓冲区里塞顶点 = 顶点格式与 shader 不匹配 →
   GL 按错位的属性解释 ⇒ 画出来是**散落的深色块状物**，而**日志零报错**。
   同一阶段画 alpha 渐隐（太阳边缘、半透明云）还要 `enableBlend()/defaultBlendFunc()`
   —— 原版天空盒画完时混合是关的。
   ⚠️ 典型踩法：黑穹（纯色、写了这行）与天穹（渐变，漏了这行）**两段几乎一样的代码**，
   复制时漏一行 ⇒ 一个正常一个稀碎。**同类渲染代码要成对 review**。
3. **云的绘制在 `AFTER_SKY` 事件之后**（`renderLevel` 调用序：AFTER_SKY → 实体 →
   粒子 → 云 → 天气）—— 遮罩盖不住云。要「某场景无云」得走
   `DimensionSpecialEffects` 钩子（`RegisterDimensionSpecialEffectsEvent` 注册，
   键 = `dimension_type` JSON 里 `effects` 的值；`renderClouds` 返回 true = 吞掉原版云）。

### 7.3 天穹/天空层：颜色要跟着原版走，别写死（2026-10-14 实测）

自绘「某个维度/某个区域的天空」时，**不要写死 RGB**：

- 取 **`ClientLevel#getSkyColor(pos, partialTick)`**（1.20.1 签名实测：`(Vec3, float) → Vec3`）
  = 群系天空色 × 昼夜 × 天气。于是「不同群系/位面不同天空」与**昼夜**全部免费拿到；
- 夜里要做**淡出**（`alpha = clamp(平均亮度 × 8, 0, 1)`）而不是硬切：透明度归 0 时
  原版的**星空与月亮**自然露出来 —— 写死白天蓝的后果是「夜里地面全黑、天却是白的」，
  一眼就不像天空（这正是用户反馈「模拟的天空不像」的直接原因）；
- 反过来：**天空层盖不住比它更远的真方块**（天空不写深度 + 地形后画）——
  球壳/穹顶这类真实几何会正常压在天空之上。看到「天上有一块块板子」先想想
  **那是不是自己的球壳/穹顶**，别急着改渲染代码（本轮为此绕了一圈：
  最终靠**离线扫存档**定位到是 `crystal_wall_inner`，且渲染距离按**列**算，
  水平 ~126 格的穹顶列虽然 3D 距离 544 格、依然会被渲染）。

## 8. 验「这件东西到底算不算某标签」

mod 里一旦把行为挂在标签上（`stack.is(Tags.Items.TOOLS)`、`#c:ores`、`#minecraft:pickaxes`…），
**「标签在运行时认不认」就是整套逻辑的命门**：标签没解析上**不会报错**，代码照跑、
`is(tag)` 恒 false —— 静默失效，最坏的一类 bug。所以必须跑起来验，而且**必须配负样本**
（否则你验的是"这条判据恒真"）。

### 8.1 26.2 / 1.20.2 起：`execute if items` 一句话搞定

拿箱子当"手上的槽位"替身，不需要玩家：

```bash
setblock 0 100 0 minecraft:chest
item replace block 0 100 0 container.0 with minecraft:iron_pickaxe
execute if items block 0 100 0 container.0 #c:tools        # → Test passed. Count: 1
execute if items block 0 100 0 container.0 #minecraft:pickaxes
```

- 谓词支持 `#命名空间:标签`、物品 id，还能带组件。
- **负样本必跑**：`minecraft:raw_iron` / `minecraft:gold_ingot` 查 `#c:tools`、`#c:armors`
  都必须是 `Test failed`，才算证明了"判据能分辨"。

### 8.2 1.20.1 等老版本（1.20.2 之前没有 `execute if items`）：临时数据包 + 僵尸装备

直接跑 `execute if items` 会报 `Incorrect argument for command`。改用 `entity_properties` 谓词
+ 一只穿着被测装备的僵尸：

```json
// run/world/datapacks/tagcheck/pack.mcmeta   → {"pack":{"pack_format":15,"description":"temp"}}
// run/world/datapacks/tagcheck/data/tagcheck/predicates/mainhand_tools.json
{"condition":"minecraft:entity_properties","entity":"this",
 "predicate":{"equipment":{"mainhand":{"tag":"forge:tools"}}}}
```

```bash
# 带装备召唤（槽位：mainhand → HandItems[0]；头盔 → ArmorItems[3]，顺序 boots→legs→chest→head）
summon zombie 0 100 0 {HandItems:[{id:"minecraft:iron_pickaxe",Count:1b},{}],NoAI:1b,PersistenceRequired:1b,Tags:["tagcheck"]}
execute as @e[tag=tagcheck,limit=1] if predicate tagcheck:mainhand_tools run data get entity @s Health
# 命中 → "Zombie has the following entity data: 20.0f"；未命中 → 无输出（不是 "Test failed"）
```

- 放 `run/world/datapacks/<名>/` 后 `/reload` 即生效（`--pack_format 15` = 1.20.1）。
- 🔴 **1.20.1 的物品谓词里标签必须写 `"tag"` 字段**。写成 `"items": ["#forge:tools"]` 会在
  `/reload` 时解析失败，日志是 `Couldn't parse element predicates:...` + 根因
  `Non [a-z0-9_.-] character in namespace of location: #forge:tools`；**而随后所有
  `if predicate` 都只报 `Unknown or incomplete command`** —— 看着像命令语法错，其实是资源没加载。
  （`"items"` 能直接写 `#tag` 是 1.20.5+ 的事。）
- 反过来用这条规律当判据：**报 `Unknown or incomplete command` = 谓词没加载；
  无输出 = 谓词加载了但判 false**，两者别混。
- 换物品要重新 `summon`（先 `kill @e[tag=...]`），别拿同一只反复换装备。
- 验完**删掉数据包再 `/reload`**，别把探针留在别人的存档里。

### 8.3 RCON 复用连接会被"零输出命令"带偏（实测踩过）

`rcon.py` 的 `send()` 按「一条命令一个响应、整包读完」设计，但 **`/kill` 匹配 0 个实体这类
零结果命令可能压根不产生响应包**。复用同一连接连跑多条时，响应会整体**错位一格** ——
本次就出现过「铁镐的结论被安到铁矿头上」这种张冠李戴，还差点当成 mod 的 bug。

**规矩：判据类批量验证，一条命令开一条连接**（连上→发→读→关）；
或让每条命令都自带回显（`execute if entity … run …`）。
