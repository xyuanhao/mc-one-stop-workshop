# 模组迁移指南（低版本 → 高版本）

> 适用范围：1.20.1 及更新版本之间互相迁移。
> 编制日期：2026-09-04。核心结论基于 NeoForge 官方 release notes（21.2 / 21.4 / 21.5 / 21.9 / 21.11 / 26.1）与 Fabric 官方博客一手核实。
> 别凭记忆改代码——每个编译错误先用「双工作区对照法」确认正确写法（见第 2 节）。

---

## 0. 先回答：要不要迁？

| 情况 | 建议 |
|---|---|
| 目标 1.21.1，且当前在 1.20.1 | ✅ 值得迁。1.20.1 是 Forge 时代 API，1.21.1 是当前生态主力 |
| 目标 26.x | ⚠️ 慎重。迁移成本最高（见第 4 节），且 26.x 生态仍在成长。若追求稳定优先 1.21.1 |
| 整合包用户（不是作者） | ❌ 不用迁。换整合包版本即可 |
| 纯客户端小 mod（HUD/键位等） | ✅ Fabric 下迁移成本相对低 |

**一次别跳太多版本。** 官方推荐的务实做法是逐级迁移：`1.20.1 → 1.21.1 → 1.21.4 → 1.21.9 → 1.21.11 → 26.1`。
每一级都用「双工作区对照法」过一遍编译错误，稳定后再跳下一级。
只有小 mod（只注册物品/方块/配方）才能考虑大跳。

## 1. 迁移路径总览

```
1.20.1 (Forge/NeoForge互通, Java 17)
   │  ① 若原 Forge：切 NeoForge（生态分离，见 §3.1）
   ▼
1.20.4~1.21 (Java 21)
   │  ② 1.20.5：物品 NBT → Data Components（全量重写点 1）
   │  ③ 1.21：Identifier 工厂方法 / Registry→Registries / RecipeInput / 数据目录去复数 / 附魔数据驱动 / 网络包 StreamCodec
   ▼
1.21.1 (NeoForge 主力版，Java 21)
   │  ④ 1.21.2：注册表方法改名 / BlockEntityType 无 Builder / 物品 Ingredient JSON 简化 / GuiGraphics.blit 签名
   │  ⑤ 1.21.4：物品模型定义迁移 items/*.json / datagen 拆分
   │  ⑥ 1.21.5：SwordItem等基类移除 / NBT Optional 化 / 客户端初始化提前
   │  ⑦ 1.21.9：FML 重构 / BER 渲染状态化 / KeyMapping.Category / RenderHighlightEvent 移除
   │  ⑧ 1.21.11：ResourceLocation → Identifier / RenderType → RenderTypes / JSpecify
   ▼
26.1 (Java 25, 无混淆)
   │  ⑨ 工具链换代（Loom/插件/mappings 全变） / ItemStackTemplate / GuiGraphics→GuiGraphicsExtractor / ChunkPos 工厂
   ▼
26.2 (当前最新)
```

**各跳变的最痛变更**（详细对照在 §3）：

| 跳变 | 最痛的 3 件事 |
|---|---|
| →1.20.5 | 物品 NBT→Data Components；附魔 JSON；give 命令语法 |
| →1.21 | `new Identifier/ResourceLocation` 全失效；`recipes/`→`recipe/` 等目录改名；Container→RecipeInput |
| →1.21.2 | `Registry` 方法改名（getEntry→getOptional 等）；BE Type 构造方式；Ingredient JSON |
| →1.21.4 | 物品模型：`models/item/*.json` 只留模型，新增 `assets/<ns>/items/*.json` 定义 |
| →1.21.5 | 自定义武器/工具/盔甲类全废（SwordItem 等删除，改数据组件） |
| →1.21.9 | 方块实体渲染改成 render state 三方法制；自定义按键类别 |
| →1.21.11 | `ResourceLocation` 全局改名 `Identifier`（批量替换即可） |
| →26.1 | **工具链换代**（见 §4），比改代码更麻烦的是改构建 |

## 2. 迁移核心方法：双工作区对照法

NeoForge 官方推荐的流程（来源：neoforged.net/news/21.11release 等）——**不要猜 API 怎么改，让原版代码告诉你**：

1. 保留一个**能编译的旧版本工作区**（如 1.21.1）+ 开一个进行中的新版本工作区（如 26.1）。
2. 找到新版本编译不过的函数调用。
3. 在旧工作区找到同一调用，右键跳到一个 **vanilla 用法**（IntelliJ：需附加 MC 源码，搜索范围设为 `All Places`）。
4. 去新版本工作区看同一个 vanilla 用法改成了什么样。
5. 照着把改法套到自己的代码上。

更大的范围同理：想学某个系统（配方 datagen、方块渲染）在新版怎么写的，就用两个工作区分别跳原版实现对比。

### Fabric 侧的半自动工具

| 工具 | 用途 | 备注 |
|---|---|---|
| Loom `migrateMappings` 任务 | 把 Yarn → Mojang 官方名半自动迁移 | 不支持 Kotlin；迁移后仍需人工 review，尤其 Mixin |
| Ravel（IntelliJ 插件） | GUI 迁移对话框 | 支持 Kotlin；Fabric API 自己就用它迁的 |
| mcsrc.dev | 在线浏览 MC 反编译源码 | 查 26.x 方法名/签名 |

Loom 迁移示例（1.21.11 → 26.1 的 mappings 迁移）：
```bash
# 在旧工程里（升级 gradle.properties 前先跑）：
gradlew migrateMappings --mappings "<新版本号>"
```
> 26.1 起无 mappings（Yarn 停更），迁移到 26.1 前**必须先**把代码切到 Mojang 官方名。见 §4.4。

## 3. 破坏性变更速查（旧 → 新）

> 每个条目：`[生效版本]` + 改法。完整代码对照见 `references/代码片段.md` 与 `references/版本差异矩阵.md`。

### 3.1 平台层：Forge → NeoForge
`[1.20.2 起生态分离]`
- Forge 与 NeoForge 的 jar **互不兼容**（1.20.1 除外，两者互通）。
- `mods.toml` → `neoforge.mods.toml`；包名 `net.minecraftforge.*` → `net.neoforged.*`；`ForgeRegistries` → `Registries`。
- 事件：mod 事件总线仍在，但构造函数注入写法变了（`FMLJavaModLoadingContext.get().getModEventBus()` → 构造参数 `IEventBus`）。
- 最快路径：直接换 NeoForge 官方 MDK 模板（本 skill `templates/neoforge-*`），保留业务代码，改 API 调用。

### 3.2 物品 NBT → Data Components
`[1.20.5]`
```java
// 旧
stack.getOrCreateTag().putInt("charges", 5);
int c = stack.getTag().getInt("charges");
// 新（需注册 DataComponentType）
stack.set(ModComponents.CHARGES.get(), 5);
int c = stack.getOrDefault(ModComponents.CHARGES.get(), 0);
```
- `/give` 语法：`give @p mod:item{tag...}` → `give @p mod:item[mod:charges=5]`
- 附魔、药水、自定义名字等全部组件化（`[custom_name=...]`）。
- **存档里的旧数据**：物品组件在升级后会自动转换大部分原版组件；自定义 NBT 需要写转换逻辑或接受丢失。

### 3.3 Identifier / ResourceLocation 构造
`[1.21 起构造器失效；1.21.11 Mojang 侧改名 Identifier]`
```java
// 1.20.4 及以前
new ResourceLocation("mymod", "thing");
new ResourceLocation("mymod:thing");
// 1.21（NeoForge/Mojang）
ResourceLocation.fromNamespaceAndPath("mymod", "thing");
ResourceLocation.parse("mymod:thing");
// 1.21.11+：整个类改名
Identifier.fromNamespaceAndPath("mymod", "thing");
Identifier.parse("mymod:thing");
```
Fabric 侧一直叫 `Identifier`，1.21 起 `new Identifier(...)` → `Identifier.of(...)` / `fromNamespaceAndPath(...)`。
> 1.21.11 的改名是**纯机械替换**：`ResourceLocation` → `Identifier`（类名替换即可，方法不变）。

### 3.4 注册表
`[1.21 Registry→Registries；1.21.2 方法改名]`
```java
// 1.20.x → 1.21
Registry.register(Registry.BLOCK, ...)  →  Registry.register(Registries.BLOCK, ...)
// 1.21 → 1.21.2（Fabric 侧）
registry.getEntry(key)      →  registry.getOptional(key)
registry.entryOf(key)       →  registry.getOrThrow(key)
// NeoForge 1.21.2
registryAccess.registryOrThrow(R)  →  registryAccess.lookupOrThrow(R)
registry.getHolderOrThrow(key)     →  registry.getOrThrow(key)
registry.get(rl)                   →  registry.getValue(rl)
```

### 3.5 方块 / 物品 Properties 需要 ID
`[1.21.2]`
```java
// 手写构造时必须 setId：
new MyBlock(BlockBehaviour.Properties.of().xxx().setId(ResourceKey.create(Registries.BLOCK, rl)));
// 用 DeferredRegister 则自动处理：
BLOCKS.registerBlock("my_block", MyBlock::new, props -> props.xxx());
ITEMS.registerItem("my_item", MyItem::new, props -> props.xxx());
// BlockItem 记得（否则 lang key 用错前缀）：
props.useBlockDescriptionPrefix();
```

### 3.6 方块实体类型
`[1.21.2 移除 Builder]`
```java
// 旧
BlockEntityType.Builder.of(MyBE::new, BLOCK.get()).build(null);
// 新
new BlockEntityType<>(MyBE::new, BLOCK.get());
```

### 3.7 配方
`[1.21 Container→RecipeInput；1.21 起 Recipe 客户端只收 RecipeDisplay；1.21.2 Ingredient JSON 简化]`
```java
// 旧
public boolean matches(Container inv, Level level) { ... }
// 新
public boolean matches(RecipeInput input, Level level) { ... }
```
Ingredient JSON（1.21.2+）：
```json
// 旧
{ "ingredient": { "item": "minecraft:diamond" } }
// 新（接受 holder set 简写）
{ "ingredient": "minecraft:diamond" }
// 旧 tag
{ "ingredient": { "tag": "c:ingots/copper" } }
// 新
{ "ingredient": "#c:ingots/copper" }
```

### 3.8 物品模型定义（资源）
`[1.21.4]`
- 模型文件拆两层：`assets/<ns>/items/<id>.json`（定义：model/composite/condition/select/range_dispatch）+ 底层 `models/item/*.json`（纯几何）。
- 旧的 `custom_model_data` overrides 写法失效 → `minecraft:range_dispatch`。
- 完全对照见 `references/资源文件.md` §5.3。

### 3.9 武器/工具/盔甲
`[1.21.5 移除 SwordItem / DiggerItem / ArmorItem]`
- 不要再继承这些类。用数据组件配置：`WEAPON`（伤害）、`TOOL`（挖掘）、`ARMOR`（护甲）、`ATTRIBUTE_MODIFIERS`、`MAX_DAMAGE`、`DAMAGE`、`REPAIRABLE`、`ENCHANTABLE`。
```java
// 1.21.5+
Item.Properties()
    .component(DataComponents.MAX_DAMAGE, 250)
    .component(DataComponents.TOOL, toolComponent)
    .component(DataComponents.WEAPON, weaponComponent)
```

### 3.10 NBT 读取
`[1.21.5 NBT API 重写]`
```java
// 旧
tag.getString("name");
tag.getInt("count");           // 无此键时返回 0
// 新（返回 Optional / get*Or）
tag.getString("name").orElse("");
tag.getIntOr("count", 0);
```

### 3.11 客户端渲染系统
- `[1.21.6]` 实体渲染迁到 render state（EntityRenderState）。
- `[1.21.9]` 方块实体渲染（BER）也状态化，`render(...)` 拆成 **createRenderState / extractRenderState / submit** 三方法（代码见 `references/代码片段.md` 或官方 21.9 release notes）。
- `[1.21.9]` `RenderHighlightEvent` 移除 → `ExtractBlockOutlineRenderStateEvent` + `CustomBlockOutlineRenderer`。
- `[1.21.11]` `RenderType` 静态成员移到 `RenderTypes`；`BakedQuad` 的 `int[]` 存储改为显式字段（`getVertices()` 之类失效）。
- `[26.1]` GUI 渲染方法改名：`Screen#render` → `extractRenderState` 等；`GuiGraphics` 相关也连带调整。
- **判断原则**：若只做普通物品/方块渲染（模型 JSON + RenderType 简单使用），这些渲染重构大多不碰；一旦自定义 shader / BakedQuad / BER 绘制，就要按目标版本的写法重写。查官方 primer：`github.com/neoforged/.github/tree/main/primers`

### 3.12 按键绑定
`[1.21.9 KeyMapping.Category]`
```java
// 旧
public static final String MAIN = "mymod.key.categories.main";
// 新
public static final KeyMapping.Category MAIN = new KeyMapping.Category(Identifier.parse("mymod:main"));
// 且必须在 RegisterKeyMappingsEvent 里 registerCategory(MAIN)
```

### 3.13 FML / 环境 API
`[1.21.9]`
```java
// 旧 → 新
FMLEnvironment.dist               →  FMLEnvironment.getDist()
FMLEnvironment.production         →  FMLEnvironment.isProduction()
FMLLoader.getGamePath()           →  FMLLoader.getCurrent().getGameDir()
```

### 3.14 运行时依赖
`[1.21.9 起]`
```gradle
// 旧：additionalRuntimeClasspath（MDG 2.0.111 起针对 1.21.9+ 禁止）
// 新：直接
jarJar(implementation("org.commonmark:commonmark:0.21.0"))
```

### 3.15 空值注解
`[1.21.11 javax → JSpecify]`
```java
import org.jspecify.annotations.Nullable;   // 取代 javax.annotation.Nullable
```
注意：`@Nullable Map.Entry` 不合法 → `Map.@Nullable Entry`；数组语义不同：`@Nullable Object[]`（元素可空）vs `Object @Nullable[]`（数组可空）。

### 3.16 数据目录与文件
- `[1.21]` 所有数据目录去复数：`recipes/`→`recipe/`、`loot_tables/`→`loot_table/`、`tags/blocks/`→`tags/block/`…
- `[1.21]` 附魔数据驱动化：代码里 `Enchantments.SHARPNESS` 变成 `ResourceKey`，用 `Holder<Enchantment>` 取值。
- `[1.21.9]` `pack.mcmeta` 的 pack_format 小数化 + min_format/max_format。
- `[1.21.6]` JSON 严格解析（不能有注释/尾逗号）。

### 3.17 自定义内容清单一页纸（迁到 1.21.1 必查）
- [ ] 所有 `new ResourceLocation` → 工厂方法
- [ ] 所有 `Registry.X` 静态注册表 → `Registries.X`
- [ ] 物品 NBT（tag/自定义数据）→ Data Components
- [ ] `Recipe<Container>` → `Recipe<RecipeInput>`
- [ ] 数据目录名去复数
- [ ] 附魔/属性/药水的 Holder 化
- [ ] 网络包 → CustomPacketPayload + StreamCodec
- [ ] 语言文件键、模型、纹理核对（id 不变则无需改路径）

## 4. 迁移到 26.x 专题（成本最高，单独说）

### 4.1 迁移顺序建议（官方推荐路径）

**必须从 1.21.1 或 1.21.11 起跳**，不要从 1.20.1 直接跳 26.1（中间隔了 1.21.2/1.21.4/1.21.5/1.21.9/1.21.11 五轮破坏性变更，一次全改基本不可能）。

若当前在 1.20.1：先按 §1 路径逐级到 1.21.1 → 稳住 → 再考虑 26.1。
若当前在 1.21.1：先读完 NeoForge 21.2/21.4/21.5/21.9/21.11 五篇 release notes，把对应改动消化掉（§3 有浓缩版），再跳 26.1。

### 4.2 工具链升级（构建脚本）

26.1 的变更清单（官方博客 + 官方 MDK 实测）：

| 项 | 1.21.1 | 26.1 |
|---|---|---|
| Java | 21 | **25** |
| Gradle | 8.x | **≥ 9.1.0** |
| NeoForge 插件 | MDG 2.0.x | MDG **2.0.146+**（或 NG 7.1.38+） |
| NeoForge 版本号 | `21.1.113` | `26.1.0.19-beta`（四段） |
| Parchment | 需要（参数名） | 可删（Mojang 参数名内置） |
| datagen run | `data()` | `clientData()` |
| 依赖嵌入 | `additionalRuntimeClasspath`（1.21.9 前） | 仅 `jarJar(implementation(...))` |

快速换法：直接用本 skill 的 `templates/neoforge-26.1-mdg/`（或 `-ng`）覆盖旧工程的 `build.gradle` / `gradle.properties` / `settings.gradle`，再把自己的类拷进来逐个修编译错误。

### 4.3 关键代码变更（26.1，官方实测）

```java
// ① ItemStack 需要注册表已加载 → 数据文件/早期代码用 ItemStackTemplate
ItemStackTemplate t = ItemStackTemplate.fromNonEmptyStack(stack);
ItemStack stack2 = t.create();
// ② 注册 lambda 化
BLOCKS.registerSimpleBlock("b", p -> p.mapColor(MapColor.STONE));   // 旧：传 Properties.of() 实例
ITEMS.registerSimpleItem("i", p -> p.food(...));                    // 旧：new Item.Properties().food(...)
// ③ ChunkPos
new ChunkPos(blockPos) → ChunkPos.containing(blockPos)
ChunkPos.asLong(...)   → ChunkPos.pack(...)
new ChunkPos(l)        → ChunkPos.unpack(l)
// ④ GUI 渲染（若用到 Screen 绘制）
Screen#renderBackground(...) → Screen#extractBackground(...)
// ⑤ 新增 MutableQuad 等渲染助手（BakedQuad 相关 mod 关注）
```

### 4.4 Fabric → 26.1：mappings 与工具链

这是 Fabric 侧最麻烦的部分，**先迁 mappings 再升版本**：

1. 还在用 Yarn？**先**在旧版本上迁到 Mojang 官方名：
   - Loom `migrateMappings` 任务，或 Ravel 插件（支持 Kotlin）。
   - 混合用 Parchment 可选，但 26.1 后非必需。
2. 升级构建脚本（对照官方 example mod）：
```gradle
// 插件 id 变化
- id 'fabric-loom' version '...'
+ id 'net.fabricmc.fabric-loom' version '...'      // 26.x 不再 remap
// 依赖配置变化
- modImplementation "net.fabricmc:fabric-loader:..."
+ implementation "net.fabricmc:fabric-loader:..."
// 移除 mappings 行（Yarn 已停更）
- mappings "net.fabricmc:yarn:..."
// 打包任务
- remapJar
+ jar
```
3. `gradle.properties` 版本升级：`minecraft_version=26.x`、`loader_version=0.19.x`、`loom_version=1.17+`、`fabric_api_version=0.158.0+26.x`（以 https://fabricmc.net/develop 为准）。
4. API 改名对齐官方名：`ItemGroupEvents` → `CreativeModeTabEvents`、移除 `HudRenderCallback`（→ `HudElementRegistry`）等。
5. Java 25、IntelliJ 2025.3+。
6. 老 mod 在 26.1 需要**至少重新编译**（混淆移除导致二进制不兼容，即使有源码也要重新编译）。

### 4.5 26.x 特有的验证
- `runClient` / `runServer` 都跑一遍（世界存储有重大变更，升级存档前备份）。
- 旧版 mod jar 不能直接丢进 26.x 的 mods 目录——必须重新编译打包。
- 渲染走 Vulkan 的新后端测试（26.2 起可选 OpenGL/Vulkan），使用裸 OpenGL 调用的代码要迁到 Blaze3D API。

## 5. 通用迁移工作流（按顺序做）

1. **盘点**：跑 `scripts/检查工程.py <工程>` 摸清现状（平台/版本/已有反模式）。
2. **定目标**：确认目标 MC 版本 + 加载器（参考 SKILL.md 版本推荐表）。
3. **备份**：git 提交或整体拷贝（迁移不可逆，随时可回退）。
4. **换构建**：复制目标版本官方模板的 `build.gradle`/`gradle.properties`/`settings.gradle`（本 skill `templates/` 现成），保留自己的 src。
5. **升级环境**：JDK（1.21.x→21，26.x→25）、`gradle/wrapper/gradle-wrapper.properties` 的 Gradle 版本。
6. **跑构建**：`gradlew build`，拿编译错误清单。
7. **逐个修**：每个错误用「双工作区对照法」确认改法，别猜。改完一个系统跑一次增量编译。
8. **查结构性变更**：对照 §3 逐项核对（Data Components、Registry、配方、模型、渲染…），编译能过 ≠ 运行正确。
9. **迁资源**：目录去复数、物品模型 items/*.json（1.21.4+）、JSON 严格化（去注释/尾逗号）。
10. **跑游戏**：`runClient` 验模型/合成/物品栏，`runServer` 验服务端不崩。
11. **检查**：再跑一次 `scripts/检查工程.py`，用 `scripts/迁移检查.py --to <目标版本>` 复核是否漏项。

> 用 `scripts/迁移检查.py <工程> --to 26.1` 自动生成「还差什么」的清单。

## 6. 反模式：迁移时最容易犯的错

| 错 | 后果 | 正确做法 |
|---|---|---|
| 一次跨太多版本 | 错误堆积无从下手 | 逐级迁移（§1） |
| 照抄网上 1.20.1 教程改 1.21+ 代码 | 编译失败/运行崩溃 | 用双工作区对照原版改法 |

# 5. 反向移植：高版本 → 1.20.1（实操记录）

前面几节都是「低 → 高」，这一节反过来：把一个 **NeoForge 26.1** 的模组整个搬到 **Forge 1.20.1**。
实测规模：6500 行 / 51 文件的模组 → 重写为 7000 行 / 50 文件，一次会话内走完编译 + 真机验证。

## 5.1 先分清「写法不同」和「当时根本没这东西」

后者必须换实现思路，改 import 是没用的：

| 26.1 有 | 1.20.1 | 换法 |
|---|---|---|
| 玩家数据附件 `AttachmentType` | 无（Capability 也行，但样板多） | 玩家持久化 NBT + 内存缓存；每 20 tick 落脏、`PlayerEvent.Clone` 手动搬死亡数据 |
| `DataComponents`（数量上限 [1,99] 就在这） | 无 | 数量在存档/网络里是 **byte** → mixin `ItemStack#save/of` + `FriendlyByteBuf#writeItem/readItem` |
| 属性 `WATER_MOVEMENT_EFFICIENCY` | 无 | mixin `LivingEntity#getWaterSlowDown` |
| 属性 `BLOCK_BREAK_SPEED` | 无 | mixin `Player#getDigSpeed`（**是 Forge 加的方法 → `remap = false`**） |
| 属性 `MAX_ABSORPTION` | 无 | 自己算上限 + `setAbsorptionAmount` |
| `AbstractCraftingMenu` | 无（1.20.2 才抽出来） | 继承 `AbstractContainerMenu`，自己建 `TransientCraftingContainer` + `ResultContainer` |
| `CraftingInput` / `RecipeHolder` | 无 | 直接拿 `CraftingContainer` 当配方输入；`getRecipeFor` 返回**配方本身** |
| `CustomPacketPayload` + `StreamRegistrar` | 无 | `SimpleChannel`（只有 `consumerMainThread` / `consumerNetworkThread`，**没有**通用 `consumer`） |
| GUI `extractRenderState` 两段式 | 无 | `render(GuiGraphics, ...)` 一步到位；`Screen.font` 是**字段**不是 `getFont()` |
| `BlockDropsEvent` / `HarvestDropsEvent` | **都没有** | mixin `Block#getDrops` 的六参重载 |
| `EntityTickEvent` | 无 | mixin 注入目标实体的 `tick()` |
| `ForgeMod.BLOCK_REACH` 用 `.get()` | 同左（RegistryObject） | 原版 `BLOCK_INTERACTION_RANGE` 这时**还不存在** |

## 5.2 真机上才暴露的十一个坑（编译期全都看不出来）

1. **Forge 新增的方法没有 SRG 映射**：`getDigSpeed` 会让注解处理器直接报
   `Unable to locate obfuscation mapping for @Inject target`。
   判据：去 `forge-<ver>-srg.jar` 里 grep 方法名 —— vanilla 方法全是 `m_xxxxx_`，
   **Forge 加的是可读原名**。→ 这类注入点写 `remap = false`。
2. **`@Redirect` 的 handler 拿不到外层方法的参数**（只能拿到被替换调用的接收者与实参）。
   想让 handler 拿到原方法的参数，只能用 `@Inject`。写错会在**启动时**崩：
   `Critical injection failure: Redirector ...`。
3. **`@Inject` / `@Redirect` 的方法名写错，编译期一声不吭**，只在启动应用 mixin 时报
   `could not find any targets matching ...`。实测踩了两处：
   - `isEntityCollidingWithAnythingNew` → 1.20.1 叫 `isPlayerCollidingWithAnythingNew`，
     而且**少一个 entity 参数**（那时只处理玩家，直接从 `this.player` 取）；
   - `Inventory#getSlotWithRemainingSpace` 里**根本没有** `getMaxStackSize` 调用 ——
     真正的判据在 `hasRemainingSpaceForItem`。
   **所以每个注入点都要 `javap -c` 对着字节码确认，别凭直觉或凭高版本的记忆。**
4. **`(byte)1024 == 0`，而 `ItemStack.of` 对数量 ≤ 0 直接返回空栈** ——
   高位截断会让高堆叠物品**静默消失**（表现为 `/summon` 出来是 `Air`）。
   正确做法：真值另存一个自己的键（int），原版 `Count` 里留一个**非零占位**，
   读的时候再从自己的键恢复。
5. **MixinGradle 只负责写 jar 清单，不生成 refmap**：必须显式加
   `annotationProcessor 'org.spongepowered:mixin:0.8.5:processor'`。
   少了它 → 开发环境一切正常，**发布出去的 jar 里所有 mixin 静默失效**。
6. **`Slot#isActive()` 1.20.1 是有的**（别按"高版本才有"想当然）；
   但 `Slot#getMaxStackSize(ItemStack)` 是 `min(容器上限, 物品上限)` ——
   要让背包堆叠上限生效，这半截也得改，否则"一次只能搬 64 个"。
7. **`AbstractContainerScreen` 的几处签名**：构造器只有 3 参
   （`imageWidth/imageHeight` 是 `protected int`、**不是 final**，可手工改）；
   `hasClickedOutside` 是 **5 参**；`mouseScrolled` 是 **3 参**；
   `LevelRenderer.renderVoxelShape` 比 26.1 **多一个 boolean 尾参**。
8. **RCON 里看到 `Summoned new Air`** 是"物品 NBT 被解析成了空栈"的信号，
   别去查命令语法 —— 去查数字类型的宽度。
9. ⭐ **「属性存在」不等于「玩家在用这个属性」**：
   `Attributes.JUMP_STRENGTH` 在 1.20.1 里**只有马 / 骆驼那几个动物类在读** ——
   把整个 jar 搜 `generic.jump_strength`，命中的只有 6 个 `animal` 类；
   而玩家跳跃走的是 `LivingEntity.getJumpPower()` 里的**硬编码 `0.42F`**，压根不看属性。
   原版要到 **1.20.5** 才让玩家读它（所以 26.1 的属性写法在那边成立、在这边不成立）。
   **这类坑最难查**：编译过、不报错、属性面板上数字也在动，就是游戏里没效果。
   **判据**：拿属性的字段名去 mapped jar 里搜**引用它的类**，看命中的是不是你要作用的那类实体。
   （实测 1.20.1 高危项：`JUMP_STRENGTH`；`MAX_ABSORPTION` / `BLOCK_BREAK_SPEED` /
   `WATER_MOVEMENT_EFFICIENCY` 是**连类都没有**，反而好查。）
10. ⭐ **Forge 1.20.1 有两条事件总线，挂错 = 那段代码一次都不执行**：
    `RegisterKeyMappingsEvent` / `FMLClientSetupEvent` / `FMLCommonSetupEvent` 这类
    **加载期**事件在 **MOD 总线**上，而 `@Mod.EventBusSubscriber` 的 `bus` 默认值是 **FORGE**。
    不写 `bus = Bus.MOD` 的后果：按键注册不上（**按了完全没反应**）、菜单-界面绑定不执行 ——
    编译期没有提示，启动期没有报错，只有玩家会发现"按键失灵"。
    **判据**：看事件类有没有 `implements IModBusEvent`。
    NeoForge 的总线已经合并，所以 26.1 的代码里根本看不出这个问题。
11. ⭐⭐ **拦「包装方法」= 白干 —— 必须拦真正的实现**（本次造成过真实的物品丢失）：
    `FriendlyByteBuf` 的物品写出是一层套娃：
    ```
    writeItem(stack)               → 第一条指令就是转发给 writeItemStack(stack, true)
    writeItemStack(stack, boolean)  → 真正的实现（byte 就写在这里）
    ```
    我拦了外层 `writeItem`，而 **`ServerboundContainerClickPacket`（客户端点击槽位的包）
    直接调内层 `writeItemStack`** —— 它绕过了注入、仍按 byte 写，
    而读端按 varint 读 → **两端协议错位**。
    现象是「往合成格里放东西会丢 / 翻页失灵 / 堆叠凭空消失」这类**看着毫不相干**的怪事，
    而且**只在"玩家自己操作"时出现**（服务端→客户端的包走 `writeItem`，反而是好的）——
    这个"单向出问题"的特征本身就是最好的线索。
    **做法**：
    - 拦之前**先用 `javap -c` 看目标方法是实现还是包装**（包装就拦内层，外层会自动转发进来）；
    - **搜「谁在调它」比看签名有用**：`ServerboundContainerClickPacket` 这种
      客户端→服务端的包，往往走更底层的那一个方法；
    - 顺带：`writeItemStack` **是 Forge 抽出来的新方法**（SRG 版里名字可读）
      → 还得配 `remap = false`（判据同第 1 条）。

## 5.3 国内网络的工程配置（不配就是无限静默）

- **`plugins.gradle.org` 国内直连超时**（实测 25 秒零响应）：Gradle 解析插件时会一直等它，
  表现是「daemon 起来之后再无任何输出」，看着像卡死。
  改 `settings.gradle` 的 `pluginManagement.repositories` → 官方 forge maven + BMCLAPI，
  **不要声明 `gradlePluginPortal()`**；顺带把 HTTP 超时压短，让它快速失败换下一个仓库。
- **插件版本写精确值**：范围版本（`[6.0,6.2)`）会逼 Gradle 枚举**每个**仓库的
  maven-metadata。另外注意镜像不一定全 —— 阿里云 gradle-plugin 里 ForgeGradle 的
  plugin marker 只有 7.0.0，命中不了 6.0.x，别把它放第一位。
- **首次构建的 "MCP 环境初始化" 只下载不耗 CPU**：会跑
  `downloadClient / mergeMappings / listLibraries` 一串步骤，几十分钟不奇怪。
  **别按 CPU 占用判断死活** —— 去看 `~/.gradle/caches/forge_gradle/` 里是不是在长文件。
- 1.20.1 要 **JDK 17**：官方启动器里 `java-runtime-gamma-snapshot` 才是 17，
  `java-runtime-delta` 是 21、`java-runtime-epsilon` 是 25（那俩给 26.x 用）。
  脚手架若自动挑了"版本够的"那个，要手动改回 17。
- 模板 bug：`forge_version` 里**不要带 MC 前缀**。`build.gradle` 拼的是
  `${minecraft_version}-${forge_version}`，写成 `1.20.1-47.3.0` 会变成
  `1.20.1-1.20.1-47.3.0` 然后解析失败。

## 5.4 真机验证能验到哪一层

专用服务端 + RCON 能验：**16 个 mixin 全部应用成功**（有没有 InjectionError）、mod 加载、
命令系统、分类器这类**纯逻辑**（摆方块 → 探针读结论 → 连锁收集结果），
以及 NBT 读写的**闭环**（构造本 mod 自己的格式写进去、读回来）。

**验不了**：需要真人客户端的部分 —— GUI、按键、面板交互、网络包往返、伤害/属性实际手感。
交付时必须如实说明验证到哪一层。
