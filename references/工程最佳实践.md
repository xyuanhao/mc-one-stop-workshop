## 1. 逐项目分析

### 1.1 Create（重型科技 mod，渲染/物理复杂）

- **仓库**：`https://github.com/Creators-of-Create/Create` @ `mc1.20.1/dev`
- **目录结构（根）**：`build.gradle`、`gradle.properties`、`settings.gradle`、`src/`、`gradle/`、`.github/`。**单 Gradle 模块**，无子项目。
- **Java 包结构**：`com.simibubi.create`，顶层是 6 个目录 + 一组「`All*`」扁平注册类：
  ```
  com/simibubi/create/
  ├── AllBlocks.java          AllItems.java          AllBlockEntityTypes.java
  ├── AllRecipes.java         AllTags.java           AllCreativeModeTabs.java
  ├── AllEntityTypes.java     AllMenuTypes.java      AllParticleTypes.java
  ├── AllSoundEvents.java     AllPackets.java        AllPartialModels.java ...  (共 35 个 All* 文件)
  ├── Create.java             CreateClient.java       # 入口：common + client 分离
  ├── api/          # 对外 API
  ├── compat/       # 与其他 mod 的兼容
  ├── content/      # 按功能的内容模块（齿轮、传送带、列车等）
  ├── foundation/   # 基础设施（data/recipe、注册辅助、渲染基类）
  ├── infrastructure/ # 世界生成、网络等
  └── impl/         # 实现细节
  ```
- **注册中心组织**：**集中式 + Registrate**。每个 `All*` 类集中注册一类对象；内部用 `CreateRegistrate` 流式 API。真实片段（`AllItems.java`）：
  ```java
  public class AllItems {
      private static final CreateRegistrate REGISTRATE = Create.registrate();
      static { REGISTRATE.setCreativeTab(AllCreativeModeTabs.BASE_CREATIVE_TAB); }

      // 字段名=全大写蛇形；类型=Registrate 的 ItemEntry<T>
      public static final ItemEntry<Item> WHEAT_FLOUR =
          taggedIngredient("wheat_flour", AllItemTags.WHEAT_FLOUR.tag, AllItemTags.FLOUR.tag),
          DOUGH = taggedIngredient("dough", ...),
          ...
      public static final ItemEntry<CombustibleItem> CARDBOARD = REGISTRATE.item("cardboard", CombustibleItem::new)
          .tag(AllItemTags.CARDBOARD_PLATES.tag, PLATES.tag)
          .onRegister(i -> i.setBurnTime(1000))
          .register();
  }
  ```
  - 命名惯例：`All` + 复数名词（`AllBlocks`/`AllItems`）；`public static final` 字段 **SCREAMING_SNAKE_CASE**；注册路径（`"wheat_flour"`）与字段名一致但小写。
- **资源目录**：标准 `src/main/resources/assets/create/...` 与 `src/main/resources/data/create/...`（具体子目录未能逐层展开，但遵循社区标准：`models/item`、`models/block`、`textures/item`、`textures/block`、`lang`、`blockstates`、`recipes`、`loot_tables`、`tags`）。
- **数据生成（datagen）**：**使用 Registrate 驱动的 datagen**。`AllItems` 中 `.tag(...)` 链式调用会在 datagen 阶段自动产出 `lang`、`tags`、`models`；另有专门的 DataGen 运行配置（`gradle` 的 run 配置里 `genData`）。具体 provider 类组织**未能获取**。
- **客户端/服务端分离**：`Create.java`（common，`@Mod` 入口）+ `CreateClient.java`（client，专门放客户端初始化/渲染注册）。客户端逻辑用 `DistExecutor`/ sided 事件保护。
- **配置系统**：**未能获取**（Create 自有配置体系，未在本次读取范围内）。
- **构建脚本关键点**（`build.gradle` 摘要，`gradle.properties` 真实）：
  - 插件：`net.neoforged.moddev.legacyforge`（ModDevGradle）、`blossom`、`silk`、`mod-publish-plugin`。
  - `gradle.properties` 真实片段：
    ```properties
    mod_id = create
    mod_name = Create
    mod_author = simibubi
    mod_version = 6.0.8
    minecraft_version = 1.20.1
    forge_version = 47.1.33
    registrate_version = MC1.20-1.3.3
    flywheel_version = 1.0.6-beta-266
    parchment_version = 2023.09.03
    use_parchment = true
    ```
  - 依赖通过 `modImplementation(jarJar(...))` 引入 Registrate / Flywheel / JEI / Curios；mixin 通过 `mixin { config "create.mixins.json" }` 与 `refmap` 配置；`jar`/`slimJar` 任务写入 `MixinConfigs` 清单并发布到 CurseForge/Modrinth/GitHub。
- **最值得学的 3 点**：
  1. `All*` 集中注册 + 字段常量（`AllBlocks.IRON_BLOCK` 全局引用），杜绝魔法字符串，引用即编译期校验。
  2. `content/` 按**功能**而非类型分模块（传送带、齿轮、列车各自成包），大型 mod 仍可读。
  3. Registrate 把「注册 + 标签 + 模型 + 本地化」串成一条流水线，datagen 几乎零额外代码。
- **最不该学的 1 点**：`All*` 类动辄数百行、集中注册所有同类对象，对小型/中型 mod 没必要，反而增加合并冲突面；中小项目用模块化或 `ModItems` 单类即可。

### 1.2 Botania（跨平台魔改向，自定义渲染/数据驱动）

- **仓库**：`https://github.com/VazkiiMods/Botania` @ `1.20.x`
- **目录结构**：根目录是 **多模块**：`Xplat/`（跨平台核心）、`Forge/`（Forge 装载）、`Fabric/`（Fabric 装载），外加 `doc/`、`scripts/`、`garden_of_glass/`、`spotless/` 等。
- **Java 包结构（Xplat）**：`vazkii/botania` 下：
  ```
  vazkii/botania/
  ├── api/          # 对外 API（大量接口）
  ├── client/       # 客户端渲染
  ├── common/       # 通用游戏逻辑
  ├── data/         # datagen providers
  ├── integration/  # 与其他 mod 联动
  ├── mixin/        # Mixin
  ├── network/      # 网络包
  ├── xplat/        # 跨平台抽象层
  │   ├── XplatAbstractions.java        # 服务端/通用平台抽象（接口，各装载实现）
  │   ├── ClientXplatAbstractions.java  # 客户端平台抽象
  │   └── BotaniaConfig.java            # 跨平台配置入口
  └── test/
  ```
- **注册中心组织**：**未能获取**具体注册写法（Botania 历史上是手写注册、现按装载分别走 Forge `DeferredRegister` 与 Fabric `Registry`）。其架构核心是 `XplatAbstractions` 接口：common 代码只依赖抽象，Forge/Fabric 模块各自提供实现。
- **资源目录**：`Xplat/src/main/resources/` 下放共享 `assets`/`data`；`Forge/`、`Fabric/` 各放平台专属资源（如 `META-INF/mods.toml` 或 `fabric.mod.json`）。具体子目录未能逐层展开。
- **数据生成**：`vazkii/botania/data/` 存在，说明使用 datagen providers 生成配方/标签/语言等。具体组织**未能获取**。
- **客户端/服务端分离**：`client/` 包 + `ClientXplatAbstractions` 双重隔离；跨平台通过 `XplatAbstractions`/`ClientXplatAbstractions` 接口注入实现。
- **配置系统**：`xplat/BotaniaConfig.java` 作为跨平台配置入口（具体字段/后端**未能获取**，但位置明确在 `xplat` 而非各装载模块）。
- **构建脚本**：单 `build.gradle` 管理三模块 + 子模块 `Xplat/Forge/Fabric` 各自 `build.gradle`；使用 `spotless` 统一格式化。细节未能获取。
- **最值得学的 3 点**：
  1. **`Xplat` + 装载模块**的三分结构，是「一份逻辑、多平台发布」的清晰范式。
  2. `XplatAbstractions`/`ClientXplatAbstractions` 抽象层：common 代码零平台 API 泄漏。
  3. `api/` 与 `common/` 严格分离，对外只暴露 `api/`，内部改动不破坏第三方集成。
- **最不该学的 1 点**：`api/` 与 `xplat/` 抽象层非常重（大量自写工具类与接口），对小 mod 是过度设计；且历史 mixin 较多，维护成本高。

### 1.3 JEI（三平台共存典范）

- **仓库**：`https://github.com/mezz/JustEnoughItems` @ `1.20.1`
- **目录结构（根）**：**多模块 Gradle 工程**：`Common/`、`CommonApi/`、`Fabric/`、`Forge/`、`FabricApi/`、`ForgeApi/`、`Gui/`、`Library/`、`Debug/`、`buildSrc/`、`buildtools/`。构建用 **Kotlin DSL**（`build.gradle.kts`、`settings.gradle.kts`）。
- **Java 包结构**：`mezz/jei`（位于 `Common/src/main/java/mezz/jei`）。JEI 本身是 UI/API mod，注册的游戏对象极少（主要是配方类别/组件），因此**注册不是其重点**。
- **注册中心组织**：N/A（JEI 不注册大量方块/物品；核心是 `Plugin` 与 `RecipeManager` 的运行时注册）。其价值在**工程结构**而非注册范式。
- **资源目录**：`Common` 放共享资源，`Fabric`/`Forge` 放平台资源。具体子目录未能获取。
- **数据生成**：不适用（UI mod，几乎无游戏数据）。
- **客户端/服务端分离**：JEI 是**纯客户端** mod（`Gui/` 模块 + `Client` 入口）；`Common` 是共享逻辑，`Fabric`/`Forge` 提供装载桥。
- **配置系统**：**未能获取**（JEI 配置较轻量）。
- **最值得学的 3 点**：
  1. `Common` + `CommonApi` + `Fabric`/`Forge` + `FabricApi`/`ForgeApi` 的**四层拆分**：实现与 API 分离、共享与装载分离，是大型跨平台库模的标杆。
  2. `buildSrc/` + `buildtools/` 把构建逻辑与代码生成工具化，保证三平台构建一致。
  3. Kotlin DSL 构建脚本，类型安全、可维护性高。
- **最不该学的 1 点**：多模块 + `buildSrc` + `buildtools` + Api 分离的复杂度**极高**，只适合需要同时支持多平台、对外提供 API 的库模；普通内容 mod 照搬会拖垮开发效率。

### 1.4 Supplementaries（Architectury 跨平台中型 mod）

- **仓库**：`https://github.com/MehVahdJukaar/Supplementaries` @ `1.21.1`
- **目录结构（根）**：`common/`、`fabric/`、`neoforge/`、`loom-deobf/`（Fabric 侧辅助）、`build.gradle.kts`、`settings.gradle.kts`。标准 **Architectury 三模块**。
- **Java 包结构（common）**：`net/mehvahdjukaar/supplementaries`：
  ```
  net/mehvahdjukaar/supplementaries/
  ├── Supplementaries.java         # 跨平台入口（common 侧）
  ├── SuppPlatformStuff.java       # 平台抽象实现（服务端）
  ├── SuppClientPlatformStuff.java # 平台抽象实现（客户端）
  ├── api/          # 对外 API
  ├── client/       # 客户端
  ├── common/       # 通用逻辑
  ├── configs/      # 配置类集合
  ├── dynamicpack/  # 运行时动态数据包
  ├── integration/  # 他 mod 联动
  ├── mixins/       # Mixin
  ├── reg/          # 注册中心（按类型分文件）
  └── unused/       # 保留的未使用代码
  ```
- **注册中心组织**：**模块化集中式**——`reg/` 目录按类型放注册类（类似 `ModBlocks`/`ModItems`，具体类名**未能获取**，但 `reg/` 目录明确）。入口 `Supplementaries.java` 统一触发注册。
- **资源目录**：`common/src/main/resources/` 放共享 `assets`/`data`；`fabric/`、`neoforge/` 放平台专属（含 `META-INF/mods.toml` 或 `fabric.mod.json`）。具体子目录未能逐层展开。
- **数据生成**：存在 `dynamicpack/`（运行时向游戏注入数据包），datagen provider 具体组织**未能获取**。
- **客户端/服务端分离**：`client/` 包 + `SuppClientPlatformStuff`/`SuppPlatformStuff` 平台实现双轨。
- **配置系统**：`configs/` 目录集中放配置类（具体后端**未能获取**，但该目录清晰表达了「配置独立成包」的约定）。
- **最值得学的 3 点**：
  1. Architectury `common/fabric/neoforge` 三模块，是**中小 mod 跨平台的最省心方案**（比 Botania/JEI 的手写三分轻得多）。
  2. `reg/`、`configs/`、`client/`、`common/` 用**语义目录**而非巨型单类，职责一目了然。
  3. `SuppPlatformStuff`/`SuppClientPlatformStuff` 把平台差异收敛到两个类，common 代码干净。
- **最不该学的 1 点**：仓库里有 `unused/` 目录保留未使用代码、`dynamicpack/` 等高级机制——对新手属于过早抽象，普通 mod 不需要。

### 1.5 Twilight Forest（内容型：结构/生物群系/维度）

- **仓库**：`https://github.com/TeamTwilight/twilightforest` @ `1.20.1`
- **目录结构（根）**：`build.gradle`、`gradle.properties`、`settings.gradle`、`src/`。**单模块**。
- **Java 包结构**：`twilightforest`，**按类型分包**（20 个目录 + 8 个根文件）：
  ```
  twilightforest/
  ├── TwilightForestMod.java   TFConfig.java   TFTickHandler.java   # 入口/配置/全局 tick
  ├── block/  item/  entity/  enchantment/  potions/  inventory/
  ├── world/            # 维度、生物群系、世界生成、结构
  ├── advancements/  loot/  data/  network/  capabilities/
  ├── client/          # 客户端渲染/模型
  ├── events/  command/  compat/  dispenser/  enums/  init/  util/
  └── init/            # 注册中心（TF 前缀类，按类型分散）
      ├── TFBlocks.java  TFItems.java  TFBlockEntities.java  TFEntities.java
      ├── TFBiomes.java  TFRecipes.java  TFCreativeTabs.java  TFSounds.java
      ├── TFStructures.java  TFMobEffects.java  TFMenuTypes.java ... (共 33 个 TF* 文件)
  ```
- **注册中心组织**：**按类型分散 + `TF` 前缀集中类**。`init/` 下每个 `TF*` 文件负责一类注册（与 Create 的 `All*` 思路一致，但用 `TF` 前缀且位于 `init/` 子包）。真实条目：`init/TFBlocks.java`、`init/TFItems.java`、`init/TFBlockEntities.java`、`init/TFEntities.java`、`init/TFRecipes.java` 等。
- **资源目录**：标准 `src/main/resources/assets/twilightforest/...` 与 `data/twilightforest/...`；含 `update.json`、`crowdin.yml`（本地化走 Crowdin）。具体子目录未能逐层展开。
- **数据生成**：`init/TFRecipes.java` + `data/` 包存在，疑似 datagen 与手写 JSON 混合；**具体 datagen 组织未能获取**。
- **客户端/服务端分离**：`client/` 包放渲染；`TwilightForestMod` 主类 + `world/` 服务端逻辑；网络走 `network/`。
- **配置系统**：✅ 真实读取到 `TFConfig.java`，使用 **Forge Config（`ForgeConfigSpec`）**：
  - 结构：`TFConfig.Common`（对应 `ModConfig.Type.COMMON`，管理维度/传送门/拆解台等）+ `TFConfig.Client`（对应 `ModConfig.Type.CLIENT`，管理渲染/音效）。
  - `Common` 内用 `Dimension`、`MagicTrees`、`UncraftingStuff` 等**嵌套静态类分组**。
  - 声明方式：`ForgeConfigSpec.Builder` 链式 `.comment().translation().define()/.defineInRange()/.defineList()`，监听 `ModConfigEvent` 做热重载与同步（dedicated server 时向客户端发 `SyncUncraftingTableConfigPacket`）。
  - 真实片段：
    ```java
    originDimension = builder.translation(config+"origin_dimension")
        .comment("The dimension you can always travel to the Twilight Forest from...")
        .define("originDimension", "minecraft:overworld");
    maxPortalSize = builder.translation(config+"max_portal_size")
        .comment("The max amount of water spaces the mod will check...")
        .defineInRange("maxPortalSize", 64, 4, Integer.MAX_VALUE);
    ```
- **最值得学的 3 点**：
  1. `init/` 用 `TF` 前缀按类型分散注册，既集中又可并行编辑，兼顾可读与合并友好。
  2. **配置用 `Common`/`Client` 双层 + `ModConfigEvent` 热重载同步**，是 Forge 配置的标准样板，值得直接复用。
  3. 内容型 mod 的 `world/`（维度/群系/结构）、`loot/`、`advancements/` 独立成包，扩展内容不互相干扰。
- **最不该学的 1 点**：根包下直接平铺 20 个类型目录（`block/`、`item/`、`entity/`…）在内容爆炸时会让每个包都很臃肿；更优做法是再按**功能/维度区域**（如 `world/twilight/`、`content/block/`）进一步分组。

- **配置系统**：**未能获取**。
- **最值得学的 3 点**：
  1. `client/` 与 `common/` 顶级二分，从包层面强制**客户端代码不泄漏到服务端**，dedicated server 崩溃风险最低。
  2. `buildSrc/` + `annotation-processor/` 把重复样板（如方块/物品/GUI 注册）代码生成化，规模化后极大减错。
  3. 单 `src/` + 内部 `common/client` 的简洁根，比多 Gradle 模块更易导航（前提是团队接受重 `build.gradle`）。
- **最不该学的 1 点**：`build.gradle` 40KB、`buildSrc` + `annotation-processor` 自定义代码生成——工程化极其重型，**普通 mod 完全不需要**，会显著拉高上手门槛。

## 2. 综合：mod 工程组织最佳实践

### 2.1 推荐的目录结构模板

#### 方案 A：跨平台 mod（Architectury，推荐 AI 生成的默认目标）


#### 方案 B：单平台 mod（仅 Forge/NeoForge 或仅 Fabric）

直接去掉 `common/fabric/neoforge` 三层，把上述内容平铺到 `src/main/`：
```
src/main/java/com/example/mod/
├── Mod.java          # 入口
├── registry/         # ModBlocks / ModItems …（替代 reg/，命名更直白）
├── client/  common/  config/  data/  network/  content/  util/

```

> 选择建议：**内容型/中型 mod 用方案 A（Architectury）** 以便将来扩平台；纯学习或小工具 mod 用方案 B。AI 生成时默认产出方案 A 的 `common` 部分即可覆盖 90% 需求。

### 2.3 注册代码的标准写法范式

#### 范式一：集中式 `DeferredRegister`（NeoForge/Forge 原生，小/中型首选）
```java
// 示意写法（基于 neoforged/MDK 真实片段）
public class ModBlocks {
    public static final DeferredRegister<Block> BLOCKS =
        DeferredRegister.create(ForgeRegistries.BLOCKS, ExampleMod.MOD_ID);
    public static final RegistryObject<Block> EXAMPLE_BLOCK =
        BLOCKS.register("example_block", () -> new Block(BlockBehaviour.Properties.of().mapColor(MapColor.STONE)));
    public static void register(IEventBus bus) { BLOCKS.register(bus); }
}
```
- 适用：注册量 < ~200 对象的中小 mod；无需额外库；与官方 MDK 一致，最易上手。

#### 范式二：模块化 `Registrate`（Create 风格，大型/数据驱动首选）
```java
// 示意写法（基于 Create AllItems 真实片段）
public class ModItems {
    private static final Registrate REG = ExampleMod.REGISTRATE;
    public static final ItemEntry<Item> WHEAT_FLOUR = REG.item("wheat_flour", Item::new)
        .tag(ModTags.Items.FLOUR).register();
}
```
- 适用：大型 mod、希望 datagen 自动产出模型/标签/语言；需要 Registrate 依赖。

#### 范式三：按功能模块自注册（巨型 mod 的内容拆分）
- 每个 `content/<feature>/` 包内含自己的 `register(IEventBus)` 或 `DeferredRegister`，由入口统一调用。Mekanism/Create 的 `content/` 即此思路。
- 适用：功能极多、需多人对不同功能并行开发的超大型 mod。

> **选择矩阵**：对象少且想零依赖 → 范式一；对象多且重 datagen → 范式二；功能巨多且团队大 → 范式三（或范式二 + `content/` 分组）。

### 2.5 常见反模式清单

1. **所有东西塞进一个 main 类**：注册 + 事件 + 配置 + GUI 全在 `ExampleMod`。MDK 示例故意如此，但真实 mod（见 Create/TF/Mekanism）都拆 `reg/`、`config/`、`client/`。→ 用 2.1 的目录树。
2. **硬编码字符串不用常量**：到处写 `"examplemod:example_block"`。→ 用 `MOD_ID` 常量 + `id()`/`ResourceLocation.fromNamespaceAndPath` 助手（fabric-example-mod 已示范 `id()`）。
3. **服务端逻辑写在客户端类 / 客户端调用进服务端**：在 common 代码直接 `Minecraft.getInstance()`，dedicated server 启动即崩。→ 客户端独占逻辑放 `client/` 包，或用 `@Mod.EventBusSubscriber(modid=, value=Dist.CLIENT)`、`DistExecutor`、`FMLEnvironment.dist` 做 sided 检查（neoforged/MDK 已示范）。
4. **忘记 sided 检查导致 dedicated server 崩溃**：`@OnlyIn`/`Dist.CLIENT` 使用不当，把客户端类加载到服务端。→ 入口与事件严格区分侧；网络包在两端都需的类不要引用 `minecraft.client.*`。
5. **注册 id 与资源路径不一致**：Java 注册 `"my_block"`，但模型文件叫 `MyBlock.json` → 资源找不到、物品变紫黑块。→ id 全小写蛇形，与文件名严格一致（见 2.4）。
6. **包名 / modid 用大写或非法字符**：modid 必须满足 `[a-z][a-z0-9_]{1,63}`（neoforged/MDK `gradle.properties` 注释明确）。大写 modid 在部分平台直接报错。**中文更不行**——`mod_id` 只能小写英文数字下划线；想要中文名请改 `mod_name`（见下条），别动 `mod_id`。
6.5 **`mod_name` 直接写中文 → `displayName` 变 mojibake**（26.x 实测踩过）：
   ```
   直接写 mod_name=无尽深渊
   → jar 里读到 displayName="æ\x97\xa0å°½æ·±æ¸\x8a"   ← UTF-8 字节被按 Latin-1 重解释
   ```
   **根因**：Gradle 按 Java `Properties` 规范用 **ISO-8859-1** 读取 `gradle.properties`，
   与文件本身是不是 UTF-8 无关。构建不报错、`gradle.properties` 看着也正常，
   只有打开 jar 里的 `META-INF/neoforge.mods.toml` 才能发现。
   **修法：用 `\uXXXX` 转义**（转义序列是纯 ASCII，任何编码下都安全）：
   ```properties
   # 「无尽深渊」= U+65E0 U+5C3D U+6DF1 U+6E0A
   mod_name=\u65E0\u5C3D\u6DF1\u6E0A
   ```
   算转义：`''.join('\\u%04X' % ord(c) for c in '无尽深渊')`
   （注意别在 shell heredoc 里算，`\u` 会被 shell 先吃掉一层——写进 .py 文件再跑）。
   **验证必须开 jar 看**，不能只看 `gradle.properties` 或构建成功：
   ```python
   import zipfile, glob
   z = zipfile.ZipFile(sorted(glob.glob('build/libs/*.jar'))[-1])
   t = z.read('META-INF/neoforge.mods.toml').decode('utf-8')
   assert '无尽深渊' in t, 'displayName 乱码了'
   ```
   > 同理，**Java 源码里的中文日志**（`LOGGER.info("[无尽深渊] ...")`）没这个问题 ——
   > `build.gradle` 已设 `options.encoding = 'UTF-8'`，编译期就是 UTF-8。
   > 只有 `.properties` / `.toml` 这类走 `Properties` 或平台读取器的才要小心。
   **推荐写法：让显示名只有一个来源**（26.1 + 1.20.1 两个工程实测通过）：
   既然 `\uXXXX` 会被 `Properties` 还原成中文，就**没必要在模板里写死中文** ——
   改成走占位符，以后改名字只改 `gradle.properties` 一处：

   ```properties
   # gradle.properties（转义，详见上）
   mod_name=\u4EBA\u95F4\u4E4B\u795E
   ```
   ```toml
   # mods.toml / neoforge.mods.toml
   displayName="${mod_name}" #mandatory
   ```
   两条链路都验过（NeoForge 26.1 的 `neoforge.mods.toml` 与 Forge 1.20.1 的 `mods.toml`，
   两者的 `processResources.expand` 都能正确替换）—— 构建后开 jar 读 toml，显示名是正常中文。

   ⚠️ **算转义时有两处 shell 陷阱**（本仓库都踩过，各一次）：
   - `python - <<'PYEOF'` 里写 `"\u%04X"`：shell 会**先吃掉一层反斜杠**，
     Python 收到的成了 `"\u%04X"` → 直接 `SyntaxError: truncated \uXXXX escape`；
   - `python -c "...'\uXXXX'..."`：同样炸（`\u` 原样进了 Python 字符串字面量）。
   **一律把补丁写进 `.py` 文件再跑**（Write 工具是字面传递、不经 shell），
   或者在代码里用 `chr(92)` 拼反斜杠。

   > 🔴 还有个更阴的：转义写错时**构建照样成功**，只有开 jar 才看得见 ——
   > 所以"改完名字"这件事的验收判据**必须是读 jar 里的 toml**，
   > 而不是"构建成功了"或"gradle.properties 里看着是中文"。


#### 6.6 「模组改成中文名」其实有**三处**，先问清楚是哪一处

| 改哪 | 怎么改 | 玩家在哪看到 |
|---|---|---|
| **显示名** | `mods.toml` 的 `displayName`（推荐走 `${mod_name}`，见 6.5） | 游戏「模组」列表里的名字 |
| **文件名** | `build.gradle` 的 `base { archivesName = mod_name }` | mods 文件夹 / 启动器的模组管理 |
| **内部 id** | `mod_id` | 模组列表里名字下面那行小字 |

🔴 **`mod_id` 不能改**：只能 `[a-z][a-z0-9_]`，中文非法；而且它是**存档数据键与资源路径的一部分**，
改了等于所有存档、配置、资源全部失效。想要中文名请改前两项，别动它。

```groovy
base {
    // 产物文件名用中文显示名 → 人间之神-1.0.0.jar
    archivesName = mod_name     // mod_name 在 gradle.properties 里是 \uXXXX 转义，Gradle 会还原成中文
}
```

⚠️ **换文件名之后必须把旧 jar 删掉**：两个 jar 带着同一个 modid 会让 NeoForge **直接拒载**
（不是"取新的"，是报冲突）。换完扫一眼目录、确认 modid 只出现一次。
（`.bak-xxx` / `.disabled` 这类不以 `.jar` 结尾的文件不会被扫到，可以安心留在目录里。）

> **非 ASCII 文件名 NeoForge 认不认？认。**（26.1 实测：把 `中文文件名测试-1.0.0.jar`
> 丢进 `run/mods/` 起服务端，日志里是 `Found valid mod file 中文文件名测试-1.0.0.jar`、
> `Loading mod file ...`，模组列表也正常列出 `中文文件名测试 1.0.0 (nametest)`，无拒载无报错。）
> 真要说不放心的地方是**上传发布**（某些平台对非 ASCII 文件名不友好），本地运行没问题。

> **问需求时先分清"他眼睛看的是哪一处"**：玩家说"把模组名改成中文"，
> 多半指**他实际看到的那一个**。如果 `displayName` 本来就是中文，那他说的**大概率是文件名**。
> 本仓库就栽过：我把 `mod_name`（内部配置项）改了，游戏里当然看不出任何变化，
> 于是被回了一句"并没有改" —— **先问"你在哪看到的"，比闷头改配置快得多**。
6.6 **cross / 含透明像素的方块不声明 cutout 渲染层 → 游戏里是「黑底方块」**（2026-10-13，1.20.1 实测）：
   自己写的树苗、十字模型类方块，如果只用 `"parent": "block/cross"` 而不声明渲染层，
   进游戏看到的是**一个黑底方块**：贴图图案还在，但本该透明的部分被画成**不透明黑**。
   第一反应往往是"贴图导坏了"去重画贴图 —— 白费功夫。
   **根因**：原版树苗之所以正常，是因为 `ItemBlockRenderTypes` 内部有一份**硬编码的方块名单**
   （`static` 初始化里一个个 `put(Blocks.OAK_SAPLING, rendertype)`），把它们放进 cutout 层。
   自定义方块不在名单里 → 落到默认的 **solid 层** → 透明像素按不透明处理。
   **修法（两条都配上最稳，重复设置无副作用）**：
   1. **model JSON 里声明**（Forge 官方推荐）：
      ```json
      { "parent": "block/cross", "render_type": "minecraft:cutout",
        "textures": { "cross": "mymod:block/my_sapling" } }
      ```
      依据：`ItemBlockRenderTypes.setRenderLayer` 自 **1.19 起被 `@Deprecated`**，废弃注释原文即
      *"Set your render type in your block model's JSON (eg. `"render_type": "cutout"`)"*；
      Forge 的 `ExtendedBlockModelDeserializer` 会解析该字段。
   2. **Java 侧兜底**（防某加载器版本没解析 JSON 字段）：
      ```java
      @Mod.EventBusSubscriber(modid = MODID, bus = Mod.EventBusSubscriber.Bus.MOD, value = Dist.CLIENT)
      public final class ClientSetup {
          @SubscribeEvent
          public static void onClientSetup(FMLClientSetupEvent event) {
              event.enqueueWork(() -> ItemBlockRenderTypes.setRenderLayer(
                      ModBlocks.MY_SAPLING.get(), RenderType.cutout()));
          }
      }
      ```
   > ⚠️ **这个坑无头服务端永远测不出来**：`runServer` 不碰任何渲染，
   > 静态检查 / `build` / RCON 驱动验证可以**全绿**，进游戏一看还是黑方块。
   > 无客户端自动化通道时的低成本判据：把方块铺满一片地面 → 起客户端进世界截图 →
   > 统计**纯黑像素占比**（正常趋近 0%，只剩准星是黑的；真踩坑时黑占比会很高）。
   >
   > **版本差异（别用错）**：上面这套适用于 **1.20.1 ~ 1.21.x**。
   > **26.1 起 `render_type` 字段已被彻底删除**（MC / NeoForge 里都没有解析代码，原版资源也删干净了），
   > 渲染类型改为**按贴图 alpha 自动判定** —— 存在 `0 < alpha < 255` 的像素就走半透明批次，否则走 cutout。
   > 即 26.1 上**不用写这个字段**，要透明就得把 alpha 真正做进 PNG（基准：`glass.png` 只含 0/255 → cutout）。
   > 详见「MC一站式工坊」`SKILL.md` 反模式清单第 16 条。
7. **静态初始化里过早 `.get()`**：`RegistryObject.get()` / `ItemEntry.get()` 在注册完成前调用返回 null。→ 只在 `onInitialize`/`FMLCommonSetup` 之后访问，注册阶段只声明。
8. **手写海量 JSON 而不用 datagen**：Twilight 风格，小 mod 起步 OK，但规模化后配方/标签/语言极易错漏。→ 推荐 datagen（Create/Botania/Supplementaries 均用）；至少语言与标签用 datagen。
9. **配置热重载不同步**：改了 `COMMON` 配置不重新读取/不向客户端同步，导致客户端服务端状态不一致。→ 学 `TFConfig`：监听 `ModConfigEvent` 重算缓存并向客户端发包同步。
10. **平台 API 直接写进 common 代码**：在 `common/` 里 `import net.fabricmc...` 或 `import net.minecraftforge...`。→ 走 `platform/IPlatformHelper` 抽象（Botania `XplatAbstractions`、Supplementaries `SuppPlatformStuff` 范式）。
11. **保留未使用代码/过早抽象**：如 `unused/` 目录、`dynamicpack` 等高级机制在小 mod 中徒增负担。→ YAGNI：先用范式一 + 单模块跑通，再按需拆分。

### 2.6 从零到可运行的标准开发流程

```
1. 脚手架
   - 选模板：跨平台→architectury-templates 的 common/fabric/forge；
             仅 Forge/Neo→neoforged/MDK；仅 Fabric→fabric-example-mod。
   - 改 gradle.properties：mod_id、mod_name、mod_version、minecraft_version、group。
   - 确认 resources 下有 fabric.mod.json（Fabric）或 META-INF/mods.toml（Forge）。

2. 注册第一个物品
   - 建 reg/ModItems.java（或 AllItems/ModItems），用 DeferredRegister/Registrate 声明
     public static final 字段，注册到 mod event bus。
   - 入口类持有 MOD_ID 常量，构造/初始化时触发注册。

3. 加模型与纹理
   - textures/item/<id>.png（16x16 占位图即可先跑通）
   - models/item/<id>.json（用 "parent":"minecraft:item/generated" + 纹理层）
   - 方块还要 models/block/<id>.json + blockstates/<id>.json。

4. 加配方/战利品
   - data/<modid>/recipes/<id>.json（手写 JSON 起步；规模化改 datagen）
   - data/<modid>/loot_tables/<id>.json
   - 把物品加入创造选项卡（CreativeModeTab / Fabric ItemGroup）。

5. 本地化
   - assets/<modid>/lang/en_us.json：{"item.<modid>.<id>":"My Item", ...}
   - 同步写 zh_cn.json（中文项目必做）。

6. 跑客户端验证
   - Forge/Neo：./gradlew runClient
   - Fabric：     ./gradlew runFabric（或 runClient）
   - 检查：物品显示、纹理正确（非紫黑）、配方可用、日志无注册/资源报错。
   - 如做服务端：另跑 ./gradlew runServer 验证无 sided 崩溃。

7. 打包
   - ./gradlew build
   - 产物：build/libs/<archivesName>-<version>.jar
   - 放入游戏 instances/mods 目录测试。
```

## 3. 结论要点（给 AI 生成器的约束清单）

- **默认目录**：Architectury 式 `common/{reg,content,client,common,config,data,network}/` + `fabric/`、`neoforge/`。
- **默认注册范式**：`DeferredRegister`（零依赖、与 MDK 一致）；对象多时升级 Registrate。
- **命名铁律**：modid 小写蛇形且合规；注册字段 `SCREAMING_SNAKE_CASE`；注册 id = 资源文件名。
- **侧隔离铁律**：客户端独占放 `client/` 且必须 sided 保护；common 代码不得引用 `minecraft.client` 或任一平台 API。
- **资源铁律**：`assets/<modid>/{models,textures,lang,blockstates}` 与 `data/<modid>/{recipes,loot_tables,tags,advancements}` 不可省略 `lang`（至少 en_us + zh_cn）。
- **配置铁律**：Forge 用 `ForgeConfigSpec` 的 `Common`/`Client` 双层 + `ModConfigEvent` 同步（参考 TFConfig）；不要散落 `boolean` 常量。
- **反模式红线**：单类全塞、硬编码字符串、id/文件名不一致、common 引平台 API、静态块过早 `.get()`——生成时主动规避。
