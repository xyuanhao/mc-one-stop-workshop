# 26.x 跨模组方块识别（「只要是矿物/木头就认」）+ 运行时探针

做连锁挖矿、矿物嗅探、自动分类这一类功能时，「什么算矿物、什么算木头」是最核心的问题。
写成硬编码方块列表（或者只查名字里有没有 `ore`），原版能跑，**一装模组就废**。

26.1 实测。配套脚本：`tools/检查连锁分类.py`（结构）、`tools/实测分类器.py`（真服务端行为）。

---

## 1. 🔴 三级判据：标签 → 名字 → 掉落物

按**可信度**从强到弱排列，**任何一级命中就算**。三级是互补的，少一级就有一批模组认不出来。

### 第一级：标签（最可信）

```java
Tags.Blocks.ORES          // c:ores      —— 跨模组约定，主流模组都会打
BlockTags.COAL_ORES, BlockTags.IRON_ORES, ...   // 原版各族，双保险
BlockTags.LOGS            // minecraft:logs
```

关键认知：

- **`c:ores`（NeoForge `Tags.Blocks.ORES`）是生态约定**，Mekanism / Thermal / Create /
  Immersive Engineering 的矿石都会进这个标签。它是"通用方案"的主力。
- **`minecraft:logs` 比 `c:ores` 还要可靠** —— 模组木头**不打这个标签就等于废了**
  （不能当燃料、合不出木板、原版配方全用不了）。所以木头基本可以只靠这一级。
- **子标签会被并进父标签吗？** 27 个方块实测结果：
  `minecraft:ancient_debris`（远古残骸）的判定是 **true**，说明
  `c:ores/netherite_scrap` 确实被并进了 `c:ores`。
  但**别假设**：这条要用探针实测，因为标签的 include 关系是数据包决定的。

### 第二级：名字（兜住不打标签的模组）

🔴 **绝对不要写 `path.contains("ore")`** ——
`forest`、`more`、`core`、`shore` 全都含 "ore"。只认**词形**：

```java
private static boolean nameLooksOre(String path) {
    return path.equals("ore")
            || path.endsWith("_ore")      // iron_ore / deepslate_iron_ore / tin_ore
            || path.startsWith("ore_")    // ore_copper（有些模组这么命名）
            || path.contains("_ore_");
}
```

木头同理，只认**词尾**（`_log` / `_stem` / `_wood` / `_hyphae`）——
`wooden_door` 这种含 wood 但不是原木的要躲开（原版注册名其实是 `oak_door`，
但模组不一定）。

> ⚠️ **这条边界的真实样本在原版里不存在**：「名字含 ore 却不是矿石」的方块**一个都没有**。
> `minecraft:forest_rock` 听着像，但它其实是**地形特征 feature**，不是方块 ——
> `setblock` 会直接报 `Unknown block type 'minecraft:forest_rock'`。
> 所以这类判据必须能**喂臆想出来的字符串**来测（见 §4 的 `probe_name`）。

### 第三级：掉落物（最本质，仅服务端）

「矿石」的行为本质是「挖出来能得到金属/宝石原料」。哪怕一个方块既没打标签、
名字也不像，只要掉原矿就该被认出来。

```java
Tags.Items.RAW_MATERIALS, Tags.Items.INGOTS, Tags.Items.GEMS,
Tags.Items.DUSTS, ItemTags.COALS
```

🔴 **但必须配两道门，否则误伤严重**：

| 门 | 不加上会发生什么 |
|---|---|
| `!state.is(Tags.Blocks.STORAGE_BLOCKS)` | `coal_block`（煤矿块）也掉煤 → **挖煤块会把一整堆煤块连锁掉**。矿物块都会进 `c:storage_blocks`，矿石不会，用它区分。 |
| `state.is(BlockTags.MINEABLE_WITH_PICKAXE)` | `glowstone`（荧石）掉荧石粉，而荧石粉在 `c:dusts` 里 → **荧石被当成矿石**。矿物**本来就必须用镐挖**，这是本质属性。 |

> ⚠️ 两道门都**不能单独用**：只靠镐的话石头也是镐挖的（但它掉圆石，过不了掉落物检查）；
> 只靠 `storage_blocks` 挡不住荧石。得两个一起。

## 2. 🔴 「同族」：什么能跟什么一起被连锁

连锁的准入（是不是矿物/木头）和**分族**（能不能连到一起）是两件事。

| 类别 | 分族依据 | 效果 |
|---|---|---|
| 矿物 | **掉落物集合** | `iron_ore` 与 `deepslate_iron_ore` 同族（都掉 `raw_iron`）—— 它们本来就是**同一条矿脉的两种外壳**，模组的矿石变体同理 |
| 木头 | **方块本身** | 只连同一种原木 —— 砍橡树不该顺手把旁边那棵白桦也削了 |

实现上用 `Map<Block, String>` 缓存族键（掉落物计算要跑整套战利品表，不缓存会很卡）：

```java
public static String familyOf(ServerLevel level, BlockPos pos, BlockState state) {
    if (isLog(state)) {
        return "log|" + pathOf(state.getBlock());
    }
    return FAMILY_CACHE.computeIfAbsent(state.getBlock(), b -> {
        List<String> ids = ...;   // Block.getDrops(...) 的物品 id，排序后拼接
        return ids.isEmpty() ? "ore|" + pathOf(b) : "ore|" + String.join(",", ids);
    });
}
```

⚠️ 缓存以 `Block` 为键、却用到了传入的 `pos`/`state` —— 这是**有意的**：
矿石掉落物只由方块类型决定，跟坐标无关。

## 3. 🔴 客户端与服务端必须共用同一个分类器

最容易出的错：服务端连锁用一套判据，客户端嗅探自己写一套（比如查
`getDescriptionId().contains("_ore")`）。结果就是最尴尬的那种 ——
**粒子把矿石标出来了，玩家过去一挖，连锁不动**。玩家只会觉得"这功能时灵时不灵"，
根本不会想到是两套判据不一致。

做法：分类逻辑放一个类，客户端只调**它的无 level 重载**：

```java
public static boolean isOre(BlockState state);                          // 标签 + 名字（客户端可用）
public static boolean isOre(ServerLevel level, BlockPos pos, BlockState state);  // 多一级掉落物
```

客户端拿不到方块掉落物（`Block.getDrops` 要 `ServerLevel`），所以第三级在客户端自动跳过 ——
这是**接受范围内的漏**，比两套判据漂移好得多。

### 缓存必须能清

分类结果缓存以 `Block` 为键，但**标签是数据包定义的** ——
换一个服务器（或别人重载了数据包）之后标签内容可能完全不同，留着上一局的缓存会把
新服务器的矿物**静默判错**。所以要提供 `clearCaches()`，在**登录**和**退出世界**时都调。

## 4. 🔴 运行时判据要用「探针命令」暴露出来，才能被 RCON 批量验证

这一类逻辑的输入全是**运行时**的：注册表、数据包标签、战利品表。
编译期一律看不出来，静态检查也查不到。所以要在 mod 里留几条**只读探针命令**：

```
/attrlevel probe <pos>         # 某个坐标的方块分类结论 + 族键
/attrlevel probe_name <名字>    # 直接喂一个**名字**（不必真实存在）
/attrlevel chain <pos>         # 从这点出发会连锁到哪几块（只收集，不破坏）
```

有了它们，验证就变成 RCON 批处理：

```python
cmd("setblock %d %d %d %s" % (x, y, z, block))
parsed = parse(cmd("attrlevel probe %d %d %d" % (x, y, z)))
assert parsed["ore"] == "true"
```

**收益实测**：26.1 服务端上一次跑完 **30 个方块 + 18 个名字 + 6 组连锁**，
不用进游戏、不用人肉挖矿。而且它测的是**真注册表**，不是我的想象：

| 实测发现 | 说明 |
|---|---|
| `ancient_debris` → `ore=true`，族 `ore\|ancient_debris` | 它掉的是自己，全靠 `c:ores` 子标签认出来 |
| `coal_block` / `glowstone` / `forest_rock` → 全部正确排除 | 两道门和词形判据都真的生效了 |
| `iron_ore` 与 `deepslate_iron_ore` 族键**完全相同** | 掉同一种原矿 → 同族，挖铁矿会连深层铁矿 |
| `oak_log` 族 `log\|oak_log`，与 `birch_log` 不同 | 砍一棵不会带走整片森林 |

### 探针要分「查实体」和「查名字」两种

🔴 名字判据的边界情况**在原版没有真实样本**（见 §1）。所以 `probe_name` 是必需的 ——
它让你能喂 `forest_rock`、`more`、`core`、`shore`、`mekanism:tin_ore`
这类**臆想出来的**名字，把那条边界真正测到。

### `chain` 探针要**只收集不破坏**

这样可以在同一个世界里反复试不同的摆法（矿脉形状、混不同矿种、测上限），
不必造假玩家、也不必真的挖。**连锁真正容易失控的地方全在收集这一步** ——
连太多、连到别的矿种、上限没生效 —— 后面的破坏只是一遍原版 API 调用。

配套的实测用例（真服务端上跑过）：

| 摆法 | 期望 | 验的是 |
|---|---|---|
| 3×3×3 实心铁矿，从中心出发 | 26 块（不含起点） | 基本连通范围 |
| 上面再**紧贴**一块金矿 | 仍 26，不含 `gold_ore` | 同族过滤 |
| 5×5×5 铁矿（125 块） | 截到上限（64） | `CHAIN_LIMIT` 生效 |
| 竖直 5 格橡木 + 接一段白桦 | 4 块，不含 birch | 木头分族 |
| 一片石头 | 0 块，且报「不可连锁」 | 准入门 |

## 4.5 🔴 嗅探半径做大之后：扫描和显示都得换（26.1 实测）

需求从 10 格提到 64 格时，**原来的实现两头都撑不住**。

### 扫描：不能再三重循环硬扫

10 格 = 21³ ≈ 9 千格还行；**64 格 = 129³ ≈ 215 万格**，每 20 tick 跑一次必然卡死。

改成先按**区块 section** 粗筛：

```java
LevelChunk chunk = level.getChunkSource().getChunk(cx, cz, false);   // false = 没加载就别生成
for (int i = 0; i < sections.length; i++) {
    LevelChunkSection section = sections[i];
    if (section == null || section.hasOnlyAir()) continue;
    if (!section.maybeHas(BlockClassifier::isOre)) continue;   // ← 调色板级判断，一次问出"这 16³ 有没有矿"
    scanSection(level, section, cx, chunk.getMinSectionY() + i, cz, center, radiusSqr);
}
```

`maybeHas` 把 99% 的纯石头 / 纯空气 section 一次就跳过，只有真含矿的才逐格细看。
另外**扫描立方体 + 球形过滤**：不然墙角那些"隔着一百格"的也会被算进来。

### 🔴 上限的截断必须「先全收、再按距离取最近」

**症状**（玩家原话）：「高亮的区域为什么不是周围而是前方」。

**根因**：扫描是**按区块 X→Z、section 由低到高**走的，而上限写成了"边扫边判"：

```java
// ❌ 谁先被扫到谁占坑
SNIFFED.add(pos);
if (SNIFFED.size() >= MAX_SNIFFED) return;
```

矿洞深处 64 格内轻松上千个矿石，**名额被最先扫到的那个象限吃光** ——
玩家看到的不是"以自己为中心的球"，而是**偏在某个方位的一角**（看着就像只标了正前方）。

**修法**：收集阶段用一个宽松的硬上限（防内存爆），收完**排序后再取最近的 N 个**。

```java
List<BlockPos> found = new ArrayList<>();
collectOres(level, center, found);                                  // 上限 SNIFF_COLLECT_LIMIT（8192）
found.sort(Comparator.comparingDouble(center::distSqr));            // ← 关键
for (int i = 0; i < found.size() && i < MAX_SNIFFED; i++) {         // 只留最近的
    SNIFFED.add(found.get(i));
}
```

排序之后**无论上限多少，标出来的永远是离玩家最近的那一圈** —— 这才是玩家期望的语义。

**实测判据**：在 8 个方位各摆 150 个矿石（共 1200，**故意超上限**），
打印结果的**扇区分布**：

```
总数=1024  最远水平距离=29
扇区分布 0°:180 45°:175 90°:152 135°:63 180°:30 225°:82 270°:166 315°:176
```

8 个扇区**全都有**、且最远只到 29 格 = 「周围一圈」✓
（修复前会只亮一两个扇区。）数量不均是因为世界里本来就有别的矿石在更近处，
这属于正常 —— 判据看的是**方位覆盖**，不是均等。

### 显示：方块没法"发光"，只能画边

`GLOWING` 效果只能挂**实体**，方块没这个概念（生物标亮那套搬不过来）。
用同一个 `ShapeRenderer.renderShape(...)`（原版画准星选中方块轮廓就是它），
线宽粗细和原版一致，不突兀：

```java
@SubscribeEvent
public static void onAfterTranslucentBlocks(RenderLevelStageEvent.AfterTranslucentBlocks event) {
    PoseStack poseStack = event.getPoseStack();
    if (poseStack == null) return;
    Vec3 camera = minecraft.gameRenderer.getMainCamera().position();   // ⚠️ 是 position() 不是 getPosition()
    VertexConsumer lines = minecraft.renderBuffers().bufferSource().getBuffer(RenderTypes.lines());
    for (BlockPos pos : targets) {
        VoxelShape shape = level.getBlockState(pos).getShape(level, pos);
        ShapeRenderer.renderShape(poseStack, lines, shape,
                pos.getX() - camera.x, pos.getY() - camera.y, pos.getZ() - camera.z, COLOR, WIDTH);
    }
    buffers.endBatch(RenderTypes.lines());
}
```

要点：**坐标要减去相机位置**（这个阶段还是绝对世界坐标）；
选 `AfterTranslucentBlocks` 阶段 —— 隔着水 / 玻璃也看得见，线框不会被不透明方块遮掉；
类名是 `net.minecraft.client.renderer.rendertype.RenderTypes`（26.1 起在 `rendertype` 子包）。

### 🔴 线框必须用**带深度偏移**的 render type，不能用 `lines()`

**症状**（玩家原话）：「一开始还好，靠近之后高亮就消失了」。

**根因**：`ShapeRenderer` 画的是方块的**精确外框** —— 和方块表面**完全共面**。
而 render type 的深度比较不一样（都在 `RenderPipelines` 里能查到）：

| render type | 深度状态 | 结果 |
|---|---|---|
| `RenderTypes.lines()` | `LINES` → `DepthStencilState.DEFAULT`（**严格 LESS_THAN**） | 共面时被方块表面盖掉 |
| `RenderTypes.secondaryBlockOutline()` | `SECONDARY_BLOCK_OUTLINE` → `LESS_THAN_OR_EQUAL` | 贴着表面也画得出来 |
| （`LINES_DEPTH_BIAS`） | `LESS_THAN_OR_EQUAL` + **depth bias −1.0** | 同上（但 `RenderTypes` 里没给工厂） |

两者都带 `VIEW_OFFSET_Z_LAYERING`，但那是个**固定偏移**：
远看够用、线能透出来；**一走近**，透视让深度变化变快，偏移就不够了 ——
线被方块表面整个盖掉。这就是"远看有、走近没"。

**修法**：用 `secondaryBlockOutline()`（原版画准星方块轮廓用的那个）：

```java
RenderType outline = RenderTypes.secondaryBlockOutline();
VertexConsumer lines = buffers.getBuffer(outline);
... ShapeRenderer.renderShape(poseStack, lines, shape, ...) ...
buffers.endBatch(outline);   // ⚠️ endBatch 也要用同一个
```

> ⚠️ **顺带记一下 `VoxelShape` 没有 `inflate`** —— 想靠"把框撑大一点"绕开深度问题是不行的，
> 只有 `move(...)`。别在这上面浪费时间，直接从 render type 入手。

**怎么验**：这个问题**日志看不出来**，必须看图。
在玩家**脚下正前方 1~6 格**摆一片矿石（不是头顶 —— 第一次就摆错了位置，
视角朝下完全看不到，白跑一轮），低头截一张：

```java
net.minecraft.client.Screenshot.grab(mc.gameDirectory, "near-1",
        mc.getMainRenderTarget(), 1, msg -> LOGGER.info("截图完成: {}", msg.getString()));
```

存到 `run/screenshots/`。**注意它不写扩展名**（就是个 PNG 文件裸存），
要自己补 `.png` 才能用图片查看器打开。

> 💡 外部截屏（PowerShell `Add-Type` + `System.Drawing`）会被安全策略拦掉，
> 让 mod 自己用 MC 的 `Screenshot.grab` 更省事，还不用管窗口有没有被挡住。

## 5. 连锁本身的几个坑

### 5.0 🔴 最隐蔽的一个：`chainMine` 的起点，那时**已经是空气了**

**症状**：连锁**从来不生效**，而且完全不报错 —— 挖一块就只掉一块。

**根因**：`chainMine` 挂在 `destroyBlock` 的 `@At("RETURN")` 上，
进到它的时候**那个方块已经被挖掉、变成空气了**。
而 `chainMine` 开头要判「起点是不是矿石 / 原木」：

```java
BlockState originState = level.getBlockState(origin);       // ← 空气
if (!BlockClassifier.isChainable(level, origin, originState)) {
    return;                                                  // ← 每次都在这里静默 return
}
```

**修法**：在 `@At("HEAD")` 处先把状态记下来，传给 `chainMine`。

```java
@Unique private BlockState attrlevel$brokenState;

@Inject(method = "destroyBlock", at = @At("HEAD"))
private void attrlevel$beforeDestroyBlock(BlockPos pos, CallbackInfoReturnable<Boolean> cir) {
    this.attrlevel$brokenState = this.player.level().getBlockState(pos);
}

@Inject(method = "destroyBlock", at = @At("RETURN"))
private void attrlevel$afterDestroyBlock(BlockPos pos, CallbackInfoReturnable<Boolean> cir) {
    if (cir.getReturnValueZ()) Awakening.chainMine(this.player, pos, this.attrlevel$brokenState);
    ...
}
```

> ⚠️ **HEAD 注入也必须收 `CallbackInfoReturnable`**，不能图省事写 `CallbackInfo` ——
> `destroyBlock` 有返回值，Mixin 会**在运行时**抛 `InvalidInjectionException`
> 并**崩掉整个 mixin 应用**。**编译期完全不报**，所以「能编译」在这里毫无意义。

### 5.0.1 🔴 更要命的教训：是**我自己的测试**把 bug 掩蔽了两轮

第一版实现时我写了 `debugCollect(level, origin)` 探针，实测「3×3×3 铁矿从中心连 26 块」**全绿**。
但那测的是**还在的实心矿**；真实链路的起点是**挖完之后的空气**。
**两者的起点状态不同，所以测试通过 ≠ 功能可用。**

**判据**：验证一个挂在「事件之后」的逻辑时，**先问一句"这时候世界变成什么样了"** ——
你的测试夹具必须复现**那个时刻**的状态，而不是"操作之前"的状态。

**端到端二分定位法**（这次用它一次定位）：

摆两片一样的矿，一片走真实链路、一片**直接调**目标函数：

```
A 片走 player.gameMode.destroyBlock(...)（含 mixin）：剩余=26   ← 没连
B 片直接调 Awakening.chainMine(...)：                 剩余=1    ← 连掉了
```

两边一比，立刻分清是「接线断了」还是「函数自己不干活」，
比在两头分别读代码猜快得多。

### 5.1 其余几条

- **递归守卫**：连锁内部如果又走一遍原版破坏流程（为了逐块触发破坏事件、
  让领地保护能拦），会**再次进到 mixin**。必须有个 `ThreadLocal` 守卫挡住，
  否则一片矿脉连成雪崩。
- **别用 `level.destroyBlock` 代替 `player.gameMode.destroyBlock`** ——
  后者会照常触发破坏方块事件，**领地保护 / 出生点保护插件能逐块拦下**；
  前者绕过事件，等于给玩家一把无视保护的电钻。
- **必须有上限**：撞上模组的巨型矿脉，一次连几百块要算几百次战利品表、
  发几百个方块更新，直接卡成幻灯片。
- **只走 6 个正交方向**，不走斜角：矿脉和树干本身就是正交连通的，
  走斜角的话一片"棋盘状"散布的矿石会被算成一条脉。

> ⚠️ 如果整合包里已经装了 FTB Ultimine 这类连锁 mod，**注意别和它抢同一次破坏** ——
> 两边都接管会出现掉落物翻倍或被算两次。可以先看看那个 mod 在不在装载列表里，再决定要不要开自己的连锁。

## 5.5 「全面体检」怎么做：造一个满配玩家，逐项核对实际数值

想主动找 bug（而不是等玩家报）时，最有效的一招是**在真实环境里造一个满配状态，
把该对的东西全读一遍**。纯读代码查不出来，因为很多问题是"数值对不上"而不是"报错"。

### 体检要核对什么

| 项目 | 期望 | 怎么读 |
|---|---|---|
| 等级 → 属性 | 10 级 = 基础 ×2 | `player.getAttribute(attr).getValue()` |
| **修正器数量** | 每个属性**恰好 1 个** | `instance.getModifiers().size()` ← 多了就是重复挂载（属性翻倍） |
| 技能效果是否生效 | 升级后**立刻**为 true | `player.hasEffect(...)` |
| 界限数值 | 不减成负数、不超上限 | 直接打印（如 XP 成本在极高等级） |
| 界面能否构建 | 不抛异常 | `mc.setScreen(new XxxScreen())` |

### 这一步抓到的真实 bug

```
[体检] 技能效果（升级后 5 tick，应已生效）
[体检] 夜视效果 = false   ← ❌
[体检] 水下呼吸 = false   ← ❌
```

原因：`refreshEffects` 只挂在 `tick` 里那个 **200 tick** 的周期上，
所以点了升级之后，夜视这类**恒久效果要等最多 10 秒**才出现 ——
那 10 秒里界面显示已升级、身上毫无变化，玩家会以为没生效。

**修法**：升级成功后**立刻**调一次 `refreshEffects`，不要等周期。
（属性那一侧没这个问题，因为 `applyModifiers` 在升级 / 觉醒里都是接着调的。）

> **通用判据**：凡是"由 tick 周期维护的状态"，都要问一句
> **「刚改完的那一刻，状态是新的吗？」** 周期刷新只适合"持续维持"，
> 不适合"响应一次动作"。动作发生后应该立即应用一次。

### 体检的一个细节

检查**时机**要和验证目标匹配：想验"立刻生效"就得在动作后 **几 tick** 内查；
等太久会把"周期刷新终于追上"误当成"立即生效"。这次先把检查放在 40 tick 后，
结果测不出问题——把检查挪到 5 tick 后才暴露。

## 6. 🔴 查「某个符号在不在」之前，先问「它在同一个方法里出现了几次」

这一轮又踩了一次（本项目第四次）：判据写成
「`chainMine` 方法体里有没有 `IN_AREA_MINE`」，而方法体里还有两处
`IN_AREA_MINE.set(...)` —— 把**入口守卫**整个删掉，判据照样绿。

```python
# ❌ 太宽：方法里还有 .set(...)
if "IN_AREA_MINE" not in body: fail(...)

# ✅ 查"有没有读它"
if not re.search(r"if\s*\([^)]*IN_AREA_MINE\.get\s*\(\s*\)", body): fail(...)
```

同一轮还有一条同类：判据查 `"probe" not in code`，
而坏样本把 `literal("probe")` 改成 `literal("probe_disabled")` ——
**子串包含也算命中**。要用完整字面量 `literal("probe")`。

> 通用写法：**判据要查「起作用的那个形态」，不是「那个名字出现过」**。
> 子串包含、同名多处、只查声明不查调用，是这类假绿的三兄弟。
