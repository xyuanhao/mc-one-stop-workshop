# 常用代码片段（按系统分类）

> 用法：先确认你的 **MC 版本 + 加载器**，只抄对应那一节。跨版本混抄 = 编译失败。
>
> 标注 🟢 = 官方模板实测（26.x）；🔵 = 来自官方文档/社区验证；⚠️ = 待验证，用前请核对官方源。

## 1. 物品注册

### 🟢 NeoForge 26.x（实测自官方 MDK 26.1）
```java
public static final DeferredRegister.Items ITEMS = DeferredRegister.createItems(MODID);

// 简单物品（26.x 传 lambda）
public static final DeferredItem<Item> MY_ITEM =
    ITEMS.registerSimpleItem("my_item", p -> p.food(new FoodProperties.Builder()
        .alwaysEdible().nutrition(1).saturationModifier(2f).build()));

// 自定义物品类
public static final DeferredItem<Item> MY_CUSTOM =
    ITEMS.registerItem("my_custom", MyItem::new, p -> p.stacksTo(1).rarity(Rarity.RARE));
// 或（不需要额外属性时）
public static final DeferredItem<Item> MY_CUSTOM2 =
    ITEMS.register("my_custom2", () -> new Item(new Item.Properties().stacksTo(16)));
```

⚠️ **`registerItem(String, Function, Item.Properties)` 这个重载从 1.21.10 起已弃用待删**
（26.1 编译会打 `警告: [removal] Items 中的 registerItem(...) 已过时, 且标记为待删除`）。
把第三个参数从 **`Item.Properties` 实例**换成 **`UnaryOperator<Item.Properties>`（lambda）**：

| ❌ 弃用 | ✅ 现在写 |
|---|---|
| `registerItem(id, MyItem::new, new Item.Properties().stacksTo(1))` | `registerItem(id, MyItem::new, p -> p.stacksTo(1))` |

同理还有 `registerSimpleItem(id, Item.Properties)` → `registerSimpleItem(id, UnaryOperator)`、
`registerBlockItem` / `registerSimpleBlockItem` 的同名重载。**不影响运行，但会一直报警告**，
而且既然标了 `forRemoval`，下一个大版本就会真的删。

### 🔵 NeoForge 1.21.x
```java
public static final DeferredRegister.Items ITEMS = DeferredRegister.createItems(MODID);
// 1.21.x 传 Properties 实例（不是 lambda）
public static final DeferredItem<Item> MY_ITEM =
    ITEMS.registerSimpleItem("my_item", new Item.Properties().food(...));
```

### 🔵 Forge 1.20.1
```java
public static final DeferredRegister<Item> ITEMS =
    DeferredRegister.create(ForgeRegistries.ITEMS, MODID);
public static final RegistryObject<Item> MY_ITEM =
    ITEMS.register("my_item", () -> new Item(new Item.Properties()));
```
> Forge 1.20.1 用 `RegistryObject` + `ForgeRegistries`，NeoForge 1.20.2+ 用 `DeferredItem` + `Registries`。

### 🔴 可穿戴物品（26.1 实测）

**`ArmorItem` 类已删除，且没有 `p.armor(...)` 这种一步到位的工厂方法。** 26.1 给非盔甲物品加穿戴能力走 `equippable(EquipmentSlot)` 数据组件：

```java
// 眼镜/饰品/披风等「不提供护甲值」的可穿戴物品
public static final DeferredItem<Item> FUTURE_GLASSES = ITEMS.registerItem(
    "future_glasses",
    Item::new,                      // 注意是 Item::new，不是 ArmorItem::new
    p -> p.stacksTo(1)
          .rarity(Rarity.RARE)
          .equippable(EquipmentSlot.HEAD)   // ← 26.1 关键：head 槽
          .component(DataComponents.LORE, new ItemLore(List.of(
              Component.translatable("tooltip.mymod.desc").withStyle(ChatFormatting.AQUA)))));
```

判定规则：
| 想要的效果 | 26.1 写法 |
|---|---|
| 纯穿戴、无护甲值（眼镜/头盔装饰） | `.equippable(EquipmentSlot.HEAD)` |
| 真盔甲（有护甲值+韧性+装备层贴图） | `p.humanoidArmor(ArmorMaterial, ArmorType)`，见 §13.2 |

⚠️ `.equippable(...)` 有多个重载（`EquipmentSlot` / `EquipmentSlot + assetId` / `equippableUnswappable`）。**只有一个槽时传 `EquipmentSlot` 单参重载**，别手写 `new Equippable(...)`（构造签名容易对不上）。

⚠️ **`Item.appendHoverText` 在 26.1 已废弃**。要加物品说明文本，别覆写这个方法，直接在注册时塞 `DataComponents.LORE`（如上面代码）。做了 `FutureGlassesItem extends Item` 只为覆写 tooltip 的，整个类可以删掉。

### 🟢 Fabric 26.x
```java
public static final Item MY_ITEM = register("my_item",
    Item::new, new Item.Properties());

private static <T extends Item> T register(String id, Function<Item.Properties, T> factory, Item.Properties settings) {
    return Registry.register(Registries.ITEM, Identifier.fromNamespaceAndPath(MOD_ID, id), factory.apply(settings));
}
```
`Identifier.fromNamespaceAndPath` 是 26.x 的正确写法（`new Identifier(...)` 已失效）。

## 3. 方块实体（BlockEntity）

三件套：**BlockEntity 类 + BlockEntityType 注册 + 让 Block 实现 EntityBlock**

### 🟢 NeoForge（1.21.x / 26.x 通用）

```java
public class MyBlockEntity extends BlockEntity {
    public MyBlockEntity(BlockPos pos, BlockState state) {
        super(ModBlockEntities.MY_BLOCK_ENTITY.get(), pos, state);
    }
    // 存读数据（1.20.5+ 用 Data Components，方块仍用 NBT 存档）
    @Override protected void saveAdditional(CompoundTag tag, HolderLookup.Provider registries) {
        super.saveAdditional(tag, registries);
        tag.putInt("progress", this.progress);
    }
    @Override protected void loadAdditional(CompoundTag tag, HolderLookup.Provider registries) {
        super.loadAdditional(tag, registries);

public static final DeferredRegister<BlockEntityType<?>> BLOCK_ENTITIES =

public static final DeferredHolder<BlockEntityType<?>, BlockEntityType<MyBlockEntity>> MY_BLOCK_ENTITY =
    BLOCK_ENTITIES.register("my_block_entity",
        () -> new BlockEntityType<>(MyBlockEntity::new, ModBlocks.MY_BLOCK.get()));

// ③ Block 里
public class MyBlock extends BaseEntityBlock {
    @Override public MapCodec<MyBlock> codec() { ... }   // 1.21+ 需要

    @Override protected <T extends BlockEntity> BlockEntityTicker<T> getTicker(
```

**推荐：能用 datagen 就别手写 JSON**，减少路径错误。

### 🟢 NeoForge（MDG 版 run 配置已在模板里，任务名 `data`）

```java
@EventBusSubscriber(modid = MODID, bus = EventBusSubscriber.Bus.MOD)
public class ModDataGenerators {
    @SubscribeEvent
    public static void gatherData(GatherDataEvent event) {
        DataGenerator gen = event.getGenerator();
        PackOutput output = gen.getPackOutput();
        CompletableFuture<HolderLookup.Provider> lookup = event.getLookupProvider();

        gen.addProvider(event.includeServer(), new ModRecipeProvider(output, lookup));
        gen.addProvider(event.includeServer(), ModLootTableProvider.create(output));
        gen.addProvider(event.includeServer(), new ModBlockTagProvider(output, lookup, helper));
        gen.addProvider(event.includeClient(), new ModItemModelProvider(output));
        gen.addProvider(event.includeClient(), new ModBlockStateProvider(output, helper));
    }
}
```

**配方 Provider**：
```java
public class ModRecipeProvider extends RecipeProvider {
    public ModRecipeProvider(PackOutput output, CompletableFuture<HolderLookup.Provider> lookup) {
        super(output, lookup);
    }
    @Override protected void buildRecipes(RecipeOutput output) {
        // 有序合成
        ShapedRecipeBuilder.shaped(RecipeCategory.MISC, ModItems.MY_ITEM.get(), 1)
            .pattern("XXX").pattern(" # ").pattern(" # ")
            .define('X', ModItems.MY_INGOT.get())
            .define('#', Tags.Items.RODS_WOODEN)
            .unlockedBy("has_ingot", has(ModItems.MY_INGOT.get()))

            .save(output, "my_ingot_from_smelting");

}
```

## 6. 网络包（客户端 ↔ 服务端）

### 🔵 NeoForge（1.20.5+ 统一写法）
```java
// ① 定义包
public record MyPayload(String text, int value) implements CustomPacketPayload {
    public static final Type<MyPayload> TYPE =
        new Type<>(ResourceLocation.fromNamespaceAndPath(MODID, "my_payload"));
    public static final StreamCodec<RegistryFriendlyByteBuf, MyPayload> STREAM_CODEC =
        StreamCodec.composite(
            ByteBufCodecs.STRING_UTF8, MyPayload::text,
            ByteBufCodecs.VAR_INT,     MyPayload::value,
            MyPayload::new);
    @Override public Type<MyPayload> type() { return TYPE; }
}

// ② 注册
@SubscribeEvent
public static void register(final RegisterPayloadHandlersEvent event) {
    final PayloadRegistrar registrar = event.registrar("1");   // 协议版本字符串
    registrar.playBidirectional(
        MyPayload.TYPE, MyPayload.STREAM_CODEC,
        new DirectionalPayloadHandler<MyPayload>(
            (payload, ctx) -> ctx.player().ifPresent(p -> { /* 客户端收到 */ }),
            (payload, ctx) -> { /* 服务端收到 */ }
        ));
}

// ③ 发送
PacketDistributor.sendToServer(new MyPayload("hi", 1));        // C→S
PacketDistributor.sendToPlayer(player, new MyPayload("hi", 1)); // S→C
```
> 1.20.4 及以前用 `SimpleChannel` + `FriendlyByteBuf`，1.20.5 起废弃。
> ⚠️ **26.x 改名**：`ResourceLocation.fromNamespaceAndPath(...)` → **`Identifier.fromNamespaceAndPath(...)`**。
> 上面示例里 `new Type<>(...)` 那行在 26.x 必须换掉。
> 另外单向包可以用更短的三参形式，不必包 `DirectionalPayloadHandler`：
> `registrar.playToClient(TYPE, STREAM_CODEC, (payload, ctx) -> {...})`（26.1 实测）。

### 🟢 复杂结构手写 StreamCodec + 三条编解码铁律（26.1 实测）

`StreamCodec.composite` 只适合扁平字段；带**变长数组 / 嵌套 record 列表**的包要手写：

```java
public static final StreamCodec<RegistryFriendlyByteBuf, MyPayload> STREAM_CODEC =
        StreamCodec.of(MyPayload::write, MyPayload::read);
```

**🔴 铁律一：读端必须重新夹上限。**
写端 `Math.min(n, MAX)` 截断过，但**读端同样不能信任包内容** —— 否则一个损坏或伪造的包
就能让你按超大的 `n` 去 `new ArrayList<>(n)` / `new T[n]`，直接 OOM。两边都要夹。

**🔴 铁律二：别用 float 存绝对世界坐标。**
float 只有 24 位尾数，在 x≈3000 万（世界边界）处精度只剩约 2 格。
正确做法：**第 0 点写绝对坐标，其余点写相对第 0 点的偏移** —— 值域从千万级降到几十格，
精度立刻回到 1e-4 格级，包体积还不变。

**🔴 铁律三：空包是有语义的，不能省。**
如果"当前没有内容"时干脆不发包，客户端只能靠超时兜底清场，这期间会一直画上一批数据
（表现为"生物走了，幽灵轨迹还在"）。发包应当表达**"这就是当前全部内容"** —— 空列表也要发。

```java
// ---- 写 ----
buf.writeVarInt(n);
for (int i = 0; i < n; i++) {
    Vec3[] pts = list.get(i);
    int pc = Math.min(pts.length, MAX_POINTS);
    buf.writeVarInt(pc);
    if (pc == 0) continue;
    Vec3 base = pts[0];
    buf.writeFloat((float) base.x);          // 第 0 点：绝对坐标
    buf.writeFloat((float) base.y);
    buf.writeFloat((float) base.z);
    for (int j = 1; j < pc; j++) {           // 其余：相对偏移
        buf.writeFloat((float) (pts[j].x - base.x));
        buf.writeFloat((float) (pts[j].y - base.y));
        buf.writeFloat((float) (pts[j].z - base.z));
    }
}

// ---- 读 ----
int n = Math.min(buf.readVarInt(), MAX_TRAJECTORIES);   // ← 再夹一次
for (int i = 0; i < n; i++) {
    ...
    int pc = Math.min(buf.readVarInt(), MAX_POINTS);
    Vec3[] pts = new Vec3[pc];
    if (pc > 0) {
        double bx = buf.readFloat(), by = buf.readFloat(), bz = buf.readFloat();
        pts[0] = new Vec3(bx, by, bz);
        for (int j = 1; j < pc; j++)
            pts[j] = new Vec3(bx + buf.readFloat(),
                              by + buf.readFloat(),
                              bz + buf.readFloat());
    }
}
```

**公共侧的处理器别直接引用客户端类。** 收包逻辑常要按端分发，而 handler 所在的类是
公共侧（专用服务端也会加载它）—— 直接 `import` 客户端类会 `NoClassDefFoundError`。
用字符串 + 反射延迟解析，并**把 `Method` 缓存起来**（别每次收包都 `getMethod`）：

```java
private static Method clientHandler;   // 只解析一次
private static void handle(payload, ctx) {
    Method m = clientHandler;
    if (m == null) {
        m = Class.forName("com.example.mod.client.ClientHandler")
                 .getMethod("handle", MyPayload.class, IPayloadContext.class);
        clientHandler = m;
    }
    m.invoke(null, payload, ctx);
}
```
> 另一种隔离写法（整包纯客户端的场景）见 §17.5。

### 事件里做「批量破坏」：必须加重入保护（26.1 NeoForge 实测）

> ⚠️ **类名随版本变**：26.1.0.x 是内部类 `BlockEvent.BreakEvent`，
> **26.1.2 起改成独立类 `net.neoforged.neoforge.event.level.block.BreakBlockEvent`**。
> 本节代码按 26.1.0.x 写，26.1.2+ 把类名和 import 换掉即可（方法签名不变）。
> 详见 `版本差异矩阵.md` §9.3 ⑨。

连锁挖矿 / 范围挖掘 / 爆炸挖矿这类效果，都要在事件里**再破坏一批方块**。
正确做法是走原版 `ServerPlayerGameMode#destroyBlock`（掉落、耐久、附魔、
统计、其他模组事件全部保持一致），但它**会再次发出 `BreakEvent`**：

```
handle() → destroyBlock(pos) → CommonHooks.fireBlockBreak()
         → BlockEvent.BreakEvent → 自己的监听器 → handle() → ... StackOverflowError
```

```java
private static final ThreadLocal<Boolean> IN_PROGRESS = ThreadLocal.withInitial(() -> Boolean.FALSE);

public static void handle(BlockEvent.BreakEvent event) {
    if (Boolean.TRUE.equals(IN_PROGRESS.get())) {
        return;                                  // 自己链式发起的那层，放行给原版
    }
    if (!(event.getPlayer() instanceof ServerPlayer player)) return;
    if (!(event.getLevel() instanceof ServerLevel level)) return;
    if (event.isCanceled()) return;              // 已被别的模组取消，别跟着挖

    // ... BFS 收集相连的同种方块到 targets ...
    // 预构造事件筛掉被保护的坐标（尊重领地保护模组）
    List<BlockPos> breakable = new ArrayList<>();
    for (BlockPos pos : targets) {
        BlockEvent.BreakEvent pre = new BlockEvent.BreakEvent(level, pos, level.getBlockState(pos), player);
        if (!pre.isCanceled()) breakable.add(pos);
    }

    IN_PROGRESS.set(Boolean.TRUE);               // ← 只包住破坏循环
    try {
        for (BlockPos pos : breakable) {
            player.gameMode.destroyBlock(pos);
        }
    } finally {
        IN_PROGRESS.set(Boolean.FALSE);          // ← 必须 finally，异常后不能永久卡死
    }
}
```

要点：

- 标记**只包住 `destroyBlock` 循环**，不要连前置检查一起包 —— 否则别的模组
  在被链式触发的事件里做的正常工作会被误跳过。
- 其他模组的监听器**照常收到**这些事件，只是我们自己不处理。
- 破坏后 `level.getBlockState(pos)` 已是空气，**播粒子/音效要用破坏前记下的状态**：
  `int effectId = Block.getId(originState); level.levelEvent(2001, pos, effectId);`
- 别只靠 `javap` 反汇编判断"某方法不发事件" —— 经 `CommonHooks` 转发时静态很容易漏看，
  **实机跑一次才算数**。这个坑就是先在服务端跑出来的。

| 注解 | 用途 |
|---|---|
| `@Inject` + `@At("HEAD"/"TAIL"/"RETURN"/"INVOKE")` | 在某处插入代码 |

| `@Unique` | 标记自己新增的成员 |
| `@ModifyVariable` / `@ModifyArg` | 改变量/参数 |
| `@ModifyExpressionValue`（MixinExtras） | 改某个表达式的返回值 |
| `@WrapOperation`（MixinExtras） | 包裹某个方法调用 |
| `@Local`（MixinExtras） | 捕获局部变量 |

**怎么找方法名**：`gradlew genSources` 生成反编译源码后直接搜；或在线浏览 https://mcsrc.dev/ （26.x）。

### 🟢 世界渲染：逐帧画线（26.1 实测）

> 26.1 有两处破坏性变更：`RenderLevelStageEvent.Stage` 枚举**已删除**（改用独立子类事件），`Camera.getPosition()` **已改名**为 `Camera.position()`。

```java
@EventBusSubscriber(modid = MODID, value = Dist.CLIENT)
public class MyWorldRenderer {

    private static final float LINE_WIDTH = 2.5f;
    private static final Vector3f NORMAL = new Vector3f(0f, 1f, 0f);   // 线不看光照，给个固定法线即可

    @SubscribeEvent
    public static void onRenderStage(RenderLevelStageEvent.AfterTranslucentBlocks event) {
        Minecraft mc = Minecraft.getInstance();
        if (mc.level == null || mc.player == null) return;

        Vec3 cam = mc.gameRenderer.getMainCamera().position();   // ⚠️ 26.1：position()，不是 getPosition()
        PoseStack pose = event.getPoseStack();
        pose.pushPose();
        pose.translate(-cam.x, -cam.y, -cam.z);                  // 世界坐标 → 相机相对

        Matrix4f mat = pose.last().pose();
        MultiBufferSource.BufferSource buffers = mc.renderBuffers().bufferSource();
        VertexConsumer vc = buffers.getBuffer(RenderType.lines());

        // ... 逐条线写入顶点（见下） ...

        buffers.endBatch(RenderType.lines());
        pose.popPose();
    }

```

**🔴 顶点元素铁律（缺一个就崩 / 画面全黑）**

`RenderType.lines()` 背后的 pipeline 是 `RenderPipelines.LINES_TRANSLUCENT`，其顶点格式为
`DefaultVertexFormat.POSITION_COLOR_NORMAL_LINE_WIDTH` + `VertexFormat.Mode.LINES`。
所以每条线必须**按顺序**写齐四样：

```java
private static void vertex(VertexConsumer c, Matrix4f m, Vec3 p,
                           int r, int g, int b, int a, Vector3f normal) {
    c.addVertex(m, (float) p.x, (float) p.y, (float) p.z)   // ① POSITION
     .setColor(r, g, b, a)                                   // ② COLOR（否则透明/全黑）
     .setNormal(normal.x, normal.y, normal.z)                // ③ NORMAL（缺 → IllegalStateException）
     .setLineWidth(LINE_WIDTH);                              // ④ LINE_WIDTH
}
// Mode.LINES 下每 2 个顶点成一条线
```

> **核对方法（工具化，别手工读源码）：**
> ```bash
> python scripts/渲染API核对.py --project <你的工程> --list | grep -i line
> # LINES_TRANSLUCENT   POSITION_COLOR_NORMAL_LINE_WIDTH   COLOR,LINE,NORMAL,POSITION,WIDTH  (来自 LINES_SNIPPET)
> ```
> `--list` 会打印**所有** pipeline/snippet 的顶点格式，`LINES*` 这些世界渲染管线也在内。
> 注意脚本的 `state × pipeline` 匹配检查只覆盖 GUI 那几个 RenderState
> （世界渲染的线不走 RenderState 体系），所以世界渲染这边是"用 `--list` 读 pipeline 格式、
> 自己比对绘制调用"，别指望它替你检查。
>
> 上一次是靠手工翻 `RenderPipelines` 源码得出的结论，这次用 `--list` 交叉验证，
> 输出与手写代码完全一致 —— 说明结论可靠，也说明以后不用再手工翻源码了。

**自管缓冲区（多帧连续绘制更安全）**

共享的 `mc.renderBuffers().bufferSource()` 若与他人的 `endBatch` 交错可能踩踏。量大的话自己持一个：

```java
private static ByteBufferBuilder builder;      // 64 * 1024
private static MultiBufferSource.BufferSource source;

public static VertexConsumer getBuffer(RenderType type) {
    if (builder == null) {
        builder = new ByteBufferBuilder(64 * 1024);
        source = MultiBufferSource.immediate(builder);
    }
    return source.getBuffer(type);
}
```

⚠️ **释放缓冲区必须调无参 `endBatch()`，不是 `endBatch(type)`。**
带参版本只提交那一种 RenderType，**不会**复位 `ByteBufferBuilder` 的写入指针 ——
写下去就是每帧往后涨，几十帧后 64KB 写穿。
无参版本提交完所有暂存顶点后会顺带 clear 共享缓冲，指针回到起点。

```java
source.endBatch();     // ✅ 提交 + 复位（每帧）
// source.endBatch(type);  // ❌ 只提交不复位，缓冲会写穿
builder.close();       // 只在资源重载 / 退出世界时调，别每帧调
```

**顶点法线可以直接复用同一个实例。**
`setNormal(float, float, float)` 是把值**立即**写进缓冲的，不会持有引用，所以渲染线程上
用一个 static `Vector3f` scratch 就行 —— 128 条线 × 48 段，每帧能省下上万个 `Vector3f` 分配：

```java
private static final Vector3f SCRATCH = new Vector3f();

private static Vector3f normalOf(Vec3 from, Vec3 to) {
    float dx = (float)(to.x - from.x), dy = (float)(to.y - from.y), dz = (float)(to.z - from.z);
    float lenSq = dx*dx + dy*dy + dz*dz;
    if (lenSq > 1.0E-8f) {
        float inv = (float)(1.0 / Math.sqrt(lenSq));
        SCRATCH.set(dx * inv, dy * inv, dz * inv);
    } else {
        SCRATCH.set(0f, 1f, 0f);     // 退化成点：给个默认方向，别留 NaN
    }
    return SCRATCH;
}
```

同类优化：如果分段数常量恒为 1，就别写 `lerp` 插值循环 ——
算出来的 `lerp(a, b, 0)` / `lerp(a, b, 1)` 就是 `a` / `b` 本身，纯白造一堆 `Vec3`。
折线渐变用**两端各自的顶点透明度**表达，不用把一段线切成几小段。

### 15.4 客户端模型（26.2：`EntityModel<S extends EntityRenderState>`）

```java
public class MyModel extends EntityModel<MyRenderState> {
    public static final ModelLayerLocation LAYER =
        new ModelLayerLocation(Identifier.fromNamespaceAndPath(MODID, "my_entity"), "main");  // 第二个参数基础层固定 "main"

    private final ModelPart body;

    public MyModel(ModelPart root) {                 // 构造是 protected，子类可以调
        super(root);
        this.body = root.getChild("body");
    }

    public static LayerDefinition createBodyLayer() {
        MeshDefinition mesh = new MeshDefinition();
        PartDefinition root = mesh.getRoot();
        // ⚠️ 模型坐标 y 轴向下为正，脚底在 y=0：往上长要写负数
        root.addOrReplaceChild("body",
            CubeListBuilder.create().texOffs(0, 0).addBox(-4.0F, -8.0F, -4.0F, 8.0F, 8.0F, 8.0F),
            PartPose.ZERO);                          // 或 PartPose.offset(x, y, z)
        return LayerDefinition.create(mesh, 32, 32); // 贴图尺寸
    }

    @Override public void setupAnim(MyRenderState state) {    // 参数是 render state，不是实体
        super.setupAnim(state);
        float walk = state.walkAnimationPos;                  // LivingEntityRenderState 的字段
        float speed = Math.min(state.walkAnimationSpeed, 1.0F);
        this.body.y = Math.abs(Mth.cos(walk * 0.6F)) * 1.6F * speed;
        this.body.yRot = Mth.sin(state.ageInTicks * 0.05F) * 0.25F;   // ageInTicks 在 EntityRenderState 上
    }
}
```
可用字段：`ModelPart` 的 `x/y/z/xRot/yRot/zRot/visible` 都是 public；`Model#renderToBuffer` 是 **final**，模型只负责 `setupAnim`。

## 16. 实体模型与贴图（26.2，踩坑后实测）

> 「模型做出来不对 / 很丑」这类问题的根因与自查手段。**这一节比 15 节更容易翻车**，
> 因为出问题时进游戏才看得见，而丑不丑是主观的、容易反复返工。

### 16.1 🔴 铁律一：脚底必须落在模型坐标 y = 24

`LivingEntityRenderer` 渲染实体时执行 `poseStack.scale(-1,-1,1)` 再 `translate(0, -1.501, 0)`，
模型点 p 的世界高度 = `-(p.y/16 − 1.501)`：

| 脚底模型 y | 世界高度 | 结果 |
|---|---|---|
| **24** | ≈ 0 | ✅ 正常踩地 |
| 0 | 1.501 格 | ❌ **整只浮空 1.5 格** |

vanilla 参照（全是 24）：
```java
// CowModel
leg = root.addOrReplaceChild("right_hind_leg",
        CubeListBuilder.create().texOffs(0,16).addBox(-2.0F, 0.0F, -2.0F, 4.0F, 12.0F, 4.0F),
        PartPose.offset(-4.0F, 12.0F, 7.0F));      // 12 + 12 = 24
// HumanoidModel
rightLeg = ... PartPose.offset(-1.9F, 12.0F, 0.0F); // 同上
```
**建任何实体模型：先把脚底钉在 24，再往上长。**

坐标系三件事：
- y **向下为正**（数值小的在上面），`addBox(x,y,z,w,h,d)` 的 (x,y,z) 是**最小角**，h 朝 +y 生长
- `PartPose.offset` 是**旋转支点** —— 腿的支点要放在腿根，否则摆动会绕地面转
- 实体朝向 **−z**，所以"前面"是 z 更负的方向

### 16.2 🔴 铁律二：模型 UV 与贴图分区硬绑定

动了任一 `texOffs`，要同步改**三处**，少一处就出错位色块：
1. Java 模型 `createBodyLayer()`
2. 贴图生成脚本里的 UV 分区表
3. 模型预览脚本的盒子表

贴图尺寸不必是正方形：`LayerDefinition.create(mesh, 128, 64)` 合法。
一个 `12×9×16` 的躯干光自己就要 `2(12+16) × (16+9) = 56×25` 的 UV，**64 宽会塞不下**。
立方体的 UV 占用公式：**宽 `2(w+d)`、高 `d+h`**。

### 16.3 自查工具：`scripts/实体模型预览.py`

不开游戏就能出等距投影图，并做数值自检（脚底高度 / 模型尺寸 / UV 越界 / UV 重叠）：
```bash
python 实体模型预览.py                          # 内置示例
python 实体模型预览.py boxes.json --tex entity.png -o preview.png
python 实体模型预览.py boxes.json --no-render    # 只自检
```
`boxes.json` 用绝对模型坐标（`PartPose.offset` + `addBox` 相加后的结果）。
自检输出示例：
```
脚底最低点 y = 24.0（应为 24.0）✓
模型尺寸 = 高 1.62 / 宽 0.88 / 长 1.94 格
   -> EntityType.Builder.sized(底面, 1.62)，底面是正方形取 0.88 左右
UV 自检: 14 个盒子全部落在 128x64 贴图内、彼此不重叠 ✓
```
拿到"高/宽/长"就能直接把 `sized()` 填对，不用进游戏量。

### 16.4 「简陋感」多半是对比度不够，不是细节不够

实测教训：一版全身同一棕色系的生物，进游戏就是"一坨"，用户直接说简陋。改配色后判若两物。

三条原则：
- **主体**用低明度低饱和的深色（玄武岩、暗金属），明度差控制在 ±15%
- **只给一个视觉焦点**用高明度高饱和色（熔岩、能量），面积占比 **< 20%**
- 发光点/眼睛用接近白的颜色，尺寸小但最亮

方块贴图同理：底色压深、裂纹提亮。装备图标则相反 —— 它是小图，需要整体高饱和才看得清。

## 17. 自定义 HUD 图层（26.1 / NeoForge，小地图 mod 实测可用）

> **26.1 的 HUD 体系换掉了**：`net.minecraft.client.gui.GuiGraphics` 已被拆分，
> `RenderGuiEvent` 里拿到的是 **`GuiGraphicsExtractor`**；想长期挂一块自己的 HUD，
> 走 NeoForge 的 `RegisterGuiLayersEvent` + `GuiLayer`（画在所有原版 HUD 层之上），
> 而不是在 `RenderGuiEvent.Post` 里硬画。以下全部经 26.1.2.109 编译 + 服务端/客户端冒烟验证。

### 17.1 注册一个 HUD 图层（mod bus，客户端事件）

```java
public final class ClientSetup {
    public static void init(IEventBus modBus, ModContainer container) {
        modBus.addListener(ClientSetup::registerGuiLayers);   // IModBusEvent → mod bus
        modBus.addListener(ClientSetup::registerKeyMappings);
        container.registerExtensionPoint(IConfigScreenFactory.class, ConfigurationScreen::new); // 白送一个配置界面
        NeoForge.EVENT_BUS.register(new TickHandler());        // 游戏事件走主 bus
    }

    private static void registerGuiLayers(RegisterGuiLayersEvent event) {
        event.registerAboveAll(Identifier.fromNamespaceAndPath("mymod", "hud"), MyHud.INSTANCE);
        // 也可 registerAbove(VanillaGuiLayers.HOTBAR, id, layer) 指定顺序
    }
}
```

**`RegisterGuiLayersEvent` 的完整方法表**（26.1 源码实读）：

| 方法 | 用途 |
|---|---|
| `registerBelowAll(id, layer)` | 画在**所有**原版层之下（背景类） |
| `registerBelow(Identifier other, id, layer)` | 排在某个原版层之前 |
| `registerAbove(Identifier other, id, layer)` | 排在某个原版层之后（最常用） |
| `registerAboveAll(id, layer)` | 画在所有原版层之上（浮层） |
| `replaceLayer(id, replacement)` | **顶掉**某个原版层（改原版 HUD 外观） |
| `wrapLayer(id, UnaryOperator<GuiLayer>)` | 包住原版层（前后加装饰） |

常用排序锚点（`VanillaGuiLayers` 常量，都是 `Identifier`）：
`CAMERA_OVERLAYS` / `CROSSHAIR` / `HOTBAR` / `PLAYER_HEALTH` / `ARMOR_LEVEL` / `FOOD_LEVEL` /
`AIR_LEVEL` / `EXPERIENCE_LEVEL` / `SELECTED_ITEM_NAME` / `EFFECTS` / `BOSS_OVERLAY` /
`SLEEP_OVERLAY` / `SCOREBOARD_SIDEBAR` / `TITLE` / `CHAT` / `TAB_LIST`。

### 17.1b ⭐ 用 `@EventBusSubscriber` 挂（比手动 `modBus.addListener` 省事）

注解成员只有 `value()` 和 `modid()`，**没有 `bus`**）。框架按「事件有没有实现
`IModBusEvent`」自动分派 —— 所以**同一个注解既接得住 mod 总线事件，也接得住游戏总线事件**：

### 17.3 画一块动态贴图（小地图画布）

```java
// 建纹理

sampler = RenderSystem.getSamplerCache().getClampToEdge(FilterMode.NEAREST); // NEAREST：放大不糊

```

> 🔴 **26.1 最狠的一个坑（实机崩溃验证）**：
> `gfx.fill(RenderPipeline, TextureSetup, x0, y0, x1, y1)` 看着像"画贴图"，其实它生成的是
> **`ColoredRectangleRenderState`**——只有 position + color，**不写 UV0**。
> 而 `RenderPipelines.GUI_TEXTURED`(`GUI_TEXTURED_SNIPPET`) 的顶点格式是 `POSITION_TEX_COLOR`，
> 于是进世界画第一帧就抛 `java.lang.IllegalStateException: Missing elements in vertex: UV0`
> （栈：`ColoredRectangleRenderState.buildVertices` → `GuiRenderer.addElementToMesh`）。
> 原版敢这么用是因为它配的是 `RenderPipelines.END_PORTAL` 这类**不需要 UV** 的程序化管线。
> **mod 画贴图一律走 `blit(...)`**（`BlitRenderState` 会写 UV）：
> `gfx.blit(GpuTextureView, GpuSampler, x0, y0, x1, y1, u0, u1, v0, v1)`，内部即 `GUI_TEXTURED`。
> 纯色矩形（无纹理的 `fill(x0,y0,x1,y1,col)` → `RenderPipelines.GUI`，格式 `POSITION_COLOR`）不受影响。

## 18. ⭐⭐ 「能盛水的容器」方块：水要在**腔里**，不在方块里（26.1 实测）

### 18.1 两种做法，选错了不是风格问题而是**功能错了**

元的要求：「让你杯子中有水又不是方块本身有水，是杯子里面」。

| | **方块自带水**（❌ 做过，返工） | **腔里放真水**（✅） |
|---|---|---|
| 实现 | `BooleanProperty FILLED`，为真时模型里多一块半透明水面 | 方块几何留出**内腔**，生成器/玩家往里放 `Blocks.WATER` |
| 桶能不能舀 | 只能靠 `useItemOn` 手动切状态 | **原版桶直接可用**（那格就是水） |
| 玩家能不能进去游泳 | ❌ 进不去（方块是满的） | ✅ 能 |
| 水会不会流走 | 不会（假水） | **会** —— 必须几何上封闭 |
| 额外开销 | 每个状态一个模型 + `BucketPickup` 接口 | 零（原版水自己发光照/流体） |

⭐ 判据一句话：**「桶能舀、人能游、水会流」——三条只要有一条不满足，就是假水。**

### 18.2 ⭐⭐ 池子的几何：**封顶浅池**（池底 → 一层水 → 盖板）

```
        ▁▁▁▁▁▁▁        ← 盖板（叶）：把水整圈**压住**，水不外溢/不蒸发
       ▕ 水 水 水 ▏     ← 池水：**一层** Blocks.WATER
       ▕▁▁▁池底▁▁▁▏     ← 池底（叶）：水正下方必是实体
        ▏沿 6 格宽▕     ← 沿体与盖板同高，整圈围死
```

```java
int base = cupFloor + 1;                 // ⭐ 全盘统一的池底（见 18.4）
int pool = base;                         // 水面那一层（与池底同 y）
int lid  = base + 1;                     // 盖板
if (d <= rr) {                           // 池内
    putTo(out, min(base - 1, floorTop + 1), pool - 1, top, leaf);  // 垫到水面下界
    putTo(out, pool, pool, top, WATER);                            // ⭐ 一层真水
    putTo(out, lid, lid, top, leaf);                              // 盖板
} else if (d <= rr + RIM_W) {            // 池沿 rr < d <= rr+6
    putTo(out, min(base - 1, floorTop + 1), lid, top, leaf);       // 与盖板同高
} else {                                 // ⭐ 裙边 rr+6 < d <= rr+6+6（第十五轮）
    putTo(out, min(base - 1, floorTop + 1), lid, top, leaf);       // 找平台，同高
}
```
⭐ **裙边**（`SKIRT=6`）：盘沿外那圈天然岩体是**斜面**、顶面低于池底，
与盘沿之间留一条悬空带 ⇒ 水从池沿最外圈横流进去、掉下去。
裙边把该带填到与池沿同高（**不铺水、不加盖板**），池沿外缘接上实心（见 18.4c）。

### 18.3 ⚠️⚠️ 四个"看着对、实际漏水"的坑（都实测撞过）

1. **❌ `addUpTo(surf, surf, ceiling, WATER)` —— 水从池里一路灌到洞顶。**
   最后一个参数若写 `ceiling`，一列水就填满整个剩余空间（几十格高），
   沿只有两三格根本圈不住，水当场没过沿顶流走。
   实测：整个第 4 层只剩 **39 格水**（一个池子都没存住）。
   ⇒ 水只放**一层**（`pool == base`），上面立刻压盖板。

2. **❌ 沿太窄**。第一版沿 2 格、顶只高 1 格。岩檐是斜面，相邻列地板差 3~4 格，
   窄沿追不上落差 → 环上出现缺口。⇒ 沿 **6 格宽**，与盖板同高。

3. **❌ 池里没有底**。池内直接 `WATER`，下面是空的 ⇒ 水第一 tick 就漏下去。
   ⇒ 从 `base−1` 起垫实（**不是** `max(floorTop+1, base−1)`：
   floorTop 高于池底时那样写会把 `base−1` 空出来，水就悬空）。

4. **❌ ~~池面跟着逐列地板走~~ → 见 18.4，这条是**最隐蔽**的一个。**

### 18.4 ⭐⭐⭐ 池面必须**全盘统一**，绝不能逐列跟着地板（第十二轮真凶）

`floorTop` 是逐列的，倾斜岩檐上同一个池子跨的几十列地板能差出 **200 格**
（第 4 层实测 y≈280~490）。如果按"这一列地板 + 1"放水：

- 相邻列的池水落在**不同 y**，拼起来是一摞**阶梯水**（离线自检实测 11 层）；
- 高那侧的水，直接翻过低那侧的盖板 → 漏。

⇒ **池面只认"盘心那一列"的地板**（`cupFloorY`），全盘一个高度；
逐列只决定"本列的凹处要垫多高才托得住池底"。

```java
// 盘心基准面：用密度场**直接扫**盘心那一列的层内地面（盘心可能不在本区块，
// 所以不走区块三线性插值，直接调 AbyssDensity.shape）
private static final int NO_CUP_FLOOR = Integer.MIN_VALUE + 1;

private static int cupFloorY(int cx, int cz, int ownFloorTop, int seed) {
    int lo = -438, hi = 556;                       // 第 4 层高度区间
    double cdist = sqrt((double) cx*cx + (double) cz*cz);
    for (int y = lo; y <= hi; y++) {
        if (AbyssDensity.shape(cx, y, cz, seed, cdist, 0, 0) > 0.0
            && AbyssDensity.shape(cx, y+1, cz, seed, cdist, 0, 0) <= 0.0) {
            return y;                              // 实心→空气的跳变 = 地板顶
        }
    }
    return NO_CUP_FLOOR;   // ⭐ 扫不到 = 盘心在洞腔里 → 调用点必须**不建**
                           //    以前是 `return ownFloorTop` 兜底，那是静默的错
                           //    （第十四轮的漏水杯就是这么来的，见 18.4c）
}
```

⚠️ 这条**推翻了 18.4 的旧版说法**（"池子跟着逐列地板走"）—— 旧版是错的。
当时以为"每列自己封口就不漏"，忽略了**相邻列的水面高差**本身就是漏点。

### 18.4b ⭐⭐ 交付前先在**离线纯函数**上验几何（`_proto_cup.py`）

池子几何只依赖 `(rr, 沿宽, 盘心地面, 层界, bore)`，是**纯函数** —— 完全可以离线算，
不必花 52 分钟生成世界再看结果（前几轮就是这么浪费掉三轮的）。

离线判据（照着 Java 逐行抄一遍，用 dict[坐标]=块名 模拟）：
```
[C0] 池水只有 1 层厚          ← 阶梯水的特征就是"水有十几层"
[C1] 每个水格四个水平邻居都是水或实体（没有"水挨着空气"）
[C2] 每个水格正上方是盖板      [C3] 正下方是实体
[C4] 用**逐列起伏的**地面跑，仍全绿   ← 这条专抓 18.4 的阶梯水
[C5] 天花板过低（room<阈值）时整列填实、不建池
[C6] ⭐⭐ 盘子**整个坐在洞腔之外**：cdist − rr − 沿宽 − 裙宽 ≥ bore + 噪声余量
     （见 18.4c，第十四/十五轮两轮才修对）
[C7] ⭐⭐ 盘心那列必须有地板；哨兵 ⇒ 不建
[C8] ⭐⭐ **分区块模拟**：floor_of 返回 None 表示"这一列没有地板"（洞腔列，
     Java 里会被 continue 跳过）。造一个"盘心跨在洞腔边界上"的样本
     ⇒ 必须复现出"水有 N 格、敞口 M 处"（这就是真 bug 的形态）；
     再造成"整盘在洞腔外" ⇒ 必须全封死。
[C9] ⭐⭐⭐ **洞腔噪声吃掉池内列**（第十五轮）：真实洞腔外沿 > bore（噪声外扩
     几十格）。造"盘心在基准圆外、但池内一角伸进真实洞腔"的坏样本
     ⇒ 必须复现漏（实测 512 格水 / 57 处漏）；好样本 ⇒ 必须 0 漏。
[C10] ⭐⭐⭐ **判据的噪声余量**：同一个位形，旧口径（无余量）必须**放行**、
     新口径（有余量）必须**拦住** —— 这才证明余量真在起作用。
```

### 18.4c ⭐⭐⭐⭐ 盘子必须"整个坐进**洞腔之外的岩檐**上"（第十三、十四轮，两轮才修对）

这一条改了两次，**第一次改反了方向**，值得整段记下来。

#### 第十三轮：只挡住了"往外伸"，没挡住"往里探"

**bug 形态**：用 cell 网格挑盘子、取 `cell 中心`——cell 中心可能**正好压洞壁上**。
实测第 4 层 `bore ≈ 1300`，某杯 `cell(-16,-1)` 中心 `r = 1303`（> bore）：
盘子一半落在实心岩体里（被后写的岩石盖掉），另一半**悬在井腔空中**。

当时的修法（**只对了一半**）：
```java
if (cdist + rr + RIM_W > boreR || cdist - rr - RIM_W < 0) return;   // ❌ 另一头口径错了
```
- `cdist + rr + RIM_W > boreR` → 挡"盘子往外伸进岩石" ✓
- `cdist - rr - RIM_W < 0` → 只判"不为负"，**允许盘子往洞里探** ✗

#### 第十四轮：真相是"盘子探进洞腔 ⇒ 盘心那半边长不出来"

第 4 层的 `bore(y)` 在本层内就变化 **300+ 格**（`bore(0)=1322 → bore(556)=999`），
cell 网格有一半落在 `cdist ≈ bore` 上。**盘心落在洞腔里**的盘子：

1. 盘心那一列 `floorTop == NO_BOUND`（洞腔里没有地板，`fillFromNoise` 里
   `floorTop[i] == NO_BOUND` 那条 `continue` 会跳过标志地形）；
2. ⇒ **盘心那半边压根没长出来**（没有叶、没有水）；
3. ⇒ 盘子只剩"落在岩檐上"的半边，**切面就是敞口**；
4. ⇒ 水紧挨洞腔空气、且那格**下方也是空气** ⇒ **真漏**。

实测那只杯：盘心 `(-714,798)`，东半圈 `x=-720..-705` 全是空气，
水停在 `x=-721`（正好在区块边界），86 个水域**全部**有一条边会流。

**正确判据**（`cdist − rr − 沿宽 ≥ bore`）：
```java
double cdist = Math.hypot(cx, cz);
int cupFloorProbe = cupFloorY(cx, cz, floorTop, seed);
if (cupFloorProbe == NO_CUP_FLOOR) return;        // ⭐ 盘心没地板 → 不建
double boreR = AbyssDensity.bore(cupFloorProbe + 1);   // ⚠️ 取**池子那一层高度**的 bore
if (cdist - rr - RIM_W < boreR) return;           // ⭐ 整盘必须在洞腔之外
```

⭐ **三个必须同时做的配套**：

1. **`cdist − rr − 沿宽 ≥ bore`**，不是 `≥ 0`、也不是 `≤ bore`。
   一句话：**盘子的最内一点也已经在洞壁之外**（整盘住进岩体/岩檐）。
2. **`cupFloorY` 扫不到地板要返回哨兵**（`NO_CUP_FLOOR`），调用点据此**不建**。
   以前是 `return ownFloorTop` 兜底 —— 那是**静默的错**：盘心在洞里也照建。
3. **`boreR` 用池子那一层高度的 `bore()`**，不能用层中点值
   （第 4 层内变化 300+ 格，用中点会放进来一批"半截杯"）。

⭐ **推广**：凡是"按网格挑位置生成有限尺寸物件"，
- 只判**中心点**合法不够 → 要判**整个占地**（第十三轮）；
- 判"整个占地"时，**合格区域是"洞腔之外"这种带内边界的区域**时，
  两头都要判：不许伸出去（`+rr+wobble ≤ 外沿`）**且不许探进来**（`−rr−wobble ≥ 内沿`）。
  只判一头 = 另一头静默失效（第十四轮）。

#### ⚠️ 第十五轮：判到"洞腔之外"还不够 —— **洞腔外沿不是 `bore` 那条圆**

第十四轮的口径（`≥ bore`）看似正确，实测**仍有漏杯**。解剖那只杯（盘心 `(1386,-42)`、
`rr=18`）：

- 判据算出 `cdist − rr − RIM_W = 1386.6 − 18 − 6 = 1362.6 > bore(1322)` ⇒ **放行**；
- 但那一侧洞腔**实际外扩到了 1373**（比 `bore` 多 51 格）；
- ⇒ 池内列（`d = 13~16`，本该铺水）整片变成 `NO_BOUND` ⇒ **水面在 x=1376 处整列缺失**；
- ⇒ 水从池内直接横流入洞腔空气、那格下方也空 ⇒ **真漏**（实测 6 格水会流走，
  剖面图上 1 处红点）。

**为什么外扩 51 格**：`bore` 只是几何基准半径，洞腔真实外沿还要往外走
`CAVITY_SOFT = 24` 的软化带 + 洞穴/岩板噪声在腔壁上的外凸（团块尺度 30~50 格）。

**修法**：判据加**噪声余量**，按"洞腔**最外**能到哪"判：
```java
final double CAVITY_MARGIN = 56.0;    // > 实测外扩 51，留冗余
if (cdist - rr - RIM_W - SKIRT < boreR + CAVITY_MARGIN) return;
```

**代价**：第十五轮实测只砍掉 1.6% 的杯子（2044 → 2011），且被砍的全是
`cdist ∈ [1300,1400]` 那圈**紧贴洞腔**的危险位 —— 用 1.6% 换整圈安全，划算。

⭐ **推广**：凡"按**解析/平均**边界判合格区"的判据，都要问一句
「**真实边界有噪声扰动吗？扰动幅度多大？**」
- 有噪声就必须**按最坏情况留余量**（`+ 噪声幅度`），不能按基准值判；
- 余量取值要**从实测反推**（本次：实 medida 51 ⇒ 取 56），不是拍脑袋；
- 判完要**统计代价**（砍掉多少合法物），确认不是"为了安全把东西全砍光"。

⭐ **第十五轮还补了一个"裙边"**：盘沿（`rr..rr+RIM_W`）外还要再铺一圈
`SKIRT=6` 的**找平裙**，把"盘沿外缘 → 天然岩体"之间因**岩檐斜面**留下的
悬空带填到与池沿同高。判据里 `−SKIRT` 也要算进去。

### 18.4d ⭐⭐⭐ 判据必须**按原版水流规则**判，不能判"四邻是不是实体"（第十四轮）

第十三轮写了个 `_verify_seal.py`：水格"四个水平邻居有空气"就算漏点。
结果**86 个域全部报漏**，而 `_judge_goblet.py` 的 `[G4]`（水底实心）全绿 —— 两边打架。

解剖后发现绝大多数是**沿外即洞腔**的正常形态：水只有 1 层、正上方盖板、
正下方池底 ⇒ **原版水不会流**，哪怕侧边是空气（水往侧边流还需要
"那一格的下方也有空间"，而它下方是池底）。

⇒ 判据改成**逐格按原版规则判**，这才是"会不会流"的唯一正确口径：

```python
def flows(x, y, z):
    if block_at(x, y-1, z) in AIR:  return True    # 正下方是空气 → 直接往下掉
    for dx, dz in ((1,0),(-1,0),(0,1),(0,-1)):
        if block_at(x+dx, y, z+dz) in AIR and block_at(x+dx, y-1, z+dz) in AIR:
            return True                            # 侧邻是空气**且其下方也空** → 有地方去
    return False
```

⚠️ **这条判据必须双向验证**：
- 拿**改好的**世界跑 → 应该全密封（`真会流 0`）；
- 拿**改动前的**世界跑 → 必须报出漏点（实测 `真会流 86/86`，
  每个域都有"侧邻空气且其下方也空"的边）。
只跑一边，"全绿"什么都说明不了。

⭐ **别把"沿外是洞腔"当漏点** —— 那是悬空杯的正常形态。
判"会不会流"要问「**水有没有地方去**」，不是「**隔壁是不是石头**」。

### 18.5 判据：验**水的形状**，不验"有没有水"（`_judge_goblet.py`）

```
[G0] 采样前置：**环带里已加载**的区块数 ≥ 下限（没生成的区块整列是空气，会假绿）
[G1] 层里确实有水（格数 ≥ 下限）—— 为 0 直接 SystemExit，绝不判绿
[G2] 每个水连通域水平跨度 ≤ 80（盘直径上限 68 + 余量）—— 长带 = 流走了
[G3] 每个连通域厚度 ≤ 4（池里只有 1~2 格）—— 瀑布/阶梯水会远大于此
[G4] 每个连通域最低一层水的下方全实心（水坐在池底上，没悬空）
```

⚠️⚠️ **采样范围必须覆盖「物件实际生长的地方」**（第十三轮踩的坑）：
杯子长在第 4 层的**岩檐环带**（`hypot ∈ [420, bore+84]`），**不在轴线上**。
早前判据只扫"十字带"（`cz=0`/`cx=0` 两条轴）⇒ 整条轴线上一个杯子都没有
⇒ 判据报 **0 格水**，把"判据看不见"误读成"杯子没生成"（还差点又去改几何）。
⇒ 改成扫**整个环带**；同时 `[G0]` 不能要求"整环带都生成"（生成时只 forceload
了十字带，环带大部分本来就没生成），改成"**已加载区块**数够多、且只扫已加载的"。

⭐ **负样本必须先跑通**：拿改动前的存档跑，`[G1]` 必须报红
（旧版是方块自带的假水，一个真水格都没有）。实测：
`✘ [G1] 第 4 层有水（0 格，下限 300）` → 判据确实会报错。

### 18.5b ⚠️⚠️ 判据的**盲区**：「水格会不会流」查不出「水格**根本没生成**」（第十五轮）

第十五轮修完后，`_judge_goblet.py` 的 `[G5]`（按原版水流规则判）与
`_verify_seal.py` 都**没有报出**那只漏水杯 —— 但 `_slice_goblet.py` 出图
**明明看到红点**。为什么？

因为那只杯的漏法是：**池内一角整列没生成**（`floorTop == NO_BOUND` 被 continue），
⇒ **那一角压根没有水格** ⇒ 两个"逐格判水会不会流"的脚本**扫不到它**（没有水格可判）。
出图脚本的俯视图能看到红点，是因为它**扫了更大范围**、把"水格旁边的空格"也算进去了。

⇒ **教训**：判据的**采样对象**决定了它的盲区。
- 判"水会不会流" ⇒ 只覆盖**已存在的水格** ⇒ **对"缺失"完全无感**；
- 要抓"缺失" ⇒ 必须判**形状/完整性**（俯视图上水是不是被一圈实心围住、
  水面投影是不是接近圆），而不是逐格判物性。

⭐ **推广（值得背）**：
> **判据按"每个已存在的元素"逐个判，就永远查不出"该存在却不存在"的元素。**
> 交付前除了"物性判据"（每个东西好不好），还要有**"完整性判据"**
> （该有的东西是不是都在、形状是不是闭合）。
> 本次补的 `[C9]`（泛洪测漏）就是完整性判据：它从水格出发泛洪，
> **走出盘子覆盖范围**即报 —— 这样"缺一角"必然导致泛洪逃逸，绕开了盲区。

⚠️ 但**判据绿 ≠ 形态对**：判据只给数字，形态要靠**出图**看。第十轮 `_judge_*`
全绿的情况下，截面图 `r10_goblet.png` 清清楚楚显示水在沿**外面**散成斜带 ——
数字是"有 78 格水、跨度 12、厚 2"（全在阈值内），形态却是漏的。
⇒ **数字判据 + 出图（截面图 + 俯视图）两个都要。**
俯视图专看"蓝水是不是被一圈绿沿完整围住"（有缺口 = 会漏）。

### 19.1 Screen：渲染入口换了，而且必须调 super

```java
public class MyScreen extends Screen {
    private final Button[] buttons = new Button[ROW_COUNT];

    public MyScreen() { super(Component.translatable("mymod.gui.title")); }

    @Override
    protected void init() {
        for (int i = 0; i < ROW_COUNT; i++) {
            Button b = Button.builder(Component.translatable("mymod.gui.upgrade"), btn -> onUpgrade(i))
                    .bounds(rowX(), rowY(i), 96, 20)
                    .build();
            this.buttons[i] = b;
            this.addRenderableWidget(b);
        }
    }

    @Override
    public void tick() {            // 每 tick 刷新按钮可用性（经验够不够）
        super.tick();
        for (int i = 0; i < ROW_COUNT; i++) this.buttons[i].active = canAfford(i);
    }

    @Override
    public void extractRenderState(GuiGraphicsExtractor gfx, int mouseX, int mouseY, float partialTick) {
        gfx.fill(0, 0, this.width, this.height, 0xB4000000);        // 背景暗化，没人帮你画了
        gfx.fill(panelLeft(), panelTop(), panelRight(), panelBottom(), 0xF0181820);
        gfx.outline(panelLeft(), panelTop(), panelWidth(), panelHeight(), 0xFF7A7AC8);
        gfx.centeredText(this.getFont(), this.getTitle(), this.width / 2, panelTop() + 8, 0xFFFFFFFF);
        // ... 逐行 gfx.text(font, Component.translatable(...), x, y, color) ...
        super.extractRenderState(gfx, mouseX, mouseY, partialTick);   // ★★ 漏了这行，按钮全都不显示
    }
}
```

🔴 三条实测结论：
1. **`super.extractRenderState(...)` 必须调** —— `Screen` 的默认实现就是遍历 `renderables` 画子控件。
   漏了它不崩不报错，只是"面板上没有按钮"，从日志里查不出来。
2. `render(GuiGraphics,…)` / `renderBackground` 都不存在了（见 `版本差异矩阵.md` §9.3 ②）。
   背景要么自己 `fill`，要么调 `extractBackground(gfx, mouseX, mouseY, partialTick)`（public）。
3. `init()` 会在窗口 resize 时重跑，布局尺寸一律写成方法（`panelLeft()`/`rowY(i)`…）而不是字段，
   保证 `init()` 里放按钮和 `extractRenderState()` 里画文字用的是同一套坐标。

### 19.4b ⭐⭐ 读「玩家有多少经验」别信 `totalExperience`

`Player` 上跟经验有关的是**三个**字段：`experienceLevel` / `experienceProgress` / `totalExperience`。
正常游玩时它们一致，但 **`/xp add <玩家> <n> levels` 只加 `experienceLevel`** ——
`giveExperienceLevels(int)` 的字节码里只有 `experienceLevel` 的写入（`IntMath.saturatedAdd`），
`totalExperience` 压根不碰。于是：

```java
player.totalExperience >= cost          // ❌ 指令给的等级在这里是 0，面板一直说"经验不足"
```

同理 `giveExperiencePoints(-n)` 也是**增量**维护三个字段的，一旦等级被单独改过，
再用它扣经验会算出与等级/进度条对不上的结果。

**正确做法：拿等级 + 进度条推算总经验**（它俩是玩家看得见、也一定会同步到客户端的东西）：

```java
// 正向：等级 + 进度 → 总经验
int total = totalXpForLevel(level) + (int) Math.floor(progress * xpNeededForLevel(level));

// 反向：总经验 → 等级（二分，别写循环 —— 等级上限可能被顶到很高）
int level = levelForTotalXp(total);
float progress = (float)(total - totalXpForLevel(level)) / xpNeededForLevel(level);
```

三段公式（0-15 / 16-30 / 31+ 的 `2n+7` / `5n-38` / `9n-158` 求和），
`totalXpForLevel` 与 `xpNeededForLevel` 必须互为差分 —— 写完**离线对一遍**：

```python
bad = [l for l in range(0, 200) if total(l+1) - total(l) != need(l)]     # 必须为空
bad = [l for l in range(0, 300) if level_for(total(l)) != l]             # 往返回来的等级必须一致
```

自己改完经验字段，**得手动发同步包**（原版不会替你发）：

```java
player.connection.send(new ClientboundSetExperiencePacket(progress, total, level));
```

### 19.5 Mixin：配置怎么写 + 怎么**证明**它真的注进去了

`<modid>.mixins.json` **跟 NeoForge 官方一样，不写 `compatibilityLevel`**：

```json
{ "required": true, "minVersion": "0.8", "package": "com.mymod.mixin",
  "mixins": ["PlayerExhaustionMixin"], "injectors": { "defaultRequire": 1 } }
```

> 写 `"compatibilityLevel": "JAVA_25"` 会换来另一条警告
> （`… higher than the maximum level supported by this version of mixin (JAVA_13)`）；
> 不写则是一条 `Class version 69 required is higher than… (JAVA_21 supports 65)`。
> **两种写法实测都能正确注入**，而后者 NeoForge 自己的 mixin 也照样打，
> 所以跟官方保持一致（不写）。
> `required: true` + `injectors.defaultRequire: 1` 的含义是"注不进去就直接崩"——
> 这是好事：**服务端起得来 = 注入点存在且签名没变**。

⭐⭐ **想拿到"它真的注进去了"的硬证据，用 Mixin 的导出开关**：

### 19.6 ⭐ 跨构建号的坑：NeoForge 事件类名会在**补丁版本之间**变

同一个小版本内 MC 的 API 基本不变，但 **NeoForge 自己的事件类名会变**（2026-09-27 实测）：

| 构建号 | 「破坏方块」事件 |
|---|---|
| 26.1.0.19-beta | `net.neoforged.neoforge.event.level.BlockEvent$BreakEvent`（内部类） |
| 26.1.2.109 | `net.neoforged.neoforge.event.level.block.BreakBlockEvent`（独立类） |

**查法**（改代码前先对目标区间的两端各跑一次）：

```bash
python scripts/JarSig.py <26.1.0.19-universal.jar> net.neoforged.neoforge.event.level 2>/dev/null | grep Break
python scripts/JarSig.py <26.1.2.109-universal.jar>  net.neoforged.neoforge.event.level 2>/dev/null | grep Break
```

**回避办法：把注入点下沉到 MC 自己的类** —— MC 的公开方法在一个小版本内稳定得多：

```java
@Mixin(ServerPlayerGameMode.class)                    // MC 的类，不是 NeoForge 的
public abstract class ServerPlayerGameModeMixin {
    @Final @Shadow protected ServerPlayer player;      // 目标是 protected final，@Shadow 里去掉 final

    @Inject(method = "destroyBlock", at = @At("RETURN"))
    private void xxx$areaMine(BlockPos pos, CallbackInfoReturnable<Boolean> cir) {
        if (!cir.getReturnValueZ()) return;            // 没真破坏成功就别连带挖
        // ... 走原版 destroyBlock 破坏周围方块（必须加 ThreadLocal 重入保护）
    }
}
```

`destroyBlock(BlockPos)` 在 26.1.0 与 26.1.2 上签名逐字节一致（对两个 jar 各 javap 一次即可证）。

> 同理值得警惕的还有 **`MinecraftClient`/`Screen` 这类客户端 GUI 类**：26.1 里
> `Screen#render` 整个没了（见 `版本差异矩阵.md` §9.3 ②），跨小版本用之前先核实。

### 19.7 ⭐ 服务端 Mixin 怎么在**没有玩家**的情况下验证

Mixin 是**类加载时**应用的。像 `ServerPlayerGameMode` 这种只有玩家进服才加载的类，
`runServer` 一路跑到 `Done!` 也根本不会碰它 —— 日志里看不到 `Mixing ... into ...`，
看着像"没注入"，其实只是还没机会。**别把"没报错"当成"注入了"。**

办法是临时强制加载（改一行，验完撤掉）：

```java
// 主类构造里，仅验证期间保留
Class.forName("net.minecraft.server.level.ServerPlayerGameMode");
```

`required: true` + `injectors.defaultRequire: 1` 下，注入失败会直接崩在启动阶段，
所以**"能起来"就是"注入成功"**。想要字节码级证据再加导出开关（见 §19.5）。

两个现成的信号：

- 日志里 `Preparing <modid>.mixins.json (N)` 的 **N = 配置里登记的 mixin 数量**。
  写了两个 mixin 却显示 `(1)` → **mixins.json 根本没改成功**
  （2026-09-27 实测踩过：Write 工具报了错但没复核，jar 里只登记了 1 个）。
  交付前一条命令自查：
  ```bash
  python -c "import zipfile;print(zipfile.ZipFile('build/libs/xxx.jar').read('<modid>.mixins.json').decode())"
  ```
  ⭐ **改这类 JSON 时，Edit 的 old_string 若带了已有条目、new_string 又没原样保留，就会静默删条目**
  （同一天踩了三次：lang 的 `level_cap`、mixins.json 的两个 mixin）。**改完立刻读回来核对条目数**。
- ⭐⭐ **客户端玩家 `LocalPlayer` 覆盖了很多 `Entity`/`Player` 的方法**（实测 `move(MoverType, Vec3)`
  就是它自己实现的，服务端那个 `Player` 反而没覆盖）。所以钩 `Entity` 的注入
  **覆盖不到客户端玩家** —— 服务端放行了、客户端本地预测仍会停下，症状是"功能无效且不报错"。
  涉及玩家移动/碰撞的注入，记得**额外给 `LocalPlayer` 写一份**，并登记在 mixins.json 的 `"client"` 段。
- `Mixing <Mixin类> from <modid>.mixins.json into <目标类>` 出现了，才算这个 mixin 真的应用过。

### 19.8 ⭐ 面板内容超出屏幕：用 `visible` 判定做滚动，别上 scissor

自定义面板（编辑器 / 列表 / 多页设置）迟早会超出屏幕：内容行数会涨、窗口会被拉小、
玩家 GUI 缩放还不一样。**26.1 的 `Screen` 默认渲染不裁剪** —— 超出面板的控件会实打实地
盖在标题栏、底栏、别的控件上面，看起来像"界面画糊了"。

**别急着做真裁剪（scissor）**：那意味着把内容控件从 `renderables` 里摘出来、自己 `enableScissor`
+ 自己调每个控件的 `extractRenderState`，还要**自己转发 `keyPressed` / `charTyped` 给 `EditBox`**
（它不在 children 里就收不到键盘）。为一个"往下滚一点"的诉求做这么多，收益不划算。

**够用且省事的做法**：记下每个内容控件的**未滚动基准 y**，滚动时整体平移 + 按可见性隐藏。

```java
// 构建时把内容控件登记起来（页签 / 底栏不登记，它们固定不动）
private final List<AbstractWidget> content = new ArrayList<>();
private final Map<AbstractWidget, Integer> baseY = new IdentityHashMap<>();
private int scroll;

private <T extends AbstractWidget> T addContent(T w) {
    content.add(w);
    baseY.put(w, w.getY());          // 记"未滚动"位置，反复滚不会累积漂移
    addRenderableWidget(w);          // 仍然进 renderables，事件分发照旧
    return w;
}

private void applyScroll() {         // 每 tick 都调（窗口会 resize，滚动量要重新夹）
    int top = contentTop(), bottom = contentBottom();
    for (AbstractWidget w : content) {
        w.setY(baseY.get(w) - scroll);
        w.visible = w.getY() >= top && w.getY() + w.getHeight() <= bottom;
    }
    // 🔴 滚出去的输入框必须交还焦点，否则键盘还在往看不见的框里打字
    if (getFocused() instanceof AbstractWidget w && !w.visible) setFocused(null);
}

// 滚轮：一格滚"一行"，比滚固定像素自然（行高通常是算出来的，不是常量）
@Override
public boolean mouseScrolled(double mx, double my, double sx, double sy) {
    if (maxScroll() <= 0) return super.mouseScrolled(mx, my, sx, sy);
    scroll = Math.max(0, Math.min(maxScroll(), scroll - (int) Math.round(sy * ROW_H)));
    applyScroll();
    return true;
}
```

四个关键点：

1. **用「完全可见」而不是「与可视区有交集」**：有交集的控件会露出半截盖到标题栏上。
   整块进出的观感就是"一行一行滚"，和原版列表差不多。
2. **`visible = false` 同时挡住绘制和点击** —— `AbstractWidget.mouseClicked` 里就带
   `if (this.active && this.visible)`，所以**不用自己拦鼠标事件**。这是这个方案能这么短的原因。
3. **内容控件必须走同一个登记入口**：漏登记一个，那一个就"别人滚它不动"，
   而且它在构建期就被摆好了、看起来完全正常，只有滚动时才暴露。
4. **滚轮夹取、位置重算都放进每 tick 的 `applyScroll()`**，不要只放在滚动事件里 ——
   玩家拉窗口改变行高之后，只靠事件触发的实现会留下一屏错位的控件。

**绕开布局的循环依赖**：内容高 → 面板高 → 面板顶 → 内容顶 → 行位置，这是一条环
（内容多高要构建完才知道，而构建又得先知道内容顶在哪）。两种破法：
- **让面板固定占满可用高度**（`panelHeight() = Math.max(最小可用高, this.height - 8)`）——
  编辑器这类"整屏一块板"的场景最自然，一行代码断环；
- 或者让内容顶只依赖 `this.height`，不依赖内容高。

最小可用高要留够**标题 + 一行内容 + 底栏**：窗口矮到面板放不满屏幕时，
至少保证底栏的「保存 / 关闭」不被挤出画面 —— 否则玩家连关都关不掉。

**顺手可以离线验**：布局是纯整数运算，把公式照抄进脚本跑遍所有尺寸，
查「可视区非正 / 面板超出屏底 / 该滚却不滚」三类异常。真实窗口尺寸下应该零异常，
剩下的只有"MC 自己都放不下"的荒谬尺寸（GUI 高度 < 80 那种）。

#### 19.8.1 布局坐标只能有**一个来源**（本仓库真实踩过）

面板里「标签」和「控件」往往是两处代码画出来的：`buildXxx()` 决定控件摆哪，
渲染函数里一串 `drawLabel(..., y)` 决定标签画哪。两边**各自** `y += ROW_GAP` 累加，
迟早错位 —— 而且错位方式很难一眼看出规律：

> 规则编辑器有三页整体错开一行。根因是**渲染那侧先多画了一行说明文字**
> （`global_hint` / `stat_hint` / `preset_hint`），控件那侧却没有对应占位。
> 所以「带说明行的页全错、不带的全对」——看着像玄学，其实是纯粹的算术。

**修法**：抽一个 `rowY(index)`，两边都写**行号常量**、谁也不许自己累加 y：

```java
/** 内容区第 index 行的基准 y。build 与 render 必须共用它。 */
private int rowY(int index) { return contentTop() + index * ROW_GAP; }

// build：this.xpMultBox = addNumberField(rowY(1), ...);
// render：drawRowLabel(gfx, rowY(1), "attrlevel.gui.rules.xp_mult", ...);
```

顺带把「整块额外间距」（原来散落的 `y += ROW_GAP + 4`）也去掉，改成统一的段间距 ——
行号一变，视觉分组交给只画标签的小标题行来表达，比隐式偏移好维护。

#### 19.8.2 给布局加一条静态判据（并用**成对样本**验它）

这类错位 grep 不出来，但可以离线判：**把「build 用到的行号集合」与「render 用到的行号集合」
做差集，差值必须正好等于登记过的「只有标签的行」/「只有控件的行」**。

两条经验（这次写检查器时一条条撞出来的）：

- 🔴 **判据自己必须先被验证**。第一版检查器自己有两个 bug：
  ① 注释里写的 `rowY(1)`（说明"这行没控件"）被正则当成代码，于是永远对不上；
  ② 分支切分用了 `line.startswith("else if (...)")`，而真实代码里那行是
  `} else if (this.tab == 2) {`、**行首是 `}`** —— 结果所有分支都没切出来。
  跑出来满屏 FAIL，全是误报。**做法：拷一份源码、把 bug 注入副本、确认判据会报**；
  正常样本过 + 坏样本报，这条判据才算立起来。
- 🔴 **「同一行被两个控件占用」这类判据要带上横向位置**。同一行并排两个按钮
  （如「保存为预设 / 应用此预设」）是完全正常的布局，只按行号判会一路误报 ——
  **误报的检查等于没有检查**，因为人很快就开始无视它。

#### 19.8.3 「整对象替换」的 setter + 闭包快照 = 静默回滚别的字段

数据类写成 `record`、改字段靠 `withXxx(v)` 返回新对象时，**千万别把「构建期捕获的快照」喂给它**：

```java
// ❌ 组建界面时捕获了 tier 这一份快照
AwakenTier tier = tiers.get(idx);
box.setResponder(v -> tiers.set(idx, tier.withLevel(v)));       // 改等级
box2.setResponder(v -> tiers.set(idx, tier.withItem(v)));       // 改材料 → 等级被打回旧值
button.onPress(() -> tiers.set(idx, tier.withAbility(pick)));   // 改能力 → 等级/材料/数量全被打回

// ✅ 每次都现取现改
private void updateTier(int idx, UnaryOperator<AwakenTier> f) {
    if (idx >= 0 && idx < tiers.size()) tiers.set(idx, f.apply(tiers.get(idx)));
}
box.setResponder(v -> updateTier(idx, t -> t.withLevel(v)));
```

`withXxx` 的语义是「**整对象**替换」，喂它旧对象等于把**别的字段一起还原**。
症状是"我明明改了 A，B 也跟着变回去了"，看起来像界面显示不同步、像缓存没刷新，
排查方向很容易跑偏到网络同步上去（其实纯粹是闭包抓了一份过期快照）。

配套做法：**把「直接塞一个对象进去」的那个入口删掉**（本仓库删了 `replaceTier(...)`）。
只留 `updateTier(..., UnaryOperator)` 一个口子，就没有"随手把快照递进去"的机会了 ——
这类 bug 靠自觉是防不住的，靠**接口形状**才防得住。

静态判据也很便宜：源码里不该出现 `tier.withXxx(`（只认那个快照变量名即可），
命中就报。同样用坏样本验一遍。

#### 19.8.4 手绘文字的悬停提示：**画到哪就记到哪**

`gfx.text(...)` 画的标签**不是控件**，没有 `tooltip` 可以用。要给它们加说明有两条路：

- ❌ 另写一张「行号 → 提示」映射，再按鼠标位置反算 —— 等于同一套坐标写两遍，
  这个界面已经因此整体错位过一次（见 19.8.1）。
- ✅ **绘制时把命中框记下来**：

```java
private final List<LabelHit> labelHits = new ArrayList<>();
private record LabelHit(int y, String tipKey) {}

private void drawRowLabel(GuiGraphicsExtractor gfx, int baseY, String key, int color) {
    int y = baseY - scroll;
    if (!Scrolling.fullyVisible(y, 9, contentTop(), contentBottom())) return;
    gfx.text(this.getFont(), Component.translatable(key), labelX(), y + 5, color);
    labelHits.add(new LabelHit(y, key + ".tip"));   // 说明键由标签键推导，不维护第二张表
}

// 每帧开头先 labelHits.clear()；命中判定：
Component tip = labelTipAt(mouseX, mouseY);
if (tip != null) gfx.setTooltipForNextFrame(tip, mouseX, mouseY);
```

四个要点：

- **命中框与绘制同源** —— 滚动、换页、拉窗口都不会错位，这是这套写法的全部价值。
- `setTooltipForNextFrame` 是「后写的覆盖先写的」，而控件自己也会设提示；
  把手绘提示放在 `super.extractRenderState(...)` **之后**。两者命中区本来就不重叠
  （标签列 vs 控件区），顺序其实无所谓，但这样最直观。
- 命中带放宽到「整行文字高度 ±3px」（文字画在 `y+5`、高 9px，判 `y+2 ~ y+15`）——
  玩家不会像素级对准，行距够大就不会串行。
- ⚠️ **说明键要补全**：键是从标签键推导的，漏一个就会把**键名原样**写进提示
  （`attrlevel.gui.rules.xxx.tip`）。编译期查不出来 —— **加一条静态判据拦**：
  扫源码里所有 `drawRowLabel(..., "键", ...)` 与 `Tooltip.create(...("键"))`，
  拿去两个语言文件里核对存在性。也要用坏样本验一遍。

控件那半边直接 `Button.Builder.tooltip(Tooltip.create(Component.translatable(...)))`
（`AbstractWidget.setTooltip(Tooltip)` / `setTooltipDelay(Duration)` 也在）。

#### 19.8.5 想让底色铺在**文字下面**：同一段绘制代码跑两遍

手绘面板常要「整行悬停高亮」这类底色，它必须画在**文字下面**。
可标签是边算边画的（一串 `drawRowLabel(gfx, rowY(n), …)`），
画到第 3 行时才刚知道第 3 行在哪 —— 想先铺底色就得**另算一份坐标**，
而那正是 19.8.1 那个整体错位的来源。

正解：**同一段代码跑两遍**，用一个开关区分「只登记」与「真的画」：

```java
private boolean recording;

// 第一遍：只登记行位置（不画字）
labelHits.clear();
recording = true;  drawRowLabels(gfx);  recording = false;
// 中间：拿刚登记下来的坐标铺底色
drawRowHover(gfx, mouseX, mouseY);
// 第二遍：真的画字（压在底色上面）
drawRowLabels(gfx);

private void drawRowLabel(GuiGraphicsExtractor gfx, int baseY, String key, int color) {
    int y = baseY - scroll;
    if (!Scrolling.fullyVisible(y, 9, contentTop(), contentBottom())) return;
    labelHits.add(new LabelHit(y, key + ".tip"));
    if (!recording) gfx.text(font, Component.translatable(key), labelX(), y + 5, color);
}
```

- 两遍跑的是**同一段代码**，坐标不可能不一致 —— 这是它相对「另算一份」的全部价值。
- 顺手把这段标签绘制从 `extractRenderState` 抽成独立方法（`drawRowLabels(gfx)`）：
  既方便跑两遍，也让本来就臃肿的渲染函数短一截。
- ⚠️ **这段代码一搬家，基于它写的静态判据就得跟着改**：本仓库的
  `tools/检查规则界面行号.py` 原本是去 `extractRenderState` 里找页签分支的，
  搬家之后它一路报「找不到分支」。判据锚在"哪个方法上"时，方法搬家＝判据失效 ——
  改完渲染代码记得顺手跑一遍判据。

**配色抽成一个主题类**（`UiTheme`）：两个界面共用同一套色常量与画法
（面板双层描边 / 标题 + 分隔线 / 分组小标题 / 行悬停 / 进度底纹 / 滚动条）。
理由不是「少写几个常量」，而是**两个界面的配色必须一起变** ——
散在两处就一定会漂，玩家一眼能看出"这俩界面不是同一套东西"。

全部只用 `fill` / `outline` / `text` 画，**不依赖任何贴图**：自定义贴图要挂资源路径、
要处理打包与图集，而这里要的只是"有层次、能看清"。几个见效最快的：

| 手法 | 效果 |
|---|---|
| 底色 + **双层**描边（外亮边 + 内极淡白） | 面板立刻有"边框"，不再是一张纸 |
| 标题下一条分隔线 | 头部与内容分开 |
| 说明行改成「左侧 2px 色条 + 亮色字」 | 从"一行看不清的字"变成**可见的分节** |
| 行悬停低透明度底色（`0x22FFFFFF`） | 配合悬停提示，不用猜在看哪一行 |
| 数值字段：继承值（`-1`）**变灰** | 一眼分出"自己设的"和"跟随全局的" |
| 整行低透明度进度底纹 | 等级进度不用读数字也看得见 |

> 加装饰之后记得**核一遍竖向占位**：标题 / 分隔线 / 页签 / 下划线 / 内容顶
> 这几段 y 区间不能互相压。这是纯算术，写成几行断言跑一下就知道，
> 比进游戏盯着看快得多。

## 20. ⭐⭐ 在世界空间画自定义几何体（描边 / 线框 / 世界空间文字）——必须过滤光影的 shadow pass

**症状**：开了光影（Iris / Oculus，任意光影包）之后，画在世界里的自定义几何体会在画面上
**多出一批**：位置完全不贴方块、互相糊成一团、看着像"贴在视野里、随视角跑"。
**关掉光影就正常**。玩家会一口咬定是你 mod 的坐标算错了 —— **其实不是**。

### 为什么

Iris / Oculus 在正式渲染之前，会先**从太阳 / 月亮的视角**再渲染一遍地形来生成 shadow map。
`ShadowRenderer` 里 `shouldRenderTerrain` / `shouldRenderTranslucent` **都是 true** —— 也就是
这一遍**走的是同一套原版渲染流程**（`MixinLevelRenderer` 在 shadow pass 时换掉 frustum /
culling 数据，然后让原版 `renderLevel` 自己跑）。

而 Forge 的渲染事件就是从原版流程内部发出来的：

```
LevelRenderer.renderLevel
  └─ renderSectionLayer(RenderType, …)                        // m_172993_
       ├─ …渲染该层…
       └─ ForgeHooksClient.dispatchRenderStage(RenderType, …) // ← 事件在这里发
```

⇒ **`RenderLevelStageEvent` 的所有 stage（含 `AFTER_TRANSLUCENT_BLOCKS`）在 shadow pass 里会被
再触发一次**，而那时的 modelview / projection 是**光源视角**的。正片那一遍（相机视角）完全是
对的，被污染的只是阴影这一遍。

### 修法：检测并跳过（可选依赖 → 必须反射）

光影不是所有人的依赖 —— 只有装了光影的整合包才有这些类（Fabric 版 `Iris`、Forge 版
`Oculus`，**包名统一是 `net.irisshaders.iris.*`**）。直接 `import` 的话，没装光影的玩家一进游戏
`NoClassDefFoundError`。所以要**反射调官方 API**，拿不到就当"没开光影"：

```java
// Iris / Oculus 官方 API：net.irisshaders.iris.api.v0.IrisApi
private static final Object IRIS_API   = findIrisApi();
private static final Method SHADOW_PASS = findShadowPass();

private static Object findIrisApi() {
    try {
        Class<?> api = Class.forName("net.irisshaders.iris.api.v0.IrisApi");
        return api.getMethod("getInstance").invoke(null);
    } catch (Throwable noIris) { return null; }          // 没装光影
}
private static Method findShadowPass() {
    if (IRIS_API == null) return null;
    try { return IRIS_API.getClass().getMethod("isRenderingShadowPass"); }
    catch (Throwable ignored) { return null; }
}
private static boolean isShadowPass() {
    try { return SHADOW_PASS != null && Boolean.TRUE.equals(SHADOW_PASS.invoke(IRIS_API)); }
    catch (Throwable ignored) { return false; }          // 永远零误伤
}
```

渲染回调**最开头**加一行：

```java
if (isShadowPass()) return;
```

> ⚠️ 这个坑**不分版本**：1.20.1 / 1.21.x / 26.x，只要装了 Iris/Oculus 都一样。
> 凡是"往世界里画自定义几何体"的 mod 都得加这道过滤。

### ⭐ 用"红蓝叠加"证明"某个东西到底贴不贴世界"（视频/截图通用）

玩家说"它跟着视角跑"时，光靠盯画面判断不了。**抽两帧，一帧染红一帧染蓝，重叠处会显品红**：

- 东西**贴世界**（正常的）→ 两帧位置不同 → 红蓝**分离**；
- 东西**贴屏幕 / 被光照视角污染**→ 两帧位置相同 → **完全重叠**（品红）。

```python
import cv2, numpy as np
def grab(t):                        # 按时间取帧
    cap = cv2.VideoCapture(VIDEO); cap.set(cv2.CAP_PROP_POS_MSEC, t*1000)
    ok, fr = cap.read(); cap.release(); return fr
f1, f2 = grab(0.2), grab(2.0)
a, b = cv2.cvtColor(f1, cv2.COLOR_BGR2GRAY), cv2.cvtColor(f2, cv2.COLOR_BGR2GRAY)
ov = np.zeros_like(f1)
ov[..., 2] = a      # 红 = 第一帧
ov[..., 0] = b      # 蓝 = 第二帧
cv2.imwrite(out, ov)
```

> ⚠️ `cv2.imwrite` 遇到**中文路径会静默失败**（返回 False 但不报错）—— 输出目录用纯英文。

**实测记录（2026-10-03，AttrLevel 的矿物嗅探）**：整合包 `The Fungal Infection`
（Fabric + Sinytra Connector 跑 Forge mod）+ Oculus 1.8.0 + Insanity Shader。玩家报"远古城市里
远处一堆密集金色线框、不贴方块、随视角跑"。红蓝叠加证实：正常那批框跟着地形滑（分离），
另有一批两帧完全重叠（糊成一团）。三刀 `javap` 定位到 shadow pass，加 `isShadowPass()` 过滤后修复。

## 21. ⭐⭐ 26.1 自定义附魔（数据驱动 = 写 JSON，不是代码注册）

**一句话**：1.21 起附魔是 **datapack 注册表对象**，定义在 `data/<ns>/enchantment/<id>.json`。
代码里**拿不到静态的 `Holder<Enchantment>`**，只能持有 `ResourceKey`，用到时再问存档的注册表要。

**实例**：`GodsEnchant模组`（23 个附魔 = 8 属性 + 15 功能），
JSON 由 `tools/生成附魔.py` 批量产出，别手改生成物。

### 21.1 JSON schema（除 `primary_items` / `exclusive_set`，其余每个字段都必需）

```json
{
  "description": { "translate": "enchantment.mymod.night_vision" },
  "supported_items": "#minecraft:enchantable/head_armor",
  "slots": ["head"],
  "max_level": 2,
  "weight": 2,
  "min_cost": { "base": 2, "per_level_above_first": 8 },
  "max_cost": { "base": 20, "per_level_above_first": 8 },
  "anvil_cost": 4,
  "effects": {}
}
```

| 字段 | 值 |
|---|---|
| `description` | 名字的翻译键（语言文件里 `enchantment.<modid>.<id>`）|
| `supported_items` | 能附在哪：`#minecraft:enchantable/{armor,head_armor,chest_armor,leg_armor,foot_armor,weapon,mining,bow,crossbow,durability,…}` |
| `slots` | `head` / `chest` / `legs` / `feet` / `armor` / `mainhand` / `offhand` / `hand` / `any` |
| `weight` | 附魔台随机池权重（越小越稀有）|
| `min_cost` / `max_cost` | `{"base":N,"per_level_above_first":M}` |
| `effects` | **可以是 `{}`**（原版 `binding_curse` 就是空，靠 tag 生效）|
| `exclusive_set` | 可选，如 `#minecraft:exclusive_set/armor` |

### 21.2 纯 JSON 就能做的效果（零 Java）

| 效果 | effects 键 |
|---|---|
| 属性加成（生命 / 攻击 / 移速 / 挖掘 / 跳跃 / 交互距离…）| `minecraft:attributes` |
| 伤害减免（原版保护那套）| `minecraft:damage_protection` |
| **无限箭**（不消耗箭）| `minecraft:ammo_use`（`set 0` + `match_tool` 条件）|

```json
"effects": { "minecraft:attributes": [
  { "amount": { "type": "minecraft:linear", "base": 2.0, "per_level_above_first": 2.0 },
    "attribute": "minecraft:max_health", "id": "mymod:enchantment.vitality", "operation": "add_value" }
]}
```
属性 id 从 `Attributes` 类 `javap` 读（`minecraft:<小写下划线>`）：`max_health` / `attack_damage` /
`movement_speed` / `block_break_speed` / `jump_strength` / `armor` / `mining_efficiency` /
`block_interaction_range` / `entity_interaction_range` …
`add_value` 加点、`add_multiplied_base` 加百分比（0.05 = +5%）。

### 21.3 代码里怎么读等级（实现「穿上 / 手持才生效」）

```java
private static final ResourceKey<Enchantment> NIGHT_VISION = ResourceKey.create(
        Registries.ENCHANTMENT, Identifier.fromNamespaceAndPath(MODID, "night_vision"));

Holder<Enchantment> holder = entity.registryAccess()
        .lookupOrThrow(Registries.ENCHANTMENT).get(NIGHT_VISION).orElse(null);
if (holder == null) return 0;   // 数据包没加载 → 安静返回，别抛异常
int lv = EnchantmentHelper.getItemEnchantmentLevel(holder, entity.getItemBySlot(EquipmentSlot.HEAD));

// 或一次扫完身上所有装备（护甲 + 双手）取最高
int any = EnchantmentHelper.getEnchantmentLevel(holder, livingEntity);
```

**「盔甲穿上生效 / 武器手持生效」**：自己遍历该生效的槽位取最高 ——
护甲类扫 `HEAD/CHEST/LEGS/FEET`、武器类扫 `MAINHAND/OFFHAND`。
比直接调 `getEnchantmentLevel(...)` 准（后者连命令错附到其它槽的也会算）。
⚠️ `getItemEnchantmentLevel` 第二参签名是 **`ItemInstance`**（26.1 的 `ItemStack implements ItemInstance`，直接传即可）。

🔴 **改一个附魔的「生效部位」要同时改三处**：附魔 JSON 的 `slots` + `supported_items`、
以及代码里那份槽位表（枚举 / 常量）。少改一处就是**静默漂移** ——
JSON 说"能附在护甲上"、代码却只扫手部，玩家附上去**什么都不会发生，也不报错**。

⚠️ 服务端验证脚本别用「日志里有 `Done`」判断服务端在不在跑：上次的日志还在磁盘上，
会误判成"还活着"从而跳过启动，之后所有 RCON 全连不上。而且 `rcon.py`
**连接失败时退出码也是 0**，靠它探活同样不行 —— 正解是**直接探端口**
（`socket.connect_ex(('127.0.0.1',25575))`）。

### 21.4 让附魔台能出它

候选池是 `#minecraft:in_enchanting_table` → 指向 `#minecraft:non_treasure`。
在自己 mod 里放**同名 tag 追加**即可（datapack 标签默认 `replace:false` = **合并**，不覆盖原版）：

`data/minecraft/tags/enchantment/non_treasure.json` → `{ "values": ["mymod:vitality"] }`

### 21.5 26.1 实测踩的坑

| 坑 | 症状 / 正解 |
|---|---|
| **`BlockTags.ORES` 不存在** | 拆成了 `COAL_ORES`/`IRON_ORES`/`DIAMOND_ORES`…；判矿石要组合标签，再加 NeoForge 的 `Tags.Blocks.ORES`（`c:ores`）覆盖模组矿 |
| **`AttachmentType.serialize` 要 `MapCodec`** | 传 `Codec` 报「`Codec<X>` 无法转换为 `MapCodec<X>`」。用 `ItemStack.OPTIONAL_CODEC.listOf().fieldOf("items").xmap(...)` |
| **`ChestMenu` 行数不自由** | 只有 `threeRows`/`sixRows` 带自定义 `Container` 的重载；要 1/2/4/5 行得用公开构造 `new ChestMenu(MenuType.GENERIC_9xN, id, inv, container, rows)`，MenuType 行数必须对上 |
| `Options.autoJump` | 是 `OptionInstance<Boolean>`：`minecraft.options.autoJump().get()/.set(v)` |
| `state.is(TagKey)` | 在 `BlockBehaviour.BlockStateBase` 里（javap 输出长，别被前面的重载骗了以为没有）|
| 空 `effects` | `"effects": {}` 合法，不用造假效果 |

### 21.6 堆叠上限（顶开原版 `intRange(1,99)`）

原版**三处**用 `ExtraCodecs.intRange(1, 99)` 卡死数量：`DataComponents`（`MAX_STACK_SIZE` 组件）、
`ItemStack`（自己的 codec，**网络包 + 存档都走它**）、`ItemStackTemplate`（配方模板）。
三处都要 `@ModifyExpressionValue` 顶开，少一处就"一发超量物品 `DecoderException` / 踢下线"。

```java
@ModifyExpressionValue(method = "lambda$static$1",
        at = @At(value = "INVOKE",
                target = "Lnet/minecraft/util/ExtraCodecs;intRange(II)Lcom/mojang/serialization/Codec;"))
private static Codec<Integer> raise(Codec<Integer> original) { return ExtraCodecs.intRange(1, 1024); }
```

**只改玩家背包**（箱子照旧）+ 给 `Inventory` 加方法：

```java
@Mixin(Inventory.class) public abstract class InventoryStackSizeMixin {
    @Final @Shadow public Player player;
    public int getMaxStackSize() { ... }                 // 无参
    public int getMaxStackSize(ItemStack s) { ... }      // 带参不能省，否则工具/药水也被顶上去
}
```
原理：原版 `Inventory` **没有自己实现** `getMaxStackSize`（吃 `Container` 接口默认值），
Mixin 合并进类的方法会盖住接口默认实现。
**验证**：RCON `summon` 一个 `count:500` 的物品 → `Summoned new Stone` 即顶开成功（否则报 `[1;99]`）。

### 21.7 交付前的服务端验证（无需玩家）

```bash
# 逐个附魔 id 都能解析 + 写得进物品
rcon.py 'summon minecraft:item 0 100 0 {Item:{id:"minecraft:stone",count:1,components:{"minecraft:enchantments":{"mymod:night_vision":1}}}}'
# -> Summoned new Stone  = 附魔 id 有效
```

⚠️ `minecraft:enchantments` 组件的 NBT 是**直接 map**（`{"mymod:x":1}`），
**不要**包 `levels`（写成 `{levels:{…}}` 报 `Not a number`）。
⚠️ `rcon.py` 的 `--host/--port/--password` **必须写在命令前面**，写在后面会被当成要发送的命令。
⚠️ 注入型 mixin 靠 `injectors.defaultRequire=1`：**服务端能起来 = 注入点全部匹配**（这是免费的 mixin 验证）。

### 21.8 ⭐ 附魔等级怎么定（比"数字对齐"更重要的铁律）

🔴 **每一级都必须有能感觉到的变化** —— 绝不能留「升了一级什么都没变」的**空壳级别**。
实测踩过：一版 23 项附魔里有 **7 项是空壳**（虚化 / 熔炼 / 隐匿 / 越障 / 追踪各写着 3 级，
但代码里只用 `has()`，2、3 级纯占位；水下呼吸第 3 级、无限箭第 2 级也是空的）。
玩家花材料把附魔升上去、发现毫无变化 —— 这比"等级数字不统一"严重得多。
**定 `max_level` 时先问：第 N 级比第 N-1 级多什么？答不上来就别写那个 N。**

两个"必须让步"的场景：
- **原效果天生只有一档**（如"隐身""飞行"）→ 就写 `max_level = 1`，别硬凑 3 级。
- **界面有物理上限**（自定义容器最多 6 行之类）→ 直接封在物理上限；
  为了"跟别的附魔对齐"写个够不着的等级 = 人工制造空壳。

另外「读等级」的写法决定了等级有没有用：`has()` 只判有无、`level()` 才分档 ——
**只调 `has()` 的附魔，它的 `max_level` 一定写错了**（这是自查空壳最快的办法）。

**把「等级 + 材料解锁」的老系统改造成附魔**：激活条件从 `等级 ≥ N 且已消耗材料`
换成 `身上装备带着这个附魔`，效果逻辑可以整段照搬。注意属性类要改成**每 tick 挂修正器**——
老系统只在升级时推一次，附魔却随时会穿脱。

### 21.9 26.1 又两个改名（取方块 id）

| 老写法 | 26.1 正解 |
|---|---|
| `state.getBlock().builtInRegistryHolder().key().location()` | **没有 `location()`** → 用 `BuiltInRegistries.BLOCK.getKey(state.getBlock()).getPath()` |
| `Holder.Reference.key()` 再取 location | 同上，直接走 `BuiltInRegistries.BLOCK.getKey(...)` |




## 22. ⭐⭐ 「存档级可编辑规则 + 全局预设 + 主菜单设置界面」（26.1，实测）

场景：把原本写死在枚举/常量里的平衡数值（经验成本、等级上限、解锁材料、能力绑定）
改成**玩家可编辑**，并且「存档内改动只影响该存档」「可另存为全局预设」「主菜单模组设置里编辑」。

### 22.1 三级解析是这套东西的骨架

```
存档内规则（存在存档里，改过才有）  →  全局默认预设（config/<modid>/presets.json）  →  出厂设置（代码里的常量）
```
**没有存档文件 ≠ 有一份"默认存档配置"**：本地规则表带一个 `custom` 标记，
`custom=false` 时直接返回全局预设。这样没动过手的存档**不会生成任何文件**，
「新增一个存档」也不会莫名多出一份要被同步维护的配置。

### 22.2 26.1 的存档级数据：`SavedDataType` + `SavedDataStorage`

旧版的 `DimensionDataStorage` + `SavedData.Factory` 已经没了，26.1 是：

```java
public class MyRulesData extends SavedData {
    public static final Codec<MyRulesData> CODEC =
            CompoundTag.CODEC.xmap(MyRulesData::fromTag, MyRulesData::toTag);   // 手写 NBT 读写，不碰 DFU 那套
    public static final SavedDataType<MyRulesData> TYPE = new SavedDataType<>(
            Identifier.fromNamespaceAndPath(MODID, "rules"),
            MyRulesData::new,                       // Supplier：没有文件时用它造一个空的
            CODEC,
            DataFixTypes.LEVEL);

    public void applyRules(Rules r) { this.rules = r; this.custom = true; setDirty(); }  // 只有真改过才脏
}

// 取：
SavedDataStorage storage = level.getServer().overworld().getDataStorage();
MyRulesData data = storage.computeIfAbsent(MyRulesData.TYPE);   // 同一实例，重复调用很便宜
```

**落盘位置踩过一次：** 用 `server.overworld().getDataStorage()` 时文件写在
`<存档>/dimensions/minecraft/overworld/data/<modid>/<名字>.dat`，
**不是** `<存档>/data/`。别照着老教程去 `world/data/` 找，"文件没生成"多半是找错了地方。

`setDirty()` 只在内容真变了时调 —— 没调就永远不写文件，这正是「没编辑过就不产生文件」的实现方式。

### 22.3 一份数据同时喂 NBT、JSON 文件、网络包：`CompoundTag.CODEC` 当枢纽

```java
// 存进 SavedData 用的就是上面那个 CODEC（NBT 侧）
// 写 config 里的 JSON 文件、以及网络传输，都走 JsonOps：
JsonElement json = CompoundTag.CODEC.encodeStart(JsonOps.INSTANCE, rules.toTag())
        .result().orElseGet(JsonObject::new);
Rules back = CompoundTag.CODEC.parse(JsonOps.INSTANCE, JsonParser.parseString(text))
        .result().map(Rules::fromTag).orElse(null);     // ⚠️ 用 parse，不是 decode
```

- ⚠️ **`Codec.decode` 返回 `DataResult<Pair<T, JsonElement>>`，不是 `DataResult<T>`。**
  要 `DataResult<T>` 必须用 `parse`。写错的话 `.ifPresent(x -> fromTag(x))` 会在编译期报
  "Pair cannot be converted to CompoundTag"——不算难查，但很容易顺手写错。
- 手写 `toTag/fromTag` 而不是搭 DFU Codec 组合子：**读不到的字段一律退回默认值**，
  于是老存档、手改坏的 JSON、跨版本结构变更都不会把游戏搞崩（最多那一项回到出厂值）。
  这比 Codec 组合子的"缺字段整份解析失败"稳得多。
- 物品**存字符串 id 不存 Holder**（`"minecraft:dragon_egg"`，用时 `BuiltInRegistries.ITEM.getValue(Identifier.tryParse(id))`）。
  理由：同一份数据既要有注册表上下文的 NBT 侧，也要没上下文（或上下文不同）的 JSON 侧，
  存 Holder 的 codec 在 JSON 那边直接解码失败。认不出的 id 退回空气即可。

### 22.4 网络同步：规则整体走**一段 JSON 字符串**

```java
buf.writeUtf(rulesJson);            // 而不是逐字段 writeVarInt/writeBoolean…
```
结构会随功能增删字段，逐字段写包意味着「改结构 = 改包 + 改读端 + 两端版本必须同步」。
JSON 是自描述的、读端缺字段能兜底，几 KB 的包只在登录与编辑后发一次，完全不是瓶颈。
（读端对 `writeUtf` 的字符串仍然要设长度上限，别对坏包不设防。）

**「能不能编辑」也在同一个包里下发**：权限只在服务端判，客户端拿布尔值决定
要不要显示「编辑」按钮 —— 而不是让所有人看到按钮、点了才被拒。

### 22.5 权限判据（单机 / 联机要分开）

```java
boolean creative = player.isCreative();
boolean op = player.permissions().hasPermission(Permissions.COMMANDS_GAMEMASTER);   // 26.1 的权限 API
MinecraftServer server = level.getServer();
if (server.isDedicatedServer()) return creative && op;                    // 联机：创造 + OP
return creative || server.getWorldData().isAllowCommands();               // 单机：创造 或 开了作弊
```
`Player#hasPermissions(int)` 那套也不在了，26.1 是 `player.permissions().hasPermission(Permissions.XXX)`。

### 22.6 主菜单「模组 → 某某 → 设置」里的界面：`IConfigScreenFactory`

```java
// 客户端专用！整个注册动作要放在一个只在客户端加载的类里
container.registerExtensionPoint(IConfigScreenFactory.class,
        (IConfigScreenFactory) (mod, parent) -> new MyRulesScreen(parent, sink));
```
- 入口：模组构造器改成 `public MyMod(IEventBus bus, ModContainer container)`，然后
  `if (FMLEnvironment.getDist().isClient()) ClientOnlyEntry.register(container);`
  （`FMLEnvironment.dist` 是**方法** `getDist()`，不是字段。）
- ⚠️ **`IConfigScreenFactory` 在客户端专用包里**（`neoforge.client.gui`）。
  在公共代码里直接引用，专用服务端启动会 `NoClassDefFoundError` ——
  所以外层判 dist、内层放在 `client` 包的一个独立类里，两边都要。
- 同一个编辑器类可以两用：构造时传一个「落点」接口，
  存档内 = 发网络包（服务端判权限），主菜单 = 直接读写 config 目录的 JSON。

### 22.7 把「硬编码常量」抽成可编辑规则时的两个必改点

1. **「上限」要存成相对增量，不能存绝对值。**
   老代码的 `caps[i]` 存的是绝对值（默认 30，突破后变成封顶值）。
   一旦上限变成可编辑的（比如允许调成 20 或 500），存绝对值就会两头不讨好：
   把初始上限调低之后，突破过的玩家永远认那个旧数字；调高则对新玩家生效而老玩家不动。
   正解：存 `capBonus[i]` = **相对规则初始上限的增量**（0 = 从未突破），
   实际上限 = 规则初始上限 + 增量。老档迁移时按「绝对值 − 出厂初始值」折算。
2. **能力门控要按「能力身份」判，不能按「哪项属性 / 哪个技能」判。**
   原本到处是 `isAwake(player, UpgradeStat.MAX_HEALTH)` —— 这等于把「生命值第 1 档」和「金心」焊死，
   一旦允许「把这项能力换成别的」，全部门控点都要改。
   做法：建一个**能力注册表**（枚举，名字即存档 id），门控统一走
   `has(player, Ability.GOLDEN_HEART)`；「谁授予了它」由规则表反查。
   带等级的技能则额外给一个 `specialLevel(player, skill)`：
   自己练的等级优先，没练过但被某个觉醒档位赠送了就按满级算。

### 22.8 规则改了之后必须做一次「收敛」

玩家可能在「6 档」的规则下觉醒了 6 档，之后规则被改成 2 档。
那些残留的位如果留着，「某个已解锁档位绑定了能力 X」这条判据会继续成立 ——
**玩家凭空保留一项规则里已经没有的能力**。所以在应用新规则之后对每个在线玩家跑一遍：

- 超出当前档位数的觉醒位清掉；
- 超过当前上限的等级夹回去；
- 超过当前满级的技能等级降下来。

### 22.9 顺手的两个小坑

- **Brigadier 的 `StringArgumentType.word()` 只吃 ASCII**（`readUnquotedString` 的字符白名单里
  没有 CJK），中文参数会报 `Expected whitespace to end one argument, but found trailing data`。
  命令参数里的名字类参数一律用 `greedyString()`（游戏内 GUI 输入不受影响，只有命令会踩）。
- **调试命令别要求「必须有玩家」**：`source.getPlayerOrException()` 从控制台 / RCON 执行会直接抛错，
  于是「服务端起好了但命令用不了」，自动化验证直接卡住。改成用 `source.getLevel()`。
  同理，凡是希望被 RCON 驱动验证的东西，都要保证控制台能跑。

## 23. ⭐ 追踪 / 制导类效果：判据用 `Enemy`、修正频率决定命中率（26.1 实测）

做「射出的箭自动追敌人」「导弹」「自动索敌」这类效果时，两个坑几乎必踩。

### 23.1 「追什么」按需求选**抽象判据**，不要用具体实现类

判据别写成"某个具体类"，写成**接口 / 抽象**：

```java
// 要"只追敌对生物" → 判 Enemy 接口
level.getEntitiesOfClass(LivingEntity.class, box,
        e -> e instanceof Enemy && e.isAlive() && e != owner);
// 要"追所有生物" → 直接判 LivingEntity（记得把自己排掉）
level.getEntitiesOfClass(LivingEntity.class, box,
        e -> e.isAlive() && e != owner);
```

⚠️ **别拿 `Monster` 这种具体实现类当判据。** 原版里一大堆敌对生物**只实现 `Enemy`、
不继承 `Monster`**：`Slime` / `MagmaCube`（`extends Mob implements Enemy`）、`Ghast`、
`Phantom`、`Shulker`（`extends AbstractGolem implements Enemy`）、`Hoglin`、`EnderDragon` …
按 `Monster` 过滤会**整批漏掉**，而漏的正好包含玩家最常遇到的史莱姆。

实测（RCON 摆好几种生物，24 格内探针）：

```
Enemy 判据命中 10 个 [zombie, skeleton, creeper, ghast, enderman,
                      phantom, shulker, wither_skeleton, blaze, hoglin]
其中 4 个不是 Monster（用 Monster 判就会漏）[ghast, phantom, shulker, hoglin]
```

**顺手留一条只读探针**（如 `/attrlevel homing_probe <pos>`）：把「按当前判据会认下哪些目标」
直接打出来。判据属于「读代码看不出、必须问注册表 / 字节码」的那类，
留个探针比对着继承关系猜可靠得多。

⚠️ 探针与正式逻辑**必须共用同一份判据方法**（`isHomingCandidate(entity, owner)`）——
各写一遍的话，探针说"能追"而实际不追，等于白测。

### 23.2 制导的**修正频率**决定命中率 —— 先算一算再定参数

一个「每 N tick 把速度朝目标掰一点」的追踪，命中率几乎完全由
**「每次修正之间飞了多远」**决定：

```
修正间隔 N tick × 速度 v 格/tick = 每次修正之间飞行的格数
```

满蓄力箭 v ≈ 3 格/tick。写 `N = 3` 就是**每 9 格才修正一次方向** ——
目标在 20 格外时误差根本来不及收敛，箭已经飞到了：

| 修正间隔 / 每次插值 | 20 格外目标、初始偏 20° 的**命中瞬间横向偏差** | 结果（僵尸半宽仅 0.3 格） |
|---|---|---|
| 每 3 tick / 45%（改前） | **2.2 格** | 必然从旁边擦过去 |
| 每 1 tick / 60%（改后） | 0.01 格 | 命中 |

结论：**间隔取 1**（每 tick 修正，代价只是一次 AABB 查询）、速率 0.5~0.7。

改参数之外还有三件同样重要的事：

- **贴身阶段直冲**：进入 4 格内就不要再插值了，直接指向目标。
  插值是"渐进逼近"，最后几格还在渐进的话，箭会带着残余横向速度**掠过**目标。
- **提前量**：目标在动，就按「距离 ÷ 箭速」预测它届时的位置再瞄。
  不打提前量的话，追一个横着走的僵尸会一直吊在它后面。
- **瞄碰撞箱中心**（`getBoundingBox().getCenter()`）而不是 `position()` ——
  后者是**脚底**，瞄脚底会让箭一路扎向地面。
- ⚠️ `dirA.lerp(dirB, t).normalize()` 在两个方向**接近反向**时结果趋近零向量，
  `normalize()` 会算出 **NaN**，实体直接废掉（位置崩坏 / 卡住不动）。
  必须兜一下：长度过小就退回「直接用目标方向」。

### 23.3 验证这类效果的姿势

- **纯几何部分可以离线算**：把「间隔 × 速度 → 命中瞬间横向偏差」用一段脚本跑出来，
  对着目标的实际宽度（僵尸 0.6 格）判"打得中打不中"。参数该取多少一目了然，
  不用反复进游戏试。
- **目标筛选部分可以 RCON 实测**：`summon` 一批生物（记得 `NoGravity:1b, NoAI:1b,
  PersistenceRequired:1b` —— 否则它们会在半空摔死，样本直接消失，白测一轮）
  → 探针命令读结论。

### 23.4 「优先追准心上的」= 角度当主键，距离只用来破平

需求从「追最近的」变成「优先追准心上的」时，**别去改距离公式**，换成打分制：

```java
double cos      = aimDir.dot(toTarget.normalize());   // 1 = 正对准心，-1 = 正后方
double offAxis  = 1.0D - cos;                         // 0 ~ 2
double distTerm = Math.sqrt(distanceSqr) / range;     // 0 ~ 1
double score    = offAxis + W * distTerm;             // 越小越优先
```

- **W 必须小（实测取 0.1）**：它只负责「都在准心附近时挑更近的那只」。
  取大了就会盖过角度，等于又变回「优先追近的」——那是另一套判据了。
- **「准心」用射手的视线**（`shooter.getLookAngle()`），**不要用"箭当前方向"**：
  箭一旦开始追踪，它自己的方向就已经被掰偏了，再拿它当准心就成了"追着上次追的东西跑"。
  射手读不到时（区块卸载 / 非玩家射手）再退化成箭的朝向。
- 瞄的仍然应该是**碰撞箱中心**（见 23.2），不是 `position()`（那是脚底）。

实测（准心 +Z，摆 5 只，同一份打分函数）：

```
★ villager 夹角  7°  距  4.0  打分 0.024   ← 选中
  cow      夹角  1°  距 20.0  打分 0.083
  pig      夹角 81°  距 20.2  打分 0.936
  sheep    夹角 90°  距  3.0  打分 1.013
  zombie   夹角179°  距 20.0  打分 2.083
```

- 正前方 **20 格**的牛压过**只有 3 格**的侧向羊 → **准心优先成立**（距离没翻盘）；
- 村民与牛都在准心附近（≤7°）时，**更近的村民胜** → 距离破平生效。

**给探针加「打分」输出是这套东西的验收关键**：把每个候选的 `夹角 / 距离 / 打分` 打出来、
按打分排序、标出会选中的那个，一眼就能看出判据是否按预期工作 —— 比"射一箭试试"可靠得多，
而且这套打分是纯几何，**可以离线用脚本复算**（先算期望、再拿实测对，两边吻合才算数）。
